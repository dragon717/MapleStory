## 0. 先给结论

**当前仓库已经有第一轮空中侧壁修复。下一步不是再加一次“跳跃也检测墙”，更不是换物理引擎，而是保留现有实现，修复运动预测、碰撞候选和事件顺序之间的不一致。**

本次推荐的最小路线：

1. 确认用户实玩的运行版本与失败位置，补出同一侧壁的最小失败用例。
2. 同一物理步只生成一份实际将采用的运动方案，侧壁、落地和入水查询都使用它。
3. 将“可能入水便跳过侧壁”改为按真实接触先后裁决；撞墙后只取消横向穿入，剩余纵向运动继续。
4. 对有失败证据的长链、分段墙和空中锚点问题，扩大到经过连通性验证的侧壁候选，不把全地图竖线全部实体化。
5. 补齐左右镜像、缓降、入水、墙顶、第三邻居和真实地图轨迹测试；前端继续显示服务端权威位置。

本次维持现有 `f64` 脚点模型、50 像素侧壁身高代理和 50ms 世界时间步，不引入角色宽度，不改变跳跃初速、重力、单向平台与合法瞬移规则。[R02][R03][R04]

**重要边界：源码中的风险已能定位，但用户此前遇到的那一次穿墙，尚未与具体地图、侧壁 ID、输入轨迹和正在运行的二进制关联。不能把下面任意一项直接宣布为那次问题的唯一根因。**

## 3. 核查结果：哪些已确认，哪些仍需复现

### F1：入水预判会关闭本步侧壁查询【代码事实已确认；具体实玩影响待验证】

当前流程的核心条件：[R04]

```rust
let water_entry_ahead = map.water_entry(/* 预估路径 */).is_some();
let chain_wall =
    (!water_entry_ahead && player.state.vx != 0.0 && chain_anchor != 0)
    .then(|| map.chain_wall_on_sweep(/* 同一步的侧壁查询 */));
```

问题不在于“支持入水”，而在于任何预判入水都会使物理侧壁失效，代码没有比较墙和水谁先被到达。

**一个用于新增测试的数学反例，不是已经运行通过的 Rust 测试：**

```text
期望脚点路径：(190,170) → (210,190)
侧壁：x=200，y=140..240
水域：x=205..260，水面 y=188，底部覆盖该落点

到侧壁的时刻 t_wall  = (200-190)/(210-190) = 0.5
此时脚点 y=180，侧壁代理 [130,179] 与墙重叠。

到水面的时刻 t_water = (188-170)/(190-170) = 0.9
此时 x=208，落在水域范围内。
```

正确结果是先碰墙，不能因为墙后面有水就穿过去。该反例只验证几何和当前条件之间的冲突；还需构造有效拓扑、角色状态，接入 `step_player` 测试。

**修复目标：** 用同一路径上的 `t_wall`、`t_water`、`t_landing` 比较顺序；墙先发生时，重新检查被墙截断后的剩余纵向路径能否入水。不得简单删除整个入水机制。

### F2：缓降的碰撞预测与实际移动使用不同速度【代码事实已确认】

当前墙体查询使用：[R04]

```rust
projected_vy = (vy + GRAVITY * dt).min(FALL_SPEED);
```

但实际空中推进在缓降窗口内还会使用：

```rust
next_vy.min(MAGIC_WAVE_SLOW_FALL_SPEED) // 当前为 95
```

因此有扫掠算法，也可能算错扫掠路径。`projected_vy` 的一次重力预估还用于入水预判，这个差异并不限于侧壁。

建议加入两个独立几何夹具：

| 参数 | 墙顶误挡夹具 | 墙底漏挡夹具 |
|---|---:|---:|
| `dt` / 原 `vy` / 重力 | 0.05 / 100 / 2000 | 相同 |
| 未计缓降的步末 `vy` | 200 | 200 |
| 实际采用的步末 `vy` | 95 | 95 |
| 到墙时间 | 0.5 | 0.5 |
| 起始脚点 `y` | 96 | 246 |
| 预测接触 `y` | 101 | 251 |
| 实际接触 `y` | 98.375 | 248.375 |
| 墙范围 | 100..200 | 100..200 |
| 冲突 | 预测身体下沿 100，实际下沿 97.375 | 预测身体上沿 201，实际上沿 198.375 |

这说明既可能多挡，也可能漏挡。数字是按当前常量推导的预期值，**不代表本轮已运行项目、确认某张实图发生了这两种现象**。

**修复目标：** 缓降、跳跃、击退等规则先形成唯一运动方案，再交给查询与执行；不得维护一套“碰撞专用重力”和另一套“移动专用重力”。

### F3：只查两个邻居，空中锚点不会随横向经过的平台更新【代码事实已确认；扩大范围需由夹具驱动】

`chain_wall_on_sweep` 使用 `for _ in 0..2`，空中主要依赖最后稳定落脚点。[R03][R04]

需要验证的失败形态：

- 一面墙位于三段以上短地面线段之后，仍在同一条有效轮廓中。
- 一段高侧壁被拆成多个连续竖直线段，角色高度只与更后面的线段重叠。
- 离开平台后飞行较远，或在空中转向，原锚点按移动方向查询的两条边已不包含实际接触墙。
- 游泳离水等路径将两个 foothold ID 都清零后，需要如何恢复有效碰撞上下文。

真实数据中已看到一个可用于定向测试的链条：[R11]

```text
地图 000010000，原始组 foothold/2/10

51：(-495,425) → (-444,425)，next=59
59：(-444,425) → (-405,425)，next=60
60：(-405,425) → (-366,425)，next=61
61：(-366,425) → (-366,450)，next=0
```

以 51 为锚点向右查询时，当前两次循环只看到 59、60，看不到第三邻居 61。这是**真实数据上的候选范围证据**，不是“已找到用户此前穿墙地点”的证据；角色能否在合法轨迹中重现，还要通过夹具验证。

**修复目标：** 有限且经过端点验证的拓扑遍历。不要直接把所有竖直 foothold 加入全局碰撞。`last_foothold_id` 还负责跌落恢复，不能为了扩大候选不断改写它。

### F4：候选阶段把接触时刻直接限制到 `[0,1]`【代码事实已确认；遮蔽后续候选的影响待验证】

当前在遍历候选时对时间比例执行 `clamp(0.0, 1.0)`，之后才在 `step_player` 判断是否真的跨越返回的墙平面。[R03][R04]

这会使“本步到不了的候选”也可能先成为返回值；调用方不跨越它，并不意味着查询继续找到了其他真正命中的候选。

**修复目标：** 先判断墙是否在实际路径上，再做重叠和排序。只有超出端点很小的数值误差可以在容差范围内归一化；不能把 `t=-2` 或 `t=4` 变成合法的本步命中。

### F5：墙后落地、入水查询可能使用错误的整步直线【顺序结构已确认；具体回归待验证】

当前先把最终 X 截到墙边，随后用 `old_x → 截断后的 x` 和完整纵向位移调用落地/入水扫掠。[R04]

但“斜向移动到墙 → 沿墙继续上下移动”的实际路径是两段折线，不是一条斜率变小的新直线。窄平台、墙顶与水面交接处有必要验证。

**修复目标：** 查询剩余位移时从真实接触点开始；这次只实现所需的“最多一段侧壁接触＋其后的纵向段”，不建设通用刚体求解框架。

### F6：现有测试断言对左右方向不对称【代码事实已确认】

`assert_no_tunneling` 使用：

```rust
let lo = prev.0.min(x);
let hi = prev.0.max(x);
let crossed = lo <= wall_x && hi > wall_x + CROSS_EPSILON;
```

从左到右恰好停在墙上通常不会被判穿越；从右侧恰好停在墙上却满足该条件。反过来，从墙平面向左越入另一侧又可能不满足条件。测试本身因此需要修正。[R05]

此外，终点连线无法完整描述撞墙后的折线路径，也无法区分落地吸附、跌落恢复与瞬移。不能继续把所有位置变化都解释成一段普通自由运动。

**修复目标：** 左右镜像夹具、明确停墙与穿越区别、针对小场景使用独立预期值；复杂回放记录运动分段和接触事件。断言不能直接调用被测函数来计算正确答案。

## 4. 本次行为契约

本节是项目规则，不宣称是 TMS273 原客户端逐帧实测结论。

| 场景 | 必须保留或实现的结果 |
|---|---|
| 低平台向相连高平台行走 | 保持现在的侧壁阻挡，不自动抬上台 |
| 上升斜撞已确认实体侧壁 | 横向停住，纵向继续；不落地、不重置跳跃次数 |
| 下落斜撞侧壁 | 横向停住，纵向继续；随后仍能落地或进入实际可达水域 |
| 身体仍与有限墙段重叠 | 在该墙既定阻挡语义下不能穿入 |
| 代理身体已经越过墙顶 | 允许通过；不把墙向上无限延伸 |
| 角色贴墙后反向离开 | 立即允许离开，不粘墙、不反复回拉 |
| 普通悬空平台 | 上升穿透、下降承接；不因上下投影重合生成侧墙 |
| 下跳 | 仅忽略指定落脚面，不能关闭侧壁查询 |
| 缓降、普通击退 | 用实际生效的速度检测，不能以角色动作名决定墙是否存在 |
| 入水 | 只有实际可达的水域才能切换游泳状态；先碰墙则先处理墙 |
| 合法瞬移、传送门、复活 | 保留独立的位置迁移语义；不纳入普通连续移动扫掠 |
| 地图外边界、跌落恢复 | 保留当前独立规则，不因修侧壁把角色钉在起跳点 |

### 4.1 碰撞体不能顺手扩大

当前侧壁代理以脚点 X 为横向位置，纵向检测范围是：

```text
body_top    = foot_y - BODY_HEIGHT_PX  // 50
body_bottom = foot_y - 1
```

这是现有窄代理，不是完整人物矩形。披风、武器、头发或宽动画帧看似进入墙面，不一定意味着权威脚点穿墙。需要同时画出脚点与代理范围，区分几何错误和美术轮廓差异。[R02][R03][R07]

这次不增加人物半宽，不改为胶囊或 AABB；否则平台可达性和贴边站立距离会一起改变。如果以后要改身体宽度，单列手感变更。

## 5. 推荐设计：一份运动方案，少量纯查询，单一裁决入口

### 5.1 状态所有权保持不变

```text
玩家输入意图 / 技能已生效状态
                ↓
Rust 世界中的 step_player
                ↓
形成这一物理步的运动方案
                ↓
侧壁 / 落脚面 / 水域查询：只读地图，不改玩家
                ↓
按接触顺序裁决、提交合法位置与速度
                ↓
服务端快照
                ↓
Phaser / TypeScript 显示
```

不增加每角色模拟任务，不把碰撞搬进网络层，不让前端提交“已经修正好的权威位置”。沿用仓库的单一权威世界规则。[R12]

### 5.2 唯一运动方案

先复用当前状态分支处理跳跃、下跳、击退、缓降；再生成本步实际使用的速度和位移。

需要特别明确：

- 空中：重力与缓降只结算一次；墙、水、落地用同一个 `next_vy` 和目标 Y。
- 地面：目标 Y 是实际地形跟随结果，不是凭空增加一段自由落体位移。
- 走出平台变成空中：保留当前经回归锁定的离地时序；不要顺便重算完整的连续离地物理而改变手感。
- 游泳/爬梯专用路径：保持其模式切换；本次审核出口如何交回普通移动，不扩大为游泳系统重写。
- 碰撞求解后继续剩余时间，不应再叠加一次整步重力。

下面只是建议的内部值类型，不是仓库已有 API，也不需要通过网络传输：

```rust
struct MotionSegment {
    from_x: f64,
    from_y: f64,
    to_x: f64,
    to_y: f64,
}

struct WallContact {
    foothold_id: u64,
    t: f64,          // 对当前查询段的比例，必须为有效区间内的有限值
    x: f64,
    foot_y: f64,
}
```

落地结果原本已在函数内部计算 `t`，可以保留并返回；水域结果同样需要可比较的接触时刻。只增加解决排序需要的信息，不引入泛型事件总线或通用碰撞对象继承树。

### 5.3 侧壁候选与窄相检测分开

候选来源保持地图驱动。每一个候选至少满足：

1. 是项目当前规则认可的竖直侧壁，而不是任意装饰或无关轮廓。
2. 符合源轮廓的连接关系和既定阻挡方向；左右镜像场景都必须正确。
3. 其实际墙平面处在本步运动范围内。
4. 到达墙平面时，代理纵向范围与该有限墙段有重叠。

到达时刻：

```text
dx = to_x - from_x

若 |dx| 很小：不产生新的横向穿越；贴墙/初始重叠单独处理。
否则：
    raw_t = (wall_x - from_x) / dx
    若 raw_t 明显小于 0 或大于 1：排除候选。
    在端点容差内规范化 t。
    contact_y = from_y + (to_y - from_y) * t
    使用 contact_y 计算代理与墙段的纵向重叠。
```

`chain_wall_on_sweep` 当前返回的是前驱线段边缘 `edge`。不能未经核验直接把它替换成 `candidate.x1`；先用端点连续性检查确认两者应相同，不一致时记录数据与兼容语义，而不是制造新假墙。[R03]

多候选用有效 `t` 排序。先做有限数检查；用确定的排序与 ID 兜底。不要把“误差小就视为相等”写成不满足传递性的比较器。

### 5.4 侧壁、落地、入水按时间裁决

```text
原始期望路径
   ├─ 侧壁：最早的有效 t_wall
   ├─ 单向落脚面：最早的有效 t_floor
   └─ 入水：最早的有效 t_water
                ↓
          先处理真正先到达的事件
```

关键规则：

- 墙先到达：移动到墙的接触点，去掉朝墙内的 X 速度和剩余 X 位移；继续剩余 Y 位移。
- 落脚面先到达：按现有落地约定设置脚点、`grounded` 和 foothold；本次不新增落地后的额外水平余程。
- 水域先到达：按现有入水约定切换状态；但不能忽略更早发生的墙或落地。
- 没有接触：提交期望终点。

水与地面改变优先级可能涉及既有岸边适配，因此必须配套“合法入水不回归”的测试。不是将 `water_entry` 统一挪到最后就算修复。

### 5.5 撞墙后最多追加一段纵向查询

本次普通移动无需复杂的多次反弹求解器：

```text
第一段：起点 → 首次侧壁接触点
第二段：接触点 → 保留剩余纵向位移的终点
```

第二段只对剩余实际路径检查落地/入水，不能从原起点到截断后的终点重新连一条斜线。第二段查询的局部 `t` 要换算成原物理步时间后，才能记录或与原事件比较。

接触后在同一步越过墙顶，可以下一物理步再恢复横向移动；不要求本轮新增“半步越顶后自动恢复横向余程”的复杂行为。对精细手感有需求时再单列。

同一时刻接触墙顶和平台时，先按代理范围判断墙是否真的重叠，再处理有效接触组合。不要用无条件“墙总优先”或“水总优先”掩盖角点几何问题。

### 5.6 容差、贴墙与不合法初始状态

优先统一已有约 `0.001` 的几何容差与现有 1 像素脚底留空语义。二者不是同一个概念，不要合成一个任意可调的“大吸附距离”。[R03]

`t=0` 的接触要区分进入与离开；不得因为角色已经在墙边而阻止其反向离开。左右镜像必须验证。

出生、复活或加载存档后已处于不合法位置的恢复，不依靠给普通跳跃增加任意大回退量解决。本轮只对照现有恢复入口，出现问题时单独记录，禁止拿“无碰撞”作为默认修复。

## 6. 长链与无锚点：只做有证据的局部扩展

### 6.1 同一连通轮廓内扩大查询

当回归夹具证明“两邻居”不足时：

- 从有效锚点沿 `prev/next` 查询经过验证的连续轮廓，不按固定两个节点提前截断。
- 用访问集合或明确的访问标记防止环；上界可取本地图 foothold 数量，而不是无限循环。
- 用运动的 X 范围缩小候选；不能因为一个横向端点已经超过范围，就误丢同 X 的连续竖直墙段。
- 合并共线竖段只能发生在端点连续、语义一致的段之间；有空隙的墙段不得合并。
- 遇到断链、非连续端点或来源不明的连接，保留可追踪的诊断；不要把“跳过验证”当作向后兼容。

仓库长期规范明确指出当前线性 foothold 查询可以继续使用，因此本轮默认不增加空间树、ECS 或多线程查询。[R12]

### 6.2 不滥用 last_foothold_id

该字段既给侧壁查询提供锚点，也给跌落恢复提供最后稳定平台。[R04]

如果确实需要新的“空中当前碰撞轮廓”，采用独立的短期内部上下文，并明确哪些事件建立、继承、清理它。只有失败证据表明必要时才新增字段。

| 状态变化 | 要求 |
|---|---|
| 正常起跳 | 保留可用的侧壁上下文，但当前落脚状态为离地 |
| 下跳 | 忽略的只是落脚面；上下文仍可识别有效侧壁 |
| 空中落地 | 新平台成为稳定锚点；清理过时接触 |
| 爬梯弹出 / 游泳离水 | 不假定总有有效 last foothold；使用已验证的出口规则 |
| 换图、复活、合法瞬移 | 清理旧图或旧位置的短期接触；按新落点重建必要信息 |
| 跌落边界恢复 | 不被空中临时查询覆盖原恢复语义 |

无锚点不等于“所有墙关闭”，也不等于“所有地图竖线都阻挡”。若必须从局部几何恢复归属，需要先使用可靠的源数据和出口上下文，不以最近的一条任意平台或相同渲染层代替证明。

- 不用 `min(x0,x1)/max(x0,x1)` 的不对称条件偷代双向穿越；给“从哪边接近、是否只停在墙上”明确判据。

## 13. 风险、回滚与非目标

### 13.1 主要风险

| 风险 | 防护 |
|---|---|
| 入水修复把原本可以下水的岸边挡死 | 先后两种接触顺序成对测试；只允许实际可达水域接管 |
| 扩大候选使无关层变成假墙 | 用有效轮廓、端点与来源约束；不全局扫所有竖线 |
| 更新空中锚点破坏跌落恢复 | 不挪用 `last_foothold_id`；恢复路径定向回归 |
| 提升碰撞精度顺便改变落地/起跳手感 | 保持时间步、尺寸、初速与已有落地剩余位移约定 |
| 旧补丁覆盖新模块拆分 | 只做符号级小改动，不复制 `.sidewall-fixed` 全文件 |
| 测试文件未接线或过滤 0 个用例 | `--list` 加实际运行数量记录 |
| 代码正确但旧服务器仍在运行 | 把构建、运行、用户实玩三种证据分开记录 |

### 13.2 回滚

每个行为改动保持小而可独立回退：速度一致性、事件顺序、候选范围分别留明确提交边界。保留揭示问题的回归用例与诊断证据，不用放宽断言制造“回归通过”。

回滚以对应代码差异为单位，不能覆盖整个 `world.rs`；已经落地的聊天、背包、任务等拆分不在回滚范围内。运行版本切换仍通过统一启动脚本并取得用户允许。

### 13.3 明确不做

本次不做 Three.js/Phaser 引擎迁移、完整刚体系统、角色宽碰撞体、自动攀墙、蹬墙跳、吸附上台、地图实体填充、多线程世界、前端预测/回滚、全地图资源重导出，也不修改合法瞬移和任务传送的玩法规则。

## 14. 常见 2D 平台游戏实践，如何适配本仓库

### 14.1 Celeste / TowerFall：借鉴共用移动能力，不照搬整数像素模型

开发者的公开说明中，角色使用共同的 `MoveX/MoveY`，移动与碰撞回调分开；其实现采用整数矩形碰撞体和逐像素推进。[E01]

本项目借鉴“不同角色状态复用同一组可靠碰撞能力”。不把现有 `f64` foothold 改成整数 AABB，也不为了本问题引入逐像素全地图扫描。

### 14.2 Box2D：借鉴沿路径查询与相邻边信息

Box2D 的官方碰撞说明提供 shape cast / time of impact，并讨论相邻线段内部顶点导致的 ghost collision 与邻接信息。[E02]

本项目已有沿路径求交，应复用它；本次新增重点是正确轨迹、接触先后、有限墙段与可靠候选。这里只借鉴几何原则，不依赖 Box2D 库。

### 14.3 原版行为证据边界

Nexon 的 MapleStory Worlds 移动说明是另一个产品的资料，不能自动证明 TMS273.7 原客户端行为。本轮读取其网页只能稳定取得文档入口与标题，未取得足够正文来重新核验旧版方案中的具体 API 行为，因此本版不把该网页作为“官方必须空中挡墙”的论据。[E03]

此次规则依据是用户明确要求，加上仓库现有地形与权威移动模型。源代码里的 v83/HeavenClient 注释属于历史或跨项目参考，也不等于 TMS273 原版逐帧验收。
