## 0. 先给结论

截图中的任务文字与公开 TMS 数据的 **Quest 36306** 相符。该条目指向 **NPC 22000：霸西力**，公开 NPC / 地图数据将其关联到 **枫之岛—码头，Map 2000100**。[S01][S02][S03]

最关键的异常是：**脸型资源 22000 也存在，台服名称正是「小怪物粉豆脸型」**。截图底部把这个脸型名称当作 NPC 名称使用。[S04]

因此，第一优先级不是到处补 NPC，也不是替换一句显示文字，而是核查以下链路是否丢失资源类别：

```text
任务目标 NpcId(22000)
  → 名称导出 / 名称解析 / 共享缓存
  → 被误解释为 FaceId(22000)
  → UI 显示「小怪物粉豆脸型」
```

这是**高可信根因假设**，尚不是已经读到源码后的结论。它能解释错误引导，但还不能证明 NPC 实体确实缺失；NPC 可能存在但名称错误，也可能另有地图、生成或脚本问题。

**正确的玩家操作定位：先找枫之岛的码头和霸西力，不要寻找名为「小怪物粉豆脸型」的 NPC。** 与正确 NPC 交互后，应进入本任务对应的接取 / 登船处理。完整转场、扣票与完成时机需要进一步核验，不能直接假定是普通「交物品领奖」任务。

## 4. P1：修复资源类别丢失与名称串表

### 4.1 最小正确改动

建议在本次涉及的链路显式区分 NPC、脸型、物品、地图、任务等类型。若当前运行时已经绑定唯一地区 / 版本，可由 catalog 对象承载这些上下文；共享缓存跨内容集时，键必须包含相关上下文。

```text
错误：nameCache[22000]
正确：nameCache[(content_manifest, locale, "npc", 22000)]
正确：nameCache[(content_manifest, locale, "face", 22000)]
```

至少检查三个地方：

- **导出器：**是否递归扫描不同 String 节点后，用裸数字 ID 写进一张名称表；是否后写覆盖先写。
- **调用处：**任务目标查询是否误用物品 / 外观名称函数，或丢了目标类别。
- **缓存：**即便调用函数已分开，是否仍共用裸 ID 缓存，导致结果随加载顺序变化。

修正后重建相关派生数据并更新内容版本。只修改运行时查询但继续读取已污染的导出表，不算完成。

### 4.2 Rust 类型约束示意

以下为新增设计示意，按现有类型体系落地；不要无必要重构整个工程。

```rust
#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct NpcId(pub u32);

#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct FaceId(pub u32);

#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct QuestId(pub u32);

#[derive(Clone, Copy, Debug, Eq, PartialEq, Hash)]
pub struct MapDefId(pub u32);
```

名称访问接口应表达类别，例如 `npc_name(NpcId)` 与 `face_name(FaceId)`。不要仅用 `type NpcId = u32` 冒充类型隔离：Rust 类型别名仍是原类型，而 newtype 能提供不同类型之间的编译期隔离。[S07]

### 4.3 TypeScript 名称解析示意

```ts
type NameRef =
  | { kind: "npc"; id: number }
  | { kind: "face"; id: number };

interface NameCatalog {
  readonly npc: ReadonlyMap<number, string>;
  readonly face: ReadonlyMap<number, string>;
}

// catalog 由当前内容清单与语言构造，不能混合多个未知版本。
function resolveName(
  ref: NameRef,
  catalog: NameCatalog,
): string | undefined {
  switch (ref.kind) {
    case "npc":
      return catalog.npc.get(ref.id);
    case "face":
      return catalog.face.get(ref.id);
  }
}
```

这里的判别联合用于保留资源种类并约束分支。[S08] 对外协议反序列化仍需运行时校验，不能只依赖 TypeScript 声明。

缺少 NPC 名称时，开发模式显示 `NPC #22000（名称缺失）` 并记录错误。**不得回退到脸型或道具名称表。** 数字显示长度和前导零只属于序列化格式，不能拿来代替资源类别。

| 参数 | 当前状态 | 取证方式 |
|---|---|---|
| 接取 NPC、前置条件、脚本名 | 有公开候选值 | 与项目精确版本数据对照 |
| 任务是否启用、是否允许跳过 | 未确认 | 内容清单、剧情入口与对应版本实测 |
| 船票 itemId、消耗数量 / 时机 | 未确认 | 前序任务实际发放记录、合法可读脚本或对应版本实测 |
| 中间场景、目标 mapId / portal | 未确认 | 任务处理器、转场链与实测 |
| Accepted / InProgress / Completed 的提交时机 | 未确认 | 实际任务行为和持久化设计 |
| 奖励及后继剧情 | 未确认 | 原始任务定义、处理器和对应版本实测 |

这些参数必须在开启完整可玩流程前补齐；不能用 `0`、空数组或任意传送点当默认成功行为。必要逻辑不支持时，返回明确的内容未就绪原因，而非让玩家继续寻找一个无法完成交互的 NPC。

### 6.3 服务端校验边界

客户端只提交交互意图；最终身份、任务资格、背包、NPC 和地图位置来自服务端事实。

建议处理顺序：

```text
已认证会话的玩家
  → 验证当前地图实例与 NPC 实体
  → 验证 NPC 模板、可见条件、距离或合法远程交互规则
  → 验证任务状态、前置任务、职业等适用条件
  → 验证交互会话与玩家选择
  → 根据已核实参数验证船票及转场目标
  → 准备并提交一次业务变更
  → 下发任务、背包、场景变化与结果
```

不得仅凭客户端传入 `npcId=22000` 就允许登船。必须绑定真实实体 / 受支持交互来源，拒绝远程伪造、跨实例、过期对话与重复操作。

### 6.4 避免扣票、完成、转场各成功一半

建议先验证全部必要条件与目标可用性，再通过项目现有持久化边界提交。

若正确业务需要消耗船票，应保证：

```text
同一合法交互最多消耗一次；重复点击不重复扣除。
提交前失败：背包与任务事实不变。
提交成功但客户端未收到响应：重连仍恢复已提交结果。
目标切换需要分步执行：持久化可恢复的转场意图或阶段。
```

数据库事务、角色聚合快照、持久化事件等均可按现有工程选择；不要仅用一次内存修改声称已经具备断电一致性。若转场跨越不同写入边界，需显式恢复机制，而非把网络传送放进“理论上的原子块”。

本任务若是不可重复任务，应以已提交的任务进度和业务结果防重；仅记录客户端 requestId 不能阻止换一个 requestId 再次消费。若业务允许重复，应使用已确认的重复规则和交互实例标识。

## 7. P4：修正引导、状态与错误反馈

### 7.1 状态不要由船票数量单独推断

截图同时显示「可接取」与「船票 1/1」，这本身不矛盾：角色可以在接取任务前持有物品。

建议保留清晰区别：

| 显示状态 | 依据 | 引导 |
|---|---|---|
| 不满足条件 | 服务端返回未满足条件 | 显示具体前置条件，不提示立即可办 |
| 可接取 | 尚未接取，已满足当前接取条件 | 找正确接取 NPC |
| 进行中 | 服务端已经接受任务 | 展示当前实际步骤 |
| 可完成 | 已接取且完成条件、目标交互均满足 | 找实际完成目标；脚本任务按真实阶段展示 |
| 已完成 | 服务端已提交完成事实 | 展示后续剧情或完成记录 |
| 内容未就绪 | 必需地图 / NPC / 处理器不受支持 | 给出明确原因，避免死路引导 |

`Available / ReadyToComplete` 可以是由服务端事实派生的视图，不要求为了 UI 新增重复持久化状态。

### 7.2 推荐显示结果

在确认该候选数据就是项目正确配置后，任务引导应类似：

```text
前往「枫之岛—码头」，与「霸西力」交谈。
船票：1 / 1
```

「接取任务」「准备登船」「提交船票」等动作文字，应与当前阶段一致，不提前承诺未验证的完成行为。

展示 NPC 名字来自 NPC 名称表；地图名来自地图名称表。导航目标来自结构化目标和可达性判断，不从说明文字反向猜测。

开发模式可附带 questId / npcId / mapId / contentVersion；玩家界面不需要暴露整套诊断字段。

### 7.3 错误必须能区分

建议区分：前置未满足、道具不足、NPC 不在当前实例、交互过期、脚本未实现、转场目标不可用、内容版本不匹配。

错误码按现有工程命名；日志保留结构化原因。不要全部显示成「找不到 NPC」或静默无响应。

## 10. 启动、验证与回滚

### 10.1 启动约束

集成验证与人工复测统一使用项目已有入口：

```bash
./启动3010.command
```

不得另用 `cargo run`、`npm run dev` 或直接执行服务端二进制绕过该脚本启动服务。需要新参数时先修改并审查脚本，而不是假称已有某个参数。

单元测试、类型检查和格式检查按真实工作区执行。若 P0 确认后端 manifest 确实在 `server/Cargo.toml`，可采用：

```bash
cargo fmt --manifest-path server/Cargo.toml --all -- --check
cargo test --manifest-path server/Cargo.toml --locked
```

`cargo test` 的 manifest 与锁文件行为以 Cargo 官方文档为准。[S09] 前端命令以真实 `package.json`、工作区和 lockfile 为准，本文不虚构测试脚本名。测试夹具本身不得偷偷启动独立服务绕过统一入口。

### 10.2 旧存档修复

名称修复通常只涉及派生数据；先确认没有把错误名字或错误资源类别持久化进角色数据。

需要迁移时，只处理可识别的受影响记录，保留迁移版本与前后状态。必须覆盖：未接取但持票、已接取、异常扣票、已完成但转场未恢复等实际存在的状态。不能全体补发船票、全体完成任务或重置整条主线。

迁移须可重复执行而不重复补偿；不凭“任务未完成”就认定玩家一定丢票。

### 10.3 回滚

代码和派生内容按兼容版本一起管理。保留上一个有效 manifest，避免修复后的代码继续读取污染数据，或旧代码读取不兼容的新 schema。

若存在不可逆的背包 / 任务变更，不仅回滚代码；需要保留已提交业务结果并提供兼容读取或定向恢复。不要删除现有玩家数据来证明新角色能过任务。
