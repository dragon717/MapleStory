# 冒险岛复刻与超越：世界意识、玩家投入曲线与翻车事件 v0.1

日期：2026-09-10  
性质：设计提案与最小验证规格。未修改项目代码，未声称已完成实现或玩家验证。文中事件、NPC、规则和时间参数均为本项目原创提案，不是冒险岛原作事实。

## 0. 决策摘要

复刻主线继续围绕“打怪—成长—换打法—挑战 Boss—进入新区域”。创新支线先验证一个很窄的命题：当一个可理解、可自由绕过的世界需求出现时，玩家是否愿意付出一点时间；当这种付出产生真实改变并被具体的人记住时，玩家是否更愿意把这里视为自己生活过的地方。

**首版不是完整商队系统，而是：同一个 NPC，两次相遇，一次真实改变。**

“世界意识”不是全知 AI，不是读心术，也不是不断制造事故的导演。它是：世界有自己的事实和目标；实体能够在有限信息内发现需求、采取行动；有效行动改变事实；知情者能够保留记忆并作出相称的回应。

“玩家投入曲线”不是在线时长最大化，也不是根据一次帮助给玩家贴上人格标签。它描述：玩家如何从看见、理解、尝试，走到主动贡献、感到有用、被记住，以及安心离开。

核心边界：

> 世界需求由事实和实体目标产生；玩家偏好只影响真实机会的呈现，不得反向捏造事故。关系回应可以个性化，共享世界的事实不能各说各话。

## 1. 与既定冒险岛复刻目标的关系

已读项目文档《00_RESEARCH_AND_REMAKE_PLAN.md》v0.1将研究范围锁定为 TMS V273，要求不混入其他地区、怀旧服或后续版本规则，并优先做完整体验切片而非内容大而全。本提案沿用这个边界。[P0]

这里有两个独立验收面。

| 验收面 | 本阶段应回答的问题 | 不允许的替代 |
|---|---|---|
| 冒险岛核心复刻 | 移动、攻击、职业能力、成长和区域推进是否形成完整体验？ | 用温情对白掩盖打击、移动或成长尚不可玩 |
| 原创世界增量 | 同一行动是否产生可见、持久、能被准确认出的世界后果？ | 用更多职业、地图、任务数量代替世界反应 |

翻车事件应插在既有冒险路径旁，不替代练级图、不阻塞主线、不成为 Boss 或核心成长材料的前置。

“超越”在当前阶段只指一个可验证的增量维度：除了角色变强，玩家还能感到自己改变过这个地方。不能用一次成功的互动宣称全面超越原作，也不应把原作概括成“没有叙事、社会关系或动态内容”。

## 2. 世界意识模型

### 2.1 因果结构

```text
世界事实与实体状态
    ↓ 结合实体自己的目标
规则识别当前缺口
    ↓
产生实际需求与可行动方式
    ↓
NPC 自行处理 / 玩家介入 / 无人介入
    ↓
产生新的世界事实
    ↓ 仅沿实际感知或传播渠道
形成具体实体的知识与记忆
    ↓
影响后续行为、称呼、交谈和关系
```

不是“先随机给玩家一项扶车任务，再生成需要帮助的人”。

正确例子：货车侧倾，使这批货无法按原计划继续移动；车主希望送达货物，因此存在恢复通行能力的需求；玩家可以介入，但需求不是为了玩家才存在。

### 2.2 四类数据及其边界

| 层 | 保存或计算什么 | 本例 | 禁止混入什么 |
|---|---|---|---|
| 事实 | 客观且权威的实体状态 | 车侧倾、货物未固定、车主轻伤、货单目的地 | “玩家已经完成两个任务”冒充世界事实 |
| 目标与需求 | 实体想实现什么，当前哪些事实妨碍它 | 车主想继续送货，但车辆不能移动 | “玩家喜欢照顾人，所以必须产生伤员” |
| 知识与记忆 | 哪个实体通过什么方式知道了哪件事 | 车主亲眼见到玩家扶车 | 全村自动共享玩家行为历史 |
| 表达 | 在当前语境下如何呈现已知事实 | 下次相遇时认出扶车者 | 声称不知道的事、夸大贡献、凭空承诺奖励 |

形式化约束，作为工程设计，不作为心理学结论：

```text
Needs_t = derive(Facts_t, ActorGoals_t, AvailableCapabilities_t)
Events_t = resolve(Facts_t, ValidatedActions_t, DueNpcActions_t)
Facts_{t+1} = apply(Facts_t, Events_t)
Memory_{npc,t+1} = remember(Memory_{npc,t}, observed_by(npc, Events_t))
Response_{npc,player} = express(known_facts, local_memory, current_context)
```

需求尽量从事实推导，而不是复制一份容易失真的任务完成状态。

### 2.3 世界知道、NPC 知道和客户端知道是三件事

后端可以知道全部事件，但 NPC 不因此全知。首版只支持直接参与或目击形成的记忆，不做传闻扩散。将来需要转述时，必须存在明确的讲述者、接收者及来源事件。

私有交谈可以因关系不同而变化；车辆是否扶正、是否已经离开等共享事实对同一世界实例内所有玩家一致。

NPC 也不需要每次认出玩家都完整复述过去。一次点头、一个合适的称呼、偶尔一句具体回忆，就能作为回应。首版可采用固定文案，完全不需要大模型。

### 2.4 不围绕玩家旋转

无人帮助时，NPC 会按既定行动计划自救、休息、整理和继续行程。玩家离开不让时间停止，也不让 NPC 永久保持求救姿势。

无人介入的结果可以是“更晚送达”，而不是专门为了惩罚路过者设计的死亡、全镇断药或主线失败。玩家不是这个世界唯一有能力的人。

首版允许注入一组固定的事故初始事实用于测试。没有必要先做导致翻车的完整物理仿真。**动态首先指状态会真实改变，而非每个事故都必须随机生成。**

## 3. 最小事件：林间岔路的侧倾货车

### 3.1 地点与角色

地点为原创测试区域，可复用既有地图的一段路边空间，不声称属于原作某个任务。

同一 NPC 使用稳定身份。暂名“阿榆”，身份为送货者；另一名同行者负责协作和自救。第二次相遇复用现有村庄或驿站的路径，不另外做一张专用重逢地图。

初始事实：货车一只轮子卡在沟沿，车身侧倾，但结构没有断裂；货物没有全部固定；送货者擦伤，行动慢但不处于致命危险；车上急救包有可供使用的绷带；道路仍可通行。

不要同时设计成“车轴完全断裂”又允许“扶一下就开走”。场景表达必须和规则一致。

### 3.2 玩家第一次看到什么

先看到车和人处于不太对劲的状态，再靠近看出可以做什么。

送货者扶着车辕，同行者看看货物、再看看路。可以有一句低频自言自语：“先把这边稳住……”但不隔着地图追喊玩家，不刷屏求助。

正常交互距离内显示简短动作提示，如“扶一把”“递绷带”“我看着路”。提示不是任务接受框，也不产生任务日志。

“没有强制任务”不等于故意隐藏操作方式。字幕、对比度、交互提示和无障碍设置仍应保留，避免把看不清或操作困难误判为不愿投入。

### 3.3 三个并行入口，不是一条三步任务链

以下耗时仅作为第一轮原型起点，不是原作数值或已验证最佳值。

| 行动 | 进入条件 | 暂定操作成本 | 真实改变 | 相称回应 |
|---|---|---|---|---|
| 扶车 | 车仍侧倾，支撑位置可用 | 约 2–4 秒，可取消 | 车恢复直立，解除车辆恢复这一缺口 | “稳住了，多亏你搭了把手。” |
| 递药 | 伤员仍需要绷带，急救包中仍有绷带 | 约 2–3 秒 | 绷带从急救包移交；NPC 随后包扎，姿态和行动状态改变 | “这下方便多了。” |
| 看路 | 整理工作尚未完成，NPC 当前需要兼顾警戒 | 约 6–10 秒，可提前交还 | NPC 把警戒注意力转回整理，实际推进货物固定 | “刚才你看着路，我才能把绳子系好。” |

递药使用场景急救包，不消耗玩家稀缺背包药剂；首版先测试时间投入，不混入财产损失或补偿预期。

看路需要一次明确的接手动作。经过或在附近挂机不算承担职责。NPC 需要在画面上明显从张望变成工作，不能只是后台计时后弹出一句感谢。

看路不是“站够十秒获得完成奖励”；它是让某个现有工作得以推进。途中离开时，NPC 接回职责，已经完成的整理不倒退。不要求为这个行为新增一波怪物，否则会变成强制战斗任务。

三件事可以任做一件、任做两件、全部不做。出发所需的剩余条件由 NPC 补完。玩家不需要一个人承担整个事件。

### 3.4 当前事实与需求示例

```text
Cart.pose                 = Tilted | Upright
Cart.mobility             = derive(pose, structural_integrity)
Cargo.securing_work       = 实際完成的固定工作
Driver.condition          = MinorInjury | Recovering | FitToTravel
FirstAidKit.bandages      = 剩余数量
Shipment.state            = Stopped | InTransit | Arrived
NpcPlan.next_action_at    = 下一次计划动作时间
```

不要额外保存“玩家扶车任务完成”“玩家递药任务完成”“玩家站岗任务完成”作为世界推进的唯一依据。

贡献记录需要保存，但它回答“谁对哪次事实改变做过什么”，不取代事实本身。

### 3.5 无玩家介入的路径

同行者协助简单包扎，调整两人的分工，逐步固定货物，再合力把车扶正，之后继续运输。可以比有玩家帮助慢，但必须最终推进。

首版采用离散的 NPC 行动和计划时刻，不必在无玩家地图上维持完整物理帧模拟。重新载入时根据已持久化状态和到期行动推进。处理量需有上限，避免重启补算耗尽服务器。

玩家途中离开时，已经提交的帮助仍成立。未完成的独占动作释放占用。NPC 自救接续剩余事实，不整段回滚。

### 3.6 两次相遇之间的连续性

第一次：玩家扶车，车真正立起来；送货者当场道谢，然后继续自己的工作。

之后：货车按世界计划离开；同一批货和同一 NPC 抵达后续地点。

第二次：玩家正常路过村庄，看到这个 NPC 正在卸货或整理空车。NPC 认出玩家，点头，偶尔说：“上次那段坡，总算过去了。”

曾递绷带的玩家可以听到与伤势有关的回应。曾看路的玩家得到与协作有关的回应。完全没帮助的路人仍得到正常礼貌，不被羞辱。

帮助一次不换来“全镇救世主”称号。没有好感度数字、关系经验条、连续帮助奖励、折扣、隐藏战斗增益或成就进度。

### 3.7 回应为什么可信

回应按五个条件验收：

1. 有来源：指向实际发生过的事件。
2. 有主体：由参与或知情的 NPC 作出。
3. 有尺度：小帮助获得小而具体的回应。
4. 有延续：下次相遇不是完全清零，也不是永远重复感谢。
5. 无债务：不会因为帮了一次就强迫玩家连续承担后续工作。

NPC 可以感谢“递过绷带”，但在绷带尚未使用时，不应声称玩家“治好了伤”。文案精度不能超过事实精度。

## 4. 玩家投入曲线模型

### 4.1 理论依据与适用限度

Ryan、Rigby、Przybylski 的游戏动机研究将自主、胜任和关系需要与游戏享受及后续游玩联系起来。[R1] 这支持本提案分别检验“我自己选择”“我做的事有用”“对方认出我”，但不证明翻车事件必然有效，更不证明物质奖励应该从整个游戏里消失。

另一项研究区分“想玩”与“不得不玩”式投入，并显示游玩时长与享受并非可以直接互换的指标。[R2] 本项目不把增加在线时长当作这个事件的首要成功条件。

开发者对《战争之影》Nemesis 系统的 GDC 分享把可记忆角色及长期玩家—角色关系作为设计重点。[R3] 这里借鉴的是“具体角色、共同经历、后续相遇”的结构，不是复制该系统规则或推断其必然适用于本项目。

### 4.2 不使用单一“投入度 83 分”

投入不是可由服务器直接读出的心理变量。首版记录状态和证据，而不制造精确但不可解释的总分。

```text
PlayerEngagementView = {
    encounter_stage,           // 当前可观察参与阶段
    observed_choices,          // 明确且有效的自愿选择
    causal_understanding,      // 访谈/回忆证据，缺失则 Unknown
    relationship_evidence,     // 认出同一NPC、提到共同经历等证据
    perceived_burden,          // 玩家自报或已证实的阻碍；不能仅由离开推断
    opportunity_context,      // 当时是否看得到、是否仍可参与、是否正忙
    confidence                 // 每个判断分别保留不确定性
}
```

线上存储应以必要的行为事件为主，主观维度可以只用于取得同意的研究。不要将研究访谈结果转成永久人格画像。

### 4.3 快曲线：一次相遇中的投入变化

```text
路过 → 注意到异常 → 理解需求 → 确认能帮 → 选择行动
                                               ↓
安心离开 ← 得到相称回应 ← 看见自己造成的改变
```

这是有退出分支的体验路径，不是所有人必须走完的等级表。

| 阶段 | 玩家可能关心什么 | 设计需提供什么 | 可观察证据及限制 |
|---|---|---|---|
| 注意 | “那里怎么了？” | 清楚但不强迫的场景信号 | 进入视野只是曝光代理；不能证明真的注意到 |
| 理解 | “他们卡在哪里？” | 状态和动作之间可解释的关系 | 可在事后描述需求；仅停步不足以证明理解 |
| 判断 | “我做得了吗？能走吗？” | 可读的交互、低初始成本、自由退出 | 查看或尝试交互；不能推断道德动机 |
| 贡献 | “我来搭把手。” | 确实可改变的局部状态 | 权威提交的帮助行为，不以区域挂机替代 |
| 确认 | “刚才真的有用。” | 可见的姿态、动作或进度改变 | 玩家能指出哪个变化由自己促成 |
| 回应 | “他知道是我帮的。” | 精确且相称的当场回应 | 记得回应内容；不是读取隐藏分数 |
| 离开 | “这件事有个好收尾。” | 无追债式后续要求 | 结束离开可以是成功，不自动计为流失 |

曲线的高潮不是最长站岗，也不是最大特效，而是玩家把“我的动作”和“世界变化”联系起来的那一刻。之后操作负担应该下降，允许玩家回到原本的冒险节奏。

### 4.4 慢曲线：跨相遇沉淀关系

```text
陌生人
  → 认得这张脸
  → 记得一起经历过一件事
  → 对这个具体人形成有限期待
  → 逐渐把这条路或村庄视为熟悉的地方
```

这不是必然发生的五级关系条；不同玩家可能停留在不同位置，也可能完全无感。

对一个路人帮忙，不应自动推导成对整个商会的信任，更不能推导成玩家“善良”或“照顾型人格”。关系必须有对象、有经历、有信息来源。

长期方向是多种经历，而非重复救同一辆车：以后可能平常路过、同行一段、交换道路信息或一起遇到新问题。但这些不是首版开发项。

**快曲线检验“我愿意做一点”；慢曲线检验“我记得这里和这里的人”。**

### 4.5 玩家偏好与个性曲线的使用边界

本阶段不自动给玩家分配不同任务。对同一事实同时提供几种合理的参与方式，让选择先发生，再讨论能从中学到什么。

后续存在足够多真实需求时，可采用以下过滤顺序：

```text
真实存在且未解决的需求
    → 位置可达、玩家能力可处理
    → 当前没有战斗/赶路等明显冲突
    → 玩家明确表达的偏好或有置信度的近期选择
    → 非排他的呈现顺序
```

玩家喜欢照顾 NPC，不使 NPC 更频繁受伤；玩家喜欢战斗，不使其面前的每辆车都遭遇劫匪。选择某类行为，只增加对此类行为的有限证据，不永久关闭其他入口。

一次路过不帮助不算负样本。玩家可能没看到、没理解、正在赶路、已有人处理，或只是不喜欢这个事件。涉及推断时必须保留机会暴露和上下文。

首版的偏好状态统一从 Unknown 开始，不需要训练模型、人格问卷、推荐算法或商业化行为画像。

## 5. 最小工程模型：Rust 权威后端，Web/TS 表现

以下为建议的逻辑分层，不是假定仓库已有这些类型或目录。

### 5.1 最少实现边界

```text
CartIncident
    世界实例、实体标识、当前事实、修订版本、下一次NPC行动时刻

ActionResolver
    距离、目标状态、交互占用、资源与会话有效性校验

ContributionRecord
    来源事件、玩家、实际行动、确切作用对象与已提交结果

NpcMemory
    NPC、被记住的玩家、来源事件、事实摘要、记忆表达节制信息

ResponsePresenter
    只读世界快照与该NPC被允许知道的记忆，选择动画和文案
```

开发时可以把前四项放在同一服务和少量模块中，不需要新增微服务、Kafka、通用事件编排平台或统一“世界大脑”。不要求先重构全项目 ECS。

### 5.2 一次帮助的权威链路

```text
客户端：提交一次带请求ID的交互意图
    ↓
服务端：检查目标版本、空间范围、当前条件、会话与动作占用
    ↓
计算事实差异与贡献结果
    ↓
提交事实变更 + 来源事件 + 贡献/相关记忆 + 待广播记录
    ↓
提交成功后返回结果，并推送版本化世界增量
    ↓
客户端播放与已提交事实一致的结果表现
```

客户端可以立即播放抬手等尝试动画，但车是否已经扶正、绷带是否移交、谁被记住，都以服务端结果为准。提交失败时不能播放最终成功或建立记忆。

首版推荐将一次离散帮助的事实、贡献和记忆放在同一个持久化事务边界内。若未来记忆改为异步派生，需使用可靠事件记录、幂等消费者和显式延迟状态，不能悄悄丢失。

### 5.3 幂等、并发和短时职责

一次交互的稳定请求标识应包含会话命名空间，避免重连后简单自增序号碰撞。相同请求重发返回先前结果，不重复消耗绷带、不重复追加贡献。

同一辆车只发生一次 Tilted → Upright。两人同时请求时由服务端决定实际成立的动作；后到者得到“已经扶稳了”等事实反馈，不获得虚构贡献。多人协作扶车若尚未实现，不假装每个人都完成了完整扶车。

看路使用有明确接手、释放与超时的短时职责。玩家离开或断线后，职责不能无限占用；NPC 接回警戒。已提交的整理里程碑保留，未确认的在线时间不在重启后补成玩家贡献。

无需持久化每个表现帧。持久化改变世界意义的里程碑、计划时刻、来源与稳定身份；表现进度可按已确认状态重建。

### 5.4 共享世界与个人回应

首版锁定一个固定世界/地图实例，不做跨频道身份迁移或全服经济同步。

同一实例内，晚到玩家看到已改变的车和货物，不能为了给他个人制造体验而重新翻车。已离开的货车不会因另一个玩家进图又出现。

NPC 可以对不同玩家说不同的话，前提是这些话分别来自真实记忆。个人化称呼和对话不等于个人化世界事实。

首轮可先在单人体验中验证，再用两个客户端验证共享正确性；这不是增加事件机制，而是验证权威世界边界。

### 5.5 表现层的重点

最高优先级不是长对白，而是：角色与物体接触位置正确、扶起前后轮廓明显不同、NPC 有与帮助对应的动作变化、货车离开与重逢身份连续。

若只能先做好一个入口，就先做“扶车 → 车立起来 → NPC 当场回应 → 下次认出”。另外两个入口在这一条闭环成立后复用相同的贡献与记忆链路。

### 5.6 工程验收用例

| 用例 | 必须观察到的结果 |
|---|---|
| 全程无人帮助 | NPC 按计划处理并继续运输，没有永久冻结 |
| 只扶车后离开 | 扶正保持，NPC 补完剩余工作 |
| 重复发送同一交互 | 无重复世界变更、无重复记忆 |
| 两个玩家同时扶车 | 只有一次实际扶正；贡献与真实结果一致 |
| 看路途中离开或断线 | 及时交还职责，已完成工作不回滚 |
| 交互提交失败 | 没有最终成功表现和凭空记忆 |
| 提交后重启 | 事实、NPC身份和记忆一致恢复 |
| 玩家晚到或重新进图 | 获取当前权威状态，不重演私人版事故 |
| 未目击的 NPC 相遇 | 不知晓未经传播的具体帮助 |
| 玩家直接路过 | 不扣好感、不追债、不阻塞主线 |

## 6. 如何验证“愿意投入”

### 6.1 先区分四种结论

```text
停下来 ≠ 愿意帮忙
帮了一次 ≠ 已经相信世界
记得这次经历 ≠ 会长期留存
小样本有人喜欢 ≠ 已经全面超越冒险岛
```

停步可能来自好奇、误操作、道路阻挡、寻找任务入口或等待隐藏奖励。研究目的不是否认停步的价值，而是避免把早期信号直接当最终结论。

### 6.2 第一轮：可理解性与自主参与

建议先招募约 8–12 名测试者进行观察和事后访谈。这个人数只是用于尽快发现问题的工作量建议，不是统计显著性或代表性保证。

让测试者在可玩的冒险切片中自由行动，不提前提示“这里有一个测试你愿不愿帮忙的感人事件”。应告知原型测试和必要的数据记录，但不要引导他们表演研究者想看的行为。

主要检查：玩家是否确实注意并理解需求；是否知道能直接离开；是否主动选择一个有效行为；是否看懂自己造成的改变；事后是否仍期待尚未发放的奖励。

不要因为玩家先问“给什么”就判定失败；应进一步理解是长期任务习惯、成本担忧还是对本次互动缺乏兴趣。

### 6.3 指标与分母

| 指标 | 操作定义 | 不能声称什么 |
|---|---|---|
| 可参与曝光 | 事件可交互时进入可见区域，并排除加载、遮挡、不可控演出等明显情况 | 不能等同于真实注意或理解 |
| 有效帮助率 | 在可参与曝光机会中产生至少一次权威有效帮助的人次比例 | 不能直接称为利他意愿或人格比例 |
| 首次行动成本 | 从可参与曝光到有效行动的时间和操作路径 | 越短不必然越好，也可能是误触 |
| 因果理解 | 事后能说明哪项世界变化由自己的动作促成 | 自报理解不等于永久记忆 |
| 再会识别 | 有自然再会机会时，能识别同一 NPC 或共同经历 | 没有再会机会的人不得作为失败样本 |
| 感到被迫 | 是否担心不帮会失去主线、战力或受到惩罚 | 正常离开不等于负担证据 |

所有比例应同时展示人数、分母和条件，不设一个没有依据的行业合格率。

分析事件使用去标识化研究ID；NPC业务记忆与分析日志分开，记录必要数据即可，不收集无关聊天或键盘内容。

### 6.4 第二轮：单独检验延迟记忆

两个版本保持同样的事故、互动成本、实际结果和当场感谢。

A 版本在自然再遇时给普通、礼貌的招呼。B 版本在自然再遇时给与过去行为一致的具体辨认。

只改变“延迟的具体辨认”，比较再会识别、被记住的感受以及重逢时自愿交流等结果。首轮帮助发生在这个差异之前，因此不能拿首次帮助率声称延迟记忆起效。

共享世界测试应按独立测试世界或测试批次分配版本，避免同一实例中互相传播造成混淆。不要给 A 版本故意制作糟糕体验，也不要给 B 版本隐藏物质奖励。

玩家第二次看到的应该是继续生活的同一个人，而不是为了测试再次翻同一辆车。真正长期投入仍需要更长时间和更多情境的数据，首版只验证第一步关系连续性。

### 6.5 判断下一步改哪里

| 观察结果 | 优先检查 | 不应立即做什么 |
|---|---|---|
| 大多没看见 | 场景构图、视野、声音/字幕、路边位置 | 加奖励、加自动追踪 |
| 看见但不懂 | 需求表达与动作可读性 | 判定玩家冷漠 |
| 想帮但不会 | 输入、站位、提示、可取消性 | 扩大机制深度 |
| 帮过但没觉得有用 | 真实状态变化和对应表现 | 延长对白或站岗时间 |
| 只等隐藏奖励 | 成本、交互语法、是否暗示任务结算 | 直接宣布无奖励路线失败 |
| 当场喜欢但再会不认人 | 身份辨识、地理连续性、重逢机会 | 立刻扩展完整 NPC 社会网络 |
| 记住且不感到负担 | 尝试下一个复用相同因果结构的小变化 | 直接开放全球供给与价格系统 |

## 7. 通往完整商队供给的扩展路径

### 7.1 首版就保留一个真实连接

即使不做完整经济，也给货车一张简单的货单：稳定货单ID、货物批次、出发地、目的地和当前运输状态。

帮助的意义之一是减少或解除这批货的延误；同一个 NPC 抵达目的地，而不是事故结束后凭空销毁、另一个无关版本的 NPC 出现在村里。

首版货单只验证状态连续性，不引起商店涨价、核心药水断供、玩家战力差距或全服物资危机。

### 7.2 三道扩展门

**门一：回应成立。** 一次帮助有真实改变，当场回应准确，再会认得，玩家能自在离开。未通过就打磨同一个点。

**门二：因果可组合。** 在同一条运输路径中引入少量新状态，让不同能力解决同一类真实缺口，仍不做完整经济。玩家不是接到更多模板任务，而是有更多方式介入已有事物。

**门三：供给闭环有必要。** 再连接生产、仓储、运输、消耗和库存需求。必须先说明这些变量如何改善已经验证的冒险体验，否则不增加。

完整供给的未来约束可表述为：

```text
节点下一时刻库存
    = 当前库存 + 生产 + 到货 - 发货 - 消耗 - 损失

发货产生在途批次；到货结束对应批次；同一批货不得同时计入在途与到货。
需求来自实体目标和库存/运输事实，不来自玩家画像需要更多事件。
```

未来可以让延误产生温和的区域变化，但应保留核心成长供给与恢复路径，避免一个不愿帮忙的玩家或一个恶意玩家锁死其他人的正常冒险。这是后续系统设计边界，不是首版任务。

## 8. 第一张开发卡

**标题：同一个 NPC，两次相遇，一次真实改变。**

第一步只实现扶车这一条纵向闭环：侧倾事实 → 玩家主动交互 → 服务端提交扶正与来源 → NPC 当场回应 → 记忆持久化 → 自然重逢认出。

第二步补 NPC 无人帮助时的推进、离开/重启/重复请求正确性，再加入另外两个并行入口。无需为后两个入口发明新奖励或新关系系统。

第三步进行小样本体验观察和双客户端一致性验证。根据问题修改交互与反馈，不因为代码完成就自动扩大机制。

首版不做：全服经济、动态物价、商会势力、道德值、好感经验条、每日委托、事故随机生成器、人格推荐、LLM NPC、全村传闻、为站岗而新增的刷怪战。

完成标准不是“事件脚本走完”，而是：

> 不帮，世界继续；帮一点，事实改变；离开，贡献不清零；再见，同一个人记得；全过程不阻塞原本的冒险。
