# S1 施放窗（窄口径：自增益窗）实现计划

## Context（为什么做、做多窄）

plan.md 第②项「战斗机制纵深」缺口 A：技能**施放窗** `time`/`updatableTime` 仍未实现
（`time` 仍在门禁 `PHYSICAL_MECHANISM_FIELDS['time']` 的「未实现」表里），落点是
**接上 `player_status.rs` 既有唯一时钟**，不新建第二套窗口状态。

**口径（用户已确认：窄口径·自增益窗）**：门禁把 `time`/`updatableTime` 当一个 `buff-window`
组挡，但实测它挡住的是 **9 条物理线攻击技能**，`time` 有**三种不同语义**：
- 自增益/姿态窗：`1201013 騎士密令`(time=2)、`1221052 神之滅擊`(time=10)
- 打中怪后的负面状态窗：`1211018`、`1221019`、`1301014`、`3121052`、`4121017`、`1121015`
- 召唤/箭座存活时长（即 S5 召唤）：`3111013 箭座`(time=3000)

**关键纠缠事实（决定窄口径的安全边界）**：从 `shared/mage-skills.json` 逐技能核对，删除 `time`
这条「未实现」记录后，`PHYSICAL_AREA_ATTACKS` 只会新增这 4 条——
`1221052 神之滅擊`（自增益，✓当接）、`3121052 波紋衝擊`（负面，✗）、`4121017 挑釁契約`
（负面，✗）、`1121015 烈焰翔斬`（DoT 纠缠，✗）；其余 5 条**不动**：`騎士密令/神聖衝擊/神聖烙印/
追隨者衝擊` 因**孤立的 `prop`**（trigger-roll，另一未实现机制）仍被挡，`箭座` 因 `subTime`
仍被挡。⇒ 窄口径下的干净自增益候选恰是 **`1221052 神之滅擊`**，它无任何其它机制字段
（仅 mpCon/damage/mobCount/attackCount/time/cooltime/lt/rb），可一条技能端到端跑通，
并借它立起可复用的「施放窗状态机器」。

## 目标

1. 在服务端立起**自增益施放窗**状态机器，复用 `player_status.rs` 的唯一时钟。
2. 把 `1221052 神之滅擊` 端到端接入 `PHYSICAL_AREA_ATTACKS`（施放→挂窗→到期收回），
   并为将来更多自增益技能留出同一套窗口。
3. 门禁重构：`time`/`updatableTime` 的「未实现」语义从「整组」收窄为「自增益窗已实现、
   负面状态窗/召唤仍未实现」，**保持其余 8 条技能挡住**（双向断言守住）。

## 实施方案

### Phase A — Rust：PlayerStatus 新增自增益施放窗（复用既有时钟）

文件：`server/src/player_status.rs`

- 在 [`Release`](file:///Users/muniao/Code/MapleStory/server/src/player_status.rs) 增加变体
  `CastWindow`（自增益施放窗到期时要收回的附属状态；若窗口仅是纯时长、无可收回属性，则用
  `None` 即可，不强行加变体）。**沿用既有纪律**：新增 `Expiry` 变体后，`world.rs` 的清理
  `match` 到全部变体会**编译强制**你补清理点，不必手写名单。
- 复用 `apply_buff`/`buff_active`/`buff_remaining_ms` 既是现有唯一时钟，只需保证自增益窗
  通过它落地（`skill_id → TimedBuff`）。若施放窗有「刷新不延长/取长」差异化语义，在
  PlayerStatus 内按既有刷新口径补齐，并加单元测试对齐 `tick` 语义（参考既有
  `buff_deadline_matches_the_old_remaining_ms_countdown`）。

### Phase B — Rust：mechanics.rs 唯一入口派生施放窗时长（反向断言落点）

文件：`server/src/mechanics.rs`

- 在 [`AttackPlan`](file:///Users/muniao/Code/MapleStory/server/src/mechanics.rs#L67-L74) 增字段
  `self_buff_window_ms: Option<u64>`，在 `AttackPlan::of(level)`（既有一切攻击计划的唯一入口）
  从 `level.time` 派生（`updatableTime` 若成对出现则作为「可刷新子窗」另行派生，仅在确实消费时
  接）。
- 这提供了 `scripts/check_tms273_damage_pipeline.cjs` §3g 对 `level.time` 的**读取点**——
  「宣布已实现」必须有消费点撑腰，否则反向断言会红。

### Phase C — Rust：施放链接线（仅 1221052 端到端）

文件：`server/src/skills.rs`、`server/src/world.rs`

- `world.rs` 的 `PHYSICAL_AREA_ATTACKS` 新增 `1221052`（并在 `skills.rs::handle_cast_skill`
  的施放派发里走既有 `cast_elemental_area` 范围管线，施放时把 `AttackPlan.self_buff_window_ms`
  通过 `PlayerStatus::apply_buff(...)` 挂到施法者身上）；`type:` 事件照常广播。
- 到期收回走 Phase A 的清理点。**不宣称**负向/召唤技能有任何行为变化。

### Phase D — 门禁重构（关键，守住其余 8 条仍被挡）

文件：`scripts/check_tms273_damage_pipeline.cjs`

1. 从 `PHYSICAL_MECHANISM_FIELDS` 删除 `time`、`updatableTime` 两条（=宣布自增益施放窗已实现）；
   同步把它们加入 §3g `IMPLEMENTED_MECHANISM_FIELDS`（`time→time`、`updatableTime→updatable_time`），
   使 §3g 要求 mechanics.rs 真有读取点。
2. **引入新机制组 `monster-status-window`** 接住负向技能的 `time`，理由登记如
   「怪物负面状态窗（眩晕/烙印/挑衅）尚未实现；由状态字段 s2/u2/v2/w2/s/u/w/z 等标注」，
   使 `波紋衝擊`/`挑釁契約`/`烈焰翔斬` 仍归 `physicalAttackExcused`。
3. 反向断言（新增）：
   - `1221052` 进入 `physicalAttackExpected` 与 `PHYSICAL_AREA_ATTACKS`；
   - `波紋衝擊`/`挑釁契約`/`烈焰翔斬` 仍在 `physicalAttackExcused`（不新增 world.rs 常量）。
4. 客户端镜像：`client/src/features/skills/view.ts` 的 `ACTIVE_SKILLS` 同步补入 `1221052`
   （§3f 逐项相同）。
5. `subTime`/`prop` 相关既有断言（`1221009`/`1201013`/`4211002`/`4221052`/`4121016`/`4221010`）
   逐一复核是否符合解码后的新判据，更新注释措辞不轻动断言真值。
