# S5 召唤通用化（收口成通用槽位）实现计划

## Context（为什么做、做多宽）

plan.md 第②项「战斗机制纵深」缺口 B：`elemental.rs::ThunderSummon` / `step_summons` **仍是冰雷专属**，
要收口成通用槽位；`Player::summon` **仍是独立单槽**（三转球形闪电「同技能重放即替换」），
**未**并入 `SUMMON_BUDGET`（在 `mechanics.rs` 的文档里明确登记为待办）。

**口径（零回归路径）**：本轮**只做机制收口**，不接新召唤技能、不动门禁判据、不升内容版本。
合并后同时存在的召唤物上限取 **3**（= 现状「队列 2 + 单槽 1」），因此
冰魔 / 冰鋒刃 / 閃電球三者的**共存与到期行为逐字不变**，是纯重构而非玩法改动。

## 目标

1. 实体与槽位通用化：`ThunderSummon` → `Summon`；`Player::summon` 单槽并入 `Player::summons` 队列，
   容量判据只剩 `World::summon_slots_available` 一处（`SUMMON_BUDGET`）。
2. 脉冲周期收口：`step_summons` 里按 `skill_id` 硬编码的周期（`SKILL_ICE_DEMON => 1080`、
   `SKILL_FROZEN_ORB => attackDelay`、球形闪电 `subTime`）收口成 `mechanics.rs` 的**唯一派生点**。
3. 清理点收敛：8 处 `player.summon = None` 改为整队列 `summons.clear()`，死亡 / 换图 / 复活后
   不再有「只清了单槽、队列靠 `step_summons` 惰性清」的两套语义。

## 关键事实（源字段核对，决定周期判据）

从 `shared/mage-skills.json` 逐技能核对，源里**没有**统一的「召唤物攻击间隔」字段：

| 技能 | 源字段 | 现行为 | 派生 |
|---|---|---|---|
| `2221005 召喚冰魔` | `time=115`（秒）、`subTime=8` | 周期字面量 `1080ms` | `subTime` 未按毫秒书写（< 一拍），回落契约值 1080 |
| `2221012 冰鋒刃` | `time=4000`、`subTime=8`、`attackDelay=210` | `attackDelay`（210） | `attackDelay` 已按毫秒书写，优先 |
| `2211011 閃電球` / `2211015`（hidden） | `time=63 / 22`、`subTime=1080` | `subTime`（1080） | `subTime` 已按毫秒书写（≥ 一拍），直接用 |

⇒ 判据：**`attackDelay` > `subTime`（仅当其 ≥ 一拍）> 契约值 1080**。该判据在四件召唤上
逐一复现现行为（210 / 1080 / 1080 / 1080），**零行为漂移**。

## 实施方案

### Phase A — Rust：槽位合并（`world.rs` / `mechanics.rs`）

- `world.rs`：`ThunderSummon` 更名 `Summon`（结构体本身字段不动：`expires_at` / `anchored` /
  `next_hit_at` / `summon_id` 等通用语义保留）；`Player` 删 `summon: Option<Summon>` 字段，
  `summons: Vec<Summon>` 成为唯一权威；快照投影删 `.summon.iter().chain(...)`（单槽原先也是并进
  同一个 `summons` 数组投影的，**客户端报文形状不变**）。
- `mechanics.rs`：`SUMMON_BUDGET` 2 → 3，文档改为「唯一预算」并删掉「待办」措辞。

### Phase B — Rust：脉冲周期唯一派生点（`mechanics.rs`）

- 新增 `World::summon_pulse_ms(&self, skill_id, level) -> u64`，判据见上表（毫秒槽优先）。
  它落在 `mechanics.rs` 而非 `elemental.rs`：该模块自己的宪章表里第 5 行就是
  「召唤物脉冲 `summon-pulse` / 独立时间轴（`step_summons`）」。
- 隐藏形态（`2211015`）的**周期查表**与**伤害几何查表**是两件事：周期查自己那行，
  几何仍回落父行 `2211011`（既有行为，逐字保留）。

### Phase C — Rust：施放与步进（`elemental.rs` / `skills.rs`）

- `elemental.rs::step_summons`：单槽分支与队列分支**合并成一个循环**（原先球形闪电走
  `player.summon.take()`，冰魔/冰鋒刃走 `std::mem::take(&mut player.summons)`）；死亡即清空整队列；
  `next_hit_at` 推进改用 Phase B 的派生值；冰鋒刃的水平位移保留（`192.0 * TICK_MS`/s 仍是技能自己的
  运动学，不是周期）。
- `skills.rs::cast_thunder_sphere`：「同技能重放即替换」语义逐字保留（非锚定重放 → 换新实例；
  锚定重放 → 就地改 `anchored`/`skill_id=hidden` 并把 `expires_at` 收紧为 `min(旧, now+时长)`，
  `summon_id` / `next_hit_at` / `pulse_index` 不动）；改为对 `summons` 队列做 `retain` + push。
- `skills.rs` 的「锚定重放不吃 mpCon」判据（现读单槽）改为在队列里找球形闪电。

### Phase D — 清理点收敛（8 处）

`boss.rs` / `revive.rs` / `portals.rs`（2 处）/ `quest.rs` / `monsters.rs` / `inventory_ops.rs` /
`elemental.rs`（死亡分支）：`player.summon = None;` → `player.summons.clear();`。
净效果与原行为一致（原先队列部分由 `step_summons` 在死亡 / 换图时惰性清掉，现在提前到同一处）。

### Phase E — 验收（既有纪律）

- `third_acceptance.rs` 现有那条 3 转用例改为读队列（**断言真值不动**：重放不叠加、不重复扣 MP、
  锚定模式 `next_hit_at` 不变、到期精确收回、快照 `stationary` 一致）。
- 新增一条：冰魔 + 冰鋒刃 + 球形闪电**三者共存**（= 3 槽满），第 4 件被 `summon_limit` 拒；
  三者各自的脉冲周期与源字段一致（210 / 1080 / 1080）。
- `scroll_acceptance.rs` 的 `player.summon.is_none()` → `player.summons.is_empty()`。

## 交付记录与版本

## 落地结果与偏离（2026-09-23 完成）

五个 Phase 全部落地，交付记录见 `docs/plan/history/2026-09-23/S5召唤通用化.md`。
`cargo test` **654 过 / 0 失败**；`check_tms273_damage_pipeline.cjs`、`check_tms273_runtime.cjs` exit 0；
`run-checks.mjs` **56 / 63**（技能与机制项全 PASS）。内容版本 `tms273-40` 与协议 `34` 均未动（零 `shared/**` 字节）。

**与本计划的偏离（三处，均为实现约束所迫，语义不变）：**

1. **Phase B 的派生点写成自由函数而非 `World::summon_pulse_ms(&self, …)`**。计划原写「新增
   `World::summon_pulse_ms(&self, skill_id, level)`」，但调用点（`step_summons` / 两个施放函数）正同时持有
   `player` 的可变借用，`self.方法()` 会被借用检查器挡下。最终签名为
   `pub(super) fn summon_pulse_ms(skills: &MageSkills, skill_id: u32, level: u32) -> u64`（直接借用
   `self.mage_skills` 字段）。落点仍是 `mechanics.rs`，唯一派生点的性质不变。
2. **Phase A 的「结构体字段不动」不成立**：`anchored: bool` 必须换成 `motion: SummonMotion`。
   原因是「冰魔锚定 / 球形闪电跟随」这一对原先靠单槽分支与队列分支分开处理，合并成一个循环后
   若继续只留布尔量，`step_summons` 就无法区分「跟随的球形闪电」与「自行前进的冰鋒刃」
   （两者在旧代码里都不是 `anchored`）。位移形态因此改为**施放时定下、步进时只读**。
3. **Phase E 的「第 4 件被 `summon_limit` 拒」改为直接断言容量判据**
   （`!World::summon_slots_available(...)`）。真实内容只有 3 件召唤技能，凑不出第 4 件，
   硬造一个合成技能去触发 `summon_limit` 会把判据从「容量」偷换成「某个不存在的技能」；
   直接断言 `SUMMON_BUDGET` 判据本身更贴近要钉住的东西。

**另外如实登记**：`run-checks.mjs` 实测 **7 红**（本计划按 `PLAN.md` 写的基线 6 红），
第 7 项 `features/hud/gauge.check.ts` 由提交 `2a17688` 引入、与 S5 无关、本轮未修；
本轮一并把 `PLAN.md` §0 与台账 §0/§5.1 的落后基线回写为实测值（654 / 63 项 7 红 / `tms273-40`）。

## 明确不做的（保持窄口径）

- 不接 `3111013 箭座` 等新召唤技能，不动门禁的 `subTime` / `prop` 判据。
- 不统一召唤**存活时长**的书写差异（冰魔 `time` 按秒、冰鋒刃 `time=4000` 按毫秒，各自施放函数里的
  现值逐字保留）——登记为残留，不在本轮扩大战线。
- 不改 `HyperVortex`（它是另一套实体，快照里只是同样并进 `summons` 数组）。
