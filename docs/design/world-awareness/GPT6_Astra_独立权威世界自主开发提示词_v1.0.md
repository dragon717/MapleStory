## 1. 你承担什么，我承担什么

你不是只负责回答问题的顾问，也不是只负责输出计划的策划。你需要承担这个项目的设计整合、技术决策、实际实现与交付责任。

我的根本要求是：

> **世界先于玩家被创造。但我首先是一个玩家；我需要一个完整、连贯、可以亲自体验的东西，才能告诉你，你做的事情是否正确。**

我已经提出了方向：能力锁、地标、信息缺口、规则驱动、世界回应、世界记忆，以及具有长期文化生命的原创幻想世界。不要把这些方向重新变成一份需要我逐项填写的需求问卷。

我负责表达感受，并在亲自玩过后判断是否喜欢。你负责提出设计假设、做出选择、实现因果、修好链路，并诚实说明完成度。

“新的迪士尼”在这里指长期方向：拥有自己的名字、地方、人物、声音、经历和共同记忆。不指第一版就制作无边界宇宙、完整商业版图或保证商业成功。

## 2. 唯一一次产品提问

先阅读仓库入口与核心设计，理解已经明确的事情；随后只向我问下面这一个问题：

> **你最希望在这个世界里亲自经历、并在离开后依然记得的一个瞬间，是什么？**
>
> 可以讲真实玩过的经历，也可以只描述一个想象中的画面，不需要给出玩法方案。

这不是让你用一个问号塞入十个子问题。不要追加题材、职业数量、系统列表、技术栈、配色、游戏名、预算和优先级问卷。

收到回答后，将它整理成一段简短的“体验锚点”，直接开始自主推进，不再要求我确认每个方案。如果我说暂时不知道，就采用现有文档已经确立的默认锚点：因为好奇出发、因为理解而抵达、因为行动被具体的人记住。

我的回答是情绪与表达的参考，不是用来替代整个世界的唯一剧情。不要为了精准表演这个瞬间而伪造世界条件。

如果这个问题已经在当前会话得到回答，就直接沿用，不再重复提问。

正常、可逆的产品与实现取舍由你负责，写明假设，不等待我批准。真实的权限、资源或执行环境障碍要如实报告；不要把无法执行伪装成“还需要我做产品选择”，也不要声称已完成无法执行的工作。

## 4. 本次必须解决的十件事

下面十件事共同构成一个世界，不是十个互不相干的功能。前三件是身份与表达的基础，不意味着要花三成工作量写命名方案。

### 第一件：让游戏有自己的名字

为游戏选择一个贴合核心的原创工作名，并给出一句话的作品承诺。

不要只把“冒险岛”换成另一个同义词，也不要交一大串备选让我当场拍板。你可以内部比较候选，最终自主选择一个主方案，保留少量备选作为记录。

名字应当能容纳好奇、远方、温柔与危险、世界回应以及长期历史，而不是只对应一个技能或一张地图。

将工作名接到实际可见的位置：新世界入口、相应页面标题、首章标题与必要说明。保留原版复刻资料的来源标记，不冒充官方产品，也不抹掉技术历史。

该名称是可更换的工作名，不宣称已经完成商标、域名或商业使用核验。

**交付判据：我进入这段原创体验时，能够明确知道自己正在进入什么作品；它不是仅在 Markdown 中改了名字。**

### 第二件：让世界有自己的名字与存在理由

为世界命名。区分作品名、世界名、地区名和地标名，不必机械规定它们必须完全不同，但必须说明各自承担的角色。

用简短的世界基础定义回答：这里的地理关系、自然规律、居民生活、交通与物资为何形成现在的样子，以及不依赖玩家也存在的未解变化。

先让首个地区成立，不先写几千年编年史。需要有稳定的日常，而不只是等待英雄解决的事故集合。

让世界名通过居民用语、地图、路牌、旅行记录或环境进入体验，不要求玩家先读百科。

**交付判据：拿掉玩家之后，这里仍有居民想去的地方、正在做的事和受到的限制；玩家能在现场看见其中一部分。**

### 第三件：建立贴合世界的概念命名体系

整理本轮会实际出现的关键概念：世界节点、天命、魔念或虚影、行动痕迹、地区、能力、设施、重要物件与人物称呼。

区分三个层面：

1. 面向开发的明确概念，例如“公共设施”“局部记忆”“独立实例”。
2. 面向玩家的世界内称呼。
3. 持久化、协议和配置使用的稳定 ID。

为它们建立可追溯的映射，包含原称呼、新显示名、核心含义、实际行为、对应 ID、出现位置与旧称别名。

不是所有通用 UI 都必须改名。“设置”“背包”等名称可以保持易懂。不要为了新奇制造理解障碍，也不要把“世界认出人”改名后做成好感经验条。

优先修改显示层和内容层，保留兼容别名。没有迁移必要时，不全仓替换 crate 名、目录、地图 ID、数据库键和协议字段。

**交付判据：同一个概念在入口、地图、对白、物品与说明中语义一致；旧数据不会因换名失联。**

### 第四件：建立有限但真实的世界规则闭环

沿用现有 Rust 权威世界，落实这条因果链：

```text
经过校验的行动或到期的世界行为
→ 事实变化
→ 相关规则读取事实
→ 产生变化量
→ 受控提交
→ 新事实
→ 实体行为与快照表现
→ 必要历史与局部记忆
```

最初实现少量能够跨对象复用的规则，不先做通用宇宙模拟器。

以当前风铃内容为起点，核查哪些只是固定交互，哪些已经能按材料、热量、湿度、受风条件、通行状态等事实运行。需要泛化时，先让一组规则在两个真实场景或对象上成立。

例如，点火不能直接调用“让玩家飞到终点”。热源改变相关事实，燃烧与气流规则产生结果，角色满足受风条件后才能获得移动效果。

同条件同处理，不代表抹掉玩家、怪物和 NPC 的实际能力差异。身份、能力、资源、距离与冷却仍须验证。

**交付判据：至少一条核心因果链存在不依赖玩家的触发或推进途径；至少一种规则能更换作用对象或来源而复用，不是任务专用脚本。**

### 第五件：让移动、地标与能力锁组成探索网络

保留已经成立的横版手感，检查跳跃、绳梯、侧壁、落点、镜头、前后景和实际碰撞的一致性。不要为了凑新地图外形随意篡改整套移动参数。

以现有风铃岛的根道、放桥、借火路线为优先基础：同一空间、多种办法，而不是每个职业一扇专用颜色门。

首章必须包含一个玩家能先看到、暂时不容易抵达、后来可以自主回访的地方。至少一种新增或深化的能力，要在两个不同情境中改变可行动方式，其中包含一次旧地点的新解法。

能力锁要有可读的条件，不用隐形任务标记假扮物理障碍。允许合理绕行与替代办法，不能为了保护标准答案禁止已经符合规则的行动。

远处可交互地标应当兑现。纯远景则明确其表现边界，不能让镜头承诺一个实际上永远进不去的核心目的地。

**交付判据：我能凭观察产生目的，并至少有一次因为新的能力或理解，自主想到回到旧地点。**

### 第六件：保留真正好玩的行动、战斗、成长与补给

不要把项目变成“走路—看对白—点扶车按钮”的温情演示。复用已有移动、战斗、职业能力、掉落、背包与恢复能力，让它们服务于探索和世界交互。

在首章中安排能够形成完整往返的行动链：准备、出发、遭遇、作出选择、获得变化、使用变化、返回安全地点。

成长至少一次改变行动方法，而不只是提高数字。战斗要有看得清的危险、受击与反馈；非战斗参与也能产生真实后果，但不强迫每个目标都必须战斗或必须助人。

物品、材料、消耗和奖励沿用权威状态与事务边界。有限资源必须有来源和恢复途径；失败不能把主体验永久卡死，也不能通过重连、重进或重复请求无限领取。

不以本轮为理由扩建完整邮件、拍卖、公会、强化、生活技能和全服经济体系。

**交付判据：脱离世界观说明，实际操作仍值得玩；成长能用于后续行动，补给与失败形成可理解的选择，而不是单纯制造等待。**

### 第七件：让一个公共节点真正恢复流动

优先衔接已有风铃桥，先核查实际实现，不再另造一套同功能灯塔前置系统。

节点不是贡献条。修复通路、运输货物、形成停留条件与居民改变行动之间，要有事实上的依赖。

同一共享范围内，桥的状态、碰撞、货物与建设进度只有一份；个人贡献、知情关系和旅行见闻可以不同。个人实例必须有明确边界，不能在同一公共地图中给不同玩家相反的桥梁碰撞。

必须支持部分参与、直接绕过、途中离开、晚到以及未贡献者使用公共成果。NPC 根据自己的目标和能力推进剩余工作，不能永远等玩家接任务。

**交付判据：一个玩家做了一部分后离开，世界可以继续；他回来能看见后果，后来者能使用成果，没有贡献的人不会被虚假感谢。**

### 第八件：让具体人物记住我，并出现天命的萌芽

复用稳定 NPC 身份与已有旅人内容，做出“同一个人、两次相遇、一次真实改变”。

人物记忆必须有来源：参与、目击，或已经明确实现的信息传播规则。服务器知道不代表每位 NPC 都知道。

可选帮助不是三步必做任务。扶车、递物或看路改变真实状态，NPC 据此作出准确而克制的回应；离开或不帮助，也应有正常的世界进展。

天命先实现被看见、被记住、被回应的萌芽，不因第一次帮助就给人格定性、发永久身份或偷偷关闭其他道路。较大边界必须可理解并由玩家主动承担。

不要新增天命币、刷取条、排行榜或每日作业。世界回应也不只意味着赞美；它必须与实际经历相称。

**交付判据：我能遇到一次有事实依据的再次相认，而不是收到通用感谢模板；未参与者不会得到同一段虚假回忆。**

### 第九件：让失败与行动留下可感知的历史

先核查并复用当前死亡世界实现，保留原有死亡、复活和资源结算边界。不要重做已落地部分，也不要把设计中的后续能力宣传成已经完成。

首章至少存在一种可见且有持久依据的行动痕迹。死亡相关内容以已批准的适用范围为基础：角色复活不等于历史被抹除，临时墓碑或残响有自己的生命周期。

必须区分死亡表现、墓碑、独立虚影、经验球和觉醒 NPC。虚影来自玩家，不意味着归玩家所有；不是离线刷怪宠物，也不把自杀变成收益最优解。

当前风铃实例不落碑的边界不能顺手删除。需要在原创首章中提供死亡痕迹体验时，选择已允许的危险区域，或明确实现一个范围受控、可回退的区域策略。

不强迫玩家死亡来推进章节。虚影主动行为、经验球、融合与独立 NPC 若不属于当前可完成范围，保留明确接口与后续事项，不假装已接通，也不拿它们阻挡首章交付。

**交付判据：重要行动或失败能够留下来源明确的痕迹，重连不会重复制造；我可以理解它，而不是只有数据库多了一行日志。**

### 第十件：把前九件合成一个完整、可亲自判断的首章

最终交付不是十个按钮、十段说明和十个独立测试页，而是一段可以自然进入、探索、行动、回来并继续生活的经历。

首个完整版本的默认设计假设：约 30—60 分钟自然游玩能够形成一段有起承转合的首章，探索习惯不同可以更短或更长。这不是开发工期承诺，不是硬性通关时钟，也不能用走空路、等待刷新和重复刷怪凑时长。

它可以范围有限，但必须有完整入口、可读操作、地标吸引、多种行动、一次成长或理解的跃迁、一次回访、一次公共后果、一次人物回应、可返回的安顿处与下一段旅程的真实线索。

章节结束不是弹出“Demo 完成”后关门。玩家应当可以返回、闲逛、使用新通路、感知已经发生的改变；世界不必回到最初状态。

首章必须有可辨识的原创人物与地方、统一的视觉语言、可感知的声音反馈。复用已核实的风铃资产与音频契约，不以整张概念插画代替地图，不以单张立绘声称完整动作，也不以文字描述代替已经要求的表现。

**交付判据：我不必先读你的设计方案，也不必输入 GM 命令或开启开发者工具，就能进入并理解这段完整经历。**

## 5. 十件事如何成为一条因果链

采用下面的结构作为默认组织假设，而不是不可偏离的固定剧情：

```text
有自己名字的作品与世界
→ 一个有日常生活、正在运转的地区
→ 我看到远处值得去的地方
→ 通过观察和行动学会一条规则
→ 用自己的办法抵达
→ 经历一次有风险的探索与成长
→ 用新的理解重新进入旧地点
→ 可选地参与一处真实的世界需求
→ 公共条件改变，居民开始采取不同的行动
→ 再次遇到一个有理由记得我的人
→ 看见自己或他人留下的痕迹
→ 回到可以安顿的地方，也看见下一段旅程
```

已有风铃岛、风铃桥、旅人与规则链是优先整合基础，不必原样保留所有临时命名或把所有内容压在一张地图。需要增加过渡区域时，先解决空间、叙事、资源与实例边界的连续性，不为了地图数量扩张。

允许设计初始地形、人物、对白、目标和初始事件条件；不允许为了按秒制造高潮而强行更改事实。时间分段是观察玩家体验的窗口，不是“第 30 秒自动放桥”的脚本指令。

可跳过帮助、错过龙影、提前学会替代办法、较晚进入公共地区的玩家，也应获得成立的经历。不要把拒绝设计师安排当作错误操作。

“世界先于玩家”的本轮执行解释：**因果先成立，玩家再介入；同时，必须把这些因果做成可以观察和体验的东西。** 它既不是彻底取消手工内容，也不是在可玩之前先模拟整个宇宙。

## 6. 实施边界：渐进整合，而不是大重写

### 6.1 复刻基础与原创世界分开标记

研究并理解现代冒险岛，不等于先实现全部 TMS273 系统才能验证原创世界。保留已有操作、战斗、资源和 UI 基础，在明确的原创范围中改变世界组织与回应方式。

不擅自修改我已经确定的管理员政策、快捷转职、既有角色数据和与本轮无关的原版规则。原版复刻内容与原创 P 内容保持可识别的来源边界。

新名字不自动赋予现有素材原创身份或商业使用权。列清原创内容、既有参考素材、待替换资产及未核定来源，不作没有依据的授权声明。

### 6.2 权威、性能与生命周期

- Rust 中保持一个清楚的逻辑状态拥有者，网络处理不直接修改世界；不新增每角色模拟任务或第二套独立权威时钟。
- 客户端只提交意图，不提交奖励、最终坐标、完成状态或代替其他角色操作的身份。
- 规则读取明确输入、输出变化量，在既有顺序流程中受控提交。不要让规则互相递归调用，也不要创建与当前状态重复的第二套事实库。
- 先覆盖当前活动区域与少量到期行为；无人区域可以有限步进或有界补算，不要求所有地图每帧完整模拟。
- 规则传播、补算、墓碑、事件与记忆都有处理预算和保留上限。区分必须长期保存的事实、可压缩的历史和可到期的临时表现。
- 同次交互、物品变更、建设与死亡副作用要有清晰幂等边界；持久化失败不能留下“显示已成功但实际没保存”的假事实。
- 协议或内容变更同步所有实际消费者与对应版本；不为了显示改名破坏旧存档。
- 优先简单数据与明确函数，不为了未来宇宙预建全套 ECS、脚本语言、分布式服务和抽象工厂。

### 6.3 表现必须解释真实状态

碰撞与画面一致，场景与角色比例一致，交互距离可理解。风、火、桥、居民动作与音效尽量由真实状态驱动。

“世界语言优先”不等于去掉必要 UI。保留基本操作提示、字幕、可读对比、音量控制与适当的方向辅助，不把不知道按哪个键误认为有探索深度。

沿用当前已确认的分层 2D 呈现和现有工程。除非明确证明本轮体验无法成立，否则不将 Three.js、桌面壳、完整缓存体系或 UI 换框架列为前置任务。

### 6.4 保护工作区与在线状态

本委托授权当前任务范围内的可逆代码、配置、内容和文档修改，以及符合仓库政策的必要定向自检。

不因此授权删库、覆盖未提交修改、访问用户真实账号数据、强推、破坏性迁移、购买资源、公开发布、批量停进程或中断正在运行的用户服务及陪测机器人。

统一启动入口遵循仓库当前 `启动3010.command` 的真实契约。不要擅自改变它的默认行为；不能为了证明加载成功偷偷重启用户服务。需要用户按既有入口重新加载时，在交付中给出明确操作与状态，而不是谎称当前在线版本已经包含新功能。

## 7. 自主执行方式

### 阶段 A：核查与唯一提问

完成入口、核心文档与当前相关实现核查；记录基线与真实缺口。只提出第二节的唯一问题，等待这一次回答。

### 阶段 B：形成可执行决策，然后继续动手

将体验锚点、命名主案、十件事的落点和首章结构整理为短设计决策，写入合适的设计文档；任务、依赖和状态仍只维护在 `PLAN.md`。

每件事都写清：来源、当前已有部分、实际缺口、本轮动作、状态拥有者、代码或内容路径、可玩的入口和完成证据。这个表是实现用的，不是让我逐项审批的。

不以“方案如下，是否开始”为阶段终点。收到唯一回答后，已经得到正常范围内继续实现的产品授权。

### 阶段 C：沿一条端到端路径实施

先跑通一条最短完整旅程，再在同一世界上补足其他路线、世界后果与人物回应。不要十个系统同时各完成百分之十，最后没有任何可玩的路径。

每推进一段，都保证它接入真实入口、当前协议、服务端状态和实际表现。已经完成的模块优先整合与修正，不重复发明。

若有真实的子代理工具，按照仓库规定拆分正交职责，共享协议与公共状态由统筹唯一协调。没有工具时顺序执行，不虚构已启动的代理、模型档位或并行进展，也不要求我充当代理之间的协调员。

### 阶段 D：必要自检与诚实交付

只执行本轮改动需要的编译、类型检查与定向规则检查，保留具体结果。不要默认恢复独立 QA、反复全量验收或自动操作用户在线角色。

处理确实影响本次入口、功能或构建的缺陷；把与本次无关的既有红灯和本次回归分开记录。不能把“旧测试通过”当作新功能证明，也不能把“测试能跑”当作好玩证明。

边界不明时，先从现有文档、代码、配置与日志解决；剩余产品取舍由你作出可回退的合理决定并记录，不再向我追加问卷。

## 8. 交付前必须考虑的验收情境

下面是首章需要满足的行为要求，不代表授权启动额外在线测试或独立 QA。按仓库政策，在纯规则、临时测试数据与必要的针对性检查中验证能验证的部分；运行表现交我亲测，并标清未验证项。

| 情境 | 期望结果 |
| --- | --- |
| 全新玩家进入 | 不靠 GM 指令、开发后台或预知攻略即可开始，操作提示与地标清楚 |
| 不帮忙直接走开 | 世界有合理后续，主体验不被惩罚性锁死 |
| 用另一种合理能力处理同一对象 | 规则按真实条件成立，不因不是标准路线而无故拒绝 |
| 获得能力后回访 | 至少一处旧地点出现真正的新行动可能 |
| 只参与一部分 | 保存实际改变和贡献，不冒称完成全部工作 |
| 同一公共范围的两位玩家 | 关键地形、设施、物资和结果一致；私人回应可以不同 |
| 晚到且从未贡献 | 能使用公共成果，不看到为自己重新损坏的公共桥，也不被错误感谢 |
| 重复发送交互或奖励请求 | 不重复消耗、发放、施工或生成痕迹 |
| 离开后返回、断线重连 | 按正确生命周期恢复，不靠页面变量假装世界记忆 |
| 服务重启恢复逻辑 | 用隔离的持久化检查验证，不能借此重启或清空用户实际环境 |
| NPC 没有目击或消息来源 | 不知道不该知道的行为，不读取全知好感数据库 |
| 死亡与复活 | 保留原有语义；适用区域中的痕迹按自身生命周期保留，不重复制造收益 |
| 资源缺失、版本不一致 | 给出真实可定位的信息，不把旧构建或占位符当作新世界交付 |
| 名称更新 | 显示一致，稳定 ID 和旧数据引用不因改名损坏 |

体验由我作为玩家判断；你不能通过这张表自动宣布“用户已经感到惊奇”。

## 9. 最终交付必须让我能够直接去玩

最终报告保持可操作，不用大段愿景重复代替结果。至少提供：

1. **作品与世界身份**：采用的工作名、世界名、核心概念及它们与实际玩法的关系。
2. **真实进入方式**：使用哪个现有入口、必要操作、当前是否需要按既有流程重新加载，以及可辨认的构建与内容标识。
3. **不剧透的游玩说明**：只说明怎么进入、怎么操作和可以自由探索，不先告诉我每个秘密的标准答案。
4. **十件事完成表**：每项对应代码、内容与入口；分别标记已实现、已做定向检查、已加载、用户待验或实际阻塞。不能用总完成百分比抹平差别。
5. **证据与边界**：实际运行过的命令和结果、未测内容、临时素材、尚未接入的后续机制，以及本轮没有触碰的用户环境。

首章的软件、内容与操作链路是你负责完成的；情绪效果和最终取舍由我亲自体验后判断。

如果受真实权限或资源缺失影响，优先完成并保存可交付的部分，指出精确阻塞与尚不能进入体验的原因。不要编造启动成功、素材完成或实玩通过，也不要用“之后会做好”结束当前工作。

不要把地图数量、代码行数、Markdown 数量或架构复杂度当作成果。成果是：**我能够进入一个有自己名字、内部因果成立、动作与成长值得玩、行动会被留下来的世界。**

## 10. 最后的优先级

当时间、上下文或工程复杂度发生冲突时，优先保护：

```text
真实可进入的完整体验
> 世界因果与已有状态的正确性
> 移动、战斗、探索与表现可读性
> 有来源的世界回应与历史
> 内容数量与高级扩展
```

缩小地理范围、人物数量和高级系统规模，都比交付一大堆无法连起来的半成品更好。但不能用“缩小范围”取消首章的入口、行动、成长、后果与返回闭环。

**先创造一个自己成立的小世界，再让我进入；不要让我先替你设计完世界，才开始创造。**
