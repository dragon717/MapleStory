# 世界规则驱动游戏：设计原则知识库 v0.1

> 目标：不是先问“我要给玩家什么体验”，而是先问：
>
> **“我要创造一个怎样运转的世界，让这些体验自然发生？”**
>
> 这份文档用于后续冒险岛复刻、独立权威世界、玩法设计与工程实现的统一设计语言。

---

# 0. 总纲：世界先于玩家

传统功能式设计常从玩家出发：

> 玩家点击技能 → 播放效果 → 命中目标 → 发奖励 → 开下一任务。

这种方式很容易做出“功能完整但世界是死的”游戏。

我们希望反过来：

> **世界先存在 → 世界有事实 → 事实受规则约束 → 实体参与规则 → 规则产生新事实 → 玩家介入其中 → 体验自然发生。**

玩家不是世界的中心，也不是特殊规则的唯一触发器。

玩家只是世界中的一个实体，但拥有更高的观察、学习、组合和利用规则的能力。

---

# 1. 世界的基础结构

整个世界按以下因果链构造：

```text
世界事实 Facts
    ↓
世界规则 Rules
    ↓
实体状态 Entities / Components
    ↓
系统运行 Systems
    ↓
实体交互 Interactions
    ↓
产生新事实 New Facts
    ↓
形成历史 History
    ↓
形成玩家体验 Experience
```

再进一步：

```text
事实
  ↓
规则
  ↓
实体
  ↓
交互
  ↓
结果
  ↓
世界反馈
  ↓
玩家理解规则
  ↓
玩家主动利用规则
  ↓
复杂组合
  ↓
涌现玩法 / 涌现叙事
```

## 1.1 世界事实

事实不是“任务进度”，而是世界此刻真实存在的状态。

例如：

- 时间：白天 / 夜晚 / 黄昏。
- 天气：晴、雨、风暴、雪。
- 温度。
- 湿度。
- 风向与风速。
- 地表含水量。
- 植被含水量。
- 火势。
- 地形稳定度。
- 水位。
- 光照。
- 生物种群数量。
- 商队数量。
- 道路损坏程度。
- 地区安全度。
- 地区物资供给。
- 某个桥是否已经被修复。
- 某个生命节点是否恢复。

这些事实应该尽量独立于“玩家有没有接任务”。

---

# 2. 设计原则一：能力锁（Ability Gating）

## 一句话定义

**用玩家获得的新能力改变“能做什么”，而不是单纯用等级或剧情节点决定“能不能去”。**

核心循环：

```text
看见
→ 去不了
→ 记住
→ 获得新能力
→ 想起旧地点
→ 回访
→ 发现新路径
→ 世界再次扩大
```

能力锁真正优秀的地方不在“锁”，而在：

> **玩家脑中会产生长期空间记忆。**

## 好的能力

好的能力不是一把只开一扇门的钥匙。

它应该同时作用于：

- 探索
- 战斗
- 移动
- 解谜
- 世界规则
- 社交协作

例如：

### 火焰

不是：

> 火球术可以烧开“火焰门”。

而是：

```text
火焰
→ 提高局部温度
→ 蒸发水分
→ 点燃低湿度植被
→ 制造热流
→ 改变怪物行为
→ 提供光源
→ 烧毁部分障碍
```

于是“火焰”不是钥匙，而是一个世界能力。

---

# 3. 设计原则二：地标驱动探索（Landmark-driven Exploration）

## 一句话定义

**不要总是告诉玩家“去哪里”，而是让世界本身产生吸引力。**

玩家不是追着任务箭头走，而是：

> “我看到那个东西，我想去那里。”

## 地标可以是什么

- 远处巨大的世界树。
- 浮空岛。
- 天上的巨龙。
- 会移动的巨型石像。
- 一座不断喷出蒸汽的山。
- 一辆横跨世界的列车。
- 一座倒悬城市。
- 一棵贯穿多个地图层级的古树。

## 地标应该具备三层兑现

### 第一层：视觉承诺

远处就能看到。

### 第二层：途中兑现

向地标靠近的过程中，不断出现新的东西：

- 支路
- 洞穴
- NPC
- 怪物
- 环境谜题
- 新视角

### 第三层：到达兑现

到达之后必须值得。

不能只是：

> “哦，原来这里就是一个普通平台。”

否则玩家会失去对世界的信任。

---

# 4. 设计原则三：信息缺口（Information Gap）

## 一句话定义

**不要急着给玩家答案，要先让玩家产生自己的问题。**

比任务更强的驱动力是：

> “这到底是什么？”

## 核心循环

```text
发现异常
→ 产生问题
→ 得到部分线索
→ 解开小问题
→ 暴露更大的问题
→ 主动继续探索
```

例如：

玩家发现：

- 森林里大量鸟类突然迁徙。
- 古树表面出现奇怪烧痕。
- 某个 NPC 拒绝谈论北方。
- 地下偶尔传来巨大震动。
- 天空中的巨龙每隔几天改变方向。

这些都不是任务。

它们首先只是：

> **世界中的异常事实。**

当多个事实彼此关联时，玩家开始主动建立假设。

这时玩家不是在完成剧情，而是在“理解世界”。

---

# 5. 设计原则四：反馈循环（Feedback Loop）

## 一句话定义

**玩家做出行动后，要能感受到“世界真的被我影响了”。**

反馈不是只有：

- +100 EXP
- +1 道具
- 任务完成

真正好的反馈是多层的。

---

## 5.1 第一层：物理反馈

例如：

```text
火球命中枯草
→ 草叶卷曲
→ 颜色变暗
→ 火焰蔓延
→ 烟雾升起
→ 风改变火势方向
```

---

## 5.2 第二层：动作反馈

玩家利用热流：

```text
燃烧区域形成上升气流
→ 滑翔斗篷受到升力
→ 玩家真正离开原来的高度层
```

玩家感觉：

> “不是系统让我飞，是我理解了这个世界，所以我飞起来了。”

---

## 5.3 第三层：空间反馈

飞起来以后：

- 看见之前看不到的区域。
- 到达新的高度。
- 发现新的地标。
- 进入巨型石像内部。
- 发现古庙。

于是能力反馈直接改变世界边界。

---

## 5.4 第四层：世界反馈

玩家修复了一座桥：

以前：

- 商队绕路。
- 村庄物资昂贵。
- NPC 很少。

修复后：

- 商队开始经过。
- 商人增加。
- 商品价格变化。
- 旅人出现。
- 新故事自然产生。

---

## 5.5 第五层：社会反馈

重要成果不应该只有玩家本人知道。

例如：

- 稀有装备掉落产生巨大光柱。
- 世界 Boss 首杀广播。
- 极稀有物品进入跑马灯。
- 玩家修复大型设施被世界公告。
- 城镇 NPC 会谈论这件事。
- 其他玩家来到现场可以看到结果。

于是反馈链变成：

```text
我做了
→ 世界回应
→ 我理解发生了什么
→ 别人也看见
→ 世界承认这件事很重要
```

这是一种极强的情绪放大器。

---

# 6. 设计原则五：风险与回报（Risk / Reward）

## 一句话定义

**真正有吸引力的探索，不是“这里有奖励”，而是“我知道可能有好东西，但我不知道值不值得冒险”。**

关键不是奖励数量，而是：

> **犹豫。**

如果玩家完全不用判断，探索就容易退化成清单。

---

## 6.1 风险必须可感知

玩家在做决定前应该能获得信息。

例如：

- 洞穴口堆着尸骨。
- 附近植物焦黑。
- 怪物突然减少。
- NPC 说“最近没有商队从这里回来”。
- 地面有巨大脚印。

这些信息不是警告弹窗。

它们是世界自己的语言。

---

## 6.2 回报不能只有数值

回报可以是：

- 新能力。
- 新路径。
- 捷径。
- 世界秘密。
- 新 NPC。
- 新贸易路线。
- 地图视野。
- 生态信息。
- 稀有材料。
- 新移动方式。
- 世界历史。
- 一个之后几十小时都会使用的地点。

高价值奖励最重要的是：

> **它改变后续游戏。**

---

# 7. 设计原则六：动态世界（Living World）

## 一句话定义

**世界不是等待玩家触发的舞台，而是在玩家不参与时也会继续变化。**

例如：

```text
长期不下雨
→ 土壤含水量下降
→ 草地变黄
→ 易燃程度上升
→ 火灾概率提高
→ 动物迁徙
→ 某些捕食者跟随迁徙
→ 商队改变路线
→ 某地区商品供给变化
```

玩家可能完全没有参与这一切。

但进入地图以后，他能感知这些变化。

于是玩家会产生：

> “这个世界在我不在的时候也发生了事情。”

这就是“活着”的基础。

---

# 8. 设计原则七：规则优先于事件

## 一句话定义

**不要首先设计“发生什么事件”，而是设计“什么条件下世界会发生什么”。**

错误：

```text
if 玩家使用火球术 && 目标是草:
    草燃烧
    创建上升气流
```

更好的思路：

```text
规则 A：
可燃物 + 温度超过燃点 + 湿度足够低
→ 燃烧

规则 B：
持续燃烧
→ 加热空气

规则 C：
热空气密度下降
→ 形成上升气流

规则 D：
具有足够受风面积的实体进入气流
→ 获得升力
```

这里完全没有：

- 火球术
- 玩家
- 滑翔伞
- 特殊剧情

因此：

- 雷击可以点燃草地。
- 火把可以点燃草地。
- 火山可以点燃草地。
- 怪物火焰吐息也可以点燃草地。
- NPC 纵火也可以。
- 玩家甚至可以利用自然野火飞起来。

这就是规则系统的力量。

---

# 9. 设计原则八：世界语言，而不是 UI 语言

世界应该尽可能自己告诉玩家正在发生什么。

例如：

```text
乌鸦增加
→ 附近尸体 / 腐化增加

植物叶片发黄
→ 水分不足

蘑菇开始发光
→ 地下湿度提升

昆虫大量飞出
→ 即将降雨

鱼群向上游迁移
→ 下游水质异常

商队减少
→ 某条道路可能出现危险
```

玩家久而久之会学会：

> **读世界。**

这比一个状态面板告诉玩家：

> “当前区域：危险度 +25%”

更有沉浸感。

---

# 10. 设计原则九：涌现式玩法（Emergent Gameplay）

## 一句话定义

**设计师提供规则，玩家自己发现玩法。**

例如：

设计师只实现：

- 草能燃烧。
- 火会产生热。
- 热产生上升气流。
- 布料受到升力。
- 风会改变实体运动。

玩家可能自己发现：

```text
点燃山坡
→ 制造上升气流
→ 滑翔到高处
→ 绕过守卫
→ 从洞穴顶部进入
```

这条路线可能设计师从未明确安排。

这就是：

> **玩法从规则中长出来。**

---

# 11. 设计原则十：涌现式叙事（Emergent Narrative）

故事不一定全部由编剧写。

世界历史也可以由系统产生。

例如：

```text
长期干旱
→ 森林失火
→ 某村庄被毁
→ 难民迁移
→ 新聚落形成
→ 原本的贸易路线改变
→ 某 NPC 因此失去家庭
→ 数月后形成新的地方文化
```

玩家进入世界以后听到的：

> “二十年前那场大火改变了一切。”

这场“大火”最初甚至可能不是剧情脚本。

而是规则运行出来的。

于是：

```text
规则
→ 事件
→ 历史
→ 记忆
→ 文化
```

这就是我们真正想要的“世界”。

---

# 12. 把前面的原则串成一条完整体验

假设远处有一尊巨大的移动石像。

## ① 地标

玩家在很远就看到它。

> “那是什么？”

产生视觉吸引。

---

## ② 信息缺口

NPC 只知道：

> “它每隔七天会经过一次这里。”

没人知道里面是什么。

玩家产生自己的问题。

---

## ③ 能力锁

石像太高。

当前无法进入。

但玩家记住了它。

---

## ④ 世界规则

最近长期干旱：

```text
湿度下降
→ 草地枯黄
→ 易燃性上升
```

---

## ⑤ 玩家利用规则

法师点燃草地：

```text
草燃烧
→ 温度升高
→ 上升气流形成
```

玩家装备滑翔斗篷：

```text
进入气流
→ 获得升力
→ 飞到巨像手臂
```

这里没有：

> “进入巨像任务：第 3 步。”

---

## ⑥ 风险与回报

巨像内部：

- 很危险。
- 补给有限。
- 可能无法快速返回。

但里面可能存在：

- 古代技术。
- 稀有装备。
- 世界历史。
- 新移动能力。

玩家必须自己决定值不值得深入。

---

## ⑦ 反馈

如果玩家获得极稀有装备：

```text
装备落地
→ 特殊音效
→ 大型光柱
→ 世界公告
→ 跑马灯
→ 附近玩家看到
```

---

## ⑧ 新能力反过来改变旧世界

巨像内部获得：

> 风翼。

玩家突然想起：

> “之前明珠港上方那个一直上不去的地方……”

能力锁重新激活。

整个世界因此形成循环。

---

# 13. 工程实现原则

非常重要：

> **规则驱动不等于不用系统、不用事件、不用 ECS。**

代码底层仍然可以是：

- Entity
- Component
- System
- Event
- Message Bus
- State Machine
- ECS
- Actor
- 分布式服务

区别只在：

> **业务逻辑表达的是世界规则，而不是功能特例。**

# 15. 一个简化的规则模型

伪代码：

```rust
struct WorldFact {
    entity_id: EntityId,
    fact_type: FactType,
    value: FactValue,
}

trait Rule {
    fn matches(&self, world: &WorldState) -> bool;
    fn apply(&self, world: &mut WorldState);
}
```

例如：

```text
BurnRule

WHEN:
    Material.flammable == true
    Temperature >= ignition_temperature
    Moisture <= max_burn_moisture

THEN:
    Burning = true
```

而不是：

```text
FireballHitGrassRule
```

核心判断：

> **规则名里如果经常出现某个技能名、任务名、玩法名，很可能正在写特例。**

# 16. 世界宪法（World Constitution）

未来设计新系统之前，优先维护一份“世界宪法”。

它不是几百页策划案。

最初只需要几十条稳定规则。

例如：

### 物理

1. 水从高处流向低处。
2. 热量会传播。
3. 热空气会上升。
4. 可燃物达到燃点可以燃烧。
5. 湿度会影响燃烧。

### 生态

6. 植物需要水和光。
7. 生物需要食物。
8. 捕食者会追随猎物。
9. 环境变化会推动迁徙。

### 社会

10. 聚落需要资源。
11. 商队倾向选择安全且成本更低的道路。
12. 道路中断会改变贸易。
13. 供给不足会影响价格。
14. 长期事件会改变 NPC 行为。

### 信息

15. NPC 只知道自己能够获得的信息。
16. 信息会传播，但传播需要时间。
17. 重要事件可以形成地方记忆。

### 历史

18. 世界状态改变应该留下痕迹。
19. 痕迹可以被玩家重新发现。
20. 持续足够久的历史可以形成文化。

这几十条规则比几百个孤立任务更重要。

# 18. 以后评价一个设计时，不再只问“好不好玩”

统一问以下问题：

## 世界性

- 如果玩家不在，这件事情还成立吗？
- 它是世界规则，还是玩家特例？
- 它是否产生真实世界状态？

## 组合性

- 能否和其他规则组合？
- 是否只有一种标准答案？
- 玩家能否发现设计师没有明确规定的用法？

## 探索性

- 玩家会不会自己产生问题？
- 有没有值得记住的地方？
- 新能力是否重新激活旧地图？

## 反馈性

- 玩家做了以后，世界真的回应了吗？
- 反馈有没有从“数字”走向“环境”？
- 其他玩家能否感知重要事件？

## 历史性

- 这件事情结束以后，会不会留下痕迹？
- 世界是否记住玩家行为？
- 长期积累以后，是否可能形成历史？

## 情绪性

最终最重要的问题：

> **这个机制究竟想让玩家产生什么情绪？**

不是：

> “我们有火焰系统。”

而是：

> “玩家第一次发现自己能利用一场自然野火飞到天空中的巨兽身上时，他会产生什么感觉？”

技术和规则最终都必须服务于那个瞬间。

---

# 19. 当前总纲

目前整个知识库可以压缩成一句话：

> **先创造一个能够自洽运行的世界，再让玩家观察它、理解它、利用它、改变它，最终让规则之间的组合产生连设计师自己都无法完全预先写出的玩法、故事与历史。**

以及第二句话：

> **我们不是设计一百个事件，而是设计十条足够好的规则，让它们产生一百个事件。**

最终目标不是“系统很多”。

而是：

> **世界有生命。**
