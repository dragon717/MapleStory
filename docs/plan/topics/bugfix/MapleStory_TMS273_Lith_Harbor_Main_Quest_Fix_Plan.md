# 冒险岛复刻｜TMS 273 维多利亚港后主线任务修复计划

> 研究日期：2026-09-11  
> 问题：角色到达维多利亚港后，没有可继续的主线任务。  
> 目标版本：台服 TMS V273；完整小版本、热更及资源指纹待在项目中确认。  
> 项目背景：既有文档描述为 Rust 权威后端 + Web / TypeScript 客户端。  
> 交付性质：公开资料调研、候选任务关系、源码排查步骤、开发工单与验收标准。**本次未获得当前项目源码，没有修改或运行项目。**

---

## 0. 决策摘要

**要修的不是“港口后少了几条任务”，而是“职业选择—对应转职—剧情重新汇合—后续章节与等级引导”这条连续推进链。**

公开 TMS 任务条目给出的重要线索是：

```text
36306 前往维多利亚岛
  → 36307 冒险的开始
  → 与所选路线相匹配的职业任务 / 转职检查点
  → 36337 德斯的帮忙
  → 36308 失窃的宝物
  → 36309 奥莉维亚事件
  → 36310 关于变身术士的情报
  → 36311 维多利亚岛的封印石
  → 继续核验并恢复其后的有效剧情章节
```

这是一张**待 TMS273 原始资源确认的候选关系图**，不是已经验证的 273 实机攻略。公开条目明确显示 `36308` 的前置为 `36337`；`36337` 又涉及不同职业的分支检查点。因此，不应实现成 `36306 → 36307 → 36308`，也不能按任务编号加一推进。[S03][S06][S07]

第一轮应优先确认四件事：

1. `36306` 是真实完成，还是仅完成了地图传送？
2. `36307` 的选择脚本、路线信息和相应职业任务是否完整接入？
3. 职业分支是否错误地被当成“所有前置必须同时完成”？
4. `36337` 及后续脚本型任务是否被导出器、注册表或客户端任务列表漏掉？

**建议的交付顺序：**先完成一条代表性路线的纵向闭环，再覆盖项目实际开放的所有相关分支；随后完成冒险家后续章节、阶段性等级引导和旧存档恢复。不能把“一个角色能过”当作“所有职业主线已修复”。

### 2.2 真正需要恢复的是分支图

```text
                 36306 的权威完成事实
                          │
                          ▼
                36307：有效路线选择
                          │
              ┌───────────┴───────────┐
              │                       │
      普通路线候选检查点         特殊路线独立子图
      1401 / 1402 / 1403         影武者相关任务 … 2684
      1404 / 1405               重炮相关任务 … 2570
              │                       │
              └───────────┬───────────┘
                          │
               按已确认的分支条件重新汇合
                          ▼
                    36337 → 36308
                          → 36309 → 36310 → 36311
```

图中横向项目是**候选分支**，不是要求同一角色全部完成。特殊路线的完整接入位置由 273 数据裁定；不能仅因都属于冒险家，就强行套普通职业流程。

`36337` 的网页把 `1401、1402、1403、1404、1405、2684、2570` 展平展示。必须查看原始条件树、分支标记和脚本，确定哪些条件按路线适用、哪些是选择关系、哪些还附带额外约束。**既不能一律 AND，也不能为了过关全局改成 OR。**[S06]

### 2.3 港口和 NPC 不是只靠名字定位

`36307` 的 TMS 条目指向糖果 `1541002`，但该任务页没有给出可展示地图坐标；其他地区同号条目关联 Lith Harbor `104000000`。因此，这个地图 ID 只能先作交叉检索候选，再核对 TMS273 的 NPC 放置、阶段与地图实例。[S03][S20]

继承上一轮 `36306` 的回归项：`NpcId(22000)` 不得误查为同号脸型资源。名称缓存、导出映射与导航目标必须带资源类型，而不是只用裸数字。[P01]

### 3.3 把“正常等待”与“实现缺口”彻底分开

公开数据中 `36322`、`36324`、`36325–36329` 分别出现 25、30、60 级门槛。它们不是已核验的 273 数值，但足以说明：**剧情任务不一定始终连续可接。**[S12–S18]

因此，任务面板不能只有“有任务 / 无任务”两种状态。建议至少区分：

- **可以继续：**给出有效接取或继续入口。
- **暂时受限：**说明具体等级、前置或职业条件，并给出当前真实可用的成长选择。
- **当前章节已结束：**展示完成的章节与下一条独立内容轨道。
- **内容或脚本缺失：**明确为项目实现缺口，写入诊断；不得写成“原版主线已结束”。

“原版任务”和“项目成长推荐”必须分开。推荐去练级不是一条新造的原作主线，也不应强制自动接取或传送。

**不要把全文命中的第一处当作运行时实现。**应明确原始数据 → 导出器 → 服务端定义 → 条件评估 → 动作提交 → 持久化 → 客户端视图的完整调用链。二进制资源不能靠 `rg` 判断是否存在。

## 6. 内容导出与依赖图修复

### 6.1 用有效关系扩展，不用编号连续性扩展

从 `36306、36307、36337` 及项目实际职业入口出发，追踪以下关系：任务前置、路线条件、脚本转入、地图/场景事件、转职动作、章节结束与后继通知。

依赖查询既向前找“缺哪个条件”，也向后找“完成后会影响谁”。**只沿前置往前读，无法发现由脚本启动的下一章。**

`36300–36399`、`1400–1499`、特殊职业任务范围仅可作为检索线索。不得把整个区间当作有效主线，也不得把网站“任务链条”列表按显示序号执行；相关列表中还可能包含活动和废弃节点。[S06][S14]

### 6.2 每个正式启用节点需要的内容契约

| 类别 | 必须明确的内容 |
|---|---|
| 身份 | 任务 ID、地区、版本、剧情变体、源文件/逻辑节点、指纹 |
| 条件 | 等级、职业语义、路线、前置分组、变量条件、账号/角色范围 |

| 执行 | 起始/结束处理器、对话选择、地图动作、战斗/采集目标 |
| 效果 | 物品、经验、金币、职业、技能、任务变量、章节事实等真实变化 |
| 恢复 | 取消、放弃、失败、掉线、退出场景和重入策略 |
| 展示 | 当前步骤、目标实体类型、目的地、阻塞原因、可执行动作 |
| 核验 | 已确认字段、未确认字段、原版证据、项目调整与测试编号 |

每个未知字段保留原值、源位置和判定原因，便于补实现，而不是在导出时静默丢弃。

## 7. 服务端最小正确实现

本节为 `P`：复用现有 World、角色单写者和存档能力，不为主线修复先引入微服务、消息中间件或全新脚本平台。

### 7.1 保存事实，派生“现在能接什么”

建议持久化：已接受/已完成任务、步骤或目标进度、有效路线选择、需要保留的任务变量、剧情检查点，以及奖励/关键效果的提交凭据。

可接任务、NPC 头顶标记、推荐下一步通常由上述事实和当前条件计算，不再额外保存一份长期失真的“下一任务编号”。

公开任务数据中的 `state 0/1/2` 必须先映射清楚，再映射项目自身状态；不能把客户端展示的“目标满足”直接映射成“奖励已提交”。

如果现有代码已经有等价模型，只补缺字段与错误转换，不重复造另一套任务系统。[P02]

### 7.2 路线条件的实现原则

建议条件模型能表达 `all / any / not / quest-state / job-condition / variable-condition`，但**原始数据的实际语义优先**。

一个分支可接与否应由经核验的完整条件决定。不能只凭 `jobId / 100` 猜职业族，也不能只凭某个检查点完成就忽略其他条件。

特别核对：

- `1406` 是记录索引、条件容器还是实际选择编码；本轮只确认其被引用，没有确认具体值。
- `36337` 的普通路线与特殊路线如何汇合。
- `36325` 的职业列表是否适用精确职业还是某种继承/分组规则。
- `36329` 中 `36328` 和 `2643` 的关系；不得要求普通路线补特殊路线所有任务。[S05][S06][S14][S18]

### 7.3 脚本处理器先覆盖关键闭环

先为已经确认需要的脚本行为建立明确处理器或适配现有脚本运行器。起步覆盖 `q36307s`、代表路线转职脚本、`q36337s`、`q36308s/e`，再按实际节点扩展。

脚本名与处理器之间应可检查：内容定义引用的每一个必须脚本，都有可执行实现及测试。不要自动把所有 `q{ID}s/e` 注册到同一个“立即完成”函数。

对话选择需绑定角色、任务、当前步骤和会话版本。客户端只提交允许的选择意图，不能指定职业授予、奖励、目标地图或任务完成事实。

### 7.4 一次提交内保持业务一致

典型流程应是：

```text
收到任务/对话意图
  → 校验有效会话、任务当前状态与入口权限
  → 重新判断完整条件
  → 计算本步骤全部业务变化
  → 检查物品消耗、背包容量及效果能否成立
  → 经现有角色单写者与持久化机制提交
  → 得到已提交的新角色版本
  → 更新派生任务视图并通知客户端
```

转职、技能授予、对应任务完成与必要路线事实必须保持一致。奖励容量不足时，保留有效进行/可领取状态，不先完成再吞掉奖励。

重试使用稳定的业务提交身份，例如“角色 + 任务 + 本次任务运行 + 步骤”。重发同一步返回已提交结果，不能再次发奖励。允许放弃重接的任务必须区分新任务运行和旧网络重试；不可重发的一次性效果仍要独立防重。

### 7.5 传送与剧情检查点

地图变化不一定能与存档在同一物理事务完成。应先用现有机制记录可恢复的任务检查点/转场意图，再完成地图切换；重连时按同一检查点恢复或安全重试。

不要把“角色现在位于港口”视为 `36306` 完成证据，也不要让“任务已完成但人物仍在旧场景”永久卡住。

在 World tick 中不等待慢数据库或网络；异步持久化结果返回时，必须通过现有角色版本/单写者顺序校验，防止过期回调覆盖新状态。具体采取事务、原子快照或现有写入队列，由项目存储实现决定，不强制引入新基础设施。

### 7.6 区分入口权限

物理 NPC 交互需校验地图实例、剧情阶段、对象身份、距离等现有规则；通知/脚本触发入口不能被错误要求“附近必须有这个 NPC”。

反过来，不能为了支持通知任务，把所有物理 NPC 的距离和实例检查一并取消。跨玩家剧情进度不得互相替代，个人演出实体不能污染其他玩家的公共地图。

## 8. 客户端任务、导航与自动刷新

### 8.1 同一个权威视图驱动所有入口

任务列表、追踪栏、NPC 标记、通知入口与导航应读取同一份服务端派生结果。客户端可以排序和折叠，但不能自行判断另一套完成条件。

建议视图至少包含：任务/章节、当前步骤、状态、目标类型和 ID、入口类型、有效地图/实例约束、阻塞原因、允许操作、内容版本与角色视图版本。

错误示例是任务栏说“可完成”，NPC 仍只给接取对话；或者后台 `36337` 已满足，前端因没有本地图 `startNpc` 而把它过滤掉。

### 8.2 何时刷新

在相关权威变化后刷新：任务接受/完成/放弃、路线确认、等级/职业改变、目标计数变化、必要物品变化、进入地图/剧情阶段、登录与重连。

首版可采用有上限的保守重算；内容增多后再利用依赖索引仅重算受影响任务。不要在每帧或每次移动时全量遍历所有任务。

客户端发现增量版本缺口时，申请全量校正，不能一直展示旧的“无主线”。

### 8.3 “下一步”必须可执行

```text
当前：冒险的开始
操作：继续与糖果对话，确认路线
```

```text
当前：法师之路
操作：前往有效目标地图，与对应转职官交谈
说明：目的地、名字、入口来自已验证的任务定义
```

```text
当前章节暂时受等级条件限制
显示：需要等级 N，目前等级 M
提供：当前已实现且角色确实可进入的成长内容
```

以上是 `P` 展示示例，不是原版逐字文案。等级 `N/M` 从运行时真实条件取得，不能把当前公开网页的数值硬写进 273 UI。

若需要区分来源，可用 `original_quest` 与 `project_guide`。项目推荐不得伪造原作任务 ID、原作剧情奖励或未经原作核验的强制传送。

## 11. 已卡住角色的兼容与恢复

### 11.1 先分类，再修复

| 角色状态 | 建议动作 |
|---|---|
| `36306` 已完成，`36307` 未接 | 修正可用性和入口，正常继续；不补奖励 |
| 已到港但 `36306` 未完成 | 查找可证明完成的持久化转场/业务记录；有证据才补对应事实，无证据提供安全重试入口 |
| `36307` 已完成，但缺路线变量 | 先查现有选择、职业授予和历史记录；能唯一确定才恢复，存在歧义则提供受控重新确认 |
| 对应转职检查点完成，`36337` 不可接 | 修条件/注册/展示，通常无需改旧进度 |
| 当前职业已变更，但所有相关任务记录缺失 | 区分 GM/测试造号与正常升级遗漏；单独迁移，不根据职业直接补完整个剧情 |
| 剧情进行中但原实例不存在 | 使用已记录检查点重新创建/进入，或按核验规则安全放弃重接 |
| 已完成后续节点，但早期记录异常 | 不回滚已获得的真实进度；建立最小兼容事实并留迁移审计，不重播所有奖励 |

### 11.2 迁移约束

迁移前备份，并先输出 dry-run 的角色、证据、旧值、新值与原因。迁移在角色单写者/版本校验内执行，记录迁移版本和对应内容版本，重复执行不得再次产生效果。

没有足够证据的角色进入待处理集合，不能用“统一清空任务”解决。数据修复与奖励补偿分开处理；若确需补偿，应另有明确依据和防重记录。

回滚不能简单恢复整份旧存档覆盖玩家后续正常进度。应保留字段级差异，使用版本前置条件执行针对性撤销或前向修正。

禁止：批量把 `36300–36399` 标完成、给所有职业补全所有分支、把所有旧角色重置为初心者、为补条件重复调用奖励脚本。

## 13. 验收门槛与完成定义

### 13.1 内容正确性

正式开放范围内，所有有效任务的必须前置、脚本、地图、目标与效果均能解析；未知语义与未实现必须脚本为零。此指标只统计本版本实际启用的内容，不能靠把所有节点禁用来“通过”。

每条开放路线从合法起点到其章节终点/明确阶段门槛都有经过测试的路径。互斥分支与放弃重试回路可合法存在，不能机械要求整张图无环。

### 13.2 玩家体验

不借助 GM、不手动改任务表，从港口能够继续相应职业与剧情。接取、目标、交付、失败恢复和下一步入口均可用。

到达等级门槛或章节终点时，能够清楚知道当前状态和真实下一步；主线窗口不能因后端缺实现而无声消失。

### 13.3 数据安全

转职、技能、任务和奖励没有已知不一致；重复请求、断线和重启不会重复授予效果或永久阻塞；迁移不会丢失玩家已发生的有效进度。

### 13.4 工程提交

交付实际修改文件清单、关键调用链、数据来源、测试结果和已知限制。构建检查使用真实 workspace；若工程确实采用 `server/Cargo.toml`，可使用下列检查，否则按真实位置调整：

```bash
cargo fmt --manifest-path server/Cargo.toml --all -- --check
cargo test --manifest-path server/Cargo.toml --locked
cargo clippy --manifest-path server/Cargo.toml --all-targets --locked -- -D warnings

# 前端按已确认的包管理器执行项目现有 typecheck / test / build。
# 服务启动和重启仍只有这一入口：
./启动3010.command
```

不得用全局屏蔽 warning、删测试或直接返回成功掩盖任务缺口。
