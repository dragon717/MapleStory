# 冒险岛复刻：Web 后台保活、10 分钟暂离宽限与基础驻留

> 版本：v1.0 · 2026-09-10  
> 适用项目：冒险岛复刻；Rust 服务端权威世界；Web / TypeScript / JavaScript 前端。  
> 文档状态：可执行开发计划，尚未读取实际仓库、修改项目代码或运行项目测试。下文模块名和协议名均为建议，开发时必须映射到仓库现有实现。  
> 集成约束：项目构建与启动统一使用仓库中的 `启动3010.command`，不另起一套启动流程。

## 0. 执行摘要

### 0.1 要解决的体验

玩家切到其他窗口、切换标签页、最小化游戏或短暂失去网络时，不应立即丢失角色与世界的联系。

本方案实现：

1. **失焦不主动断线**：仅窗口失去输入焦点时清理按键，不退出地图。
2. **连续暂离不足 10 分钟**：服务端保留原角色及其正常世界规则；返回后同步当前状态并恢复参与。
3. **连续暂离达到 10 分钟**：进入基础驻留。其他玩家仍能在正常可见范围内看见该角色，角色标记“暂离”；停止不必要的高频同步。
4. **返回基础驻留角色**：先同步真实状态，再提示“你已离开超过 10 分钟”。玩家确认后继续冒险，也可保持暂离。
5. **连接意外中断**：允许重新认证并绑定原角色；不会仅因旧 WebSocket 关闭就删除角色。
6. **驻留有独立上限**：避免无限占用场景资源。建议以连续暂离总计 60 分钟作为首版测试配置；这不是用户已确认的时长，也不是行业标准。

### 0.2 核心判断

> **连接可以断，角色不立即退场；注意力可以离开，世界事实继续成立；恢复的是同一个角色在当前世界中的状态，不是重播离开期间的所有画面。**

“完整功能保活”在本方案中特指：**服务端业务连续性和既有玩法规则继续成立**。它不代表强迫浏览器后台满帧运行，也不代表自动替玩家移动、攻击、交易。

基础驻留减少的是无人观看的同步、无效控制连接及界面工作，**不是把仍在危险场景中的角色从伤害和物理规则中移除**。

## 1. 需求、默认决策与边界

### 1.1 原始需求映射

| 原始诉求 | 本方案的可验证承诺 |
| --- | --- |
| Web 前端窗口失去聚焦后不要断线 | 删除失焦主动退出逻辑；心跳不依赖渲染帧；真实断线时保留角色并提供恢复路径 |
| 完整功能保活 10 分钟 | 连续暂离小于 600 秒时，角色不因暂离而退场，已成立的玩法状态正常推进 |
| 10 分钟后基础保活 | 进入基础驻留，保留同一个权威角色、社交身份与恢复入口，降低本人订阅成本 |
| 其他人看得见这个角色 | 角色继续出现在同地图、同频道、同相位及正常兴趣范围内；不能只在本人浏览器留下假影像 |
| 本人弹窗“超过 10 分钟” | 服务端确认已达到阈值；客户端具备执行条件且同步完成后展示；冻结期间不承诺弹窗即时出现 |

### 1.2 本方案采用的默认决策

| 决策项 | 首版建议 | 说明 |
| --- | --- | --- |
| 暂离触发 | 页面隐藏、主动暂离、服务端发现应用失联 | **仅 `blur` 且页面仍可见，不启动十分钟倒计时**；这是避免误判双窗口观看的设计选择 |
| 长时间可见但不操作 | 不纳入本次暂离判定 | “空闲玩家检测”是独立需求，不能把最后一次按键时间当页面离开时间 |
| 宽限边界 | `< 600 秒` 为宽限；`>= 600 秒` 为基础驻留 | UI 使用“超过 10 分钟”，逻辑按达到阈值执行 |
| 危险区角色 | 继续受正常伤害、重力、碰撞和死亡规则约束 | 不因暂离获得保护，不凭空清除仇恨 |
| 基础驻留上限 | 建议连续暂离总计 3600 秒后请求正常离场 | 从同一次暂离起点计算，不是 10 分钟后再加 60 分钟 |
| 十分钟内返回 | 可自动恢复参与，但必须先完成同步校验 | 浏览器重新聚焦本身不直接改服务端状态 |
| 十分钟后返回 | 需明确的继续操作，再完成同步门禁 | 自动重连、Pong、页面显示均不能自行重置暂离窗口 |
| 无缝恢复范围 | 服务端角色会话仍在、身份有效、场景允许 | 服务器重启、封禁、会话失效、实例结束等走明确失败或重新进入路径 |

上述时长和交互是产品策略；浏览器生命周期、传输连接是否存活是技术事实。两者必须分开。

### 1.3 首版不做

- 不引入独立“影子角色”“挂机机器人”或第二套离线角色实体。
- 不新增离线收益、自动战斗、自动复活、自动拾取规则；已有正式持续玩法按原规则运行。
- 不更换现有 WebSocket 框架，不为了此功能引入 Nakama、Colyseus、Socket.IO、Redis 或消息队列。
- 不把 Worker、静音音频、假视频、屏幕常亮等作为保活正确性的前提。
- 不承诺服务器进程重启后仍恢复完全相同的内存世界；持久数据按现有恢复机制处理。
- 不绕过既有登录鉴权、反作弊、资产事务、副本清退和封禁逻辑。

## 2. 双向钢人论证与最终取舍

### 2.1 支持这项机制的最强理由

玩家的注意力变化，不等于角色主动离开世界。短暂查看攻略、回复消息不应拆散队伍或销毁地图上下文。角色持续存在，也符合本项目“世界独立运行、角色服从世界事实”的方向。

对于社交体验，“一个明确标记暂离的人仍站在那里”比“切屏即消失”更连续，也比“长期伪装成活跃在线”更诚实。

### 2.2 反对照字面实现的最强理由

浏览器可冻结或回收页面，客户端无法保证后台十分钟持续执行。[S2] 若把完整保活解释为持续沿用最后输入，会产生卡键和自动攻击；若解释为不受伤，又会把切屏变成逃避战斗的能力。

长期角色存在仍有模拟、场景容量、队伍占位和消息成本。“别人看得见”不能通过无限维持所有网络资源来实现。

### 2.3 双方真正的分歧

不是“要不要十分钟”，而是保证对象放在哪里：

| 维度 | 不采用 | 采用 |
| --- | --- | --- |
| 保证对象 | 同一条 Socket 永远不断 | 世界状态连续、角色会话可恢复 |
| 暂离后操作 | 延续旧输入，或替玩家代玩 | 没有新鲜授权就停止新的主动操作 |
| 世界后果 | 暂停受伤、冻结 Buff、清除仇恨 | 继续遵守正常世界规则 |
| 长期成本 | 无限全量推送和无限占位 | 有限驻留、有限队列、可重同步 |

**结论：把“存在”“行动”“观察”拆开管理。可以保留存在，停止无人授权的行动，减少无人观看的同步。**

## 3. 外部依据：借鉴模式，不照搬框架

| 依据 | 已核对的事实 | 对本项目的意义 |
| --- | --- | --- |
| MDN Page Visibility API [S1] | 失焦不等于隐藏；后台动画回调和定时器可能暂停或受限 | 用可见性表达离开；不要用渲染循环维持会话 |
| Chrome Page Lifecycle [S2] | 页面可能被冻结或回收；回收不保证有事件通知 | 生命周期通知只是提示，服务器必须能独立检测与恢复 |
| WebSockets Standard [S3] | 协议 Ping/Pong 控制帧不暴露为浏览器 JS API | 传输心跳不能当作游戏应用仍工作或玩家仍参与的证据 |
| MDN WebSocket [S4] | 传统 WebSocket API 没有内建接收背压 | 必须限制未处理数据，不能给后台客户端无限推流 |
| Colyseus Reconnection [S5] | 临时断开可保留房间席位并允许恢复 | 将连接断开与永久离场分开建模 |
| Socket.IO Recovery [S6] | 连接状态恢复不保证总能成功 | 始终准备完整快照与恢复失败路径 |
| Nakama 权威多人模式 [S7] | 权威世界可在玩家断开时继续推进 | 服务端角色与世界 Tick 不应依附浏览器连接 |
| Nginx WebSocket 代理 [S8] | 上游无数据的默认代理读超时为 60 秒，可配置并通过服务端 Ping 重置 | 排查链路超时，不只修改客户端或游戏服务器 |

这些材料支持架构方向，**不提供统一的“Web 游戏标准十分钟保活”规则**。本方案中的 600 秒和 3600 秒是本项目策略。

## 5. 状态模型：三条轴，不能一个 `online` 包办

### 5.1 角色参与状态

| 状态 | 定义 | 世界中存在 | 新的主动操作 |
| --- | --- | --- | --- |
| `Active` | 正常参与 | 是 | 同步就绪、连接有效、输入合法后允许 |
| `AwayGrace` | 同一次连续暂离不足 600 秒 | 是 | 先完成参与恢复；不延续旧输入 |
| `AwayIdle` | 同一次连续暂离达到 600 秒，尚未到驻留上限 | 是，标记暂离 | 需要明确恢复意图和同步门禁 |
| `Leaving` | 已请求按正常规则离场 | 取决于正常退出阶段 | 拒绝新操作，处理既有事务与退出规则 |
| `Offline` | 已完成离场 | 否 | 必须重新进入 |

`AwayGrace` 和 `AwayIdle` 是同一暂离事实随服务端时间的两个阶段，不建议保存一堆互相矛盾的布尔字段。

### 5.2 连接状态

独立维护 `Connected / Suspect / Disconnected` 或复用现有等价状态。

合法组合包括：

- `AwayGrace + Disconnected`：角色仍在，等待恢复。
- `AwayIdle + Connected`：连接仍健康，但角色已经暂离超过十分钟。
- `Active + Connected + Syncing`：仅可在恢复流程中短暂存在；若采用该表示，输入门禁必须关闭。更推荐同步完成才正式进入 `Active`。

**连接关闭函数不得直接调用角色永久离场；连接连接成功也不得直接视为参与恢复成功。**

### 5.3 观察与同步状态

建议复用现有订阅机制，增加等价于以下的策略：

| 订阅策略 | 用途 |
| --- | --- |
| `Live` | 可见且已正常参与的实时地图同步 |
| `Reduced` | 页面隐藏但应用仍有处理能力时，合并必要更新、减少表现流量 |
| `Minimal` | 基础驻留时只维护本人关键事实、会话状态和有限通知 |
| `Suspended` | 应用确认停滞、连接断开或队列达到上限时，停止高频数据生产，等待快照恢复 |

降低本人订阅，**不能把该角色从其他玩家的可见实体列表中移除**。

## 6. 暂离时间：存事实，派生阶段

### 6.1 暂离起点

- 收到当前有效连接的 `hidden` 或主动暂离请求：以服务器接受该事件的时间开始。
- 没收到通知，但发现当前应用已失联：以服务器确认失联的时间开始，并记录 `reason = application_stalled` 或 `transport_lost`。
- 已处于暂离：重复隐藏、重连、心跳、再次断线都不能重置起点。
- 只有完成合法的参与恢复，才结束当前暂离窗口；之后再次离开才创建新窗口。

无法收到隐藏通知时，真实离开时刻与服务器检测时刻会有误差。首版接受该检测误差，不信任客户端自行回填的离开时长，也不把几小时前的最后一次按键当暂离起点。

### 6.2 推荐事实结构

以下为概念代码，不是对现有仓库类型的声明。标识符可按项目风格调整。

```rust
use std::time::{Duration, Instant};

#[derive(Debug, Clone)]
struct AwayPolicySnapshot {
    full_retention: Duration, // 建议 600 秒
    max_total_away: Duration, // 建议 3600 秒；含前面的 600 秒
}

#[derive(Debug, Clone)]
struct AwayWindow {
    away_id: u64,
    started_mono: Instant,      // 当前进程内判定时长
    started_unix_ms: i64,       // 展示、日志；不作为客户端裁决依据
    policy: AwayPolicySnapshot,
    reason: AwayReason,
}

#[derive(Debug, Clone, Copy)]
enum AwayReason {
    Hidden,
    Manual,
    ApplicationStalled,
    TransportLost,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum AwayPhase {
    Grace,
    Idle,
    ExitDue,
}

impl AwayWindow {
    fn phase_at(&self, now: Instant) -> AwayPhase {
        let elapsed = now.saturating_duration_since(self.started_mono);
        if elapsed >= self.policy.max_total_away {
            AwayPhase::ExitDue
        } else if elapsed >= self.policy.full_retention {
            AwayPhase::Idle
        } else {
            AwayPhase::Grace
        }
    }
}
```

外层参与状态可采用 `Active / Away(AwayWindow) / Leaving(ExitState)`；对外展示的 `AwayGrace / AwayIdle` 由 `phase_at()` 派生。`Offline` 可由角色会话不存在表示。

原则：

- 校验 `0 < full_retention < max_total_away`。
- 不保存另一个 `away_seconds += 1` 的累计计数。
- 不把 Rust `Instant` 直接序列化到协议或持久层。
- 策略在进入暂离时取快照；普通配置热更新不悄悄缩短正在进行的宽限。
- 服务端重启属于另一恢复路径；首版不尝试从旧 `Instant` 还原内存会话。
- 日志和界面可显示服务端 Unix 时间及截止时间；客户端倒计时仅供展示。

### 6.3 阶段推进顺序

每次处理角色事件或定时检查时，先根据当前服务端时间推进到期事实，再处理本次请求：

```text
检查当前绑定与身份
    → 检查本次暂离是否已经达到驻留上限
    → 检查是否已达到 600 秒并发布必要的状态变化
    → 处理同步确认 / 恢复请求 / 游戏操作
```

不能只靠每秒扫描更新一个缓存状态，再在操作入口相信过期的 `Active/Grace` 值。

若服务端一次检查已经越过多个阈值，直接进入应有阶段，不补演过去每秒的状态。一次状态跨越只广播一次；缓存“上次已广播阶段”仅用于通知去重，不能替代事实判断。

## 7. 状态转换规则

| 当前阶段 | 事件 | 结果 | 关键约束 |
| --- | --- | --- | --- |
| `Active` | 仅 `blur`，仍可见 | 保持 `Active`，清除输入 | 不退出、不开始暂离计时 |
| `Active` | `hidden` 或主动暂离 | 创建暂离窗口，进入 `AwayGrace` | 输入立即失效；订阅可立刻降频 |
| `Active` | 应用失联或传输断开 | 创建暂离窗口 | 不能直接删除角色 |
| `AwayGrace` | 重复隐藏、Pong、普通重连 | 保持原暂离窗口 | 不续十分钟 |
| `AwayGrace` | 可见并完成同步与自动恢复请求 | `Active` | 完成时仍未到 600 秒，且未到离场期限 |
| `AwayGrace` | 达到 600 秒 | `AwayIdle` | 同一角色，广播暂离标记 |
| `AwayIdle` | 页面可见、连接恢复、只同步 | 仍为 `AwayIdle` | 可查看提示，不等于恢复参与 |
| `AwayIdle` | 明确继续，完成同步门禁 | `Active` | 当前身份、绑定、场景与版本均有效 |
| `AwayIdle` | 选择保持暂离 | 保持原暂离窗口 | 不续总驻留时间；降低订阅 |
| 任一暂离阶段 | 达到驻留总上限 | `Leaving` | 复用正常退出与战斗收尾 |
| 任一阶段 | 明确退出、封禁、实例结束等 | 既有退出/迁移规则 | 暂离不是逃避规则的特权 |
| `Leaving` | 完成正常清理 | `Offline` | 清理幂等、持久状态可靠 |

边界例子：在第 599.8 秒启动自动恢复，但第 600.2 秒才提交恢复确认，必须按 `AwayIdle` 处理并要求明确继续，不能用开始恢复时的旧阶段绕过阈值。

## 8. 玩法规则：保留世界，不替玩家玩

### 8.1 功能矩阵

| 功能 | 十分钟内宽限 | 十分钟后基础驻留 |
| --- | --- | --- |
| 权威角色实体、地图归属 | 保留 | 保留，直到正常离场或场景规则改变归属 |
| 其他玩家可见性 | 正常兴趣范围可见 | 正常兴趣范围可见，显示暂离 |
| 重力、落地、击退、危险地形 | 正常 | 正常，不能冻结物理 |
| 受伤、死亡、仇恨规则 | 不因暂离改变 | 不因暂离改变 |
| Buff、冷却、活动截止时间 | 以服务端时间正常推进 | 同样推进，不暂停、不延长 |
| 已接受的技能与业务事务 | 按原规则完成或取消 | 按原规则完成或取消 |
| 新移动、攻击、交易、拾取命令 | 恢复参与后才接受 | 明确恢复参与后才接受 |
| 原输入中的“持续向右/攻击” | 立即停止续用 | 禁止续用 |
| 已有服务端持续玩法 | 按其既有规则执行 | 按其既有规则执行；不凭此新增收益 |
| 本人的地图高频同步 | 页面隐藏后即可减量 | 默认 `Minimal` 或 `Suspended` |
| 队伍与好友 | 不因失焦直接移除 | 标记暂离；入场和占位由队伍/副本原规则处理 |
| 交易、邀请、准备确认 | 不自动接受 | 不自动接受；沿用超时与取消规则 |

### 8.2 场景政策

**安全城镇**：保留同一角色，可展示暂离图标或待机姿态。视觉姿态不能改变碰撞体、位置、受击规则。若美术资源缺失，先用名称旁小标记，不为了本功能新增整套动画。

**普通危险地图**：持续执行伤害、落地、死亡等规则。不自动无敌、回城、清仇恨或传送。死后是否留尸、复活、回安全点，沿用既有死亡规则；“继续可见”指真实世界结果，不承诺永远停留在离开前的坐标。

**Boss、副本、竞技场**：明确优先采用该玩法的退场、超时、队伍资格与公平规则。不得承诺所有特殊场景无条件驻留满 60 分钟。若仓库没有相关玩法，不在首版虚构实现；预留统一策略入口即可。

**共享世界事件**：恢复的是事件当前进度。玩家暂离不暂停全服进程，也不能将个人旧快照覆盖世界新事实。

### 8.3 在线收益与“在线人数”

不再让所有业务共用一个 `is_online`：

- 场景存在人数：按实际驻留实体统计。
- 已连接客户端数：按有效传输绑定统计。
- 正常参与人数：按参与阶段统计。
- 活动参与、领奖、在线奖励资格：按该玩法原有的服务端条件判断。

页面可见性是客户端提示，不能证明真实人类在操作。本功能不是反挂机证明系统，也不能仅凭一个 `visible` 字段授予资产、战斗保护或豁免处罚。

## 9. 前端生命周期与输入处理

### 9.1 事件处理职责

| 事件 | 前端动作 | 不允许做的事 |
| --- | --- | --- |
| `window.blur` | 清除本地按键与持续操作；尽力发送输入重置 | 不发正式退出，不直接关闭连接 |
| `visibilitychange → hidden` | 同样清输入；报告隐藏；降低渲染与音效；允许网络独立运行 | 不以停止渲染为由停止网络生命周期管理 |
| `visibilitychange → visible` | 进入恢复检查；发送最新可见性；验证应用会话并发起必要同步 | 不直接开放输入，不把旧画面当当前世界 |
| `pageshow` | 包括返回历史页面时都重新核对绑定与快照 | 不相信缓存页面中的旧 Socket 和旧控制权 |
| `pagehide` | 尽力报告离开并清输入 | 不把浏览器关闭/刷新都解释成用户主动退出 |
| 支持的 `freeze/resume` | 作为额外提示执行保存展示状态、清输入或恢复检查 | 不要求所有浏览器支持这些事件；不依赖事件一定送达 |
| 明确点击游戏“退出” | 调用已鉴权的正式退出流程 | 不与 `blur`、`pagehide` 共用同一无条件退出回调 |

失焦与隐藏的区别、后台回调限制见 [S1]；冻结和回收边界见 [S2]。

### 9.2 渲染、网络、世界三个循环分离

```text
渲染循环：可以暂停或降频，不负责会话存活与权威时间。
网络循环：独立处理连接与控制消息；依然可能被浏览器冻结，不能承诺永续。
服务端世界循环：持续推进权威事实，不取决于某个浏览器有没有帧回调。
```

若当前网络接收先放入队列、必须等渲染 `update()` 才消费，必须把恢复、会话状态、关键同步确认从该耦合中解开，并给普通表现消息设置上限。

### 9.3 防卡键与服务端输入租约

前端发送“全部松开”只是最佳努力；页面可能来不及发送，因此服务端必须兜底。

持续方向、持续攻击等输入应有短期有效期，由新的输入状态续期。建议以 500 毫秒作为本地测试起点，结合当前输入发送频率和网络抖动调参，不能直接照抄为最终线上值。

必须区分：

- 停止新的方向和攻击意图：应当发生。
- 强行清零重力、击退速度或取消已生效的技能后果：不应因失焦发生。
- 已合法释放的投射物、召唤物或正式持续技能：按技能规则结算，不一刀切取消。

新连接绑定或重新同步后，旧连接的持续输入全部清空。客户端禁止缓存并重放断线前的移动、攻击、交易和拾取指令。

### 9.4 恢复界面期间的输入

恢复完成前，游戏输入门禁关闭。用于唤醒的第一次按键或点击只表达“继续冒险”，**不顺带发出一次攻击、购买或拾取**。恢复确认后，重新采集新输入；需要松开再按下的键由界面明确提示。

仅连接建立、窗口聚焦或快照接收完成，都不足以单独打开门禁；还需服务端的参与恢复确认。

## 10. 心跳、应用进度与断线恢复

### 10.1 三种证据分别记录

| 证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| 最近有效协议 Ping/Pong 或接收活动 | 传输端点仍有响应 | JavaScript 正在消费游戏消息、玩家正在操作 |
| 最近有效应用层进度报告或消息确认 | 游戏应用最近执行过相关逻辑 | 玩家一定在观看，或者一定是人类操作 |
| 已完成的参与恢复与新鲜操作 | 服务端当前允许该连接控制角色 | 永久授权，不再需要后续合法性验证 |

WebSocket 控制帧的浏览器 API 边界见 [S3]。具体 Rust WebSocket 库如何发送 Ping、如何自动响应、读写任务是否必须持续轮询，必须在仓库核查后按其实际实现处理。

### 10.2 建议测试配置

| 配置 | 首版测试起点 | 约束 |
| --- | --- | --- |
| `AWAY_FULL_RETENTION_SECS` | 600 | 用户需求对应值 |
| `AWAY_MAX_TOTAL_SECS` | 3600 | 建议值，从首次暂离起算，需允许产品调整 |
| `WS_PING_INTERVAL_SECS` | 15 | 独立于渲染；复用现有协议能力 |
| `WS_TRANSPORT_TIMEOUT_SECS` | 45 | 基于有效端点响应，不是“发送过 Ping 就算活着” |
| `APP_PROGRESS_INTERVAL_SECS` | 5，可见时 | 独立于渲染；可复用现有应用心跳，避免重复机制 |
| `APP_STALL_TIMEOUT_SECS` | 45 | 用于暂停高频订阅、发现未上报的离开，不等于立即踢角色 |
| `CONTINUOUS_INPUT_LEASE_MS` | 500 | 必须与实际输入发送频率、延迟测试一起调整 |
| `AWAY_SWEEP_INTERVAL_MS` | 1000 | 只作为后台扫描；命令入口仍按当前时间判定 |
| `RESUME_ATTEMPT_TIMEOUT_SECS` | 15 | 单次恢复超时，不能无限占用同步缓冲 |

除 600 秒外，上述数字是测试参数，不是外部标准。正常高延迟玩家不能仅因应用进度暂时停滞就被永久离场。

### 10.3 应用进度停滞

应用进度报告应由真正执行的 JS 逻辑发出，包含当前绑定和已应用的同步序号；在世界没有变化时，也可用已有应用心跳证明处理循环仍执行。

- 已报告隐藏：暂离窗口从隐藏事件开始，不必等待应用超时。
- 未报告隐藏、传输仍通但应用进度停滞：停止高频推流，开始或保持暂离窗口；不要把协议 Pong 误认为已经恢复。
- 暂离期间应用心跳重新出现：只更新应用健康情况，不重置暂离起点。
- 背景定时器可能被限制，因此后台报告只能尽力，不作为正确性保证。[S1][S2]

### 10.4 传输真的断开

服务端取消该连接的读写任务、释放其队列与订阅句柄，保留权威角色与必要的会话恢复元数据。不要通过保留失效 Socket、任务或无界 channel 来“保留角色”。

客户端采用带抖动的退避重连，前台可较积极，后台应拉长间隔。重新可见时可立即尝试一次。认证失败、被新连接替代、封禁、会话已终止等明确结果必须停止相应的自动重试，避免循环抢占角色。

网络 `online` 或 WebSocket `open` 只触发恢复尝试，不直接宣布“恢复成功”。

### 10.5 代理排查

若仓库使用 Nginx，核查 WebSocket Upgrade 与实际 `proxy_read_timeout` 配置。Nginx 文档说明默认上游无数据超时为 60 秒，服务端定期 Ping 可重置该超时。[S8]

若不是 Nginx，检查实际代理的等价配置。不要给项目新增无关代理，也不要把十分钟角色宽限误配置成“所有网络层超时必须大于十分钟”。

## 11. 服务端所有权：一个角色只能有一个有效控制连接

### 11.1 最小职责划分

| 现有模块职责 | 需要增加或调整的能力 |
| --- | --- |
| 连接管理 | 只管理传输与当前绑定，不拥有角色永久生死 |
| 会话或角色注册表 | 通过鉴权后的角色身份找到现存角色，支持原子接管 |
| World / Scene 更新入口 | 串行处理角色参与状态、输入、到期与离场 |
| 广播 / AOI | 暂离角色仍作为实体对外发布；本人订阅可独立降级 |
| 数据持久层 | 复用资产、任务、死亡与位置的原有落地策略 |
| 正常退出处理 | 统一处理主动退出与驻留到期，保证幂等清理 |

优先复用已有 World 单线程循环、命令队列或锁边界。**不要求为了本需求改成“每个角色一个 Actor”或重写整个后端架构。**

### 11.2 必要标识

建议利用现有字段实现以下等价能力，避免重复发明：

| 字段 | 用途 |
| --- | --- |
| `character_id` | 持久角色身份；不能单独作为恢复凭证 |
| `session_id` | 当前角色驻留会话身份，区分服务器重启或重新入场后的新会话 |
| `connection_epoch` | 本会话控制连接的递增代际，拒绝旧连接命令与迟到关闭事件 |
| `away_id` | 同一次连续暂离的身份，用于计时窗口与提示去重 |
| `sync_id` | 本次同步尝试身份，拒绝过期快照确认 |
| `client_seq` | 同一连接代际中的输入/控制消息序号，用于乱序、重复或过期检测 |
| 快照基线与流序号 | 保证增量只能应用于对应基线 |

Rust 的 `u64` 等大整数标识在 JSON 中建议编码为十进制字符串或不透明字符串，避免前端数值处理丢失身份精度。协议中要统一编码约定；不要部分字段是数字、部分字段是字符串却没有转换规范。

### 11.3 原子接管规则

成功鉴权的新连接接管现存角色时，在同一权威修改边界内：

```text
验证账号拥有角色 + 会话尚可恢复
    → 核对暂离期限与场景状态
    → 递增 connection_epoch
    → 绑定新连接
    → 清除旧连接输入、同步尝试与发送资源
    → 新连接进入同步中，尚不能控制角色
    → 关闭旧连接或发送“已在其他连接恢复”结果
```

所有游戏命令、生命周期报告、快照确认和关闭事件都要携带或关联绑定代际。旧连接关闭时，仅当它仍是当前绑定，才允许修改连接状态；不能无条件对 `character_id` 执行删除。

正常登录入口也必须复用同一角色唯一性约束，不能“恢复入口防重复，普通登录入口却又创建一个同角色实体”。

### 11.4 多标签页与恢复竞争

首版建议采用“最后一个完成合法接管的连接获得控制权”。旧客户端收到 `SESSION_REPLACED` 后停止自动重连，不与新页面无限互踢。

可在浏览器同源页面间增加提示，但它只是体验优化，不承担角色唯一性的安全保证。服务端必须独立阻止双重控制。

## 12. 协议契约：复用现有消息，补齐缺失语义

### 12.1 建议消息集合

| 方向 | 逻辑消息 | 必须表达的内容 |
| --- | --- | --- |
| C → S | `ClientLifecycle` | 当前代际、序号、可见性或主动暂离意图；客户端时间只作诊断 |
| C → S | `InputReset` | 当前代际、序号；原子清除持续输入 |
| C → S | `ClientProgress` | 当前绑定、已应用基线/序号；可复用应用心跳 |
| C → S | `ResumeSession` | 现有认证材料或恢复凭证、角色/会话目标；不接受客户端指定位置和血量 |
| C → S | `RequestSync` | 本次目的：查看、宽限内自动继续、明确继续；最近已知基线 |
| C → S | `SnapshotApplied` | 当前代际、`sync_id`、快照基线；只确认确实已经应用的状态 |
| C → S | `KeepAway` | 当前代际、`away_id`；不重置任何暂离时间 |
| S → C | `PresenceState` | 阶段、`away_id`、服务端时间、截止时间、场景限制与恢复要求 |
| S → C | `SyncSnapshot` | `sync_id`、基线、当前角色/地图/必要业务状态与所属会话 |
| S → C | `ResumeGranted` | 当前代际、`sync_id`、流基线与控制权生效确认 |
| S → C | `ResumeRejected` | 可判定的原因与下一步：重试同步、重新登录、会话结束、被替代等 |
| S → 周围玩家 | 现有角色状态增量 | 暂离显示状态，不另生成第二个人物 |

生命周期事件的接收应同时清输入，不依赖独立 `InputReset` 一定先到达。

### 12.2 示例语义，不锁死序列化格式

```ts
type PresenceMode = 'active' | 'away_grace' | 'away_idle' | 'leaving';

type PresenceState = {
  type: 'presence_state';
  sessionId: string;
  connectionEpoch: string;
  mode: PresenceMode;
  awayId: string | null;
  serverNowMs: number;
  fullRetentionUntilMs: number | null;
  residencyUntilMs: number | null;
  requiresExplicitContinue: boolean;
  scenePolicy: 'standard' | 'restricted';
};

type SyncPurpose = 'inspect' | 'auto_continue' | 'explicit_continue';

type RequestSync = {
  type: 'request_sync';
  connectionEpoch: string;
  clientSeq: number;
  purpose: SyncPurpose;
};

type SnapshotApplied = {
  type: 'snapshot_applied';
  connectionEpoch: string;
  syncId: string;
  baselineSeq: string;
};
```

这些定义仅展示协议契约。若仓库使用二进制协议、共享 schema 或代码生成，应在原机制中增加字段，而不是额外建立第二套 JSON 通道。

`explicit_continue` 表达界面的继续意图，不是“人类操作证明”。服务端仍须执行鉴权、同步、场景和输入合法性校验。

## 13. 恢复顺序：先认人，再同步，再交还控制权

### 13.1 十分钟内返回

```text
页面重新可见
    → 清空旧输入与客户端预测残留
    → 检查当前连接；必要时重连并重新鉴权
    → 绑定原角色，不新建角色
    → 请求 auto_continue 同步
    → 服务端捕获一致的权威快照与同步基线
    → 客户端应用快照，重置预测/插值，再确认 SnapshotApplied
    → 服务端再次检查身份、代际、期限和场景
    → 下发必要的有界追赶增量及 ResumeGranted
    → 客户端按顺序处理完成，开放输入
```

若恢复确认时已经达到十分钟，自动继续被拒绝为 `EXPLICIT_CONTINUE_REQUIRED`，转入暂离提示。不能凭恢复前的旧倒计时放行。

### 13.2 十分钟后返回

```text
页面重新可见
    → 鉴权和绑定检查
    → inspect 同步：只取得当前状态，不恢复参与
    → 显示真实角色状态与暂离提示
    → 点击“继续冒险”或进行明确唤醒操作
    → explicit_continue 同步或经校验的当前基线续接
    → 服务端复核后发出 ResumeGranted
    → 结束本次 away_id，进入 Active
```

选择“保持暂离”时不结束 `away_id`，不延长驻留上限，并回到最小订阅。

### 13.3 一致快照与增量接缝

快照要来自同一个服务端逻辑时点，不能位置来自 Tick A、背包来自另一笔尚未确认的事务、地图却来自迁移之前。

沿用已有的同步基线机制；若缺失，至少补齐：

1. 捕获快照基线 `S`，记录本次 `sync_id`。
2. 快照之后的增量使用同一流的有序序号，且缓冲有界。
3. 客户端确认已应用 `S`，服务端复核后，按同一有序发送通道排入所需追赶增量与 `ResumeGranted`。
4. 客户端必须处理完 `ResumeGranted` 前的相关增量，才能开放输入。
5. 不要求“客户端永远追上不断增长的最新 Tick 才能恢复”；只要求基线与接缝一致，之后按正常实时同步继续。
6. 增量缺失、缓冲超限、地图迁移、`sync_id` 过期时废弃本次同步并重发新的完整快照。

**不要把恢复做成无限追赶，也不要在一次同步失败后继续拼接不兼容的增量。**

### 13.4 必须恢复的当前事实

最少包括：当前地图/频道/相位、位置与运动状态、血量/死亡状态、Buff 与冷却期限、关键任务与资产版本、队伍归属、参与阶段及场景限制。

客户端只恢复这些事实的展示。不能上报“我离开前的血量和背包”，让服务器据此覆盖当前状态。

### 13.5 恢复失败必须是正常路径

| 失败原因 | 客户端行为 |
| --- | --- |
| 登录态失效 | 提示重新登录；不持续匿名重连 |
| 暂离驻留已结束 | 进入正常角色入场流程，显示结束原因 |
| 服务器会话不存在或已经重启 | 按持久数据重新进入；不宣称无缝恢复 |
| 角色已被新连接接管 | 停止自动重连，提示已在其他页面或设备恢复 |
| 副本结束、地图不可恢复 | 按服务端现有迁移/退出规则进入合法场景 |
| 同步基线失效 | 请求新快照，仍保持输入关闭 |
| 本次恢复超时 | 取消本次 `sync_id` 与缓冲；允许有退避地重试 |
| 封禁或权限撤销 | 执行现有拒绝与退出规则 |

连接状态恢复可能失败，因此完整同步与失败分支不是可选补丁。[S6]

## 14. 后台数据策略：有界、可合并、可重同步

### 14.1 按数据语义分类

| 数据 | 后台策略 | 恢复方式 |
| --- | --- | --- |
| 位置、朝向、外观、可替代的完整实体状态 | 可合并为较新值 | 当前快照 |
| 有基线依赖的地图增量 | 不能随意丢中间片段 | 缺口时重发基线快照 |
| 伤害飘字、普通音效、临时粒子 | 不积压十分钟，允许丢弃 | 不补播 |
| 本人受伤、死亡、地图迁移、参与阶段 | 有界更新；保留最新权威状态 | 当前快照与必要摘要 |
| 背包、奖励、任务和交易结果 | 由原业务状态/记录承载，不能只放 Socket 队列 | 查询当前版本与操作结果 |
| 聊天与通知 | 复用已有历史/未读策略 | 拉取有限窗口；若原项目无历史，明确缺口，不能假称完整恢复 |

### 14.2 队列硬边界

传统 WebSocket 没有自动替应用解决接收背压问题。[S4] 必须给以下层级设置并测试上限：

- 服务端应用未发送队列：限制字节数与条数，状态更新能合并则合并。
- 已发送但客户端未确认的游戏状态窗口：超限后暂停生产，不再无限发送。
- 客户端未应用队列：达到上限则丢弃可丢弃表现，并请求快照修复状态流。
- 单次同步快照与追赶缓冲：单独限制大小、块数与总超时；大快照不能绕过总体内存预算。

具体字节值先测量当前最大地图快照与正常流量，再配置。没有测量前不得承诺一个通用数字足够所有地图。

已写入 WebSocket/TCP 的旧数据不能靠删除应用队列撤回。因此要在写入前限制生产，并根据应用确认进度控制发送。持续失去处理能力时可关闭该传输再恢复，角色继续按驻留规则保留。

### 14.3 业务幂等

断线时已经发出但没收到结果的购买、领奖、交易确认等命令，必须查询既有操作结果，或使用稳定的业务操作标识做幂等重试。

同一操作标识不能因为换了连接代际就被当作新交易；普通移动输入则不重试、不补发。若现有高价值操作没有幂等保障，应先补齐对应入口，不能把“重连成功”当作资产一致性已解决。

## 15. 交互与文案

### 15.1 对其他玩家的展示

- `AwayGrace`：可显示轻量“暂时离开”标记，不必改变角色主体外观。
- `AwayIdle`：名称旁显示“暂离”，队伍/好友列表显示相同语义。
- 不公开具体窗口行为、应用名称或精确离开时间，只展示必要的参与状态。
- 其他玩家仍按正常规则与其发生碰撞、战斗或社交请求；暂离状态不得自动替本人接受邀请、交易或队伍准备。
- 正式离场后广播真实离场，不能只删本人连接却在旁观者端残留永久假人。

### 15.2 十分钟内返回

同步顺利时不强制弹窗。若需要展示过程，使用“正在恢复当前世界状态……”；失败则展示具体结果。

连接尚未恢复时，不写“角色一定仍在原地”，因为服务器和场景状态尚未确认。可显示：“连接中断，正在尝试恢复角色会话。”

### 15.3 十分钟后、安全区域提示

```text
你已离开超过 10 分钟

角色已进入暂离驻留，其他玩家仍可看见你。
世界继续运行，角色状态已同步。
继续冒险后，将恢复正常交互。

[继续冒险]  [保持暂离]
```

仅在服务端确认驻留仍有效、当前快照已成功应用后使用上述文案。可附加服务端给出的预计驻留截止时间；剩余时间只是展示，真正到期由服务器裁决。

若状态为死亡、已迁移地图、实例结束等，用对应真实结果替换通用描述。例如：“暂离期间角色已死亡，请按当前场景规则处理。”

### 15.4 危险区域提示

使用不遮挡主要视野的横幅，而不是阻塞全屏弹窗：

```text
你已离开超过 10 分钟，当前处于暂离驻留。
危险地图中仍可能受到伤害。点击继续或按游戏操作键恢复。
[继续冒险]
```

第一次唤醒只恢复参与，不执行原技能或交易。同步未完成前明确显示“恢复中”，不要让玩家误以为已经获得控制。

### 15.5 保持暂离后的画面

选择“保持暂离”后显示持续但不打扰的状态条：“暂离驻留中，画面非实时；继续冒险后恢复实时交互。”

本人关键状态可继续有限更新。若没有实时地图订阅，不把静止怪物和旧地图画面伪装成实时世界。在危险区保持暂离仍承担正常后果。

### 15.6 提示去重

以 `session_id + away_id` 识别一次暂离。重复网络恢复或重复状态包不反复弹同一个模态框；可保持状态条或返回时的轻提示。新的暂离窗口可以再次提示。

前端“已经展示过”只影响界面，不影响服务端恢复权限、截止时间或参与阶段。

## 16. 驻留回收、容量与正常退出

### 16.1 到期不是突然删除

建议测试配置：从首次暂离起，600 秒进入基础驻留，3600 秒请求正常离场。

```text
达到驻留上限
    → 标记 Leaving，拒绝新的业务与恢复接管
    → 按正常退出规则处理战斗、交易、实例及必要持久化
    → 广播实际离场
    → 释放角色运行态与恢复元数据
```

进入 `Leaving` 后，默认不再抢回同一会话；完成退出后走正常重新进入路径，避免清理与恢复相互覆盖。

### 16.2 战斗收尾必须复用统一规则

不能为了暂离新建“到点自动无敌消失”的捷径。沿用手动退出的战斗延迟、死亡、处罚或返回点规则。

同时不能让“每次被攻击都无限延长退出”导致永远不回收。若既有退出规则没有可终止的收尾边界，必须先补齐**统一退出策略**，使手动退出和暂离到期遵守同一规则。没有安全策略的特殊场景不应悄悄启用长期驻留。

正常运行时应有可验证的回收上界。存储故障等异常下，以资产一致性为先，报警并按现有故障策略限制新负载，不为了准点删除而丢失已确认数据。

### 16.3 场景生命周期

以下场景不能因“已连接客户端数为零”而立即销毁：

- 仍有在宽限内的角色。
- 仍有允许基础驻留的角色。
- 仍有必须完成的权威事件或退出收尾。

场景回收应综合实际实体、业务生命周期和到期策略。暂离检查也不能依赖一个已经因零连接而停止的场景 Tick。

### 16.4 容量限制

基础驻留仍占用实体与场景容量，不得从容量统计中隐身。每角色唯一性、会话总量和场景驻留量应沿用现有限制并补齐监控。

若要在高负载时提前回收基础驻留角色，应作为单独明确的产品策略，带提前提示与一致退出流程。首版不默认这样做，更不能把“十分钟保留”在普通负载下变成随时可撤销的承诺。

## 17. 安全、竞态与异常清单

| 风险 | 必须具备的处理 |
| --- | --- |
| 伪造隐藏/可见事件 | 仅影响会话策略，不授予资产、无敌或特殊收益 |
| 冒用角色 ID 恢复 | 使用现有登录认证与角色归属校验，不能凭 ID 接管 |
| 凭证泄漏 | 沿用安全传输与凭证机制，不把恢复凭证写入 URL、普通日志或公开指标 |
| 旧连接继续发攻击 | 会话身份与连接代际双重核对，旧消息拒绝 |
| 旧连接迟到关闭 | 仅当前绑定可改变连接状态，不能按角色 ID 无条件清理 |
| 旧生命周期消息覆盖新状态 | 代际与控制序号检查；当前暂离窗口不得被过期消息重置 |
| 同 Socket 恢复时旧输入残留 | 隐藏/恢复时清输入；输入门禁、序号与新鲜度校验；必要时复用输入代际 |
| 多次同时发起恢复 | 每个当前绑定最多一个有效 `sync_id`；新尝试取消旧尝试及其缓冲 |
| 同一角色重复创建 | 普通登录和恢复共用唯一的角色注册/接管边界 |
| 自动重连无限抢占 | `SESSION_REPLACED` 为终止性结果，旧客户端不自动夺回 |
| 600 秒或驻留到期的竞态 | 在恢复提交和游戏命令入口再次按当前时间判定 |
| 地图迁移期间恢复 | 以当前权威归属为准，废弃旧地图基线 |
| 已发请求结果不明 | 查业务结果或以稳定操作 ID 幂等重试，不重放整段网络缓存 |
| 广播失败触发角色删除 | 审计所有发送失败、写超时、背压和 `Drop` 路径，不仅修改一个 `on_close` |
| 浏览器保留的 Socket 看似 OPEN | 返回时验证应用会话响应；超时则重新绑定，不能只看 `readyState` |
| 页面被回收无通知 | 服务端失联检测与原角色恢复兜底 |
| 维护、封禁、实例结束 | 走明确的既有政策与错误码，不能被暂离机制绕过 |

## 18. 分阶段开发任务

> 各阶段是开发顺序，不表示可以把未完成的半套会话机制直接上线。默认置于功能开关后，最小端到端安全链路通过后再启用。

### P0：定位现状，建立基线

- [ ] 找到前端生命周期、心跳、输入、恢复及服务端清理的实际入口。
- [ ] 复现并区分主动关闭、心跳超时、代理超时、页面冻结和纯渲染暂停。
- [ ] 核对场景空闲回收、角色唯一性、现有快照与正常退出规则。
- [ ] 记录当前双客户端行为、服务端关闭原因、队列和角色计数。
- [ ] 提交实际文件/函数修改清单，不在未知位置盲目新建同名模块。

**完成标准**：能够解释“目前为什么切出去就掉线”，且解释有代码或日志证据。

### P1：最小角色驻留内核与输入安全

- [ ] 从连接生命周期中分离权威角色生命周期。
- [ ] 引入单一暂离事实窗口和服务端时间派生阶段。
- [ ] 清理失焦输入，并增加持续输入租约。
- [ ] 将发送失败和连接关闭改为解绑/暂离，而不是直接删角色。
- [ ] 角色驻留期间场景不因零 Socket 立即回收。
- [ ] 为清理、角色接管和所有控制消息增加代际保护。

**完成标准**：真实断线后观察者仍能看到原角色，旧输入不会无限执行，实体数量不增加。

### P2：网络与后台订阅解耦

- [ ] 心跳、生命周期管理和关键应用消息不依赖渲染 Tick。
- [ ] 区分传输响应、应用进度和参与状态。
- [ ] 隐藏页面立即降低无用渲染与表现流量。
- [ ] 应用进度停滞时暂停高频推流，设置队列和确认窗口上限。
- [ ] 核查实际代理超时；仅调整项目正在使用的链路。

**完成标准**：后台或冻结客户端不会导致无限积压；正常切窗口不主动退出。

### P3：同角色重连与一致恢复

- [ ] 新连接经过鉴权后接管原角色，而不是创建替身。
- [ ] 补齐快照基线、`sync_id`、应用确认和 `ResumeGranted` 门禁。
- [ ] 加入十分钟内自动继续、十分钟后明确继续的最终时刻校验。
- [ ] 清理预测、插值和旧命令缓存；不补播历史战斗表现。
- [ ] 实现会话失效、实例结束、同步失败等明确恢复分支。
- [ ] 验证重连中的资产事务不重复执行。

**完成标准**：断网或页面重载后恢复当前角色事实，控制连接唯一，旧关闭事件无副作用。

### P4：十分钟基础驻留与交互

- [ ] 达到 600 秒后发布基础驻留阶段。
- [ ] 旁观者、好友与队伍显示“暂离”语义。
- [ ] 安全区使用提示框，危险区使用非阻塞横幅。
- [ ] “保持暂离”不续时、不重新开放交互。
- [ ] 唤醒输入不触发额外技能、交易或拾取。
- [ ] 同一次 `away_id` 的提示去重，状态条反映非实时画面。

**完成标准**：12 分钟返回时看到真实状态与明确选项；旁观者看到的仍是同一个角色。

### P5：驻留上限、清理与全链路测试

- [ ] 增加独立的总驻留上限配置，按统一退出规则收尾。
- [ ] 验证无连接、无人观察、地图迁移、死亡与存储故障分支。
- [ ] 测试所有队列、同步缓冲、连接任务和会话元数据能回收。
- [ ] 完成下一节中的 P0 必测用例。
- [ ] 通过功能开关启用完整链路，记录性能与恢复指标。

**完成标准**：不会无限驻留、无限缓存、重复奖励、双重控制或误删新连接角色。

## 19. 测试与验收矩阵

### 19.1 自动化原则

时间逻辑使用注入时钟或可控 `now` 测试，不让单元测试真的等待十分钟。浏览器后台和冻结另做真实环境验证，不能用模拟时钟结果代替浏览器验证。

双客户端用例中：A 为暂离者，B 为同地图观察者。既检查服务端实体数量与阶段，也检查 B 的实际可见性，不只检查 A 本地画面。

### 19.2 核心用例

| ID | 优先级 | 场景 | 验收结果 |
| --- | --- | --- | --- |
| T01 | P0 | A 失焦但游戏仍可见，持续 12 分钟 | 不主动断线；不因仅失焦进入暂离；输入被清理 |
| T02 | P0 | A 切标签 5 分钟后返回 | 同步后自动继续，无十分钟提示，不重新建角色 |
| T03 | P0 | A 隐藏 12 分钟，B 一直观察 | A 达到基础驻留，B 仍看见同一个带暂离标记的角色 |
| T04 | P0 | A 隐藏 12 分钟后返回安全区 | 先同步当前状态，再显示提示；点击继续后开放输入 |
| T05 | P0 | A 选择保持暂离，前台停留并继续心跳 | 仍暂离，原始计时和总驻留期限不变 |
| T06 | P0 | 按住向右/攻击时切出 | 立即重置或租约到期停止意图，不无限移动或攻击 |

## 20. 观测、上线与回滚

### 20.1 最少观测项

| 指标或日志 | 用途 |
| --- | --- |
| 当前正常参与 / 宽限 / 基础驻留 / 离场中角色数 | 区分人数与连接数，观察驻留是否膨胀 |
| 当前传输连接数、应用停滞数 | 识别“Socket 通但应用不处理”的情况 |
| 恢复尝试、成功率和耗时分位数 | 衡量恢复链路质量 |
| 恢复失败原因 | 区分认证、到期、替代、基线、场景错误 |
| 旧代际消息拒绝与旧关闭事件忽略次数 | 验证竞态防护，也发现异常重连循环 |
| 每连接队列字节、未确认窗口、重同步次数 | 检查背压与内存风险 |
| 暂离角色正常离场数量与收尾耗时 | 发现无限驻留或清理卡住 |
| 角色重复创建或控制权冲突 | 应为零；非零立即阻止扩大启用范围 |

角色和会话标识适合结构化日志定位，不直接作为高基数指标标签；日志中不输出认证或恢复凭证。

### 20.2 最小上线路径

先在开发环境完成双客户端纵向链路，再按实际支持的普通地图启用，随后验证危险地图和已有特殊实例策略。

以功能开关控制新策略，但身份代际校验、输入租约和资产幂等这类安全修复不应因关闭暂离策略而一并撤销。

### 20.3 回滚原则

停止新建暂离窗口时，已驻留角色按已公布的窗口或统一退出流程收尾。不能关闭开关就瞬间删除所有角色，也不能遗留永不清理的旧状态。

协议混合版本必须有明确能力协商或兼容策略。旧客户端不支持恢复门禁时，按受控的旧版本行为或要求更新处理；不能收到未知消息后无限重连。

### 21.2 不可退让的验收条件

> **同一个角色、一个有效控制者、一份权威事实、有限的资源占用。**

不得出现：失焦就退出、十分钟旧输入代玩、切屏无敌、冻结 Buff、重连重复发奖、旧关闭误删新角色、后台无限队列、零 Socket 销毁仍有驻留角色的场景。

### 21.3 给执行代理的实施指令

先核对仓库现有生命周期、输入、Socket 清理、角色注册、快照和退出入口，给出有证据的根因；然后按 P0—P5 实现最小完整链路。复用原架构与协议，不引入新的多人游戏框架或独立挂机系统。

所有恢复都从服务端当前角色事实出发。先保证角色唯一性、输入安全和恢复一致性，再优化后台流量；不得用延长一个 timeout 代替完整方案。测试报告要区分“文档设计”“实际实现”“已通过测试”和“尚未验证”。
