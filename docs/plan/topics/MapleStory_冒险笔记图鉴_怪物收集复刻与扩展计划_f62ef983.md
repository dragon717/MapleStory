## 0. 先读这一页

### 0.1 用户明确要求

复刻现代冒险岛的**怪物收集**功能，并新增**装备图鉴、道具图鉴、已收集／获得的任务道具图鉴**。四者共用怪物收集界面的视觉与交互基础；复用菜单栏原“怪物收集”入口，将可见名称改为 **`冒险笔记（图鉴）`**。不新增第二个主入口，不只改提示文字。

核心落地原则：

> **一个入口，一个窗口；怪物按收藏规则登记，物品按实际获得事实留档。共用 UI，不混用业务规则。**

### 0.2 仓库里最重要的四个发现

| 发现 | 证据与影响 |
|---|---|
| 菜单框架已有，但没有接通怪物收集动作 | `MenuView.activateEntry` 当前没有这一回调，未匹配动作进入“尚未实装”；需要接入新窗口，不是改名即可完成。[S05] |
| 菜单可见文字来自图片 | `createAssetButton` 只写 `title`、`aria-label` 并放入图片；仅改 `entry.label` 不会替换图片上的旧文字。[S05] |
| `monster_book_cards` 不是现代 Monster Collection 的现成实现 | `Store::pickup` 中的旧卡片按 `consume_on_pickup` 消耗，并把数量封顶为五；注释明确引用 Cosmic 的 MonsterBook 行为。不能直接改表名冒充现代怪物收集。[S07][S08] |
| 获得物品没有一个现成的全覆盖、全事务入口 | 拾取和现金商店有事务；任务会整包写背包；普通商店购买先改内存、再分别保存背包和角色资料且忽略错误。必须分别接入，商店路径先补事务边界。[S07][S09][S10][S11] |

### 0.3 实施顺序

先核定同版素材和菜单身份，再建立“获得事实”及事务边界，然后实现四页共用窗口，最后补齐原版勋章、奖励、探险及相关道具。登记／浏览阶段可单独交付验证，但**不能把“怪物亮图标”称为完整怪物收集复刻**。

本文所有新增文件名、消息名、表名均为**拟新增设计**，不是声称仓库已有。现有文件与已核实函数在第 1、10、14 节单独标出。

## 2. 需求边界与产品规则

### 2.1 四个页签

| 页签 | 登记依据 | 登记后物品／怪物是否被消耗 | 永久记录 | 默认浏览范围 |
|---|---|---|---|---|
| 怪物收集 | 服务端判定符合该收藏条目的击杀／原版收藏道具使用条件，再执行已核定登记规则 | 不增加额外献祭怪物／交卡要求；收藏道具是否消耗按同版规则 | 保留收藏登记，不因换图／重启丢失 | 同版原始地区、页、行与条目；明确标出尚不可收集内容 |
| 装备图鉴 | 角色实际获得目录中对应装备模板 | 不消耗装备，不要求穿戴 | 出售、丢弃、交易、过期后仍保留 | 已开放装备的全部／已获得／未获得筛选 |
| 道具图鉴 | 角色实际获得目录中对应道具模板 | 不消耗道具，不要求使用 | 使用、提交、丢弃后仍保留 | 已开放普通道具的全部／已获得／未获得筛选 |
| 任务道具 | 角色实际获得被同版资料或明确任务语义证明为任务专用的道具 | 不为登记额外消耗，正常任务仍按原逻辑交付 | 交付、任务结束、过期后仍保留 | **仅展示已获得条目**，不列未获得名称、图标、问号格及总分母 |

装备图鉴按**模板**登记，不按背包槽位、强化次数、随机属性或装备实例数量拆成多条。三个新增物品图鉴本期没有套装属性、收集加战力、提交物品、累计刷取数量领奖、探险或抽概率登记。

### 2.2 “获得”不是“持有”，也不是“看见”

满足下列语义才记录：权威业务成功地把一件真实物品授予当前角色，或可信存档能证明该角色曾经持有它。

不构成获得：商店预览、地图掉落出现但未拾取、队友拾取、任务奖励候选列表、图鉴预览、创角界面的未确认试装、发出购买请求但购买失败。

已经获得后，出售、穿脱、整理、拆堆、存取自己的仓库、消耗和移出背包都不能撤销历史。不得通过每次打开窗口扫描“当前背包”代替这一事实。

“当前持有数量”不是本期必要字段。后续展示时必须明确是背包／穿戴／仓库的实时投影，不能覆盖“曾经获得”的记录。

### 2.3 归属范围：本计划明确采用的默认值

用户没有指定跨角色共享方式，以下为 **P：实施默认方案，不冒称用户额外指令或 TMS273 已核定事实**：

| 数据 | 默认归属 | 原因 |
|---|---|---|
| 怪物收藏、其奖励资格和探险 | 同一登录账号、同一世界内共享；同版核定时复核 | 保留现代收藏的账号级结构；当前官方外服资料仅能支持结构对照，不能证明台服同期全部细则 |
| 新增装备／道具／任务道具获得记录 | 当前角色 | 最小范围记录“这个角色实际获得过什么”，防止任务剧情跨角色提前暴露；未来账号汇总可基于角色事实投影 |
| 页签、筛选、窗口位置 | 客户端偏好，按登录身份隔离 | 不是权威业务状态，不必每次写服务器 |

当前部署按一个数据库承载一个世界处理；**不得把 `CHANNEL_ID = 1` 当作全局世界 ID**。未来一库多世界时再显式扩世界键，不为本功能先重做多世界架构。

UI 清楚显示“怪物收集：本世界账号共享”“物品记录：当前角色”。若后续确认三类物品也应账号共享，保持角色获得事实不变，再增加授权后的账号聚合视图；任务道具是否跨角色展示需单独决策，不能暗中改变。

### 2.4 道具分类必须读数据，不凭号段猜测

物品目录保存 `inventoryType`／装备部位等原始属性，以及独立的 `questSpecific` 标签和其证据。规则如下：

1. 装备页按真实装备定义识别；部位继续使用 `info.islot` 等已验证信息。
2. 普通道具页覆盖当前可获得的消耗、设置／装饰、其他及现金非装备道具；同版目录中独立存在的宠物物品可按标签展示，不在此新建宠物养成系统。
3. 任务页由明确的任务专用标记或同版任务授予／交付语义支持。应先核对 `info.quest` 等候选字段的实际含义，不能把“字段名看起来像”当成证据。
4. **普通掉落材料被一个任务需要，不等于任务专用道具。** 这类材料仍在普通道具页，可显示有依据的任务用途；不自动把所有 Etc 都搬进任务页。
5. 任务专用装备确实存在并有证据时，可同时出现在装备页和任务页；两处引用同一获得事实，不重复存储，不把四个页签数量相加冒充独立总数。
6. 不收录枫币 `0`、纯脚本变量、技能、脸型／发型等非物品 ID、测试占位物、无真实定义的猜测号段。

任务页不能通过一次“接任务”就批量解锁所有关联物品，也不能根据“任务已完成”猜玩家领取了所有可选奖励。

## 3. 原版怪物收集：复刻范围与证据门槛

### 3.1 已确认的结构与尚未确认的数值

台服官方历史“怪物收藏”说明明确列出条件触发自动登记、阶段勋章、收藏后探险及探险奖励，也介绍了收藏蛋和方块椅。[O01] 当前韩国官方指南还描述了地区／行／页组织、同世界角色共享、行与页奖励等结构。[O02]

**采用边界：** [O01] 是台服历史说明，不是 TMS273 完整数值文档；[O02] 是当前跨区指南，不能把其中的当前等级门槛、每日领奖上限、槽位数等直接搬入 TMS273。本计划用它们防止遗漏功能，用同版资源和执行依据决定具体实现。

### 3.2 必须规划的原版能力

| 能力 | 目标 | 同版核定内容 |
|---|---|---|
| 收藏目录 | 地区、页、行、怪物格、登记状态、稀有度／条件提示 | 条目全集、顺序、稳定收藏 ID、模板／变体映射、星级含义 |
| 击杀登记 | 服务器对有效死亡结算进行符合条件的登记 | 击杀归属、组队资格、等级／怪物类型限制、概率及修正、不能登记的实例类型 |
| 特殊条目 | 精英、Boss、脚本变体等按真实条件匹配 | 不能只按名字相同就认为是同一收藏目标 |
| 行／页完成奖励 | 服务器判定资格和一次性领取 | 奖励键、完成条件、奖励数量、收件角色限制 |
| 勋章 | 阶段／区域条件满足后展示与领取 | 勋章 ID、阈值、是否可重复领取及适用范围 |
| 探险 | 已满足条件的收藏组合进入探险，离线时间持续计算，完成后领取 | 槽位解锁、组合排他性、时长、领取／再出发语义、奖励表及版本 |
| 收藏相关道具 | 已在同版存在且被本功能使用的收藏蛋／指定登记道具等 | 实际道具效果、目标限制、重复／全满处理、消耗条件 |
| 登记反馈 | 首次成功有图标、提示及同版音效／效果 | 素材节点与时间轴；避免重复通知 |

原版机制所需的奖励物品按核定来源补入现有物品目录和获得链路，不借机扩展无关商城、掉落经济或任务线。

### 3.3 数据缺失时的处理

同版概率未查到，不能填 `100%` 或凭感觉填写“约几千分之一”。登记可以在可控测试夹具中用注入结果验证，但正式内容配置保持 `unverified`，受影响操作说明“该收藏规则尚未核定”，不伪装已完成。

同版探险数据未查到，先完成目录、获得事实和四页窗口的可运行闭环；探险任务仍保留在当前计划为阻塞，不删除需求。完成声明应精确到“阶段 A：浏览与登记”或“阶段 B：奖励／探险已完成”。

原始页里某些怪物尚未进入项目可玩地图时：保留条目及原始行／页身份，标明“当前版本尚不可收集”；**不能删除缺失条目后让该行提前达成原版奖励资格**。

## 4. 架构：共用界面，不把四种内容硬塞成同一种系统

### 4.1 职责图

```text
同版 WZ／JSON／核定规则
    ├─ 收藏界面资源：背景、格子、页签、按钮、效果
    ├─ 怪物收藏目录与规则：条目、条件、奖励、探险
    └─ 物品图鉴目录：模板、分类、名称、图标、已核实来源
                    ↓ 导出校验／版本装配
客户端 NotebookView                     Rust 权威 World
    ├─ 共用窗口／浏览控件                  ├─ 接收查询与合法操作意图
    ├─ MonsterSection 适配器              ├─ 有效击杀 → 收藏规则
    ├─ ItemSection 适配器                 └─ 物品业务 → 实际正向授予事实
    └─ 任务页仅展示已获得                  ↓ 调用当前业务 Store 事务
                    ← 私有查询／通知 ← SQLite
                                              ├─ 怪物登记事实
                                              ├─ 角色获得物品事实
                                              └─ 奖励资格／领取／探险状态
```

只增加普通数据结构、纯规则函数及已有 World 内的编排。不要新建通用事件总线、消息中间件、通用图鉴平台、每条目一个类或深层继承体系。

### 4.2 三个不能混淆的层次

**目录：世界中有哪些可展示的条目。** 来自版本化内容文件，不随玩家背包增减而改变。

**事实：这个账号登记过哪个怪物、这个角色获得过哪个物品。** 来自服务器持久化，不由客户端写入。

**视图：在当前页签如何排列、筛选、显示进度。** 可随目录版本和屏幕变化重建，但不能反向修改事实。

“装备页看起来和怪物页相同”并不表示装备也要抽登记概率；“任务页也是物品”也不表示它应该公开未获得的全部任务内容。

### 4.3 访问权限

新持久化 helper 接受已有 `&rusqlite::Transaction<'_>`，通常只在 auth 子树可见。跨模块已有事务（例如创角事务）确需调用时，用明确的 crate 内部入口，不开放客户端“put／unlock／register”接口。

不得在持有 `Store.db` 的事务里再次调用会锁同一个 `Mutex` 的公开 Store 方法。也不要在保存整个角色资料、背包整理或普通加载时暗中触发新增收藏逻辑。

文件名是建议；不得为了遵守命名重复创建已有等价导出器。实施者先核对新增期间的 HEAD。

### 5.3 目录键与别名

服务端和数据库使用唯一规范化键，例如物品 `1302000`；图片与原始源可保留 `01302000` 等别名。规范化只接受合法十进制 ID，通过字符串规则去除多余前导零，再查真实目录。不得用浮点转换接受指数、负数、空串或任意 ID。

`assemble_tms273.cjs` 已保留一部分七位／八位物品别名；图鉴生成必须去重，不能把别名算成两种装备。[S14]

怪物使用独立稳定的 `collectionEntryId`。该键与怪物模板、运行实例、显示名称分离：

```text
monsterInstanceId：本次出生／死亡实例，用于一次性结算
monsterTemplateId：运行怪物模板，用于匹配条件
collectionEntryId：同版收藏目录条目，用于永久登记和行／页归属
```

同名怪物可能不是同一个收藏条目；同一模板在不同变体条件下也不能无条件归并。只能导出明确匹配关系，不能把 WZ 图片 `link` 直接当成收藏身份归并依据。

### 5.4 模板字段示意

以下为字段契约示意，不是可直接替代同版数据的样例配置：

```ts
interface NotebookItemDefinition {
  itemId: string;                 // 唯一规范化物品模板 ID
  inventoryType: number;          // 来自真实物品定义
  questSpecific: boolean;         // 分类与证据一起生成
  questClassificationEvidence: string[];
  nameRef: string;
  descriptionRef?: string;
  iconRef: string;
  equipmentSlot?: string;
  questIds?: string[];            // 仅表示已核实关联，不自动登记
  availability: 'obtainable' | 'unavailable' | 'unverified';
  sourceRefs: string[];
}
```

名称、描述和装备基础属性尽量复用现有目录，不复制成三份权威数据。新字段按客户端需要生成轻量展示投影；任务页不因静态目录存在而公开未获得条目。

### 5.5 可获得性与进度分母

“源资料中存在”“已导出图标”“项目中可实际获得”是三回事。物品只有在现有已开放的掉落、商店、创角、任务等真实链路可获得时才进入默认“当前可获得”分母；GM 测试授予不使一个物品自动变成正常可获得。

怪物保留原始目录结构，另算“当前可收集”摘要。原版行／页奖励继续依据完整原始集合，不使用这个缩小后的摘要分母。

任务道具页只显示“已记录 N 种”，不出现“已获得 N／所有未来任务道具总数”。下架内容的既有记录放入历史记录，不删除事实，也不造成当前完成率超过 100%。

### 5.6 构建顺序与最小资源集

```text
现有同版导入与物品／怪物定义生成
  → 收藏 UI 导出
  → 规范化目录和规则生成
  → 补齐本功能实际需要的图标／原版奖励物品定义
  → notebook 校验
  → assemble_tms273 装配
  → 前后端配套候选构建
```

执行依赖必须与现有物品、宠物、现金目录的最终合并顺序一致，不能先生成图鉴再被后面的 items 重建覆盖。不要仅手工修改 `manifest.json`；完整重导出后功能仍应存在。

不为浏览图鉴一次性加载全部地图、怪物动作或 WZ 资源。先导出当前内容需要的目录与图标；未装配内容保持明确状态，扩区时增量补齐。正式可见的条目必须有真实图标或明确的资源缺失状态，不能用相似怪物替代。

## 6. UI 与入口实施

### 6.1 “复用怪物收集 UI”的具体含义

当前已审阅的前端功能目录没有现成的收藏功能模块，`exportWindows()` 也没有导出该窗口。[S06][S18] 因此应先从 TMS273 原图建立一个收藏窗口壳，再让四类内容使用它，而不是寻找一个不存在的 `MonsterCollectionView` 直接继承。

保留原版背景、边框、按钮各态、格子、页码／分页、进度区域、提示框、纹理比例与源 anchors。新增四类内容导航属于用户授权的 **P：界面扩展**，可读文字按项目本地化绘制，不冒称整张扩展界面与原版像素完全一致。

建议结构为：

```text
冒险笔记（图鉴）              关闭
[怪物收集] [装备图鉴] [道具图鉴] [任务道具]

怪物页：保留原收藏的地区／页／行，以及勋章、探险等内部导航
物品页：复用同一窗口壳、格子和详情框，替换内容适配器
任务页：只给已获得内容，不放“未获得”开关
```

上图是信息层级说明，不是已经核定的像素线框。四类导航不能覆盖原版怪物页的地区、勋章和探险控件；必要时增加小范围外围导航区，而非删除原有子功能。

### 6.2 菜单只改原来的那一项

1. 在 NB-00 从真实 `UITotalMenu` 源确认“怪物收集／收藏”对应的 `entry.key` 与 `entry.type`，将映射写入明确配置与校验。
2. 为该项建立稳定语义动作 `adventureNotebook`，在 `MenuView` 增加 `onNotebook` 回调；其他条目的映射保持不动。
3. 保留它在菜单冒险分类的原位置、顺序和图标。打开后关闭菜单并切换至同一个笔记窗口。
4. 简体中文可见名称与 tooltip／aria-label 全部为 **`冒险笔记（图鉴）`**；英文随现有本地化机制提供含义对应文本。
5. 不在运行时依赖中文 label 模糊匹配，不猜 type 数字，不额外添加一条“图鉴”菜单。

**图片文字陷阱：** 现有 `createAssetButton()` 仅设置文本属性，视觉由图片决定。应优先从同版素材拆出不含原文的背景／图标并叠加新的 DOM 文本；无法无损拆出时，为这一项生成有审阅依据的定向派生按钮素材，覆盖 normal、hover、pressed 全部状态。不能在含旧字的图上再叠一遍新字，也不能把整张按钮横向拉长。

测试必须实际核对屏幕显示，不用“元素 title 已改变”代替完成。长名称的窄屏换行或字号调整仅限该按钮合理范围，保持可点击与可读。

### 6.3 四页交互细节

| 区域 | 怪物 | 装备 | 普通道具 | 任务道具 |
|---|---|---|---|---|
| 分组 | 原版地区／页／行 | 源装备部位、等级、职业条件 | 真实背包类别与数据标签 | 已获得物品关联的任务／章节，或“其他已记录” |

已核实的获取地点可复用现有世界地图查看入口；本任务不新增点击图鉴直接传送、不改变传送费用与权限。无法验证来源时写“获取来源待核实”，不猜地点或 NPC。

### 6.4 复用现有前端代码

- 使用 `features/ui/window-shell.ts` 的现有窗口拖动能力，并对照 `UI_WINDOW_SYSTEM.md` 的最新规则实施。
- Tooltip 复用 `TooltipController`／`tooltipSkin`；装备与道具调用 `itemDetails(itemId)` 显示模板信息，不塞一个虚构 slot 的 `InventoryItem` 让背包操作误以为可交互。
- 中文名／说明复用 `itemName`／`itemDescription` 和现有 i18n；未核定的译名不编造。
- 根节点加入共享 UI host 时使用 append，只销毁自己的节点，不能 `replaceChildren()` 清掉 NPC、任务或背包窗口。
- `app/main.ts` 只负责构造、路由和销毁；不要在这里写一千行图鉴业务。
- 维护每页自己的筛选和页码；切页不重复创建全局监听器、不重复注册窗口实例。

### 6.5 生命周期、输入及小屏

打开时请求当前身份私有快照；首次加载显示明确加载状态，失败可重试。快速切页时用 requestId、当前页签与版本丢弃过期响应，不能让上一页结果覆盖当前页。

ESC 只关闭最上层当前应关闭的窗口，不同时打开菜单。搜索输入、输入法组词、聊天输入时不触发角色攻击或快捷技能；无新增默认热键，兼容现有键位系统即可。

登出／切换角色清空私有记录缓存和 UI 实例；重连重新读服务器状态。换图不应清掉持久记录。关闭窗口暂停图标动画和不必要刷新；销毁时释放监听器、observer 与动画资源。

至少检查桌面宽屏、较小桌面、横屏和窄竖屏；建议测试 1440×900、1024×768、844×390、390×844，并测试运行中 resize。这是拟定检查尺寸，不是本次已完成测试。空间不足时采用 grid／flex、内容滚动与分区重排，保住生命状态和关闭／分页操作，不能整窗缩小到文字不可读。

## 7. 服务端状态模型与持久化

### 7.1 角色与账号身份先分清

`lobby.rs` 的 `characters` 表明确区分角色 ID 和登录账号 ID；部分既有持久化参数仍叫 `account_id`，不能仅凭命名决定收藏共享范围。[S12]

建立一个窄的服务器内部解析函数：输入**已认证连接绑定的角色 ID**，验证角色存在并解析其所属登录账号。对数据库主体使用不同的 Rust 参数名，例如 `character_id` 和 `owner_account_id`。

客户端查询与操作不接收任意 `accountId`／`characterId` 作为授权依据。缓存归属可以使用，但不能用用户名、显示昵称、频道或客户端字段替代真实关联。

### 7.2 最小核心表（拟新增）

```sql
CREATE TABLE IF NOT EXISTS notebook_item_records (
    character_id TEXT NOT NULL,
    item_id TEXT NOT NULL,
    first_obtained_at_ms INTEGER,
    recorded_at_ms INTEGER NOT NULL,
    time_quality TEXT NOT NULL,
    source_kind TEXT NOT NULL,
    source_ref TEXT,
    PRIMARY KEY (character_id, item_id)
);

CREATE TABLE IF NOT EXISTS monster_collection_records (
    owner_account_id TEXT NOT NULL,
    entry_id TEXT NOT NULL,
    first_character_id TEXT NOT NULL,
    registered_at_ms INTEGER NOT NULL,
    rules_version TEXT NOT NULL,
    PRIMARY KEY (owner_account_id, entry_id)
);

CREATE TABLE IF NOT EXISTS notebook_revisions (
    scope_kind TEXT NOT NULL,
    scope_id TEXT NOT NULL,
    revision INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (scope_kind, scope_id)
);

CREATE TABLE IF NOT EXISTS notebook_backfill_runs (
    character_id TEXT NOT NULL,
    migration_version TEXT NOT NULL,
    completed_at_ms INTEGER NOT NULL,
    summary_json TEXT NOT NULL,
    PRIMARY KEY (character_id, migration_version)
);
```

以上是最小逻辑草案；落地需按当前 SQLite schema 风格增加约束、索引和升级兼容检查。外键、角色删除语义和遗留账号迁移顺序必须一起验证，不能仅复制建表语句就当迁移完成。

`time_quality` 至少区分“真实获得事件时间”和“历史补记、时间未知”。历史补记时 `first_obtained_at_ms = NULL`，`recorded_at_ms` 表示补记时间，不得显示为原始获得时间。

不在此表复制名称、图标、分类、进度百分比或当前库存。目录修正后重新投影视图，不需要清洗成千上万条玩家文案。

本期只记录“是否曾经获得”及首次记录依据，不维护无限增长的全量获得流水、每日刷取数量或累计金额。重复获得走唯一键幂等，不刷 revision，也不重复弹“首次发现”。

### 7.3 奖励和探险表（对应完整复刻阶段）

按同版规则补充以下职责，不在浏览阶段制造空功能平台：

| 拟新增表／记录 | 必须保证的约束 |
|---|---|
| `monster_collection_reward_claims` | 同一归属与同一原版奖励键只能完成一次领取；保存真实领取角色和结果 |
| `monster_collection_actions` | 操作主体＋操作类型＋requestId 的持久回执，校验请求指纹；重复请求返回已提交结果 |
| `monster_collection_explorations` | 持久 runId、账号、槽位、组合键、开始／结束时间、规则与奖励快照、状态；同一槽位不能同时运行两次 |
| 领奖计划／已抽取结果字段 | 容量失败或重试不能通过重抽改奖励；已提交的奖励选择可恢复 |

原版奖励的“一次性资格”和请求幂等是两个约束：换一个 requestId 仍不能再次领同一份奖励。账号共享收藏但奖励发给当前角色时，也必须在同一事务里绑定与验证收件角色。

### 7.4 版本与持久化成功的定义

目录版本决定怎么展示，规则版本决定一次收藏／探险怎么结算。进行中的探险保留其开始时需要的规则／奖励定义或足够的不可变快照，不能被新部署悄悄改变时长与收益。

首次获得／登记提交后，才增加相应归属的 revision。事务失败时事实、revision、奖励以及成功回执一起回滚。

不能在 `notebook_item_records` 写失败时仍发送“登记成功”；也不能在物品授予成功后再异步试写图鉴。正式开启功能后的应记录获得事务，漏写图鉴即整笔失败，且应产生可定位错误。发布前通过目录校验排除“正常物品缺目录”导致大量业务拒绝。

确实不属于图鉴范围的物品须被分类规则明确排除，可正常授予而不留档；未知分类不是静默排除的理由。灰度关闭界面只影响展示，已经启用的事实记录不应随意停写。

## 8. 怪物登记链路

### 8.1 进入已有死亡结算边界

`auth/loot.rs::resolve_attack_with_party` 已使用 `monster_rewards` 的唯一实例行判断此次死亡是否首次认领奖励；任务击杀也在该事务里增加。[S07]

收藏登记应进入这一**首次死亡结算分支**，但不能直接复用“已接任务的击杀目标”作为收藏候选，也不能把已有任务“最后一击”资格不加核定地复制为收藏资格。

World 内先构造可信上下文：

```text
运行怪物实例 ID
怪物模板 ID + 有依据的精英／变体标签
地图 ID + 是否练习／测试实例
此次可获得收藏资格的角色列表
这些角色对应的真实账号
此次采用的收藏规则版本
```

`target_id` 是运行实例，不可直接当目录模板。模板、变体、资格都来自服务器对象，而非客户端提交。

### 8.2 原子处理顺序

```text
验证／读取已持久攻击回执
  → 认领该怪物实例的首次死亡结算
  → 按同版规则确定有资格的主体
  → 把同一账号的重复资格去重
  → 匹配收藏 entryId，跳过已登记条目
  → 仅对合法未登记条目执行一次概率／条件判定
  → 成功者插入收藏事实和 revision
  → 原有击杀副作用及请求结果一起提交
  → 提交成功后向相关在线会话推送私有变更
```

是否每账号一次、是否组队成员有资格等是 NB-00 必须核定的规则。上面的账号去重适用于账号级登记机会的已核定／明确 P 方案，不能拿它掩盖原版可能存在的资格差异。

**既有 `monster_rewards`／攻击回执能够持久标记此次判定已结算时，不必再给每次未成功收藏额外建一张无限增长尝试表。** 需要重放的结果并入已有结果或本次增量回执。关键是不论登记成功与否，已提交的死亡都不能被重试当成新的抽取机会。

事务提交前整体回滚表示本次尚未结算；已经提交的失败结果绝不重抽。不要只记录“抽中”的死亡而忘记“没抽中”也必须有已结算标记。

### 8.3 必查调用点

核对普攻、主动技能、召唤物、持续伤害、隐藏追击、反应器／脚本造成的死亡，以及多人同时命中是否都走这一共同边界。只挂 `handle_attack` 会漏掉其他击杀；不能为了方便给每个技能单独复制收藏代码。

练习图和测试生成的怪物默认不计正式收藏，这是本项目的保护策略；其与同版具体收藏资格不同的地方标 P。原先 `practice` 事实保留，不能因为收藏系统接入让练习 Boss 变成正式奖励来源。

### 8.4 旧卡片明确隔离

现有 `monster_book_cards` 及卡片最多五张行为保留原样，除非另有授权更改。不执行以下自动转换：

- 一张旧卡片等于现代收藏登记；
- 五张旧卡片等于一颗收藏星级；
- 卡片 itemId 直接等于 monsterTemplateId；
- 登录扫描旧卡片后补发所有现代收藏奖励。

旧卡片是实际获得过的物品时，可在兼容分类政策下保留物品记录，但不能因此获得现代怪物收藏资格。

## 9. 物品获得事实：统一语义，不强求立即统一所有底层写入口

### 9.1 内部事实接口

建议在 `auth/notebook.rs` 提供一个只在服务端调用的事务 helper；下列为接口示意，不要求建立大型事件系统：

```rust
// 字段与现有项目类型对齐；不是完整可编译实现。
struct ItemAcquisition<'a> {
    item_id: &'a str,
    quantity: u32,                 // 必须是这次真正授予的正数
    source_kind: AcquisitionSource,
    source_ref: Option<&'a str>,
}

fn record_item_acquisitions_tx(
    tx: &rusqlite::Transaction<'_>,
    character_id: &str,
    grants: &[ItemAcquisition<'_>],
    event_time_ms: i64,
    catalog: &NotebookCatalog,
) -> Result<NotebookChangeSet, StoreError>;
```

它验证实际定义与图鉴归属，规范化 itemId，首次插入事实，并在同一事务里更新 revision；不负责给背包加物品，不吞业务错误，不在事务内发网络消息。

业务拥有“是否成功授予”的事实；图鉴记录这个结果，不能反过来替任务、背包、商店决定能否发奖。

### 9.2 为什么不能使用最终背包差量

同一个事务可能收走一件物品又发回同 ID 物品；任务可能授予一个瞬时剧情物品后立即消费；装备换槽、仓库转移也可能看起来像“增加”。最终快照只能显示库存，不能完整表达真实的授予过程。

因此任务奖励计算应显式返回 `actual_grants`，只包含实际授予的物品，而不是把完整奖励候选列表传入记录函数。模板级多条正向授予可以在记录 helper 中去重，因为此处只关心首次获得，不改变原奖励清单、顺序或数量。

### 9.3 成功提交与 UI 提示

事务结果返回 `NotebookChangeSet` 或至少返回可用于重查的 revision。World 在提交成功后更新相关内存镜像并推送；没有新增事实则不产生首次获得提示。

若提交成功后连接断开，事实仍在；重连快照恢复已获得状态，不补演一长串旧弹窗。持久回执重放不能再生成新的首次登记通知。

### 10.2 普通商店的必要前置修复

源码与文件头注释存在差异：`handle_shop_buy` 实际先写 `player.state.inventory` 与 `mesos`，随后分别执行 `store.write_inventory` 和 `store.save_profile`，两处错误都被忽略。普通购买不能照搬“已经完整事务化”的假设。[S10]

`handle_shop_rebuy` 则先调用 `take_shop_rebuy` 删除赎回行，再处理物品与金币；`take_shop_rebuy` 自己会提交事务，不足以保证整笔赎回原子性。[S10][S11]

需要的修改限于本次获得链路：

1. 新增或重构 `Store::shop_buy`／`Store::shop_rebuy`，复用现金商店已采用的“持久状态校验—同事务变更—持久回执—成功后改 World 镜像”模式。
2. 在事务内读取余额、实际背包／槽位限制；商店合法性、NPC 距离等仍由 World 先验证，再传可信配置或校验上下文。
3. 用持久动作表保存请求指纹；相同 requestId 不同参数拒绝。不同 requestId 也不能消费同一赎回权益两次。
4. 仓库／商店 helper 若已存在独立锁与事务，提取 `_tx` 内部版本，不能在新事务中调用原公开封装造成重入锁。
5. 成功后统一返回已提交背包、余额、结果和笔记变更；失败不改内存、不发成功回执、不登记。
6. 对出售生成赎回权益的上游也核对原子性：当前源码显示出售与 `push_shop_rebuy` 分离；为使赎回闭环可靠，将直接相关的出售权益写入纳入同一交易事务，不借此重写全部物品系统。

上述修复是“购买后图鉴可靠登记”的直接前置，不是借功能名义做泛化架构重构。不能把商店全部跳过，却在交付报告中声称覆盖所有获得入口。

## 11. 原版奖励、勋章与探险

### 11.1 奖励不是客户端点亮即可领取

客户端只提交 rewardKey／runId 和 requestId。服务器重新计算或读取持久资格，验证真实身份、未领取状态、收件角色与容量，并在一个事务里提交：资格认领、物品发放、图鉴获得记录和回执。

背包满时，按核定的原版交付方式拒绝或执行已有明确交付机制；没有邮件系统时不能写“自动邮寄”并当成已实现。拒绝不得吞资格、扣道具、标记已领取或弹成功通知。

勋章若对应装备，只在真实发放时记入装备图鉴；达到条件但尚未获得物品，不应提前记“装备已获得”。

### 11.2 探险保存截止时间，不存每秒倒计时

保存 `startedAt`、`finishesAt`、规则版本和 runId；前端剩余时间仅为展示。离线、网页失焦、服务器重启后依据服务器时间恢复，不因客户端停止计时而暂停。

状态最少区分：未开始、进行中、可领取、已领取。可领取可由持久截止时间推导，不要求每秒把状态写进数据库。若原版支持继续／重新出发，再实现对应明确状态转换，不自作主张自动循环领奖。

开启探险须校验槽位、组合、收藏资格和已有运行占用；同一账号多角色同时操作也不能双开同一槽位。原版槽位数量、解锁阈值、探险时长及每日限制全部来自已核定规则，不采用当前外服指南数值填空。

### 11.3 抽奖、满包和重试

探险奖励若包含随机内容，奖励选择必须可恢复。根据同版抽取时机，在开始或首次合法结算时保存服务器私有 seed／已选择奖励方案；容量失败后的重试使用同一方案，不通过反复尝试重抽。

储存方案不等于已发奖：只有容量满足、奖励物品写入和领奖状态同事务提交后，才算领取完成。客户端不能看到可操纵的随机 seed，也不能提交自己的奖励结果。

### 11.4 时间与当前工程模型

服务器检查截止时间，客户端改系统时间不能提前领奖；服务器时间回退时不出现负耗时或反向发奖。重启加载所有活跃探险的持久时间，不创建每角色常驻计时 task。展示刷新复用 World／客户端既有生命周期，不在 50ms 世界快照里反复下发完整图鉴或每 Tick 查询 SQLite。

## 12. 私有协议与状态同步

### 12.1 建议消息

| 方向 | 拟新增消息 | 内容与权限 |
|---|---|---|
| 客户端 → 服务器 | `notebookQuery` | requestId、section、page／cursor、有限筛选；主体只来自连接 |
| 服务器 → 客户端 | `notebookState` | 对应 requestId、内容版本、scope、revision、页数据、合法摘要、serverNow |
| 服务器 → 客户端 | `notebookChanged` | 轻量私有失效通知，含 scope、revision、允许展示的新增条目；必要时客户端重查 |
| 客户端 → 服务器 | `monsterCollectionClaim` | requestId、rewardKey；服务器判资格 |
| 客户端 → 服务器 | `monsterExplorationStart` | requestId、组合／槽位身份；服务器判条件 |
| 客户端 → 服务器 | `monsterExplorationClaim` | requestId、runId；服务器判时间、容量与领取状态 |
| 服务器 → 客户端 | 收藏操作结果 | requestId、成功／拒绝原因、已提交 revision 和相关状态 |

优先采用“查询快照＋轻量失效通知”，不要求建立无限增量日志。客户端发现 revision 跳跃，直接重查；重连无条件恢复快照。客户端无需重放全部历史业务事件。

### 12.2 安全与隔离

- 不增加 `unlockItem`、`registerMonster`、`setCollected` 等客户端权威写入接口。
- section 枚举、pageSize、搜索长度、cursor、requestId 长度、请求频率必须做运行时校验；TypeScript 类型不替代服务器检查。
- 查询只返回当前授权归属。任务页的筛选、分页和摘要都在已获得集合上计算；不能先把全部未来任务条目发给客户端，再只用 CSS 隐藏。
- 本要求是正常游戏 UI 与该接口的数据约束，不声称能让已随客户端静态资源发布的剧情文本对技术用户绝对保密。
- 同账号怪物共享时，相关在线角色可以收到账号收藏变更；物品获得记录只通知当前角色。不得广播到地图所有玩家。
- 独立操作用主体＋操作＋requestId 去重，奖励另有奖励键唯一约束。相同请求 ID 不同参数须拒绝。
- `notebookState` 的目录版本与客户端不一致时返回明确版本不匹配，不套用旧页码解释新数据。

### 12.3 与现有协议同步修改

同时核对与更新：`server/src/protocol.rs`、`shared/protocol.ts`、`server/src/commands.rs`、浏览器接收／分发、相关机器人与测试消息夹具；网络层仅做解析和投递，不能直接执行 SQLite 收藏写入。

当前基线是 23／tms273-27。实际集成时先读取最新 HEAD，再分配新的协议／内容版本，不在多 Agent 并行开发中把别人已增加的版本号覆盖回去。源配置、manifest、服务器内容版本与配套构建必须一致。

## 13. 老账号迁移：可证明的补记，不捏造历史

### 13.1 可以作为证据的范围

| 存量资料 | 可补记内容 | 不能推断的内容 |
|---|---|---|
| inventory、equipped、归属已核实的 storage 当前真实物品 | 此角色至少持有过该物品 | 最初获得时间、最早地点、总获得次数 |
| `pickup_actions` 中真实成功的物品领取回执 | 曾经拾取成功的具体 itemId | 回执没有时间字段时不能补原始时间；失败／金币排除 |
| `cash_actions` 中真实成功的购买回执 | 曾经购买成功的具体 itemId | 未购买的同类商品、赠品候选、原始时间缺失部分 |
| 旧卡片记录 | 旧卡片获得兼容信息 | 现代怪物登记、星级、现代收藏奖励资格 |
| 任务存档与明确执行回执 | 仅对能证明实际授予、无选择歧义的具体物品补记 | 不把所有已完成任务的所有奖励和材料一键登记 |

是否跨角色仓库、旧账号 ID 与角色 ID 的兼容关系，必须以实际关联核查为准，不因表名／注释写“账号仓库”就错误共享任务物品。

### 13.2 执行方式

新功能启用时进行一次有版本标记、可重复执行的补记。按角色、事务和受控批次完成；以事实表唯一键去重，不发奖励、不播放首次收集提示、不重置任何收藏状态。

补记报告写明：扫描来源、证明的新条目数、别名去重数、无法归属／无法证明记录、时间未知记录，以及迁移版本。数据库出错则本批回滚，不能先写“迁移完成”标记再扫描。

以后正常业务真实获得一件已补记条目时，不伪称知道了历史最早时间：保留历史未知状态。若要记录“功能上线后首次可验证获得时间”，增加独立字段，而不是覆盖最初获得时间的含义。

### 13.3 无法恢复的历史

某个任务物品在功能上线前已经交付，而且现有库里没有可靠的实际授予证据，就无法从当前背包恢复它。对此明确报告“历史资料不足，未补记”，不要靠角色等级、完成任务数量或相似物品猜测。

这不妨碍后续新获得链路完整记录。用户验收要区分“新获得不丢”与“历史缺失可恢复多少”，不能把第二项包装成已经恢复了全部过去经历。

### 13.4 回滚

代码回滚保留新增事实表，不删除历史记录。运行中的原版探险和已发奖励不可因为 UI 回滚而重置。旧二进制是否能读取新增 schema，必须在临时数据库验证；不能直接用用户在线库试错。

正式迁移在受控发布／正常启动流程执行，遵守用户数据库保护和统一启动约束。当前计划阶段不访问或备份用户本地库，不虚构已经执行迁移。

## 14. 文件级实施划分

### 14.1 拟新增代码

## 15. Agent 工作包与依赖

工作包是执行说明，**不是本次已经启动的子代理任务**。遵守仓库现行模型分工：复杂事务和边界由架构／复杂实现角色处理，已定边界的资源与 UI 可以独立实施；无独立 QA 任务。

### 15.1 并行边界

资源导出与 UI 展示可在 NB-01 契约冻结后并行；核心数据库与商店事务修复由明确持久化所有者协调。`shared/protocol.ts`、`protocol.rs`、`main.ts`、schema、最终 assemble 等共享点不得由多个 Agent 随意同时修改。

并行任务发现需要改别人的边界，先给出需要的输入输出，由统筹整合，不复制第二套类型或 Store。无法并行时明确排队，不虚构已经启动的代理或测试。

### 15.2 可交付阶段，但不删除完整目标

- **阶段 A：实际可用的冒险笔记。** 完成旧入口、同版窗口壳、四页查询、物品获得链路、历史补记，以及规则已核定的怪物登记。未知怪物机制明确提示，不伪造概率。
- **阶段 B：完整原版收藏行为。** 完成同版行／页奖励、勋章、收藏相关道具和探险。阶段 B 未完成时，项目总计划必须继续保留相应工作。

不以“后面可扩展”替代已要求的装备／道具／任务道具图鉴，它们均属于阶段 A 的核心交付。

## 17. 用户实玩验收脚本

在必要代码和内容交付、通过统一启动脚本加载相匹配版本后，由用户执行：

**场景一：入口与四页。** 从菜单原怪物收集位置进入；屏幕看到“冒险笔记（图鉴）”，打开单一窗口，四个页签均可用；怪物页保留自己的地区、勋章和探险导航，不挤占或删除。

**场景二：任务道具真的留下了记忆。** 使用尚未完成对应任务的合法角色，触发已实现的 36301／4036846 授予；取得前任务页没有该物品，取得后出现；交付任务后背包已移除，任务页仍可查看；刷新与重登保持。角色已经越过该任务时不重置旧账号，改用允许的新测试角色或别的已核实任务场景。

**场景三：购买、使用、出售。** 正常购买一件当前可售道具或装备，图鉴登记；消耗或出售后条目保留；金币不足或满包的失败购买不登记。必须确认不是只在内存里显示成功，重登后物品与记录一致。

**场景四：怪物收藏。** 在非练习可达地图击杀符合已核定规则的怪物，使用测试检查验证判定边界，实际游戏体验按正式概率；登记后相同账号另一角色能看到，另一个账号看不到。不能要求用户在有限次随机击杀内必然中签来作为唯一验收方式。

**场景五：完整收藏。** 达到真实行／页／勋章条件后领取，满包和重复点击均不吞资格／重发；开始探险后退出再进入，剩余时间正确；到期只领取一次。该场景未通过，阶段 B 不得标完成。

## 20. 交付完成定义

**阶段 A 完成**至少要求：原入口可见名称正确；一个共用窗口的四页功能实际存在；真实获得链路全覆盖；任务交付后留档；当前可证明的历史补记；私有状态与重连恢复；物品授予和留档的事务及失败检查；目录与原素材可重复构建；未知怪物规则有明确阻塞说明。

**完整复刻完成**还要求：同版怪物登记资格与概率有依据，原版行／页／勋章奖励、收藏相关道具、探险及离线恢复均实现并通过必要检查；不能只有按钮和占位提示。未开放地图影响的是具体内容覆盖率，不得把原版完整行条件缩小后发奖。

交付报告必须包含：实际修改文件、源码／协议／内容版本、同版与 P 差异、已运行检查及数量、未运行范围、仍阻塞的规则、用户实玩步骤。不得写没有执行过的“已启动”“全通过”“像素 1:1”。

**最重要的一句话：图鉴记录玩家真正经历过的获得；它不应该要求玩家为了证明过去而永久留着物品。**
