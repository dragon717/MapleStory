## 0. 决策摘要

**不是给现有项目外挂一套「命运系统」，而是在现有权威动作旁边，补齐真实后果、持久记忆和有依据的回应。**

源码核查后，第一阶段采用以下路径：

```text
浏览器发出一个有限的互动意图
    → 现有 WebSocket／ClientMessage::valid／Command::Input
    → World 在当前地图、角色与物件状态上校验
    → Store 的一个 SQLite 事务：场景变化 + 行动事实 + NPC 记忆 + 幂等回执
    → 提交成功后更新 World 的内存投影
    → 现有 snapshot 展示共享变化
    → 现有 npcResult／NpcDialogueView 展示个人化的认人对白
```

第一段可玩的内容只做：**同一辆车、同一位旅人、两次相遇、可核对的记忆**。不先做属性、递药扣包、全世界 NPC AI、命格、神系或权柄竞争。

### 0.1 本轮拍板的工程选择

| 决策 | 本版做法 | 明确不做 |
|---|---|---|
| 服务端结构 | 一个 Rust crate；World 继续单一逻辑拥有者；沿现有 `#[path]` 子模块接入 | 重建 `runtime/application/adapters` 全套目录、拆微服务 |
| 前端结构 | 保留实际使用的 Phaser 3.90.0 + TypeScript + Vite；复用 NPC 窗口 | 为天命迁移 Three.js、Godot，或新增 React/ECS 状态层 |
| 历史与事实 | 为原创场景新增小范围持久事实；原有玩法状态仍由原模块拥有 | 把整个游戏改为事件溯源，保存每帧位置和每次普通伤害 |
| NPC 身份 | 历史主体、表现实体、素材模板明确分开 | 把 `templateId` 或当前对话节点当成持久人生 |
| 第一个提交边界 | 修车场景、贡献、记忆和回执同一 SQLite 事务 | 先宣布修好，再异步「尽力」补一条记忆 |
| 第一版存储方式 | 沿用当前短同步 Store 事务；承认并测量阻塞风险 | 声称当前已具备不阻塞 Tick 的 outbox／持久事件总线 |
| 运行入口 | 继续统一使用 `启动3010.command`，不自动执行 | 绕过脚本启动，顺手切换 HMR 默认模式，清库测试 |

**最重要的范围收缩不是少写几个模块，而是：先让「这件事确实发生过」可靠，再让「世界因此认识我」成立。**

### 1.2 修正 v0.1 中的七个工程假设

**第一，`world/`、`persistence/` 等只是旧版示意，不是当前目录。** 当前世界职责主要以平铺文件挂入 `world`，而存储已有 `auth/` 子树；两者必须分别遵循源码习惯。[R06][R10]

**第二，有命令队列不等于有持久领域事件总线。** 已读取的世界组装、Store 事务和对话发送路径不能证明存在通用可靠事件流。本版为第一段原创业务直接提交事实，不先造一套中间件，也不假装可以调用已有 outbox。[R04][R08][R11]

**第三，当前 NPC 对话状态不是记忆。** `conversation` 防止玩家互相推进对话，不能承担改名、换图、重启后的历史关系。[R07]

**第四，当前 Reactor 的重启语义不满足永久改变。** 复用其美术或交互方式可以，复用其暂态存储承诺不可以。[R07][R13]

**第五，前端不是未知渲染器。** 本版具体接入 Phaser Scene、`NpcDialogueView` 与根目录共享协议。[R18][R19][R20]

**第六，不能说「克隆 Store 放进异步任务，就不会卡世界」。** 克隆仍共享同一 `Mutex<Connection>`；旧世界同步 Store 调用仍可能等待同一把锁。异步化若有必要，应作为独立存储执行模型改造，而非一句 `spawn`。[R10][R11]

**第七，测试报告不等于当前提交的已通过结果。** 仓库留有既往基线和失败项；本轮没有复跑，不把这些结果或旧文件行数当成本轮实测。[R22]

### 1.3 证据边界

已定向读取关键入口、状态、对话、Store、协议、前端、启动和治理文件；未逐行审查全仓库，未运行游戏，也未核实本地 WZ 素材和全部导出地图的可见效果。

下文新增模块、表、类型、消息、阈值和原创 NPC 均为**拟新增**。源码基线之后若继续重构，应按符号重新定位，不能把本文件的行号当永久接口。

## 2. 不改的设计核心，与本版明确暂缓的内容

### 2.1 不变量

| 不变量 | 对应工程约束 |
|---|---|
| 世界先认识具体行为，不先宣判人格 | 保存 `CartBraced` 一类事实，不保存「善良度 80」 |
| 记得不等于全知 | 记忆必须有观察者、主体、来源事实和知识来源 |
| 正反馈不等于天命 | P1 不命名、不发数值；正式承担阶段才使馈赠与边界同时成立 |
| 边界不是任意惩罚 | 条款限定对应能力；不能顺手禁交易、削职业技能或卡原版成长 |
| 玩家可以改道 | 候选可变化；已承诺的关系通过解除／移交／背离产生新历史，而非清空旧历史 |
| 命运不是预写结局 | 不在创角时指定终局；回望只引用真实旧事 |
| NPC 也有未来 | 非玩家行动可以改变同一场景；不得等玩家进入才假装时间开始 |
| 共同世界事实不各说各话 | 同一场景的车是否扶正、NPC 在哪里只有一个答案 |
| 没参与不产生道德债 | 路过、离线、没读邀请不能自动记为冷漠或背叛 |
| 第三条路有效 | 权柄冲突的互斥条件被合法改变时，应允许解除冲突 |

### 2.2 第一阶段不做的事情

不做天命等级、经验、稀有度、每日次数、排行榜和付费洗命。不做全服人格分析，不读取私聊或现实资料。不把充值、在线时长和按键数量变成资格。

工程上暂不做全量历史回放、向量库、在线 LLM、任务 DSL、全 NPC 导航、跨频道共享人物、跨进程事务、统一 Buff 大重构、全世界神权。

这些暂缓项不是取消长期方向，而是不能作为「车夫下次认得你」的前置条件。

    └── Phaser World Scene                 scenes/world.ts

队列、状态拥有者、持久化和显示之间已有边界，但不是每个边界都有独立框架。新功能应利用这些边界，不为补齐架构图而制造层数。[R04][R05][R06][R08]

### 3.3 注册方式与依赖约束

```rust
// 以下是拟新增接线示意，不是已存在或已编译的补丁。

// server/src/main.rs
mod story;

// server/src/world.rs
#[path = "world_story.rs"]
mod world_story;

// server/src/auth.rs
#[path = "auth/story.rs"]
pub(crate) mod story;
```

`story.rs` 的规则函数只接受明确数据，不引用 `World`、`Store`、Phaser、网络连接或隐式系统时间。`world_story.rs` 是权威用例协调层，按照已有私有子模块模式调用；其中不内联 SQL。`auth/story.rs` 只接受服务端构造的提交计划，不接受原始 WebSocket JSON。

允许 `World` 新增一个私有 `StoryRuntime` 字段；不把事实全集塞进 `PlayerState`、`Profile`、`NpcState` 或 `NpcInstance.conversation`。

**不要将世界子模块命名为 `npc`。** 现有 `world.rs` 已引入 `crate::npc`，`dialogue.rs` 的模块说明明确记录过这一命名冲突。[R08]

### 3.4 哪些原有文件这轮不应重构

`combat.rs`、移动碰撞、`skills.rs` 的技能公式、`inventory.rs` 的物品规则、`quest.rs` 的原版主线，均不是 P1 的重构目标。

`world.rs` 和 `app/main.ts` 虽然是接线点，也不应继续承担大段天命业务。对它们的修改要能逐条解释为状态持有、路由、调用或生命周期接线；不能同时做纯搬移与玩法变更。

## 4. 身份、范围与状态：让「你」不会在重登后变成别人

### 4.1 四种 ID 必须分开

| ID | 来源／生命周期 | 用途 | 禁止替代 |
|---|---|---|---|
| 角色身份 `character_id` | 握手认证得到的角色身份；沿现有字符串 ID | 记录谁实际帮助、谁接受承诺 | 账号名、显示名、客户端自报 ID |
| NPC 历史身份 `story_actor_id` | 新增；同一世界连续体中持久唯一 | 记忆、资源、目标、位置和人生历史 | NPC 模板 ID、地图 life 序号 |
| 表现实例 `presentation_id` | 当前 `self.npcs` 中的实例键，字符串且全局不冲突 | 点击、快照、当前对话绑定 | 永久历史的唯一依据 |
| 素材模板 `template_id` | 既有 NPC 内容／manifest | 外形、原始帧、可复用表现 | 「这是同一个人」的证明 |

角色大厅已经区分账号与角色，旧兼容表却仍使用 `account_id` 作为部分列名。**新表明确写 `subject_character_id` 或带类型的主体字段；必须用两个同账号角色验证不会共享个人记忆。** 不为解决名字歧义全库重命名旧列。[R10][R12][R15]

### 4.2 世界连续体

首版一个运行中的世界对应数据库内一个持久 `continuity_id`。它表示这段共同历史，不表示当前进程 PID、`serverTick`、素材版本或频道标签。

第一次初始化时创建并保存；重启只加载，不再生成。开发者复制数据库做分叉世界时，必须显式记录「新连续体／继承来源」，不能把两份独立世界都宣称为同一份唯一历史。此项先作为运维规则，不开发跨服迁移工具。

当前频道限制为 1；本版不扩频道数量。既有 Boss 练习实例是私有、暂态场景，默认排除在共享天命事实之外。[R07][R15]

### 4.3 状态的权威与投影

| 状态 | 权威持久位置 | 运行时位置 | 客户端可见范围 |
|---|---|---|---|
| 车的状态、现场工具归属、场景版本 | `world_story_scenes` | `World.story.scenes` | 同地图共享 |
| 阿苇的位置、当前计划、工具与旅行阶段 | `world_story_actors` | `World.story.actors`；映射到既有 NPC 实例 | 当前地图可见表现 |
| 谁改变了什么 | `world_story_facts` | 有界缓存／按需索引 | 仅授权回顾，不全量广播 |
| 阿苇对某个角色的记忆 | `world_story_memories` | 当前对话需要的缓存 | 只给相应玩家的对白 |
| 一次离散请求的结果 | `world_story_actions` | 有界会话缓存 | 对应请求者 |
| 当前脚本对话节点 | 不持久化为人生事实 | 既有 `NpcInstance.conversation` | 当前对话窗口 |
| 倾向候选 | P2 的可重建投影 | `StoryRuntime` 的候选视图 | 不展示计分进度 |

运行期间仍只有 `World` 对已加载的玩法状态做正常修改；新增 SQL 表不是让网络或另一个进程绕过它改图的后门。

### 4.4 重要 NPC 的表现绑定

使用显式注册表建立：`presentation_id → story_actor_id → template_id`。同一时刻一个重要 NPC 只能有一个有效位置；换图从旧地图投影中移除，再在新地图投影中出现。

可以复用当前已导出的兼容 NPC 立绘，但必须给原创角色独立名字和身份，不能改写使用相同模板的原版 NPC。`spawn_npc_on_map` 与模板校验可作为表现接入参照；任何额外名字覆盖只作用于这个注册实例。[R13]

同一份角色历史不能因为重新导出地图 life 序号变化而丢失。表现 ID 变更需显式映射；未知重要身份应报错或进入隔离恢复，不悄悄创建第二个阿苇。

## 5. 第一段可玩内容：翻车、帮助、再次相认

### 5.1 交付目标

> 玩家可以绕过；帮助会真的改变一件事；旅人下次能具体认出帮过自己的那个人；服务重启后仍成立。

第一阶段拆成两个可单独验收的切片：

**P1a：原地认人。** 一张已装配地图，一个阿苇，一个翻车物件。玩家修车后离开再回来，车保持已扶正，阿苇用具体经历识别这个角色。先不移动 NPC，不假装已经有自主导航。

**P1b：不等玩家的后续。** 在 P1a 可靠后增加旅人的有限计划与合法迁移，支持无人参与时自行解决，以及在第二处地点相认。它补齐「世界本来也会运转」，不是 P1a 的假完成标记。

这样能先验证最关键的持久识人闭环，再加入当前工程尚未具备的 NPC 动态位置。

### 5.2 地图与资产选择规则

不在文档里编造未核实的安全坐标、NPC 模板和车体素材。内容接入工作包必须从当前 `shared/maps.json`、`shared/gameplay.json` 与已发布 manifest 确认一个真实可用落点，满足：

- 位于已装配地图与有效落脚面，避开现有传送门和原版 NPC 的互动区域，不挡冒险家主线。
- 原创场景的存在不依赖完成某个强制原版任务，也不新增必须领取的任务。
- P1a 固定一个落点；P1b 的第二处地点必须有真实可用路线或明确允许的旅行规则。
- 物件图像保留世界坐标与原点约定；开发占位图仅用于定向逻辑测试，不记为正式美术验收。

这些是制作前的具体配置交付，不再列为「无法访问仓库」的研究缺口。内容记录中写入真实地图 ID、落脚面／坐标依据、模板、资源路径与版本；启动校验其有效性。

### 5.3 两个互补动作，不使用在线时长

P1a 使用现场已有的木楔与绑绳，不消耗角色背包、不发放道具。既能留下有形细节，也避免牵动现有资产事务。

| 场景事实 | 可用动作 | 校验 | 成功产生的事实 |
|---|---|---|---|
| `Overturned`：车倒着，现场木楔可用 | `braceWheel`：垫稳车轮 | 同地图、活着、在近距互动范围；阶段和工具状态匹配 | `CartBraced`；木楔由现场进入车轮支撑位置；记录实际操作者 |
| `Braced`：支撑已形成，车仍倒着 | `rightCart`：扶正车身 | 当前支撑仍有效；同样校验角色状态、距离与版本 | `CartRighted`；车辆变为可整理状态；记录实际操作者 |
| `Ready`：车已扶正 | 查看／对话 | 当前 NPC 与物件仍可见 | 不再产生一条「修车成功」事实 |

两个动作共享同一 `causal_root_id`，代表一次事故的两个真实贡献，不是两段独立人生选择。一个人完成两步就记住两步；两个人协作就各认各的贡献；只有围观的人不获得伪造功劳。

交互不使用当前一般 NPC 的宽松 `800×600` 对话范围作为「已伸手修车」的证明。新增近距互动范围作为原创场景参数，并校验地图、垂直距离与落脚条件；不得利用法师导师对话例外绕过动作距离。[R08][R09]

动作可以短暂展示动作反馈，但动画完成、长按时长和客户端倒计时均不产生成功事实。第一版不声称实现了多人持续受力物理；若未来需要「有人一直扶着」，应新增开始／维持／中断的权威状态，而不是改一条台词。

### 5.4 认人台词必须有证据

| 角色实际贡献 | 第二次回应示例 | 必须存在的依据 |
|---|---|---|
| 垫木楔 | 「是你。上回垫住车轮的那块木头，还卡在那里。」 | 此角色的 `CartBraced`；阿苇知情；木楔当前确实仍留在车上 |
| 扶正车身 | 「我记得你扶住了车身。那一下之后，我才敢松手。」 | 此角色的 `CartRighted`；当时阿苇处于对应受益／参与状态 |
| 两步都做 | 合并提到两段具体贡献，但不追加称号或加分 | 两份同根事实与相应记忆 |
| 只路过 | 普通打招呼，不感谢不存在的帮助 | 无对应记忆 |
| 别人完成帮助 | 根据可知信息谈起「有人帮了忙」，不把功劳给当前角色 | 场景事实；是否知道他人名字另行判断 |

木楔后来被取走、加工或遗失时，第一句必须变为符合当前事实的另一句。不要为了保住一段漂亮对白重新生成木楔。

P1a 不需要「首次／第二次」计分器。成功动作当下的确认与之后重新发起的对话本来就是两种表达入口；关闭再开不会追加帮助事实。若以后要记「第一次亲口说过这句话」，单独定义交流事实，不等同于对方一定看见了网络消息。

### 5.5 P1b 的最小自主行动

阿苇增加有限的目标：先恢复车、再整理货物、在路线允许时前往营地。行为由当前状态与目标驱动，不由「玩家是否接取任务」驱动。

他可使用现场相同工具执行 `braceWheel/rightCart`，通过同一规则与提交路径；主体换成 NPC，不得走「直接标完成」的特权路径。若玩家先完成，他重新计算下一步，不重复记功或夺走已有贡献。

旅行采用明确的粗粒度行动模型：准备／出发／途中／抵达。P1b 不声称拥有连续平台寻路；出发与抵达必须有服务端记录、目标位置校验、路线条件和最小旅行条件。有人看着时仍应展示可理解的离场，不允许在玩家眼前无说明闪现到另一点。

无人参与不必保证成功：路线不可用时保持受阻状态或按已实现的备选行动处理。不能为了让剧情继续临时穿过封锁，也不能偷用不存在的药品和货物。

### 5.6 本切片的完成与不完成

**P1a 完成**：同一场景多人看见一致变化；两名同账号角色记忆不混；同请求重放不重复；重启后车和记忆仍一致；普通主线和 NPC 不受影响。

**P1b 完成**：玩家全部不在场、服务器仍运行时，NPC 能推进；晚到玩家看见已发生的后果；同一 NPC 的地图迁移不复制人格或丢失记忆。

只换 NPC 台词、只存一个全服完成开关、只做本地动画，均不能标记上述阶段完成。

## 6. 原子提交：先保证历史不会与现实相互打脸

### 6.1 第一版选择：短同步事务，显式承认代价

当前 Store 方法同步持有 `Mutex<Connection>` 并执行 SQLite 事务。为避免首个修车动作变成一次存储框架重构，P1 采用同样的短事务方式。[R10][R11]

这意味着：**该次互动提交可能阻塞当前世界处理，不能宣称它已经是非阻塞设计。** WAL 也不等于无限并发写入或不会等待；SQLite 同时只有一个写事务的限制仍须考虑。[E01]

P1 的边界是：只在离散互动和少量到期 NPC 行动时写入；不在每个 Tick 扫描历史、不在每份 snapshot 做 SQL、不处理大批历史重算、不消耗角色资产。记录锁等待、事务耗时、事务次数与对应世界循环延迟。

若实际测量出现不可接受的玩法停顿，先关闭这条可选互动的写入口并保留数据，提交独立的存储执行模型工作包。不要靠放宽连接超时、吞错或先发成功回执掩盖问题。**本轮未测性能，文档不提供虚构的 p99 或吞吐保证。**

### 6.2 拟新增接口

```rust
// 接口契约示意；准确类型在协议/状态冻结后实现。
// 规则层：不碰数据库、不读当前系统时间，不直接改 World。
fn plan_story_action(
    context: &StoryActionContext,
    scene: &StoryScene,
    actor: &StoryActorView,
    intent: &StoryIntent,
) -> Result<StoryCommitPlan, StoryReject>;

// auth/story.rs：一个提交计划，最多一个数据库提交结果。
impl Store {
    pub(crate) fn commit_story_action(
        &self,
        plan: &StoryCommitPlan,
    ) -> Result<StoryCommitOutcome, String>;
}
```

`StoryCommitPlan` 由 World 校验后构造，包含主体、连续体、场景预期版本、动作、前后状态、有限见证者、规则版本和幂等身份。它不接受外部自报的 `success`、积分或任意可执行脚本。

Store 事务仍要验证持久场景前置、主体有效性、版本与动作对应的合法状态转移；不能因为参数来自服务端，就把一份陈旧候选盲目覆盖进库。

### 6.3 一次动作的顺序

```text
1. 现有认证和连接检查通过；格式和频率通过。
2. World 用当前角色身份构造动作主体；查已注册的场景与物件。
3. 检查幂等回执：同 ID 同语义重放原结果；同 ID 不同语义拒绝。
4. 对新动作校验地图、位置、生命、阶段、工具与可见性。
5. 纯规则生成 StoryCommitPlan，不先修改可见内存。
6. Store 开一个事务：
   a. 再核对持久幂等记录和场景版本；
   b. 校验允许的状态转移，更新场景 revision；
   c. 写入实际行动事实及因果根；
   d. 给有依据的观察者写入局部记忆；
   e. 写入稳定请求回执；
   f. 若此动作改变 NPC 持久状态，一并更新。
7. COMMIT 成功，才将返回状态应用于 World.story 与表现投影。
8. 下一份地图 snapshot 展示新状态；向当前合法连接发送动作结果。
9. NPC 对话读取已提交记忆，选择受控文案；对白不反向增加贡献。
```

运行时是单写者，但仍保留 SQL 版本条件，防止重复请求、未来维护工具误用、恢复后陈旧计划等问题。它不是用数据库争抢锁来挑选「更值得被记住」的人。

### 6.4 幂等必须同时覆盖请求与业务状态

| 层次 | 键／约束 | 目的 |
|---|---|---|
| 请求重放 | `(continuity_id, actor_kind, actor_id, request_id)` 唯一 | 同一请求不因断线、重发、重启执行两次 |
| 请求冲突 | 保存规范化语义参数：动作、场景、对象、预期版本等 | 同 ID 换参数返回 `story_request_conflict`，不能冒用旧回执 |
| 业务去重 | 场景阶段＋revision 的合法单向转移 | 换一个新 requestId 也不能把已经扶正的车再算一次 |
| 事实唯一 | 对一次已提交转移的每项真实贡献有稳定唯一键 | 重新构建视图不追加历史 |
| 记忆唯一 | 观察者＋主体＋来源事实＋记忆种类唯一 | 重放事实不会让一个 NPC 反复「更认识你」 |

同请求的回执查询应优先于当前场景版本校验，否则已成功请求在场景推进之后重试，会被错误显示成版本冲突。基础鉴权与请求格式仍先执行，不能绕过。

新的请求若遇到旧阶段，返回当前状态与 `story_state_changed`，不自动替用户改成另一种动作。

### 6.5 崩溃和失败语义

| 故障点 | 必须得到的结果 |
|---|---|
| 世界校验失败 | 不写事实、记忆或场景成功态；给出明确拒绝 |
| SQL 事务中途失败 | 整个故事提交回滚；车仍旧态，人物不感谢未发生的帮助 |
| COMMIT 已成功、内存尚未应用时进程退出 | 下次启动从持久场景与记忆恢复；同请求返回原结果 |
| 状态已提交、连接输出队列满 | 可丢当次临时气泡；持久事实不丢，重连 snapshot 与再次对话可恢复体验 |
| 客户端收到结果后自己崩溃 | 不影响世界；重连不补做动作 |
| NPC 更换表现实例 | 按历史 actor identity 查记忆；旧对话节点清理 |
| 投影应用遇到不可能状态 | 停止该场景新动作并重载隔离；不能用旧 snapshot 掩盖已提交事实 |

现有 `send_npc_dialogue` 使用 `try_send`，这能作为临时表达路径，不能作为「这段人生已持久保存」的证明。[R08]

### 6.6 为什么 P1 不需要通用 outbox

本切片的共享场景、事实、记忆与回执都在同库同事务内；暂不向其他业务拥有者发可靠副作用。恢复通过持久场景和按需对白完成，因此无需为了一个认人场景先建可靠广播平台。

后续若独立消费者需要处理「已提交事实」，再添加对应消费位置、去重约束和事务内待处理记录。通知可重发，不得因重发再次授予道具或权能。普通 `mpsc` 的容量／背压只说明排队行为，不构成持久投递保证。[E02]

### 6.7 同步存储未来拆分时的正确边界

不能随手为每个人开一个任务调用 Store。异步改造必须先定义：不可变提交计划、受影响状态预留、世界内完成消息、重复结果处理、关闭时排空、重启恢复，以及旧同步写者的协调。

仅把 `Store.clone()` 交给线程并不能消除原共享锁的等待；另开连接也不能跳过 SQLite 写者竞争。这个改造必须单独测量和验收，不能混在第一次 NPC 记忆的提交里。

## 7. 持久模型与迁移

### 7.1 第一阶段的六张小表

表名为拟定命名；字段最终以实现评审冻结，不能仅复制表格就宣称迁移完成。

| 表 | 核心字段／约束 | 存什么，不存什么 |
|---|---|---|
| `world_story_continuities` | `continuity_id` 主键、schema/content 版本 | 这段世界历史的身份；不每次启动重新生成 |
| `world_story_actors` | `(continuity_id, actor_id)` 主键；template/presentation/map、状态、计划、revision | 重要 NPC 的持续状态；不存每帧 sprite 信息 |
| `world_story_scenes` | `(continuity_id, scene_id)` 主键；causal_root、phase、revision、状态 JSON | 车、工具、当前场景后果；不是通用物件引擎 |
| `world_story_actions` | 主体＋requestId 唯一；动作、规范化参数、结果、来源事实引用 | 跨重启幂等；不以连接 ID 作为永久归属 |
| `world_story_facts` | `fact_id` 唯一；主体、场景、因果根、前后版本、kind、证据、rule_version | 发生过的变化；不记录未发生的动机和人格 |
| `world_story_memories` | 观察者＋主体＋fact＋kind 唯一；知识来源、文案键、版本 | 谁知道哪件事；不是全服好感数值 |

主体使用带种类的字符串身份，例如 `Player { character_id }` 与 `Npc { actor_id }`；持久 ID 的生成复用项目已有安全 ID 约定，不能拿 `tick` 或客户端时间拼永久主键。

事件 ID、较大提交序等若出现在 TS 协议，优先用字符串；有限 `revision` 明确范围并用检查递增，不发生整数绕回。不要引入一个 `u128` JSON 数字再让浏览器静默丢精度。

### 7.2 事实的最小形状

```text
StoryFact
  fact_id, continuity_id, scene_id, causal_root_id
  subject: Player(character_id) | Npc(actor_id)
  kind: CartBraced | CartRighted | TravelStarted | TravelArrived | ...
  before_revision, after_revision
  actual_changes: 有限、类型化的状态差异
  knowledge_basis: 参与者/受益者/已验证目击条件
  rule_version, content_version, committed_at
```

`actual_changes` 不是任意大 JSON 杂物箱：每种 kind 有允许字段、大小上限与版本。记忆只引用已提交事实；P1 不制作传闻传播。未来有传闻时，需保存转述来源，不能把传闻直接提升为事实。

### 7.3 不给旧角色伪造过去

迁移只创建表和显式声明的初始场景。已有角色默认没有帮助记忆；不能因为已完成某个原版任务，就批量推断「这个玩家愿意承担」或生成与阿苇的旧事。

新增重要 NPC 可有作者声明的初始过去，但必须标注 `AuthoredInitialHistory`，与实际运行中发生的事实区分。预写过去不附带预写未来的胜利。

### 7.4 启动和恢复顺序

```text
既有 Store::init / 角色迁移完成
    → world-story 增量 schema 校验
    → 加载当前原版地图和玩法
    → 加载并验证原创 StoryCatalog
    → 恢复 continuity / actors / scenes / 必要记忆索引
    → 将重要 NPC 映射为当前地图表现
    → 验证场景引用和版本一致
    → 开始接受相关互动
```

只加载当前小切片与必要索引，不在启动时扫描每个角色一生的全部事件。后续历史增长再做分页与缓存；P1 没有必要先开发冷存储平台。

### 7.5 配置更新与保留

原创配置独立 `storyContentVersion`。配置更新不得自动重置已修好的车、重新生成事故、改变旧承诺条款或删除仍被记忆引用的事实。

删除内容时保留历史引用与墓碑信息；未知规则版本进入明确的只读／待迁移状态。不能把未知值当 `Overturned`，否则一次热更新就会擦掉所有人的帮助。

事实压缩可在后续实施，但所有支撑有效承诺、权柄与具体认人对白的锚点必须保留；幂等回执清理也不能使同一场景动作重新生效。

## 8. 协议、对白与前端落点

### 8.1 新增意图：只描述「我想做什么」

下面是拟新增契约示意，最终名称由共享协议唯一负责人冻结：

```typescript
// 拟新增到 shared/protocol.ts 的 ClientMessage 联合类型。
type WorldStoryInteract = {
  type: 'worldStoryInteract';
  requestId: string;
  sceneId: string;
  objectId: string;
  action: 'braceWheel' | 'rightCart';
  expectedRevision: number;
};
```

请求不含 `playerId/npcMemory/score/award/success`。`objectId` 只是指向一个已登记对象，World 仍要检查它是否属于目标场景、当前地图和合法互动范围。

服务端在 `protocol.rs` 添加对应 serde 枚举、字段重命名和 `ClientMessage::valid()` 分支；同步更新 TypeScript、发送者、接收者和相关机器人检查。入站保持当前大小和频率防线，新互动另有小型业务频控，不能靠每秒 60 包的连接总上限承担全部保护。[R05][R16][R17]

### 8.2 返回值与快照

```typescript
// 拟新增。回执只解释该次请求，不是再次执行动作的指令。
type WorldStoryResult = {
  type: 'worldStoryResult';
  requestId: string;
  success: boolean;
  code: string;
  sceneId: string;
  revision: number;
  factId?: string;
};

// 拟新增到当前地图 snapshot 的小型共享列表。
interface WorldStoryObjectState {
  id: string;
  sceneId: string;
  visualKey: string;
  x: number;
  y: number;
  phase: 'overturned' | 'braced' | 'ready';
  revision: number;
}
```

这只是 P1 的有限形状，不是以字符串参数调用任意世界规则的通用 RPC。

`worldStoryObjects` 在正常快照中只包含当前地图物件与版本，不附每个玩家的记忆、候选倾向或 NPC 秘密目标。空间坐标、物件阶段对同图观察者一致。按钮可按已知状态可用，但服务端仍重新验证。

角色自己的回应继续走 `npcResult`；P1 无需额外「天命提示」总线。动作结果丢失时，同 requestId 可以查询／重发取得结果；NPC 对话消息丢失时，重新对话读取当前事实，不补发第二份奖励。

### 8.3 对话路由必须保持原版可用

`handle_npc_talk` 先执行现有身份、地图、可见性和距离检查。随后只针对 `World.story.presentation_to_actor` 中的专属原创实例，转入小型 `handle_story_npc_talk`。

原版仓库、任务菜单、导师转职和一般脚本默认走旧分支。注册校验禁止把已承担原版商店／主线职责的摆放实例直接占用为阿苇。即使复用同一素材模板，路由也按**实例绑定**，不按 templateId 抢走整个模板族。

新路由从已提交记忆构造受控的 `DialogueView`／`npcResult`，沿用语言选择和窗口。任何菜单中能改变场景的选项都调用相同动作校验与提交函数，不能在拼对白字符串时直接改表。

### 8.4 前端责任清单

| 文件 | 这轮可以增加什么 | 不能承担什么 |
|---|---|---|
| `app/main.ts` | 注入互动回调；构造 requestId；接收回执；管理连接/地图代次 | 识别人格、执行规则、拼接几十个事件剧情分支 |
| `scenes/world.ts` | 创建和更新 `StoryObjectView`；转发互动；离图清理 | 持久保存车是否修好、用动画结束判成功 |
| `features/world/story-object-view.ts` | 根据 phase 显示物件、近距提示、受控点击区域 | import Connection 直接发包、创建第二份权威场景 |
| `features/npc/dialogue.ts` | 显示现有 `npcResult`；必要的请求匹配与拒绝提示 | 查询整个 NPC 记忆库、在本地发明认人台词 |
| `network/session.ts` | 沿既有连接路径传递消息；必要的新增消息形状防护 | 重新设计 WebSocket 连接、顺手重做 HMR |

### 8.5 生命周期与跨图消息

同一个 phase/revision 的重复 snapshot 只更新显示，不重播「第一次修好」动画、不增加监听器。回执先到而场景资源未加载时，只存有限待处理结果，不创建孤立 View。

切图、退出、重登和 Scene 销毁时清理互动监听、临时动画、提示和待处理点击。旧连接或旧场景的异步回调不能重新打开旧 NPC 窗口。

后端已提交的帮助不因玩家切图取消；只是其临时反馈不再发送到错误场景。将「业务已经提交」与「当前适合播放动画」分开。现有 app 装配和 Connection 的连接代次检查应继续保留。[R23][R25]

### 8.6 版本与构建产物

基线为协议 13、内容 `tms273-9`；真正合入时先检查 HEAD 是否已被其他任务推进，再由唯一协议负责人分配下一个兼容版本，不在并行工作中各自写死 14。[R16][R17]

若新增 wire 结构需阻止旧客户端加入，按现有严格版本握手同步升级；不能仅新增一个 story 版本字段就绕过基础协议不兼容。若资产 manifest 也变更，同步内容发布与运行检查。

`启动3010.command` 当前服务的是构建包。修改 TS 源码不等于用户正在玩的包已变；上线按现有脚本流程由用户决定重启时机，不宣称本计划已自动拥有 HMR。[R03][R21]

## 9. 内容装配：原创扩展不污染原版导出链

### 9.1 `shared/world-story.json` 的边界

该文件是小型、版本化的原创场景目录，第一版只包含一位重要 NPC、一辆车、两个动作、少量对白和已验证的摆放绑定。服务器加载路径拟为 `WORLD_STORY_FILE`，默认指向此文件；开关必须显式配置，不根据角色职业自动启用。

目录最少描述以下信息：

| 内容块 | 必须声明 | 启动检查 |
|---|---|---|
| 元信息 | `storyContentVersion`、`source: project-original`、所依赖原版内容版本 | 版本非空、兼容性成立 |
| 重要 NPC | actor ID、表现 ID、素材模板、原创名称、初始状态 | 身份不冲突，模板及可用帧存在 |
| 场景 | 场景 ID、初始因果根、物件、初始 phase | 唯一；不得覆盖持久的现存状态 |
| 摆放绑定 | 当前真实地图 ID、坐标、落脚依据、互动范围 | 地图真实存在、坐标有限、可达，不使用 `map_for` 的默认地图回退 |
| 动作 | 有限枚举、允许前置、明确状态转移 | 不接受任意脚本文本或客户端传来的后果 |
| 对白 | 本地化文字、证据要求、当前物件条件 | 缺证据不能播放对应认人台词 |
| P1b 计划 | 可行目标、路线引用、到期条件、失败退路 | 路线与端点合法，不越过原版锁定条件 |

服务端对地图不存在必须失败或禁用该场景并明确报告，不能因为现有 `map_for` 有兜底行为，就把场景静默放在出生地图。[R13]

### 9.2 服务器规则与客户端素材分开发布

NPC 记忆、识别条件、秘密目标只在服务端。客户端只获得呈现所需的 `visualKey`、素材映射、坐标和状态；发布前检查不能把整份后台规则无差别复制到公开 assets。

复用已有 manifest 模板时不改导出内容。确需原创车体资源时，在现有资源装配链追加明确的原创资源入口并校验，不能直接修改 `dist-tms273` 的打包文件，不能把未确认的 WZ 资源名写成已存在。

`check_world_story.cjs` 与服务端 `StoryCatalog::validate` 分别负责离线和加载期检查；前者失败应先于重启。不能只用「源码存在某个字符串」证明当前发布资产正确。

### 9.3 原版任务隔离

不把天命状态写进 `player_quests`，不复用 `quest_id = 36301` 的交互发放接口做修车。源码中的 `commit_quest_interaction` 对该原版任务及指定道具作了有限白名单；扩成任意发奖会破坏原有安全边界。[R11]

本场景不新增原版任务灯泡，不修改原版技能书、不占用原版任务 NPC，也不让主线缺陷被原创支线掩盖。

## 10. P2：从被记住到倾向浮现

### 10.1 第二阶段的真正输入

只有已经提交的实际行为和相关后果可以进入识别。首次翻车内的垫木楔、扶正车、被感谢共用一个因果根，其中「被感谢」不是新的行为证据。

P2 只选择一条候选方向，例如「为后来者留路」，增加少量不同情境：一次修复、一次自愿返程维护、一次实际保护了他人撤离机会。必须使用已经实现的行为原语；没有真实掩护判定，就暂不把「站在旁边」叫作保护。

### 10.2 小型规则，不是隐藏经验条

规则结果为：

```text
RecognitionCandidate
  subject
  pattern_key
  supporting_fact_ids
  conflicting_fact_ids
  unresolved_context
  rule_revision
```

候选能并存、被质疑或消失。规则不能只取一个总分最大项作为角色本质；更不能把未发生的动作当反证。

首次可使用有限、可审查的证据组合：是否有不同因果根、是否来自不同条件、是否存在实际受益者、是否发生了再次主动承担。条件中的「自由」只表达服务器能证实的场景事实，例如非强制教学、存在可合法绕过路径；不推断玩家真实心理。

同样的修桥操作重复一百次，不等于一百种生活。与此同时，真实重复帮助仍可被当事人记住；防刷的是高阶资格伪增长，不是抹掉固定队友之间的真实关系。

### 10.3 第一份异兆

只允许一个明确的地方存在，例如参加过相关通行历史的旧灯，对其感应范围内的事实产生反应。旧灯不知道另一片地图未与它发生联系的秘密。

异兆只给低风险、可忽略的感知和再次接触机会，不给能力、不立刻命名，也不关闭其他道路。玩家拒绝称呼或不回应邀请不会丢职业能力。

### 10.4 规则升级

候选是可重建投影，新规则可改变解释；过去已发生的事实不能被改写。重建只更新候选，不重发物品、不再执行修车、不重新激活已解除承诺。

P2 的实现先放在已有 `story.rs` 的纯规则区，达到需要独立维护的复杂度再拆 `story_recognition.rs`；不要为一个候选预建人格标签框架。

## 11. P3：馈赠与边界同时成立

### 11.1 第一个权能先改变地方行为，不进入伤害公式

建议用「留灯」验证：角色主动与一处地方灯路建立关系，获得维持该路线的有限能力。它的价值来自别人确实因此能够通行，而不是获得额外攻击百分比。

同源边界是：同一份维持只能锚定在已明确承担的范围；不能同时把这份力量用于封死受其承诺保护的通路，也不能无限复制到任意地图。

这是候选规格，实施前必须把「作用对象、进入条件、现有退路、离开／中断后果」写成可测试规则。若只能用「降低攻击力」表达代价，说明馈赠和身份关系还没有设计清楚。

### 11.2 先有条款，再有接受事实

拟新增 `Covenant`：

```text
id, continuity_id, bearer
terms_key, terms_revision, terms_digest
scope, accepted_by_fact_id
status: Active | Released | Broken | Transferred
source_revision
```

条款至少用朴素语言说明：能做什么、在哪里有效、不能兼得什么、如何退出、何时实际失效、会影响谁。玩家通过明确动作接受，不能因读过对白或踏入地图就被永久绑定。

接受、状态、有限能力来源和回执同一提交边界；解除写新事实，不删除旧事实。修复关系也不是花钱清空历史。

### 11.3 不误用现有技能与 Buff 实现

源码已有职业技能和 `DerivedStats` 字段，但本次未核实一个可直接复用的通用天命效果接口。因此 P3 首个馈赠只作用于已实现的故事场景能力，不假定可以调用不存在的 `EffectSystem::grant`。[R06][R17]

未来确需战斗效果时，必须进入当前唯一属性／技能结算路径，带有效来源与条款版本；不能在登录时加一次数值、退出时凭猜测减回，也不能建立平行的天命伤害公式。

### 11.4 与后台保活的连接

现有 `Detach` 表示控制连接离开，并不立刻删除角色；`Exit` 才负责退出。天命不能监听 socket 断开就生成 `CovenantBroken`。[R05][R24]

边界依据实际条款和世界事实：角色是否仍在作用范围、灯是否存在、是否有新的承接者、维持条件是否还成立。浏览器隐藏、网络故障、未读邀请都不等于主动背叛。

可能因为真实退出而不再具备某项主动维持能力，但记录应区分「维持结束」「履约失败」「主动背离」；不能把技术掉线一律写成道德评价。持续承担必须提供合理移交／退出机制，不能变成强迫每天上线的续费任务。

## 12. P4：NPC 的独立道路与无人见证的历史

### 12.1 从一位重要 NPC 开始

P1b 已证明一个 NPC 能按有限目标推进；P4 再增加知识冲突与承诺，不升级成所有村民都跑一个复杂规划器。

每个重要 NPC 读取：自己知道的事实、当前目标、可用资源、已接受的承诺。选择一个可行行动，交还 World 校验并提交。NPC 决策不是第二个世界模拟服务。

NPC 没有玩家的 socket 或角色背包结构，因此不能假装把玩家请求中的 `id` 随便换个字符串就完成同规则。`StoryActionContext` 必须显式适配 NPC 的位置、能力和资源，然后共用相同的场景规则与事实提交；未实现的玩家专属能力不能被 NPC 免费调用。

### 12.2 四种变化的可执行含义

| 变化 | 真实前提 | 需要留下什么 |
|---|---|---|
| 坚持 | 原目标仍可行，仍选择承担对应代价 | 被放弃的备选、实际行动与后果 |
| 动摇 | 已知的新事实使两个目标冲突 | 新知识来源，而非随机变阵营 |
| 背离 | 在理解承诺的前提下选择违背它 | 主动行动、条款、实际损失／新关系 |
| 争位 | 历史与承担使其具备资格，并出现具体互斥主张 | 资格来源、争议对象、后续裁决事实 |

### 12.3 时间与恢复不能混用

必须区分三种情况：

**玩家不在场但服务运行**：到期计划仍由世界循环调度；不把「地图没有玩家」当成永久暂停。

**浏览器掉线**：不影响 NPC 的世界计划；个人未接受的承诺不因此成立。

**服务进程停止**：P1b/P4 首版不补演停机期间所有移动与选择。恢复后加载持久计划，重新验证到期行动，按有限预算继续，不直接把整段旅行／争位全部判为成功。

现有 `World.tick` 在构造时从 0 开始，不能把旧进程的绝对 tick 直接存成新进程待办期限。[R07]

拟使用持久计划 ID、计划版本和 `not_before_utc_ms` 表达最早可尝试时间；运行期调度可用单调时间，恢复后重新映射。墙钟到期只是尝试资格，不是成功证据。时钟回拨／突跳要有重验证和单轮预算，不能在一次启动中无限追赶历史。

同一个计划步骤有稳定幂等身份，重启不会重复抵达或重复转移货物。随机决策若被采用，应记录实际选择和必要输入，不能在每次恢复时重抽一次过去。

### 12.4 玩家回来如何认识没有亲历的事

先看共享结果：人去了哪里、车是否还在、道路有什么变化。再通过有来源的对话或遗物知道发生过什么。

不能把后台事实全集直接塞进足迹簿，冒充玩家已知；也不能让 NPC 为了迎接玩家反复重演已完成的人生。

## 13. P5：地方权柄，不是全服神位排行榜

### 13.1 唯一性只落在具体互斥位置

```text
AuthorityKey = continuity_id + scope_id + existence_id + law_slot
```

例如「这处根火的当前运行模式」，不是整个「存续大道」。同一大道可以有许多人、NPC 与地方权柄；唯一的是某个无法同时采用两个状态的存在。

### 13.2 四步分开实现

| 步骤 | 输入 | 输出 | 不得偷换成 |
|---|---|---|---|
| 资格 | 真实历史、已承担条款、领域规则 | 有理由的候选 | 刷经验最高者 |
| 争议 | 同一存在上的不相容主张 | 争议事实与可行路径 | 同道者自动敌对 |
| 裁决 | 世界内行动、协议、让位或合法新解法 | 已解决具体主张的事实 | 谁先发包／谁先获得 SQL 锁 |
| 落位 | 裁决事实＋预期版本 | 唯一有效记录与 epoch | 一次胜利就获得 GM 权限 |

落位、历史和规则状态改变在同一提交边界内；旧 epoch 的表现或效果不能继续生效。前端缓存不是权柄来源。

### 13.3 根火样本

「封存」保护旧世印记的完整，「传续」允许其变化而进入未来。二者的冲突必须来自当前根火真实的结构约束；不是系统看到两个人都走存续，就刷出一场必死神战。

如果建立第二载体、分阶段运行或其他合法方法真的解除互斥，就允许第三条路。若某方案因不可逆损坏不能成立，应提前存在可发现的规则依据，不能最后一刻补设。

NPC 可以先取得资格、选择让位或完成裁决，不给它隐藏必败标记。玩家输了权柄仍保留旧历史与关系；失去职位不等于一生作废。

### 13.4 权柄的工程护栏

只能调用已实现、白名单内的地方规则；不能任意删除玩家、改背包、封锁所有原版成长、强迫非参与者 PvP。

首个权柄保持同一 World 和同一 SQLite 提交边界。跨频道、跨进程与合服规则另行设计，不在 P1 就加分布式锁或租约。权柄不因未上线若干天自动失效；失效依据条款、存在状态和已发生的新事实。

### 15.1 最小人工体验验收

让一名测试者只知道「这里有个人遇到了麻烦」，不要先告诉他在测试天命。先观察是否能理解并自由绕过；再观察帮助后的实际变化；之后引导正常再次相遇，而不是直接把认人对白贴给他。

只问几个围绕事实的问题：他认出了什么？你相信他为什么知道吗？你觉得世界哪里变了？不参与是否仍能正常玩？不要先问「你感不感动」，那会把测试变成迎合。

## 16. 发布、回退与维护

### 16.1 初次发布

由用户确定允许发布时机，经 `启动3010.command` 使用现有数据库和资源路径启动；不创建另一套开发脚本，不触碰 3000，不清空陪测机器人账号。[R21]

在初次执行数据库迁移前，需要可恢复的数据库备份。SQLite WAL 模式下不能把运行中的主 `.sqlite3` 文件单独复制就声称获得一致备份；使用明确的一致备份流程，且由当前运行策略允许。[E01]

本轮只提供计划，未执行备份、迁移或重启。

### 16.2 可选写入口降级

拟新增一个小型 `WORLD_STORY_WRITES` 配置开关，控制新互动与 NPC 状态推进。关闭时，已经提交的场景和记忆仍可读取，客户端显示暂不可操作；不能重新显示为未修复，也不能以异常为由抹去贡献。

从未启用过原创扩展的部署可以完全不装配该场景。曾经启用后的维护模式与「世界从未有过这个场景」不是一回事。

这一开关不是新的运营控制台；初版仅通过既有配置装配，不新增未经授权的远程 GM API。

### 16.3 回退原则

P1 不改原版地图碰撞、不改背包、不改主线，因此可通过停止故事写入、保留表和恢复对应兼容代码来隔离故障。回退不能删除新增表以求「干净」。

如果旧版本不能解释已提交的新 phase，保留只读解释或明确禁用该场景；不能用默认值重置。P3/P5 引入能力与规则效果后，必须另外制定来源失效与状态迁移方案，不能照搬 P1 的轻量回退。

### 16.4 诊断只记录必要字段

建议记录 `continuity_id/request_id/actor_kind/actor_id/scene_id/fact_id/revision/code/lock_wait/tx_duration`。不写登录 token、密码、私聊全文、现实人格推断或全量背包。

需要解释一句对白时，开发查询应能串起「对白键 → 观察者记忆 → 来源事实 → 实际状态变化」。这个解释入口是开发诊断，不把 NPC 的全部秘密公开给所有玩家。

提交前同时回答下面六个问题：

1. 把天命相关词汇删掉，世界是否仍能具体认出一个人？
2. 把认人对白全部隐藏，现场是否仍有真实、持久的后果？
3. 把客户端关掉，再重建 World，事实、记忆和回执是否仍能对应？
4. 把玩家从整个事件中移除，NPC 是否仍有合法的下一步，而不是永远等主角？
5. 把身份标签删掉，馈赠与边界是否仍由同一段关系自然成立？
6. 把策划预想的结局删掉，合法的不同选择是否真的能够改变结果？

**本版的第一项开发任务不是「实现天命系统」，而是：在当前 `World + Store + npcResult` 链路中，让一次帮助成为可靠的世界历史，并让一个具体的人下次认出它。**

|---|---|---|

| E02 | [Tokio 官方 API：mpsc][E02] | 有界通道提供背压，内存排队与持久业务提交是不同问题。没有据此给项目添加新消息总线。 |
