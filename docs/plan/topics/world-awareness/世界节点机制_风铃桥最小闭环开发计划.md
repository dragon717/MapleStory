# 世界节点机制：让这里因为我们重新活过来
## 《风铃桥》最小闭环设计与开发计划 v0.1

> 日期：2026-09-10  
> 适用项目：冒险岛复刻与原创权威世界；Rust 服务端，Web / TypeScript 客户端。  
> 本次范围：一张地图、一个公共节点、一座断桥，走通恢复前、恢复中、恢复后，以及个人回应与公共共享。  
> 文档性质：原创机制提案与开发规格，未修改、运行或审查项目源码。类型、目录、数值与时长是建议，不代表仓库现状或已经验证的结论。  
> 核心命题：不是“完成一个任务，获得一份奖励”，而是“我帮了一点忙，这里真的变了，而且后来的人也用得上”。

---

## 0. 决策摘要

世界节点不是一个换了外观的据点等级系统。它是**一个区域中，交通、停留、供给、见闻和人与人关系重新接上的地方**。

灯塔、古树、圣泉、小桥可以是不同的文化表达，但它们不能只是同一条“生命经验条”的皮肤。灯塔改善辨路条件，古树提供遮蔽与栖居条件，圣泉恢复可用水源，小桥恢复通行能力。它们改变各自真实的世界条件，再让实体据此行动。

本方案做出六项约束：

| 决策 | 本版选择 |
|---|---|
| 世界从什么出发 | 实体事实与目标 → 真实缺口 → 有效行动 → 新事实 → 行为与回应 |
| 个人与公共怎样划分 | 公共事实只有一份；个人记忆、见闻和表达可以不同；不同物理事实必须属于明确的独立实例 |
| 首个节点是什么 | 原创公共测试区域“风铃桥渡口”，桥梁是关键设施，不另造一套灯塔前置系统 |
| 如何恢复 | 玩家与 NPC 解决具体缺口，不把所有玩法兑换成一种通用贡献积分 |
| 主要回报是什么 | 通路可用、货车继续前进、旅人愿意停留、NPC 记得真实帮助、公共历史保留 |
| 首版不做什么 | 全服经济、全地图节点网络、六套完整生活技能、跨服共建、排行榜、强制维护与周期坍塌 |

**最重要的验收画面：**甲搬过材料后离开；乙接着完成剩余工作；甲回来，桥已通车。后来从未贡献过的丙，也可以直接走过这座桥。甲遇见知情的修桥匠，得到一句准确而克制的回应。

这不是先搭一个庞大的“世界大脑”。沿用已有翻车事件方案的窄入口：先验证同一个 NPC 能记住一次真实帮助，再把这个能力接到公共设施的变化上。[P1]

## 1. 定义：地图、节点、设施、事件不是同一件事

### 1.1 四个概念

| 概念 | 负责什么 | 风铃桥例子 |
|---|---|---|
| 地图 Map | 可游玩的空间与表现承载 | 河岸、上下层平台、绕行路、两侧停靠点 |
| 世界节点 WorldNode | 一组彼此关联的区域恢复目标、设施和历史 | 风铃桥渡口 |
| 设施 Facility | 实际提供某种能力的实体 | 桥梁提供通行，棚架提供停留位置 |
| 世界事件 Incident | 在当前事实下发生的一次具体变化 | 货车侧倾、木料送达、桥段装好、第一辆车抵达 |

产品上可以先让每张图有一个主要生命节点，但代码不要强制“一张图只能有一个节点”，也不要用 MapId 替代 NodeId。地图是空间组织，节点是世界关系的组织。首版只配置一对一，不提前实现跨地图节点。

### 1.2 节点恢复的四个可观察结果

**连接恢复。** 原本断掉的路、视线、运输或交流渠道重新可用。

**停留成为可能。** 实体不只是经过，还能休息、扎营、工作和交谈。

**流动真实发生。** 至少有一个带稳定身份与目的地的实体真的走过新通路，不只播放一辆无身份的背景车。

**历史留下来。** 世界记住发生了什么，具体 NPC 只记住它有来源可知的事。它们不是全知的服务器日志阅读器。[P1]

“信任”在首版表现为具体人记得可靠的共同经历，不增加全服信任值或道德分数。

### 1.3 一条因果链，而不是六个并列系统

```text
事实：桥面缺失，货车无法跨河
目标：送货者要把这批货运到河对岸
缺口：通路不适合车辆；侧倾的货车也需要扶正
行动：玩家搬材料 / 帮忙固定 / 扶车；NPC 补上剩余工作
新事实：桥可通行，货车恢复移动能力
实体行动：同一货车选择新路线，抵达并卸货
后续条件：工具抵达、棚架就绪，形成一个可停留的位置
后续行为：旅人坐下，修桥匠继续工作，新的交谈机会出现
个人回应：知情者认出做过具体事情的人
公共历史：这座桥在某个时刻被共同修复
```

首版事件内容可以手写、初始状态可以预设；关键是触发、结果和归因真实读取世界事实。不要把手写内容伪装成完整自主经济或无限涌现。

## 2. “我的世界”与“我们的世界”：两层体验，一份公共现实

### 2.1 个人层不是一套隐形的公共物理世界

同一公共地图中的玩家可以拥有不同经历，不能拥有彼此矛盾的桥梁碰撞和可交互怪物。

| 内容 | 归属 | 规则 |
|---|---|---|
| 桥是否能走、道路是否连通 | 公共事实 | 同一共享世界中一致，服务端决定 |
| 怪物生死、仇恨、掉落与可交互旅人的存在 | 公共或明确实例事实 | 不做每人不同的“公共怪物状态” |
| 商队位置、货物状态、工地库存 | 公共事实 | 不因观察者不同而变成多份资源 |
| NPC 对谁点头、称呼和私人对白 | 个人关系表达 | 必须有对应 NPC 的知情来源 |
| 地图探索记录、旧景记忆、旅行手记 | 个人事实 | 不能覆盖当前公共地形 |
| 非交互的短暂回忆、装饰性演出 | 个人表现 | 不改变碰撞，不遮挡公共危险，不冒充正在发生的公共事件 |
| 私人营地、个人修桥章节 | 独立实例，后续项 | 明确 InstanceId、进入边界和退出位置；公共桥不会因此私自通行 |

**个人化的优先实现顺序：记得我 → 对我说不同的话 → 我记得这里的过去。**

“只有我能看到旅人更多、怪物不同、桥被修好”的完整体验仍然可以存在，但应放在独立章节或明确的个人实例中，不混入同一公共地图。本版不为保证人人都有“第一次修桥”而新增私人副本。

### 2.2 灯塔驱散迷雾时也遵守同一边界

个人探索迷雾表示“我还不知道这里”，可以因人而异；世界中的真实浓雾表示“当前视线和环境条件”，同一公共范围应一致。

灯塔可以公开改善辨路条件，同时帮助到场者更新个人地图知识。不能因为玩家尚未做个人节点任务，就让他撞上队友眼里不存在的墙。

### 2.3 公共世界的共享范围

```text
SharedWorldId：共同拥有设施事实和历史的逻辑世界
RegionId：当前节点所属的区域权威边界
MapId：空间资源 / 地图定义
MapInstanceId：当前承载实体的地图实例
ChannelId：承载或分流维度，默认不单独决定桥梁历史
NodeId：稳定的节点身份
WorldEpoch：仅用于显式重置、测试隔离或版本迁移隔离
```

首版固定一个 SharedWorldId、一个公共 MapInstanceId，用两个客户端验证。

后续同一 SharedWorldId 下的多个频道共享桥梁设施状态；频道可有不同的临时路人，但不能各自扣一次同一批货、生成一次同一货单的交付收益。持久商队实体必须有明确的唯一归属；其他频道若显示装饰投影，不可交互、不可产出资源。

跨频道时允许网络传播与动画存在延迟，但关键通行需要版本门槛：承载实例尚未应用最新设施版本，就先同步或暂缓相关进入/跨桥操作，不能以陈旧副本独立裁决相反的公共通行事实。P0 不实现跨频道基础设施，只固定这一扩展契约。

不同服务器不默认属于同一个共享世界。跨服共建是独立产品决定，不因为都有同名地图就自动合并历史。

### 2.4 晚到与未贡献玩家

晚到玩家直接看到当前公共状态，不再次经历一座专门为他断掉的桥；未贡献玩家可以免费使用公共道路和休息位置，不检查贡献资格。

没有参与的人可以听到：“这座桥前些时候才修好。”不能听到：“多亏你修好了桥。”

已参与者可以查看自己的真实参与记录，但没有在线见证过开通，就不自动记成“亲眼见证第一辆车过桥”。“参与”“服务端已发生”“客户端已收到”“玩家实际注意到”是不同概念。

## 3. 首个节点：《风铃桥渡口》

### 3.1 场景范围

复用一张既有测试地图的局部空间，制作一条断桥捷径、一条始终可用的绕行路，以及同图内的出发点与到货点。

初始场景包括：一座桥面损坏的桥、一个旧棚架、一辆侧倾但结构可修复的货车、有限的修桥物料、送货者阿榆与修桥匠。旅人使用复用形象，不先制作完整城镇人口系统。

“风铃桥”是本提案的临时原创名称，不宣称是 TMS273 原作地图。它与既有单人序章中的树桥、热流等方案分开，不擅自把序章改成全服公共破坏区。[P2]

### 3.2 恢复前：玩家先看见一个断点

桥面缺了几段。货车停在岸边，修桥匠整理旧工具，风铃偶尔碰响。路仍然能绕，只是车辆不能走这条捷径。

不弹接取窗口，不强制镜头，不标记“世界节点 0/100”。靠近可以看见正常的交互提示：检查桥面、搬一份木料、扶稳货车。

一句环境对白足够：“以前这条路每天都有人过。”不要求玩家先读完背景故事才允许行动。

### 3.3 恢复中：每一次进展都改变现场

玩家送来一份修桥材料，公共材料箱真实增加库存。修桥匠开始一项有用料、有工作时间的安装作业。桥上出现一段固定好的新木板，而不是只变动面板上的百分比。

另一个玩家扶正货车，阿榆开始固定货物。即使桥还没通，车也不会重新侧倾。两条改善可以并行推进，不形成每人必须依次完成的任务链。

玩家离开，NPC 接续能够完成的工作。再次回来时，看见的是当前事实，不保证正好卡在等待他按按钮的一瞬间。

### 3.4 恢复后：不是庆祝结束，而是生活开始

桥满足通行条件，服务端启用通路。那一辆已经扶正、货物已固定的货车选择桥梁路线，去往同图的对岸停靠点。

阿榆卸下货单中真实存在的工具包，修桥匠利用工具整理旧棚架。棚架成为可停留位置后，一位已有旅行安排的路人停下来，而不是凭空多出一排“繁荣 NPC”。

本版做到一个人坐下、一辆车通过、一次具体重逢就够。更密集的商队与聚落是后续内容，不是验证这段感受的前置。

### 3.5 三名玩家的验收剧本

| 玩家 | 发生了什么 | 得到什么 |
|---|---|---|
| 甲：早来、只帮一点 | 搬来第一份材料，随后离开 | 一段真实贡献；修桥匠记得交接；回来可以看到后续结果 |
| 乙：接着做 | 送来其他材料，扶正货车 | 另一组具体贡献；不会独占“完成整座桥”的功劳 |
| 丙：晚到、不贡献 | 开通后第一次路过 | 直接使用桥；知道这里有人共同建设过；没有欠债感 |

甲、乙、丙可以同时组队过桥。不存在甲看到桥、丙掉进河里的情况。

## 4. 状态模型：保存事实，推导阶段

### 4.1 保存的最小事实

| 对象 | 需要的事实 | 不应替代它的字段 |
|---|---|---|
| 桥梁 | 已安装桥段、当前施工作业、已开放的通行能力 | 节点贡献经验 |
| 工料箱 | 材料可用量、预留量、消耗去向 | 累计捐赠总分 |
| 货车 | 姿态、移动条件、当前位置 | 扶车任务完成人数 |
| 货单 | 稳定 ID、载货、出发地、目的地、运输状态 | 某次装饰动画播放完成 |
| 棚架 | 是否可用、停留槽位 | 世界繁荣值 |
| NPC | 稳定身份、计划、所知事件 | 全体共享的玩家善恶分 |
| 节点历史 | 首次开通、首次到货、首次形成停留点的事实 | 每次登录重新生成的完成记录 |

### 4.2 五个阶段只用于表达和里程碑

| 阶段 | 由什么事实确认 | 主要表现 | 可用能力 |
|---|---|---|---|
| 沉寂 Dormant | 尚无有效恢复行动，桥断、交通停滞 | 旧木、冷清、停下的车 | 绕行与观察 |
| 有回应 Responding | 第一份有效物料交接或其他真实改善已发生 | 工匠接手、车或物料发生变化 | 局部交互改善 |
| 修复中 Restoring | 至少一个桥段已装好，尚未通车 | 新旧木板、工人动作、材料变化 | 工地逐步恢复 |
| 已连通 Connected | 桥满足通行条件并完成权威地形激活 | 可真正过桥、货车可以选择此路 | 公共通行 |
| 有生活 Inhabited | 至少一次真实到货，停留点已建立并被使用 | 卸货、休息、见面与交谈 | 公共停留和关系延续 |

阶段由事实推导，或作为可重建的读模型缓存。节点不能靠直接写 `stage = Inhabited` 来代替修桥、运输和停留事实。

将**历史里程碑**与**当前活跃状态**分开：曾经形成停留点是历史；此刻无人、下雨、夜间安静是当前状态。夜里路人离开，不应让节点回到“未恢复”。

### 4.3 桥的首轮测试配方

以下是便于测试的占位参数，不是最终平衡数值，也不代表真实工程用量。

```text
桥段数量：3
每段所需：木板 2、绳索 1
总用料：木板 6、绳索 3
首版施工作业：一名 NPC 顺序安装桥段
每段基础作业时间：10 秒，仅用于观察完整原型过程
桥梁开放条件：3 个桥段完成，服务端通行补丁已激活
```

测试物料最初放在同图的公共工地物料堆中，数量有限。搬运是两个容器之间的真实移交，不是生成材料。P0 不必先接采集技能、交易系统或玩家珍贵背包物品。

货车的运输货物是单独的工具包，与用于修桥的木板、绳索分开，不能把已经消耗在桥上的材料再计成到货物品。

上述几十秒的施工节奏仅用于压缩演示，不能直接当作正式公共世界的开放参数。正式节奏应依据参与机会与观察结果另定；不要为了让每位新玩家看到断桥而冻结或回退公共工作。

### 4.4 库存和作业守恒

```text
可用库存 = 初始库存 + 累计入库 - 当前预留 - 累计消耗 - 累计退还

开工作业：可用 → 该 JobId 的预留
完成作业：预留 → 已消耗，同时增加一个实际桥段
取消作业：尚未消耗的预留 → 可用；已完成桥段不回退
```

作业的预留、完成与释放都幂等。一个 JobId 只能完成一次，不能在重启后再次用同一套材料多造一个桥段。

P0 不需要复杂材料替换。未来添加替代配方时，由明确配方决定替代关系，不允许战斗次数直接抵扣缺少的绳索。

## 5. 贡献机制：多种玩法解决同一处现实缺口

### 5.1 不把六种玩法变成六种刷分姿势

| 玩法 | 可以解决什么 | 如何证明有效 | 边界 |
|---|---|---|---|
| 战斗 | 清除正在阻碍施工或通行的具体威胁 | 指向阻碍实体和已结算遭遇事件 | 无关刷怪不给节点加进度，不为站岗硬刷怪 |
| 探索 | 找到可用物料、辨认绕行路线、确认施工条件 | 服务端确认的发现对象或勘查事实 | 同一公共发现不被重复提交成无限资源 |
| 采集 / 搬运 | 把适用材料带到需要它的位置 | 权威资源转移记录 | 不奖励空气捐赠，不强扣稀缺物品 |
| 制作 | 把输入材料加工成适用部件 | 配方、输入消耗和输出去向 | 不要求必须有特定职业在线才能继续 |
| 护送 | 让一批实际运输中的货物抵达 | 唯一货单与到货事实 | 不按跟随时长无上限计分，不以尾刀认定整段护送 |
| 社交 / 协作 | 接手看路、扶稳部件、共同搬物或传递有效信息 | 实际职责变化和对施工/运输的结果 | 聊天条数、互赞、拉小号不产生材料和工程进度 |

所有方式通向同一个世界结果，但不是每一种方式都能无条件替代所有其他方式。材料缺口必须通过物料供给或合理替代配方解决；偏好战斗的人可以解除威胁，让有材料的 NPC 继续施工。

### 5.2 首版只落地两类贡献与一个可选入口

**必须实现：搬运 / 交接修桥材料，以及扶正同一辆货车。**前者改善公共设施，后者改善真实运输实体。两者都不依赖战斗数值。

**可选补充：短时协助固定木板。**仅在前两条成立后加入。它必须减少某个施工 Job 的剩余有效工作，不能只是站几秒后发一份贡献记录。

其余玩法只保留设计位置。若项目已有可复用的威胁、采集、制作能力，再逐条接入，不为一个节点同时开发六套玩法系统。

### 5.3 贡献记录保存“做了什么”，而非“人有多好”

每条贡献至少包含：行为者、作用对象、输入来源、实际转移或完成数量、对应事实事件、节点与世界范围、发生时间、知情者。

搬过材料的人，可以被感谢搬材料；扶过货车的人，可以被感谢扶车。即使两者都帮助了节点复苏，也不把每个人都写成“独自修好了桥”。

对共同动作只分配实际参与份额，不让两个人都获得同一个完整施工量。贡献归属来自服务器确认的参与，不来自客户端自报或最后一次攻击。

### 5.4 超额贡献与并发抢占

节点不无限吞材料。提交前展示当前实际需要，服务端在最终事务内重新判断。

默认不接受超出需求的数量；如允许部分接受，命令须显式携带 `allow_partial`，结果写清实际接收与未接收数量，只扣接收部分。

多人同时填满最后的缺口时，后到者得到“这部分已够了”的事实反馈，材料保留，不制造虚假贡献安慰他。界面应及时撤掉已失效的交互入口，减少白跑。

### 5.5 不强制凑齐不同玩家或职业

不把“必须 5 个不同账号”或“六种职业都交一次”设为基础通行的硬门槛。公共工程可以因多人协作更快完成，但低人口世界必须存在可达的恢复路径。

较大工程可以分布于更长时间和更多需求，不等于人为禁止个人完成。首版通过 NPC 有限而持续的工作能力兜底。

## 6. 世界恢复以后：让实体真的利用新条件

### 6.1 五条足够支撑首版的规则

```text
R1 施工：桥段未完成 && 材料足够 && 工匠可工作
       → 预留材料，创建或推进一个安装作业

R2 开通：全部桥段完成 && 地形激活成功
       → 公共路径可用，记录一次 BridgeOpened

R3 运输：货车能移动 && 货物已固定 && 目的地未到达 && 路径可用
       → 同一 ShipmentId 进入运输，不重复生成货单

R4 停留：工具真实到货 && 旧棚架可修整 && 有合适的 NPC 作业
       → 建立有限停留槽位

R5 回应：NPC 知道某玩家的某次帮助 && 当前重逢语境合适
       → 选择一条准确、低频的回应
```

R1 的“可工作”可以读取已有环境和威胁事实；P0 不新建复杂天气或敌人模拟。R4 的工具包和棚架修整也是明确的手写小作业，不必先做完整建造系统。

### 6.2 新支路不只是百分比触发的贴图

未来“路被踩出来”需要先有可行走的地形，实体选择它并形成真实通行记录，再让视觉磨损逐步出现。先有路可走，再有脚印；脚印达到某个值，不应凭空填平深渊。

新增可通行道路仍由设施或地形变更明确开放。装饰性踩踏只影响表现，不偷偷改变碰撞。

这条规则先写进模板，P0 不实现全地图脚印累计、土壤侵蚀或自动道路生成。

### 6.3 首辆商队不是每人一遍的庆典

`FirstShipmentArrived` 在该节点该恢复周期内只有一次。在线的人可以看到；离线的人回来读取历史并见到结果，不自动重放一辆不存在的“第一辆车”。

之后可以有正常的运输班次，但每班都要有新的合法货单，不能为了让新玩家看到动画而重复交付同一批货。

### 6.4 补给、成长和属性的取舍

本版不发永久攻击力、刷怪效率或必需成长材料。优先给公共便利、通路、休息位置与关系回应。

如后续需要小额即时回报，可复用普通交互报酬并设置明确上限，不能让最佳刷钱方式变成重复制造或重复提交同一问题。首轮情绪验证先不开经济奖励，避免无法区分玩家是在乎世界改变还是奖励。

恢复不能卡住原有练级、主线与核心药品供给。断桥是捷径和故事断点，不是唯一的正常冒险出口。

## 7. 公共工程的长期边界

### 7.1 维护不应变成每日欠债

本版修好的桥永久保留，不因几天没人登录而自动断裂，不收通行费，不要求每日捐赠保住已解锁的基础能力。

未来维护可以影响附加状态，例如路灯亮度、棚架整洁、路人数量或可选服务，但不轻易回收已共同建立的基本通行权。临时灾害如会影响交通，必须另有明确提示、替代路径和恢复机制，不直接列为本版功能。

### 7.2 人少时世界也能继续

NPC 的工作有身份、有计划、有物资来源，不能后台给节点凭空加“人气进度”。测试中没人搬料时，修桥匠可以从有限工地堆慢慢搬运和施工；玩家介入缩短这条真实工作链。

已经有人搬过的材料不重复搬，已完成的桥段不再施工。无人帮助不会被解释成某个玩家冷漠，也不触发惩罚性灾难。

公共工程的需求在恢复周期开始时固定。后续可在新工程开放前根据人口规模选择模板，但不在玩家已经投入后偷偷提高目标，让终点不断远离。

### 7.3 老玩家不能垄断公共收益

不采用最后一下独占功劳，不设“贡献前十才可用桥”，不出售决定公共通路归属的付费材料。

大额贡献者可以被准确记录，但普通帮助者也能留下具体痕迹。物料需求天然有限，再辅以请求限流、真实资源校验与操作反馈，避免把贡献量变成社交地位压迫。

### 7.4 晚来的人不一定要重复建设

一个永久节点不可能无限提供“第一次重建”。不要靠不断拆桥来假装这个问题不存在。

晚来者首先是公共成果的使用者，之后可以成为旅人、护送者、见闻提供者，或参与确有需求的后续设施。那些机会不能保证每人每次进图都有；世界不必永远欠玩家一个待完成任务。

新增棚架、路标、支路等独立工程，只有在玩法验证后才加入。不要用无穷的同类捐赠坑填充所有后来者的参与感。

### 7.5 历史与署名

公共记录优先写事实：“此桥于某日恢复通行”“首批工具已运抵”。个人可自愿显示角色别名，不显示账号标识或其他私人数据。

首版不做自由输入纪念碑、留言墙和全球广播，避免引入审核与刷屏负担。未来开放留言，需有过滤、举报、编辑历史与长度限制，且留言不能冒充官方剧情或别人发言。

## 8. 从已有翻车微事件延伸，不重新开一条大工程

已有方案把第一张开发卡收在“同一个 NPC，两次相遇，一次真实改变”，并明确先验证扶车与记忆，不做完整商队经济。[P1]

本计划与它的关系如下：

```text
已存在的最小事件能力（未实现的就先做）
  扶车 → 权威事实变化 → NPC 当场回应 → 记忆保存 → 再次认出
                                  ↓ 复用
本次增加的公共节点能力
  材料转移 → 公共施工作业 → 桥段变化 → 全员通行 → 同一货车到货
                                  ↓
  个人关系继续存在；公共成果对没有贡献的人也生效
```

不额外开第二套贡献、NPC 记忆、奖励或事件平台。先沿用既有概念与接口，缺什么补什么。

## 9. Rust 权威服务端：先把写入边界守住

### 9.1 首版部署形态

采用单进程、一个区域写入所有者，复用现有世界更新循环。公共节点、施工、货单和相关记忆可以属于少量模块，不需要新增微服务、Kafka、分布式锁或全面 ECS 重构。

Tokio 官方教程展示了由专门任务持有资源、其他任务通过消息请求的模式；简单纯内存状态也可以采用互斥保护，不必把每个对象都改成独立 Actor。[R1][R5]

本方案的具体选择是：**一个地方决定事实，其他地方发送意图或读取结果。**如果现有 world 循环已经串行管理实体，就扩展它，不再新建另一个同时修改这些实体的 NodeActor。

```text
网络会话：鉴权、反滥用、解码
    ↓ 命令
现有世界 / 区域权威边界
    ↓ 校验、决定事实变化
原子持久化：资源 + 节点/实体 + 回执 + 记忆 + 待发布事实
    ↓ 成功后激活
地图碰撞/寻路与公共读模型
    ↓
版本化快照与增量 → Web/TS 表现
```

### 9.2 建议的逻辑模块

| 模块 | 单一职责 |
|---|---|
| `node_model` | 节点定义、事实、历史里程碑与派生视图 |
| `node_rules` | 从当前事实和已验证动作计算变化计划 |
| `node_commands` | 贡献、交互、查询的入口与错误语义 |
| `construction` | 材料预留、作业完成、取消与 NPC 接续 |
| `node_repository` | 事务、幂等回执、持久化和事件发布记录 |
| `node_projection` | 共享快照、个人回应、表现配置 |

这些是建议模块名，不是已经存在的文件路径。开发前应找到现有实体、背包、NPC、地图与存储入口再落位。

### 9.3 不变量

```text
I1 同一公共作用域内，同一设施只有一份权威状态。
I2 一次已成功命令的重发，不重复扣物、不重复施工、不重复记忆。
I3 一条贡献必须能追溯到实际提交的事实变化。
I4 公共通行能力不能由个人进度或客户端字段决定。
I5 一个货单只能到货一次；在途与到货库存不能重复计算。
I6 资源预留、消耗和返还可核对；库存不能为负。
I7 NPC 的个人回应有知情来源，不默认全村全知。
I8 玩家退出、死亡、重连和服务重启不撤销已提交成果。
I9 一个当前可用设施不能只存在于贴图，不存在于权威碰撞/寻路。
I10 无贡献不扣关系、不锁主线，也不取消公共设施使用权。
```

### 9.4 类型草案

以下为边界示意，不是完整可运行代码；ID 类型应复用项目定义。`u64` 等大整数经过 JSON 时建议用十进制字符串编码；JavaScript Number 的安全整数上限为 2^53−1，不能无损承载所有 u64。[R6]

```rust
struct NodeKey {
    shared_world_id: WorldId,
    region_id: RegionId,
    world_epoch: WorldEpoch,
    node_id: NodeId,
}

struct NodeFacts {
    key: NodeKey,
    revision: u64,
    definition_version: u32,
    bridge: BridgeFacts,
    site_store_id: ContainerId,
    shipment_id: ShipmentId,
    camp: CampFacts,
    milestones: NodeMilestones,
    next_action_at_ms: Option<i64>,
}

struct BridgeFacts {
    installed_segments: u16,
    active_job: Option<JobId>,
    topology_revision: u64,
}

struct ConstructionJob {
    id: JobId,
    segment_index: u16,
    reserved_materials: Vec<ReservedMaterial>,
    remaining_work_ms: u64,
    last_settled_at_ms: i64,
    state: JobState, // Working / Paused / Finished / Cancelled
}

struct ContributionReceipt {
    actor: ActorId,             // Player 或有身份的 NPC
    request_id: RequestId,
    payload_hash: PayloadHash,
    node: NodeKey,
    source_event_id: EventId,
    outcome: ContributionOutcome, // 对象、实际资源/工作变化、是否部分接收
    committed_revision: u64,
    committed_at_ms: i64,
}

struct PlayerNodeMemory {
    player_id: PlayerId,
    node: NodeKey,
    participation_event_ids: Vec<EventId>,
    acknowledged_public_revision: u64,
    // acknowledged 表示客户端确认收到，不当作“玩家真的看见”的证据
}
```

货车位置、货单内容、NPC 记忆分别由各自权威实体保存。`NodeFacts` 引用它们，不再复制一份会独立变化的货单或 NPC 状态。

`stage`、`current_needs`、`available_actions` 属于派生读模型。客户端不能提交自己的计算结果当权威事实。

### 9.5 规则函数保持可单测

```text
decide(current_facts, validated_action, rules, server_time)
    → MutationPlan | DomainError

MutationPlan
    = 资源变更 + 实体变更 + 新事实事件 + 贡献来源 + 记忆写入意图
```

`decide` 不发网络、不发奖、不直接落库。最终事务内必须读取或核验最新版本与资源，再接受变化计划，不能依据早已过期的客户端快照扣物。

## 10. 事务、幂等与崩溃恢复

### 10.1 原子边界先于功能扩张

一次资源贡献至少要保证：资源从来源消失、进入工地、记录贡献、保存相关记忆、产生待发布事实，这些结果一起成功或一起不发生。

若现有存储支持同一数据库中的事务，可用其事务能力；MySQL InnoDB 的显式事务和锁定读是可参考的实现基础。[R3][R4] **本计划没有确认项目当前使用 MySQL，也不要求为节点更换数据库。**

若现有玩家背包只在内存中权威、定期整包保存，不能在另一个事务里直接改数据库库存，然后让旧内存快照覆盖它。必须接入已有背包写入所有者和一致的提交机制。

因此 P0 优先用同一区域内的公共场景容器，先把原子变化范围收小。真实个人背包投入在证明跨对象原子提交可用后再开放。不同存储之间的补偿流程属于后续设计，不冒称一次普通函数调用就是事务。

### 10.2 一次提交的顺序

```text
1. 会话鉴权；限制命令大小与频率；解析稳定 request_id。
2. 校验玩家所在世界/实例、距离、权限与当前交互机会。
3. 开始事务；以 (player_id, world_epoch, request_id) 占位幂等回执。
4. 若已有回执：核对 payload_hash，返回原结果；不同参数复用同 ID 则拒绝。
5. 按统一顺序锁定/校验资源、节点和目标实体的最新版本。
6. 再次验证真实需求、资源数量、来源合法性和动作完成证据。
7. 计算 actual_accepted；生成事实差异与具有真实来源的贡献。
8. 原子写入资源差异、事实、回执、已知 NPC 记忆和待发布事件。
9. 提交成功；在世界安全更新点激活内存与碰撞/寻路变化。
10. 返回回执，发布节点增量与个人回应；失败则不播放最终成功。
```

数据库死锁或版本冲突只能有限重试，并始终复用同一请求标识。所有相关资源写入者必须遵守同一锁/版本约定，单独串行化节点不足以保护其他系统也会修改的背包。

耗时数据库 I/O 不应阻塞整个地图的移动物理循环。可以暂停该节点的后续写命令，继续处理无关世界更新；但不能允许两条提交路径同时修改同一节点或资源。

涉及通路的变更，先预校验并准备可用的碰撞/寻路补丁，再提交持久化决议，提交后在安全更新点激活。发布器必须等权威内存与地形应用到事件所需修订号，才能发送对应开通事件，不能由通用事件扫描器抢先宣布可通行。重启时先按持久化事实重建地形，再开放该区域流量与补发事件；激活异常时暂停相关通路交互并报错，不返回虚假的开通成功。

### 10.3 命令幂等和业务幂等是两道防线

**命令幂等：**相同请求重发返回相同结果，处理断线重试与响应丢失。

**业务幂等：**同一个 JobId 只能完成一次、同一个 ShipmentId 只能到货一次、同一公共勘查事实不会被换 request_id 重复领取。

客户端可以为新请求生成新 ID，因此不能只用 request_id 防止重复业务收益。还要依赖实体状态、来源事件和唯一键。

首版保留整个测试世界周期内的幂等回执。未来清理历史时，必须配合服务端动作期限或不可重复的业务标识，不能一删旧回执就允许旧命令重新执行。

### 10.4 可靠广播不等于全链路“恰好一次”

AWS 的 transactional outbox 指南指出，数据库写入与事件通知分离会出现双写问题；同事务写入待发记录，再由发布过程重试，仍可能产生重复消息，消费者需要幂等。[R2]

本版可把事实事件和待发布状态放在同一张轻量事件表，不要求引入消息中间件。提交成功后发布，失败后重试；客户端和业务消费者按事件 ID 与版本去重。

| 崩溃点 | 恢复结果 |
|---|---|
| 提交前 | 整次回滚，没有成功贡献或最终成功表现 |
| 已提交，响应未到 | 同 request_id 重试返回原回执 |
| 已提交，广播未发 | 由待发布记录补发，或客户端通过快照恢复 |
| 广播已发，发送标记未保存 | 可能重发，接收方去重 |
| 施工计时中 | 从已持久化作业、预留和时间继续，不重新领材料 |
| 货车到货后重启 | 同一货单仍为 Arrived，不重复卸货与建棚 |

### 10.5 建议的最小持久化集合

| 逻辑记录 | 必须内容 | 关键约束 |
|---|---|---|
| 区域 / 节点快照 | 事实、作业、世界范围、定义版本与修订号 | NodeKey 唯一；版本可校验 |
| 操作回执 | 请求标识、参数摘要、确切结果 | 玩家 + 周期 + request_id 唯一 |
| 事实事件 / 待发布记录 | event_id、来源、对象、变更、发布状态 | event_id 唯一；可重试 |
| NPC 记忆 | npc_id、player_id、source_event_id、事实摘要 | 同一来源不重复记忆 |
| 公共里程碑 | 开通/到货等时间与来源 | 节点 + 周期 + 里程碑唯一 |

已有实体、资源与记忆存储应复用。逻辑记录不等于必须创建五张新表；小型原型可以合并快照，但原子边界、唯一约束与恢复测试不能省。

## 11. 同步与 Web / TypeScript 表现

### 11.1 客户端只提交意图

建议命令：`InspectNode`、`TransferSiteMaterial`、`AssistCart`、`BeginWorkAssist`、`CancelWorkAssist`、`RequestNodeSnapshot`。

不提供客户端可直接调用的 `AddContributionPoints`、`SetNodeStage`、`OpenBridge` 或 `SpawnCaravan`。

```ts
// 协议草案；字段名以项目已有协议规范为准。
type NodeSnapshot = {
  sharedWorldId: string;
  worldEpoch: string;
  nodeId: string;
  revision: string;
  topologyRevision: string;
  stage: "dormant" | "responding" | "restoring" | "connected" | "inhabited";
  bridgeSegments: number;
  totalBridgeSegments: number;
  availableActions: NodeActionView[];
  nextPublicActionAtMs?: number;
};

type NodeDelta = {
  nodeId: string;
  worldEpoch: string;
  eventId: string;
  fromRevision: string;
  toRevision: string;
  topologyRevision: string;
  changes: NodeChange[];
};
```

个人回应走定向消息，不把所有玩家的关系记忆塞进公共快照。

### 11.2 快照与增量规则

首次进入、重连、世界周期变化、发现版本缺口时获取快照。只有本地版本等于 `fromRevision` 才应用增量；旧事件忽略，乱序有限缓存或直接请求新快照。

节点修订号只覆盖节点结构事实，不应混入高频移动广播。货车的位置使用现有实体同步；货单出发、到达等持久里程碑使用可靠事实链路。

普通网络广播不能作为唯一恢复来源。服务端事实已存在但客户端漏包时，快照必须足以重建当前可游玩状态。

### 11.3 碰撞、寻路、贴图分工

服务端从已提交事实构建通行补丁，在安全更新点激活。激活后才向玩家报告可用通路，并允许货车选择新路径。

客户端按 `topologyRevision` 应用对应可视桥面与预测碰撞。未加载新结构的客户端先同步关键几何，不能只播放旧断桥画面又继续预测新通路；服务端不接受客户端自行开启通行权限。

桥梁施工动画可以略有表现延迟，但最终桥面与可站立区域必须对应。桥段新增不能把人压在碰撞体内；首版选择只补充地板的布局，并保留安全落点与服务器纠正位置的兜底。

**节点修好了但 NPC 寻路仍走旧图，是功能未完成，不是美术小问题。**

### 11.4 表现制作优先级

| 优先级 | 交付内容 |
|---|---|
| 必须 | 断桥、三个可辨识的桥段变化、完整桥面、统一碰撞与通路 |
| 必须 | 物料从来源到工地的清楚变化；货车扶正与真实移动 |
| 必须 | NPC 接手工作、当场回应、重逢回应；字幕与清楚的动作提示 |
| 闭环后补 | 简单棚架、一个旅人停留动作、环境声由冷清到有活动 |
| 暂不做 | 大型开通电影、全服跑马灯、复杂群演调度、生成式 NPC 台词 |

不使用强制接任务框，但保留可关闭的轻量帮助、键盘/触控交互可达性和无障碍提示。“自然发现”不能靠隐藏基本操作实现。

## 12. NPC 记忆：被看见，不是被系统评级

### 12.1 谁知道什么

交接材料时在场的修桥匠可以记得交接者。阿榆亲历扶车，可以记得扶车者。没有看到交接的阿榆，不自动知道是谁送了木板。

需要转述时，应有明确事件，例如修桥匠当面向阿榆介绍帮助者。首版无需扩展全村传闻系统。[P1]

### 12.2 三层反馈

| 层级 | 发生时机 | 例子 |
|---|---|---|
| 即时 | 贡献提交成功后 | “这两块正好用得上。”同时把木板接过去 |
| 延时 | 具体作业或运输完成后 | 那一段桥面固定好；货车离开原停靠位置 |
| 长期 | 下一次自然重逢 | 修桥匠点头：“上回你搬来的木板，已经装上去了。” |

最后一句必须能追溯到实际材料分配或安装来源。若系统只记录“捐过木板”而不知道这批材料是否已经安装，改说“上回你搬过木板吧，辛苦了”，不能让台词比事实更精确。

### 12.3 记忆应当节制

不每次靠近都感谢，不用永久发光图标追着玩家领取关系反馈，不因为没有继续贡献而冷脸。

记忆可保留有意义的首次经历与最近少量经历；去重与展示冷却分开。未来压缩记录时保留可信来源摘要，不需要永久存储每一帧站岗位置。

## 13. 离线推进与重启

世界在运行但地图无人时，不必保持完整物理帧。施工与运输可以由离散作业和到期行动推进，保存 `last_settled_at`、`next_action_at`、作业状态与实际物资。

服务重启后按持久化的计划推进 NPC 工作，不从客户端时间补算，不把离线时间算成玩家协作时长。所有时间比较采用服务器时间并处理时钟倒退，不能产生负工作或超额施工。

每次恢复的处理量有上限。超过预算继续排队或按已经证明等价的聚合规则结算，不能启动时补跑数月物理帧。

首版只有一张货单。离线期间允许根据合法路线和计划完成这次运输，但保留出发、到达的正确顺序与唯一性。未实现真实运输守恒前，不生成“错过了 300 班商队”的到货收益。

玩家重新进入时直接看到当前世界；没有亲眼看见的第一辆车不会为他重新过一遍。测试需要重放时，新建显式测试 WorldEpoch，而不是覆盖正式公共历史。

## 15. 工程验收矩阵

| 编号 | 场景 | 必须结果 |

| T01 | 玩家完全不参与 | 可绕行，不扣关系；NPC 按合法计划继续工作 |
| T02 | 只搬一份材料就离开 | 材料和贡献保留，施工使用这份真实库存 |

| T14 | 甲乙丙一起过桥 | 同一权威碰撞，无个人进度造成的隐形桥差异 |
| T15 | 桥已开、客户端仍旧版本 | 同步结构或纠正预测，不允许客户端伪造通行状态 |
| T16 | 无人地图离线推进后重连 | 只结算合法作业/货单，不补玩家挂机贡献 |
| T17 | 同一货车到货后重启 | 到货只算一次，已消耗物料不作为到货再次发放 |

## 16. 验证情绪：不把在线时长当成结论

### 16.1 观察的三个问题

**看得懂吗？**玩家能否描述：“这里为什么停了，我做的事改变了什么。”

**分得清我与我们吗？**玩家是否知道自己只帮了一部分，同时理解其他人可以接着做、所有人都能受益。

**愿意把这里当作一个地方吗？**玩家是否记得这座桥、这个 NPC 或那次共同经历，而不只是记住领奖位置。

这些是待验证的设计假设，不保证所有玩家都会产生归属感。

### 16.2 首轮观察方法

建议招募少量测试者，例如 6—10 人，覆盖早来贡献者、只帮一点就离开者、晚到未贡献者。人数只是招募起点，小样本不能证明长期留存。

同一测试世界中保留真实公共变化；为了比较不同初始状态，使用明确的新测试周期，不在一局里偷偷替玩家重置桥。

先观察不引导的游玩，再问：“你觉得刚才这里发生了什么？”“哪些变化与你有关？”“有没有觉得必须留下来做完？”避免直接问“是不是很温暖”。

### 16.3 记录什么，怎样避免误读

| 证据 | 用途 | 不能推出什么 |
|---|---|---|
| 确有未解决需求时的可见接触 | 确认有参与机会 | 进入视野不等于注意到 |
| 有效交互与提交结果 | 确认真实行动和成本 | 不等于玩家善良或忠诚 |
| 回来后查看桥或接近原 NPC | 观察延续性 | 不单凭停留时长推断归属感 |
| 玩家自主描述因果 | 检验理解 | 小样本不能保证整体玩家都懂 |
| 自报被催促、白跑或材料浪费 | 检验负担 | 离开本身不算负面反馈 |

首轮以人数、原话与行为片段报告，不制造“温暖度 86 分”。成熟节点晚到者没有修桥机会，不能被记为“不愿贡献”。

### 16.4 扩展门槛

工程正确性用例必须通过。体验上，测试者应能在没有任务讲解的情况下指出至少一条真实因果关系；贡献者与未贡献者都应能继续原本的冒险。

若大家只看见材料计数，先改动作、桥段变化和 NPC 接手。若只觉得是一项义务，先减成本与压力。若世界变化很好但没人注意，先改可见性和自然回访路径。

**不要首先用更多属性奖励、排行榜或更大的工程量补救。**

## 17. 风险与取舍

| 风险 | 典型表现 | 本版处理 |
|---|---|---|
| 经验条换皮 | 什么都加生命值，满了刷 NPC | 具体资源、实际作业、实体计划与路径 |
| 私人公共混淆 | 同队看到不同可站立桥面 | 公共物理唯一；独立实例显式隔离 |
| 范围膨胀 | 修桥前先做商会、经济和六套技能 | 两类贡献、一张货单、一个停留点 |
| 变成苦役 | 每日维护，否则桥断 | 基础设施成果持久，无强制维护债 |
| 空服锁死 | 凑不齐人数、职业或材料来源 | NPC 合法接续，不设人数硬门槛 |
| 老玩家吃完内容 | 后来者只能重复捐赠 | 接受阶段差异，共享收益优先；后续需求独立开放 |
| 贡献归因夸大 | 所有人都被称为修桥英雄 | 来源、对象、知情者和文案精度匹配 |
| 经济复制 | 一批材料多次扣/发、货单反复到货 | 同事务、业务唯一键、资源守恒测试 |
| 数据膨胀 | 保存每帧贡献和全部 NPC 对话 | 只保存意义明确的事实、来源与必要摘要 |
| 世界被玩家恶意锁住 | 长期占施工位、卡车、毁桥刷修复 | 短时职责超时、关键运输防阻塞、P0 不开放公共破坏 |

P0 中关键货车与闲置玩家不采用可永久阻断运输的碰撞规则；该交通规则对所有玩家一致并在设计中明确，不临时偷偷穿人。未来要做可阻塞交通，再提供绕行、超时处理与恶意行为治理。

## 18. 最先实施的一张开发卡

**标题：甲搬来一份材料，乙继续修桥，丙直接走过去。**

先做公共场景容器之间的一次材料转移。它触发 NPC 完成一个真实桥段，并把这次交接记到在场 NPC 的记忆中。甲离开后，剩余材料由乙或 NPC 接续；三个桥段完成，服务端开放通路。丙没有贡献记录，也能正常过桥。

随后接入已验证的同一辆货车，让它真的跨过去。最后才增加卸货、棚架和一次重逢回应。

这张卡完成前，不开全服节点列表，不做世界贡献榜，不制作第二张地图，不扩充全套商队经济。

**完成的判定不是“节点显示 100%”，而是：**

> 我的帮助没有消失，别人的帮助接得上。  
> 这里确实比以前更通畅、更有人气。  
> 我不在线，生活也会继续。  
> 我回来，有人认得我。  
> 后来的人，已经可以走在我们修过的路上。
