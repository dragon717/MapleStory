## 1. 总结：现在缺的不是一批空白系统，而是可靠、连贯的游戏过程

**建议把下一阶段目标定为：不依赖 GM 补物品、改状态或跳过任务，普通玩家可以从创号开始，完成一段有指引、有战斗收益、有装备变化、可以中断后继续的冒险，再自然进入多人合作。**

优先保留现有模块，在真正阻塞这段体验的位置做最小架构调整。不要重新从零写登录、背包、NPC 商店、组队、宠物或地图系统，也不要把“导出更多资源”和“增加更多按钮”当成完成复刻。

### 1.2 优先顺序

**先解决会破坏存档、收益或推进的缺陷；紧接着交付一条正常玩家可完成的冒险路径；然后做一条真实多人合作闭环；最后逐层扩现代成长、区域和职业。**

架构优先不意味着“先花一大阶段重构所有模块”。它意味着：在写第一个依赖某项基础能力的玩法前，先把该能力的状态归属、事务和协议边界做好。例如正式奖励与玩家交易之前先解决资产事务，批量续章之前先解决任务进度，而不是先建尚无消费者的通用事件平台。

## 2. 审计口径与限制

### 2.1 三个维度独立记录

| 维度 | 标记 | 解释 |
| --- | --- | --- |
| 实现完整度 | A | **限定范围内已有代码闭环**，应复用。不是整个原作系统 1:1 完成的认证。 |
| 实现完整度 | B | 已有可用基础，但内容覆盖、规则细节、可靠性或联动不足。 |
| 实现完整度 | C | 目标玩家能力尚未落地。C1 为显式缺失依据，C2 为已查入口未见完整接入、需开工前短核查。 |
| 实现完整度 | U | 本次证据不足，不能判定“没做”，也不能判定“已完成”。 |
| 来源 | T / R / P / U / X | 同版台服依据 / 跨区结构参考 / 项目适配或提案 / 未核定 / 时代外排除。来源级别不等于代码完整度。[E03] |
| 验证 | 静态 / 历史检查 / 本轮检查 / 用户实玩 | 必须写明时间、提交、环境。历史检查不冒充本轮检查；有代码不冒充已经加载或实玩。 |
| 保护 | LOCK / HOLD | LOCK：已明确要求保留；HOLD：差异来源未确认，先冻结行为，调查后再定。 |

一个功能可以同时是 `A + P + LOCK + 用户待验`：例如已实现、经过用户指定的快捷操作，但尚未收到当前版本的实玩确认。这种功能不能为了“原版一致”而回退。

### 2.2 什么才叫闭环

按以下链路检查，而不是只检查文件是否存在：

`玩家可找到的入口 → 客户端意图 → 服务端判定 → 权威状态变化 → 必要的持久化 → 客户端反馈 → 离图/重连/失败时的正确后果`

对于聊天、会话内组队等临时状态，不强求存入数据库；对于道具、货币、任务奖励等资产与进度，不允许用内存去重代替跨崩溃保障。组队当前明确设计为会话状态，重启后解散本身不能判为缺陷。[E13]

“完整原版复刻”还需要同版行为和画面证据。**本次没有足够证据，把整个大系统认证为“全部内容齐全、当前版本已实玩验收、原版 1:1”。** §4 的 A 是对具体窄闭环的保留判断，不是扩大范围的完成声明。

### 2.3 本次实际做了什么、没做什么

本次使用连接的 GitHub 读取固定提交的规则、当前计划、相关交付记录、协议、服务端关键模块与前端组装入口，并核对近期提交；对官方资料做了来源检索。重点追踪了任务推进、商城资产、背包装备、宠物、组队、NPC 交易、实例与定制边界。

本次未运行项目、未重新跑 Cargo/前端检查，未获得本地 WZ、完整运行素材包、账号库及 3010 实玩画面；GitHub 代码搜索接口出现超时/502，因此**没有声称完成全仓逐文件搜索或全量语义覆盖**。图数量与商品数量采用注明时间的仓库记录，没有伪装为本轮程序统计。现有测试代码和历史通过记录只能作为审阅依据。[E04][E05][E06]

C 类“未落地”只指固定提交可见的目标能力，不表示仓库没有同名素材、导出字段、草案，也不表示管理员本机不存在尚未提交的实现。所有 Agent 开工前要做提交差异与本地工作树复核。

## 8. 必须先处理或确认的具体风险

### 8.1 商城购买不是完整事务：P0

`server/src/cashshop.rs::handle_cash_buy` 目前先替换内存背包并扣内存余额，再分别调用 `write_inventory`、`save_profile`，随后记录内存请求与限购次数，最后发送成功。相关持久化结果使用 `let _ = ...` 忽略。模块头部写“原子事务”，但代码路径不能证明这一保证。[E10][E11]

**能够从代码确认的是分步写入和错误被丢弃；“已经发生丢物或复制物品”并非本次实测结论。** 其风险是故障或重试时，道具、余额、限购和成功回执无法保证共同提交。限购读取的 `.ok().unwrap_or(0)` 还会把读取失败解释成“未买过”。

必须实现一条最小 Store 事务，覆盖：校验并读取当前持久状态、扣余额、发物品、限购增量、请求指纹与最终结果；提交成功才更新 World 内存和发成功回执。相同请求重放返回原结果，不重新抽取/发放；同 requestId 不同内容拒绝。暂不强迫全项目改成新的“经济服务”。

### 8.2 限时资产的容器覆盖和到期回收：P0/P1

所查 `step_rental_expiries` 只遍历在线角色 `inventory`，先修改内存后写背包，并忽略持久化错误；不能据此证明已穿戴、仓库、离线和再次登录路径都正确到期。[E11]

应先检查其他路径是否已做限制，再补缺口，而不是直接宣布已穿戴租赁道具一定能绕过到期。到期属于同一物品实例的事实；移动、穿戴或存仓不应意外重置期限。回收事务成功后，统一刷新穿戴属性、宠物状态与客户端反馈。

### 8.3 物品实例身份与赎回保真：现代装备/交易前置

协议目前使用位置 `slot`、模板 `itemId` 与通用 `stats`；宠物和到期时间借用 `_petInstanceId`、`_expiresAt` 等键。已查表以“主体 + 容器槽位”为主键，`shop_rebuy` 仅见模板、数量、单价等字段。[E01][E08][E24]

这不是要求立刻删除旧结构或全仓换 ID，而是要求在玩家交易、现代随机强化、限时转移之前，先核定稳定实例身份和元数据保真契约。卖出/赎回、存取、装备换位不能把强化属性、期限、宠物身份或绑定状态变回模板默认值。迁移必须保留既有实例数据。

此外，历史字段名 `account_id` 不能直接证明业务状态按账号共享；应追踪 Lobby、Identity 与 Store 实际传入的键，再分别确定角色装备、账号仓库和货币归属。[E20][E24]

### 8.4 “局部可执行”与“正常可达”混淆：P0

36316/36332 的前置仍被阻塞，意味着规格验证可以通过，但玩家继续不了。55 条新增任务中的阻塞原因还相互重叠，原统计基于 44 图，不能把各原因数量相加，也不能原样当作 87 图当前统计。[E06]

应按“职业路线 + 正常起点 + 前置 + 等级 + 地图/NPC + 触发执行 + 物品来源”重新做可达性检查。不要通过给所有任务补一个随便的 NPC、自动完成前置或发免费等级来制造可达性。

### 8.5 代码已更新，实际游戏还在旧制品：诊断前置

当前计划保留了大量“统一加载后实玩”的条目。`shared/items.json` 等还被 Rust `include_str!` 编译进入二进制；只改 JSON、刷新浏览器或只更新一端不能确保生效。[E03][E04][E08]

用户报告问题时先核“源码 SHA / 候选制品 / 当前运行协议内容 / 浏览器已加载资源”，不立即重写已修复模块。核查不等于允许重启；仍遵守统一入口及在线保护。

### 8.6 本地 GM 政策不等于可以直接公开运营

当前所有角色可用 `/add`、`/cash` 是显式本地设计，不由本计划擅改；但向不受信任玩家开放时必须先决定隔离方案。GM `/cash` 也有先改内存、忽略保存结果的路径，需要在保留政策的前提下单独审查。[E17]

不能一边保留这个开发政策，一边把一般玩家经济、排行榜或市场宣布为可靠的公平联机环境。该边界作为公开联机的独立门槛，不妨碍管理员继续本地测试。

## 9. 排序原则与架构前置图

### 9.1 排序不是将三个分数机械相加

采用以下顺序判定：

1. **硬阻塞与资产/存档安全优先。** 无法登录、无法继续任务、资产可能失配优先于新增内容；不能因为某个大系统“架构分高”而压住眼前阻塞。
2. **玩法体验是主要目标。** 优先高频操作、清晰目标、真实收益、成长变化和多人互动；以正常玩家路径而非管理员操作路径评估。
3. **本轮玩法依赖的架构先做。** 只提前实现消费者已经明确的状态/事务/协议能力；更远的系统先明确边界，不提前建空架构。
4. **同一体验收益下优先复用，减少返工。** 同版数据可配置解决的不要写一个新框架；已有能力未加载的不要重新开发。

优先级：`P0`＝阻断/安全/本轮硬前置；`P1`＝核心体验和合作闭环；`P2`＝阶段性扩展与长线成长；`P3`＝低频完善或运营扩展。它们不是开发时长承诺。

### 9.2 依赖关系

```text
T01 基线、保护、实际入口复核
 ├─ T02 资产事务与持久请求结果 ─ T08 实例/到期/容器保真 ─ T11 现代装备成长
 │                               └─ 玩家交易 / 拍卖 / 商城高风险扩展
 ├─ T03 任务进度与最小场景执行 ─ T05 一条正常玩家可达续章
 │                               └─ T06 该章节需要的地图、NPC、交通
 ├─ T04 高频操作、战斗与表现校准 ─ T07 属性/技能组合边界
 │                                         ├─ T11 现代成长
 │                                         └─ T12 第二条职业纵切
 └─ T09 复用现有实例与队伍归属 ─ T10 一条多人挑战和正式奖励
                                  └─ 周期资格最小账本 / 区域高等级成长

T13 宠物/交通等完善按玩家路线穿插
T14 U 类能力调查仅在相关阶段进行
T15 商城外围体验在 T02/T08 后进行
T16 公开联机权限、发布与必要工程治理按交付门槛介入
```

T03 与 T02 逻辑上可分别设计，但只要都要改 `auth/schema.rs`、协议或 `World` 字段，就由一个整合者安排合入，不能让多个 Agent 同时写共享文件。T05、T06 也可以是同一条纵向任务，不必人为拆成两次交付。

### 9.3 已有架构继续保留

服务端继续是 Rust 权威模块化单体：网络/认证 I/O 与唯一 World 顺序模拟分离；`quest_rules.rs` 等纯规则只接收必要事实，Store 负责持久事务，前端不提交伤害、奖励或他人的身份。[E03][E15][E18]

已有 `quest.rs`、`trade.rs`、`social.rs`、`cashshop.rs`、`skills.rs`、`elemental.rs`、`movement.rs`、`boss.rs` 等模块。不要照旧计划再次把已经搬出的职责“搬一次”。热点治理优先收窄依赖与状态所有权，不单纯追求文件行数。[E15][E04]

当前前端业务入口是 `client/src/app/main.ts`，并接入 Phaser 世界与 DOM 窗口；`client/src/main.ts` 在该提交为空。依赖中有 Three.js，不等于应迁移整个渲染器。[E16][E26][E27]

## 11. Agent 开发任务卡

以下任务卡是执行设计。领取后只在 `docs/plan/PLAN.md` 登记当前状态和负责人，不在本节反复打勾形成第二套台账。

### T01｜固定基线与保护范围，不重新发明现状

- **优先级 / 体验目标：** P0。避免修改旧版问题、覆盖定制或重复开发已有功能。
- **先读：** `AGENTS.md`、`BUSINESS_DEVELOPMENT.md`、`PLAN.md`、本文件 §2–8，当前协议与实际任务涉及的交付记录。
- **工作范围：** 在开发者本地只读核 `git status --short`、`git rev-parse HEAD`，与审计 SHA 比较；核实际数据/素材是否齐全；区分代码、候选制品、在线实例。
- **输出：** 本次范围变更、需要保留的本地修改、LOCK/HOLD 列表、该模块现有实现路径和阻塞原因。复用既有证据目录，不新增平行总台账。
- **禁止：** `git reset --hard`、`git clean -fd`、临时 stash 他人修改、清库、重启服务、用旧失败汇总代替当前调查。
- **完成依据：** 任务负责人能指出会改哪些文件、不改哪些行为，且无共享文件写入冲突。

### T02｜将商城资产操作做成真正可恢复的事务

- **优先级 / 体验目标：** P0。购买结果不能表现为成功但重登丢失，也不能在重试时再次扣点/发物品。
- **现有入口：** `server/src/cashshop.rs`、`auth.rs` / `auth/`、`auth/schema.rs`，已有 `cashshop_acceptance.rs`；相关 GM 分支另列子范围。[E10][E11][E17][E24]
- **最小设计：** 在现有 Store 增加一个明确的购买事务；同一提交覆盖余额、实际物品实例、限购记录和持久请求结果。记录请求的 SN/数量等指纹，唯一键明确使用认证后的业务主体。
- **错误语义：** 读取失败不按余额零/限购零继续；写入失败不发成功；提交成功但回执丢失可重放结果。World 在提交后更新权威镜像，必要时从 Store 重载。
- **避免过度设计：** 先修这一条消费者；可以复用现有事务辅助，但不建立跨模块通用“支付中台”。
- **针对性例证：** 正常成功；满包；余额不足；限购读取失败；中途写入失败；提交后丢回执并重连重试；同 ID 不同 SN/数量；计数在重启后保留。测试使用临时库，不能连接用户账号库。
- **保护：** 不改 GM 可用角色、额度和商品价格；不把限购原版周期单位猜出来。GM 的幂等/失败回执改动单列并保持现有发放政策。
- **完成依据：** 有定向测试证明资产守恒与持久重放，客户端只在权威成功后显示完成；明确说明未实玩的商品/UI 范围。

### T03｜任务进度与最小场景执行：先解锁一类真实阻塞

- **优先级 / 体验目标：** P0。让玩家做出的行为能推进任务，而不是看到任务却永远完不成。
- **依赖：** T01；涉及奖励的提交方式对齐 T02 的可靠性原则，但不要求等待所有资产迁移。
- **现有入口：** `quest_rules.rs`、`quest.rs`、World 中的 Quest 类型、实际击杀/入图/NPC 处理、Store；`tms273_remaster.cjs`、`tms273_chapter.cjs`、`shared/gameplay.json`。[E06][E18][E23]
- **最小规则：** 为当前任务真正需要的目标增加类型化进度：例如按怪物模板计数、到指定地图、已核定的剧情步骤。来源必须是服务端已确认事实，不接收客户端“任务已完成”。
- **计数去重：** 已有怪物死亡/奖励身份优先复用，避免同一次击杀因重复消息再加进度；组队计数资格明确，不把地图上所有角色自动算完成。持有物品型目标继续按现有事实计算，不另造会漂移的副本计数。
- **脚本策略：** 对 q36315 所需步骤写明确、有限、可恢复的执行步骤与命令分发。保留 sourceScripts/sourceInfo* 溯源；不为了少数缺口先做任意 JavaScript VM 或执行不受限源码。
- **可达性输出：** 对 87 图当前数据重算：规格存在、局部可执行、正常起点可达、当前阻塞。过滤其他职业支线/内部任务，不把它们误算为冰雷主线必须完成。
- **针对性例证：** 未接任务击杀、接取后击杀、重复死亡事件、不同模板、离线重登、物品消耗后持有量变化、条件未满足领奖、同请求不同内容。
- **保护：** 不修改快捷转职、P 奖励或 OR 空集合语义；新增 P 场景执行必须逐步标注，不能改写原作剧情文本来掩盖缺失。

### T04｜高频操作与战斗表现：按真实断点修，不凭感觉重写

- **优先级 / 体验目标：** P1；发现阻断移动/施法/输入的缺陷则升 P0。
- **现有入口：** `movement.rs`、`geometry.rs`、`skills.rs`、`elemental.rs`、`attacks.rs`、`monsters.rs`；前端 `features/player/`、`features/combat/`、`features/mob/`、`scenes/` 与 `app/main.ts`。
- **工作方法：** 选首段路线的代表场景：高低平台侧壁、绳顶、游泳起跳、移动中施法、连续打怪、死亡复活、聊天输入、暂离回归。先记录服务端状态、客户端显示与输入事实，定位差异层。
- **反馈目标：** 玩家能分清施放被拒绝、攻击未命中、命中但伤害很低、目标死亡与拾取成功；不能用相同的静默反馈覆盖所有情况。
- **网络表现：** 先确认现有插值/预测与校正逻辑，再改实际问题；不直接提高 Tick 频率，不让客户端提交伤害/最终坐标，不以牺牲权威换流畅。
- **资源：** 同版 origin、named anchors、zmap、动作 delay、受击点与翻转必须一致。旧角色外观与当前目录同时检查，不删旧装备解决缺显。
- **保护：** LOCK-02/03/04；不把改善手感变成擅改技能冷却、范围或伤害。
- **完成依据：** 具体问题有修改前后证据和必要定向自检；视觉/听觉/手感仍列用户核看，不用 TypeScript 通过宣称 1:1。

### T05｜打通一段无需 GM 的续章与成长路径

- **优先级 / 体验目标：** P1，是首批工作的主要可玩成果。
- **依赖：** T03；必要的 T02/T04/T06。不要等全部任务类型齐了才交付第一段。
- **目标路线：** 从已有正常冒险起点接续到 q36315→q36316，再到一个有明确后续行动的节点。等级、职业、剧情顺序按同版来源和已授权 P 规则核定；不能为了验收自动补等级或完成前置。
- **内容清单：** 每步列入口图/NPC、前置、需要做什么、正确反馈、物品/怪物来源、奖励来源、下一步、离开重连后恢复点。
- **体验要求：** 找不到目标时给真实地图/NPC与阻塞原因；NPC 不在当前图就不显示“就在旁边”；未开放出口要有明确提示，不将错误码当剧情。
- **原版与适配：** 无脚本体时利用已经授权的 P 范围做有限执行，保留 T 文本/条件；新的跨范围临时政策单列，不默认为“允许任何替代”。
- **针对性例证：** 初次角色和已完成前段的旧角色各走一条路径；中断对话、满包领奖、死亡、跨图、重登，不丢进度且不重复奖励。
- **完成依据：** 不使用 `/add`、`/cash` 或直接写库来完成主线验收。GM 可以辅助开发定位，但不作为普通玩家可达证据。

### T06｜只扩当前旅程真正需要的地图、NPC 与交通

- **优先级 / 体验目标：** P1；纯观光扩图 P2。
- **现有入口：** 原版导出与 `assemble_tms273.cjs`、地图装配数据、`npc.rs` / `dialogue.rs` / `portals.rs` / `ship.rs`，前端场景资源。
- **最小交付：** 一片区域必须包含入口、出口、回程、死亡复活、主线 NPC、必要商店与战斗目标；地图渲染完成但这些缺失时只能算基础。
- **数据规则：** mapId/templateId/spawnId 分清，不把同模板 NPC 的不同出生点混成一个；脚本门和普通门分别处理，未装配目标不得伪造映射。
- **兼容保护：** 新区域生成不能裁剪掉角色创建或旧存档持有的装备。普通更新不得靠残留导出文件补齐运行数据。[E03]
- **交通：** 复用已经完成的六方向航线；只在目标剧情依赖时补站台脚本、票务或城镇服务，不重写班次状态机。
- **完成依据：** 一条区域路线正反走通；资源版本与两端协议配套；未打开的原版画面/未验证的门有明确信息，不计为完整覆盖。

### T07｜属性与技能组合边界：让“变强”可解释

- **优先级 / 体验目标：** P1；服务于首个合作技能、现代装备或新职业。
- **现有入口：** `derived.rs`、`combat_rules.rs`、`mage.rs`、`skills.rs`、`elemental.rs`、`growth.rs`、协议和 HUD/技能/属性窗口。
- **最小设计：** 明确基础能力、装备实例、被动、临时 Buff/异常等来源如何聚合，哪些加算、哪些独立乘算、上限和取整在哪一层发生。只对当前技能/装备真正使用的属性做类型化。
- **状态边界：** Buff 的来源、目标、到期、覆盖/叠加、死亡与离图行为明确；不能只有一串前端剩余秒数。已有技能专属状态可先通过窄接口参与，不要求一次全迁移。
- **可解释输出：** 开发态能追踪一次命中的主要输入与修正来源；正式 UI 数值与服务端实际计算一致。调试解释不向客户端开放权威写入。
- **保护：** 魔心防御指定的覆盖/抵偿/消解仍是专门回归；P 伤害表不在本任务暗改为跨区最新公式。
- **完成依据：** 同一装备/技能对自己、队友、怪物有一致结果，穿脱/取消/到期能回到正确基线，旧存档数值不会无理由跳变。

### T08｜稳定物品实例、生命周期与跨容器保真

- **优先级 / 体验目标：** P1；现代强化/交易前硬前置。
- **依赖：** T02；先追踪现有主体身份，再设计迁移。
- **现有入口：** `inventory.rs`、`inventory_ops.rs`、`auth.rs` / `auth/`、`trade.rs`、`cashshop.rs`、`pets.rs`、`shared/protocol.ts`。
- **最小设计：** 区分模板 ID、稳定实例 ID 和当前槽位；区分战斗 stats 与宠物、期限、绑定等元数据。可做兼容读取与逐步迁移，不直接删除旧 `_pet*`/`_expiresAt` 字段。
- **迁移约束：** 一件旧强化装备、一只旧宠物和一件旧租赁物品都要保持身份、属性和当前状态；事务失败不留下半迁移。与旧二进制的数据兼容性另行声明，不能把“换回旧制品”当成通用数据库回滚。
- **生命周期：** 统一明确在背包、穿戴、仓库、赎回中哪些物品允许存在、何时到期、何时收回；操作时校验与周期清理不能互相矛盾。
- **针对性例证：** 换槽→穿脱→存取→允许的卖出/赎回→重登仍保真；到期与购买/穿戴同刻的顺序；两件同模板不同期限/强化不误合并。
- **完成依据：** 资产不因容器变化失去元数据；客户端可识别结果所属实例，旧用户数据未清理或重置。

### T09｜扩展已有实例边界，而不是新造副本服务

- **优先级 / 体验目标：** P1，让队友真正处于同一次活动中。
- **现有基础：** `boss.rs` 的 source/instance map、World 的组队与场景状态、风铃活动实例；利用这些已存在的事实。[E14][E15][E01]
- **最小设计：** 地图定义/原版 mapId 与运行实例 ID 分开；实例拥有成员、实体、开始结束状态和退出规则，Party 是成员资格来源之一，不由客户端提交“全队已进入”。
- **跨模块契约：** 快照按实例隔离，NPC/怪物/掉落按实例归属；重连、离队、队长变化、死亡、全员离开和暂离驻留分别规定。
- **前端复用：** 同一原版地图定义可以服务不同实例，客户端不能把临时 instanceId 当原版资源目录去加载。
- **保护：** 原练习模式、风铃桥公共进度与个人活动状态不迁成一个混杂总状态；不增加每副本独立模拟线程或分布式租约。
- **完成依据：** 两组玩家进入同一源地图的不同实例不串怪、不串掉落、不串结算；同组成员能互相看见并按规则恢复。

### T10｜一条真正的多人挑战与正式奖励

- **优先级 / 体验目标：** P1，是多人项目与单机演示的关键分界。
- **依赖：** T02、T09，必要的 T03/T07。先选有同版依据的一项组队任务或首领，不强行把树妖王练习改成原作不存在的团本。
- **内容要求：** 明确进入条件、共同目标、失败条件、退出/重试、结果与奖励；战斗至少体现伙伴的攻击/辅助或分工，而不只是两人各刷各的。
- **资格与奖励：** 按挑战/场次/参与者定义唯一认领键，服务器结算；先验证通关事实和资格，再发资产。练习模式单独标明无正式奖励。
- **周期机制：** 当前内容真有日/周资格时才加最小周期账本；按目标版本的重置规则确定时区与周期，不能因为用户人在东京就用东京零点。
- **针对性例证：** 同时击杀、退出瞬间通关、断线重连、重复领奖、非成员请求、部分队员满包。容量不足如何处理要明确且无损，不让客户端自行补奖。
- **完成依据：** 一项正常入口可玩的合作内容完成战斗—结算—返回—重登闭环；来源不够的演示内容必须标 P，不计为完整原版内容。

### T11｜第一条现代装备成长纵切

- **优先级 / 体验目标：** P2，在 M3 成为主目标；不是在 M0 一次铺全部系统。
- **依赖：** T02、T08、T07，以及装备实际获取来源。
- **先核查：** 确认 C14 仍缺失；查同版道具/界面/规则，区分卷轴、星力、潜能和各种材料。跨区官方指南只提供结构，不拿当前 GMS 概率替代 TMS273。
- **最小交付：** 选择一种适用装备与一种明确的增强机制，跑通“获得装备→了解成本→提交意图→服务器随机/确定性结算→属性与外观反馈→保存”。
- **事务要求：** 请求重试不重新随机；材料、金币、实例修改及结果同一事务；失败、破坏、保护或保底只实现本批确有来源的分支。
- **体验要求：** 装备增强要在属性与实战中有解释，不仅变一个颜色/星数。材料来源与产出节奏有可玩途径，不仅通过 GM 提供。
- **保护：** 现有卷轴行为和旧强化属性保持；不得顺手改全局掉率、技能倍率或旧装备数值。
- **完成依据：** 一个最小成长循环真实可用，再增第二机制检验复用；没有来源的分支明确锁定/阻塞，不伪造概率。

### T12｜第二条职业纵切，再决定通用程度

- **优先级 / 体验目标：** P2。扩展战斗体验而不是增加空职业页。
- **依赖：** 当前冰雷路线质量和 T07；职业选择按同版资料、素材与当前需求决定，不把本计划的建议冒充管理员已选。
- **最小范围：** 一条新路线的可创建/可转职入口、一段成长、代表性主动/被动技能、可获得装备、任务接续与存档。
- **架构要求：** 复用输入、技能判定、Buff、伤害、资源和表现链；当确有不同机制时加普通规则/数据，不按职业复制整个 World 或做每技能继承类。
- **保护：** 不重置已有冰雷 SP/技能；快捷法师入口保持；其他职业支线不能借机成为原有角色的必做前置。
- **完成依据：** 第二条职业能从正常入口玩起来并体现不同机制，现有冰雷行为回归不变；只有当两个消费者证明必要时再抽共享点。

### T13｜宠物与交通的剩余体验按需求补齐

- **优先级 / 体验目标：** P2；真实卡在主线路径的缺陷升 P0/P1。
- **宠物范围：** 先修已实现成长/跟随/拾取的边界，再实现有来源的生命水复活；自动补药、命令等先从 U 转为明确结论。
- **交通范围：** 保留六方向航线，补本阶段需要的票务、船内事件或城内 NPC；免费登船等 P 政策不在内容补齐中偷偷改动。
- **持久化：** 复活继续使用旧宠物实例，不能换发新宠物来“复活”；相关消耗与状态变化同事务。时间单位和离线计算写出来源或 P 标记。
- **完成依据：** 宠物或交通给玩家的反馈更清楚、流程无死路；不以新增模型/地图数量替代功能完成。

### T14｜按阶段消除未知项，而不是启动第二轮无限审计

- **优先级 / 体验目标：** 随消费者安排，默认 P2/P3。
- **任务范围：** 每次只调查一个 U/C2 项，给出入口、服务端处理、状态、数据、表现和检查证据。
- **产出三选一：** 已有→复用；基础不足→限定补齐；确实没有→说明正常玩家价值和最小实现，再加入 PLAN。
- **禁止：** 找到一张图标就认定完成；搜索无结果就认定全仓无实现；为写报告增加空目录；直接将跨版本机制补成 TMS273 事实。
- **完成依据：** 一个具体未知项变成可执行且有来源的结论，而非更长的候选列表。

### T15｜商城外围与社交便利功能

- **优先级 / 体验目标：** P3；核心可靠后才扩。
- **依赖：** T02/T08；涉及别人的资产还需明确权限和收件主体。
- **最小范围：** 每次一个功能，如愿望单或礼物；不要同时开启退款、里程、限购活动和兑换系统。
- **规则要求：** 礼物有接收资格与幂等发放；退款不得凭客户端声称未使用；限购周期不凭字段名猜测。当前无真实支付，不为复刻自动接支付提供商。
- **完成依据：** 功能在现有菜单自然可找到，失败原因可理解，资产与期限在重登后正确，不破坏原有本地 GM 便利政策。

### T16｜公开联机与发布治理的必要门槛

- **优先级 / 体验目标：** 对外开放前 P0；平时工程完善按阻塞程度排。
- **权限决策：** 管理员确认“保留本地全员 GM、生产模式限制权限”或其他明确政策后才实施；认证身份决定权限，不能信任客户端发送的 GM 字段。
- **发布与恢复：** 继续统一启动入口、候选检查、成功制品成对发布与上一成功版；涉及数据库迁移单独标兼容窗口，不承诺任意旧二进制可读新库。
- **工程范围：** 只有当前改动触发的编译/检查问题才进入本批；CI、HMR 默认行为、目录热点治理按现有 PLAN 协调，不绑成所有玩法交付的前置大项目。
- **完成依据：** 外部玩家不能使用未经授权的管理入口，管理员本地仍保有批准的便利能力；发布过程不清用户数据，不以测试抢占现有服务。

## 12. Agent 学习顺序、所有权与并行边界

### 12.1 每个 Agent 只读必要上下文

通用起点：`AGENTS.md → BUSINESS_DEVELOPMENT.md → PLAN.md → 本任务卡 → 实际代码和同版来源`。历史记录仅在解释该功能、缺陷或授权时读取，不默认把整个 history 灌进上下文。[E02][E03]

| 职责 | 必须理解的现有路径 | 独占/协作边界 | 可先并行的工作 |
| --- | --- | --- | --- |
| 架构与整合负责人 | `World`、协议、Store、schema、目录/发布规范 | 共享字段、协议版本、迁移和任务顺序唯一协调；不以统筹名义重写所有模块。 | 源码审阅、契约草案、保护清单。 |

| 前端玩法与界面负责人 | `app/main.ts`、`features/`、`scenes/`、`network/` | 负责意图和反馈，不结算伤害/货币/奖励；共享 app/router 文件单写入协调。 | 基于已冻结契约做组件修改与资源核看。 |
| 地图/资源负责人 | 导出器、装配器、运行目录与来源清单 | 生成共享 JSON 时必须协调；不裁剪旧持有物品，不混 83 素材。 | 来源调查、入口和缺图清单，不同时生成覆盖别人数据。 |
| 规则/文档复核负责人 | 任务涉及的 TMS273 WZ/官方资料及 P 标签 | 不伪造原作值；未打开原图不能给视觉通过结论。 | 来源核查与差异说明。 |

仓库既有角色安排可继续使用：Astra high 做复杂度/边界与整合，Astra medium 做已验证路径的复杂实现，Luna max 做职责清楚的业务；以实际可用执行环境为准，**没有启动的 Agent 不能写成已启动**。[E03]

### 12.2 不能并行写的典型位置

`shared/protocol.ts` 与 Rust 协议、`auth/schema.rs`、World 公共字段/构造、`client/src/app/main.ts`、共享装配输出、`docs/plan/PLAN.md` 默认有唯一协调写入者。其他 Agent 可提交契约建议或专属模块改动，不能各自“顺手同步”这些文件造成覆盖。

不因为多人并行而增加重复适配层。没有真实正交边界时按依赖排队；资产事务与任务规则可先并行调查，合入时仍按共享文件所有权排序。

### 12.3 文档归属

当前行动只进入 `docs/plan/PLAN.md`；专题设计留 `docs/plan/topics/`；有证据的完成结果按任务归入 `docs/plan/history/YYYY-MM-DD/`，索引只加链接。验证产物遵循 `evidence/YYYY-MM-DD/任务名/`，不散落根目录。[E02][E05]

本文件的 A/B/C 是固定提交的审计快照，后续不作为第二套动态看板。功能变化以新提交及任务交付记录证明，必要时整体生成下一版审计快照。

### 13.3 更有意义的完成度指标

不统计“有多少个模块、菜单、地图图像”作为总完成率，也不编造百分比。推荐记录下列可复核指标：

- 主线分别记录：有源规格数、局部可执行数、选定职业正常可达数、当前版本实玩通过数；每个数都附提交与范围。
- 核心旅程记录：第一个阻塞节点、需要 GM 才能跨过的节点、存档恢复失败点，以及尚未实玩的步骤。
- 资产与实例记录：已覆盖的交易/容器路径、已验证的故障边界和未知边界；不把内存重复请求通过当成跨崩溃保障。
- 体验记录：目标是否可理解、操作失败是否可解释、成长是否产生实际作用、多人是否有共同目标。存在卡顿时再记录输入到显示/服务端确认的分段测量，不凭“50ms Tick”推断实际延迟。

这些是报告应包含的观察项，不要求为它们先建设一个遥测平台。

## 14. 每次交付必须说明的内容

使用已有任务归档格式，至少写明：

```text
任务 ID / 名称：
源码提交与实际改动文件：
实现范围：限定到玩家可做的具体事情。
来源：哪些 T、哪些 R、哪些 P；未知点是什么。
保护项：触碰的 LOCK/HOLD 与保持方式。
数据变更：迁移、旧实例保真、兼容窗口；没有变更也说明。
实际执行的检查：命令、结果、环境、产物路径。
既有失败：只有已证明与本改动无关才这样标记，不直接复制历史数量。
未验证：未加载/未浏览器实玩/缺原图/缺资料分别列出。
用户实玩入口：从哪个现有界面/NPC/地图开始，观察什么。

后续阻塞：同步 PLAN，不建立新的总台账。
```

完成说明不得用以下句式代替证据：“全功能完成”“测试全过”“完整复刻了 87 张地图”“新增 55 条可玩主线”“所有商城事务都是原子的”。必须能指向实际提交、真实范围和已执行的验证。
