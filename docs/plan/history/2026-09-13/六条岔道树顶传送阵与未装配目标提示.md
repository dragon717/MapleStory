# 六條岔道树顶传送阵：未装配目标不再报错刷屏

## 用户反馈

- 截图：角色挂在六條岔道树干长绳上，红箭头指向树身（树顶一带），反馈「没有前往魔法密林的传送阵入口」。
- 随附错误：`传送失败：map_unavailable` / `传送请求：104020000/top00 → 104020100`。

## 关键事实（源）

- `String/Map.json/victoria/104020100` = **維多利亞樹木站台**，mapDesc「這裡有負責載運旅客來往維多利亞島和其他區域的飛行船」。它的子图是 `104020110 前往天空之城站台`、`104020120 前往耶雷弗的站台`、`104020130 前往埃德爾斯坦站台`，`in01` 是脚本门 `inERShip`。**都不是魔法森林路线**。
- `104020000` 的 `top00`(-555,-1372) / `top01`(-555,-1272) 是 `pt: 3`（接触即触发）门，`tm=104020100`。它们就在树干长绳（`ladderRope/8` x=-555, y -1422..-23，与 `ladder` id 8 一致）顶端，所以玩家沿绳上爬必然踩到。
- **魔法森林路线一直都在**（源与运行时数据一致）：`104020000/eli00`(559,-203, pt=2) → `101010100 森林的起始點`(south00) → `north00` → `101010000 閃爍森林的通路` → `north00` → `101000000 魔法森林`。`eli00` 位于横贯全图的中层平台（y=-205）右端；上平台的走法：地面 → 左侧 `-946` 绳 → 157 平台 → 95/105 平台 → `-854` 绳 → -145 平台 → 跳上 -205 平台 → 一路向右。树干长绳从中层平台往上才是 -745 平台（勇士之村/墮落城市）与树顶。
- 树顶那座华丽石门是**次元傳送門**（`gran_pantheon` 美术，mapDesc 记「與格蘭蒂斯相連的次元傳送門」），源里只有 `sleepy00`(pt=7, script `EnterSWmer`)，**没有脚本体**（`portalScriptRefs.available=false`，TMS273 服务端 script 目录也无此脚本）⇒ 无 `tm`、无光束、不可进入。与本次改动无关，属既有的源侧缺口。

## 根因

1. `104020100` 不在本仓库 44 图装配目录内 ⇒ 服务端 `handle_portal` 取不到目标图，回 `map_unavailable`（服务端行为正确）。
2. 客户端把 `pt: 3` 门挂在快照循环里（`world.ts::receive` → `tryPortal(player, true)`），角色挂在绳上时**每 tick 提交一次**，失败提示连续刷屏，且玩家无法退出该状态。
3. 装配脚本对「目标图未装配」的门本来就不加光束（2026-09-10 交付记录的既有决策），于是形成"看不见却会报错"的陷阱门。

## 修法

`client/src/scenes/world.ts`：

- 新增 `catalogHasMap(mapId)`：仅当 `manifest.mapCatalog.maps` 存在时，把目标图不在录内的门判为**关闭门**；没有 catalog 的场景（单测 check、风铃场景）保持旧行为，服务端仍是唯一权威。
- `tryPortal` 里最靠近的门若是关闭门：与真实进门用同样的 1s 冷却，但改为一次性提示 `此路线尚未开放：目标地图 <id> 尚未收录`（非错误态），同一张图每次访问只提示一次；`closedPortalNotices` 在 `clear()`（切图/关闭）复位。
- 服务端未改（`map_unavailable` 仍是并发/旧客户端的兜底）。

当前目录里同类门共 **28 个**（26 个不同目标），例如 `104020000/top00|top01`、`101000000/in00|in01`、`100000000/in00..in05|east00`、`310040200/side00..side03`、`102000000/in01|in02`、`101010...`、`100010000/in00|in01`。

### 重启后「进不了」：会话表是进程内的（附带修掉一个误导文案）

重启后用户的浏览器页面报「无法连接服务器，请检查网络。」且聊天显示「连接断开，聊天暂不可用」。

- **根因**：`server/src/auth.rs:1440` 的 `sessions: HashMap<String, Session>` 是**进程内**的 ⇒ 每次重启 3010 都作废所有 token。重启前打开的页面重连时带旧 token，服务端回 `rejected{code:'unauthenticated'}`；`unauthenticated` 在客户端的 `TERMINAL_CODES` 里 ⇒ `scheduleReconnect` 主动停止重连，页面永久停在离线态。**这不是本次改动引入的**（会话表本来就不持久化），解法就是刷新页面重新登录。
- **服务端本身正常**：`/api/health` ok、`/` 返回新 bundle、用 Node 原生 `WebSocket` 实测 `ws://127.0.0.1:3010/ws` 握手成功（发空 token 时回 `invalid_hello`，符合预期）。所以问题只在页面侧。
- **顺手修掉的次生缺陷**：`client/src/network/session.ts::report()` 原先只按 `status` 去重（注释说明这是为了别让每 tick 的 snapshot 反复触发 online 处理、抢走聊天输入焦点）。后果是终端分支那句可操作的「登录状态已失效，请重新登录。」**永远显示不出来** —— `onerror` 已经先报过一次 `offline`「无法连接服务器，请检查网络。」，状态没变就被丢掉，玩家只看到网络错误、不知道该重新登录。修法：去重同时计入 `reason`（`lastReason`），`online` 路径 reason 恒为 `undefined`，原有防抖语义不变。
- **回归断言**：`session.check.mjs` 新增场景 4（先 `onerror` 再 `unauthenticated` 拒绝 + close，断言最后一条提示是「登录状态已失效，请重新登录。」且重试已停止）。已按仓库惯例做**反向验证**：把 `report` 改回只按 status 去重，断言确实失败并复现出 `actual: '无法连接服务器，请检查网络。'`。
- **验证与部署**：`session.check.mjs` PASS、`tsc --noEmit` 0、`npm run check` 29/31（仅两项基线失败）。仅客户端变更 ⇒ 备份 `build/tmp/client-backup-20260912205207-a0e54273` 后 `rsync -a`（不 `--delete`）覆盖 `build/current/client`；在线 3010 已返回新 bundle `assets/index-Chk_m7uo.js`，无需重启服务。

## 后续反馈：「傳送陣多一個」（樹頂兩道光柱）

用户截图（`菇台路 / 六條岔道`，角色站在次元傳送門前）红框标出树干绳顶：那里叠着**两道光柱**。

- **诊断**：`104020000` 的 `top00(-555,-1372)` 与 `top01(-555,-1272)` 是源里就有的**两个同目标 `pt: 3` 门**（都 → `104020100/st00`，都在同一根绳顶端，相距 100px）。上一轮「未装配目标不给光束」改成「跨图门都给光束」后，这两个门各画一道 `pv` 光束 ⇒ 画面上叠成两道，正是用户看到的「多一个」。同类还有 `104020100` 的 `under00..under10`（11 个 `pt: 3` 下平台门）也被点亮。
- **真正的规则（源侧证据，非推测）**：`Map.wz/MapHelper.img/portal` 有两个命名空间——`portal/game/{pv,ph,psh,ps}` 是**客户端在地图里会画的全部家族**，`portal/editor/<code>` 是**地图编辑器标记**（实测美术：`editor/pc` = 绿色方框、`editor/sp` = 黄箭头、`editor/ps` = 木框、`editor/ph` = 青色椭圆）。客户端按 `portal/game/<code(pt)>/<image|default>` 取图且**没有兜底**：`pt: 3` 的 code 是 `pc`，只在 `editor` 下存在 ⇒ **碰撞门在原版里根本不发光**。`pt: 7`（腳本門）是唯一特例，客户端把它强制指到可见的 `pv` 美术 ⇒ 楓之港 `east00`、弓箭手村 `Achter00` 这类脚本门确实要亮（上一轮的判断是对的）。两个独立客户端复刻项目印证了同一套解析顺序：WzComparerR2 `MapData.cs::PreloadResource`（`case 7: typeName = PortalTypes[2]` + 缺节点不回退）、PharaohStory `Portal.lua`（`pt: 3` 只在 editor 模式有动画）。
- **修法（一处口径，两条调用）**：新增 `scripts/tms273_portal_sprite.cjs` 作为唯一裁决点（`beamSpriteForType(pt)`：只有 2/7 返回 `'pv'`，并带上面全部证据注释）。`assemble_tms273.cjs` 的光束补全循环改为「只有 `pv` 家族类型才补光束」，并把原来的 `if (manifest.portals[key]) continue` 换成「导出条目沿用 + 断言类型一致」，避免静默放过陈旧类型。`world.ts` 的渲染循环只更新注释（指向该模块，并写明「缺资源 = 该门不画东西，不要加兜底光束」）；`check_tms273_runtime.cjs` 的「跨图门必须有光束」改为按类型分流：`pv` 家族缺光束报 `missing`，非 `pv` 家族有光束报 `phantom`，并点名钉住 `104020000/top00|top01`、`104020100/under00`。
- **数据影响**：装配后 `manifest.portals` **110 → 97**（删掉的 13 条全是 `pt: 3`：六條岔道 2 条 + 樹木站台 11 条），其余条目逐字节不变，manifest 其它顶层键也不变。六條岔道保留 6 个真城门（`kerning00/rith00/hene00/notil00/eli00/peri00`，均 `pt: 2`），樹木站台保留 5 个真门（`in00/in03` 与三个登机台 `out00`）。门本身照旧可进（`pt: 3` 接触触发，爬绳到顶即传送）。
- **验证**：`check_tms273_runtime.cjs` → `48 maps; 50543 source references; …`；反向验证（把旧 manifest 放回去）确实报 `Beam invented for a portal type the client never draws: 104020000/top01 (pt=3 pc), …` 13 条，断言有效。`portal.check.mjs` PASS、`tsc --noEmit` 0、`npm run check` 29/31（仍是那两项基线失败）。
- **部署**：本次只有静态资源变化（manifest 是运行时 `fetch('/assets/manifest.json')`，不是打进 bundle），服务端 `shared/maps.json` 未动 ⇒ 备份 `build/tmp/client-backup-20260912211428-f9f6c91e/assets/manifest.json` 后直接覆盖 `build/current/client/assets/manifest.json`，**无需重启 3010**。线上复核：`/assets/manifest.json` 光束 97 条，`104020000/top00` 已消失，六條岔道 6 个城门仍在。
