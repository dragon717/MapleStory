## 缺口（开工前复核的事实）

`PLAN.md` 第 90 行由提交 `3095223` 加入，而「法师分支接执行链」的提交 `3c0a356` 已在它之前落地
——所以这不是文档滞后，而是**磁盘上真有一段没接**。逐条枚举（源 `Skill/212.json` / `232.json`
的非 `hidden` 主动，对比 `world.rs` 的常量与各张表）后确认：`212`／`232` 两本里还有
**17 条**落在 `handle_cast_skill` 的主分发 `_ => {}`，即服务端会回「尚未开放施放」。

其中 **7 条**的源 `common` 与**已接线的冰雷副本逐字段同形**，因此可以在**不新增任何机制**的前提下接上：

| 接的副本 | 与之同形的已接线本 | 复用哪条既有路径 |
|---|---|---|
| `2121000` / `2321000` 楓葉祝福 | `2221000` | `MAPLE_WARRIOR_SKILLS` 表 → `apply_buff(Release::None)`，时长从源 `time`（秒 ×1000）派生 |
| `2121004` / `2321004` 魔力無限 | `2221004` | `INFINITY_SKILLS` 表 → `activate_infinity` + `player_status` 的 5 秒跳段 |
| `2121008` / `2321009` 楓葉淨化 | `2221008` | `MAPLE_CURE_SKILLS` 表 → `activate_status_cleanse`（清疾病 + 3 秒免疫窗） |
| `2121005` 召喚火魔 | `2221005` 召喚冰魔 | `DEMON_SUMMON_SKILLS` 表 → `cast_demon_summon`（S5 的通用召唤队列） |

其余 10 条**刻意不接**（理由见「遗留」）：`2121052`／`2321052`（Hyper 主动，带 `prop`）、
`2121053`／`2321053`（`indieDamR`）、`2121054`／`2321054`（`mdR`）、`2321003` 召喚聖龍、
`2321005` 進階祝福、`2321006` 復甦之光、`2321015` 神聖之水。

## 缺口（复核后的事实，与上一轮登记的「10 条」有一处更正）

上一轮把这两条与「缺机制」的那几条并列，是**登记口径偏保守**。真实状态是：

- 源 `common` **逐字段逐字节相同**（`maxLevel/mpCon/time/cooltime/indieDamR/lt/rb`，`maxLevel = 1`）；
- 源美术组也**逐组同帧**（`Skill/{222,212,232}.img` 的 `2121053`/`2321053`/`2221053`：
  `effect` 17 / `effect0` 22（含 `z` 共 23 个子节点）/ `affected` 11）；
- 机制**存在**（施放 → 给施法者所在图的队友挂窗口 → 窗口内伤害多乘一次独立伤害率）；
- **缺的只是「哪一本在计时」这件事没有收口**：`world.rs` 把 `SKILL_HYPER_ADVENTURER = 2221053`
  当单技能常量用在了 8 处（施放臂、白名单、600ms 时长、`HYPER_ACTIVE_IDS`、`clear_hyper_runtime`、
  两条伤害路径、重连冷却名单），另加 `elemental.rs` 的 `apply_buff` 与 `damage.rs` 的取值访问器。

⇒ 结论：这是**同一类收口**（与上一轮「無限在计时的那一本」同形），不是新机制。

> 上一轮登记里写的 `2121053`／`2321053`「需先有独立乘算声明」已按本条更正。
> `check_tms273_damage_pipeline.cjs` 的 `NOT_CONSUMED.indieDamR` 里那两条显式登记
> （`'2121053'` / `'2321053'`）就是这条旧判断的落点，本轮已删除。

## 偏离登记（如实报备）

1. **`check_tms273_damage_pipeline.cjs` 的判据被扩张了**（本轮唯一一处）。原判据写的是
   「源里要消费的 `indieDamR` 从 1 个变成了 N 个：**需要有人重新决定分组**」——本轮就是那次
   「重新决定」：三个四转分支各有一本 傳說冒險，分组由源字段名决定（`indieDamR` → 独立乘算），
   三本同组。判据从「个数」换成「与数据表逐项相同 + 三件形状」，比原来更强而不是更松。
2. **`elemental.rs` 的 `apply_buff` 语义**：增益挂在**施放的那一本**上，而不是统一挂一个书号。
   这与 `activate_infinity` 的既有写法一致（「挂哪一本」＝「读哪一本」），是本轮的核心判据；
   代价是队友收到别人分支的副本增益时，`hyper_adventurer_damage_percent` 读该队友自己的
   技能等级会落回 1 级（`unwrap_or(1)`）——但三本 `maxLevel = 1`，取值相同，**无行为差异**，
   与改前 `2221053` 的口径完全一致。
3. **装配器仍需仓库外驱动**（与上一轮同一原因，项目代码一字未改）：宿主文件代理在
   `mode === undefined || mode === 0` 时接管 `fs.copyFileSync`，会在
   `tms273/ride-scenes/` 的长文件名对上确定性碰撞。仍用
   `node /tmp/run-assemble-with-ficlone.cjs`（只把 mode 补成 `COPYFILE_FICLONE`）跑完。
   **用户在自己终端跑 `启动3010.command` 不会遇到这个问题。**
4. **升版带来同一个短暂窗口**：在线服务仍是上一版发布时，刷新页面会报「资源版本不一致」
   （`manifest.ts:722` 硬抛错）。本轮客户端与服务端代码都变了，本来就必须重建重启才能生效。
5. **`scripts/check_tms273_skills.cjs` 仍是既有红灯**（读的 `skills.json` 缺 `levelValues`），
   本轮同样未动、未重跑 `export_tms273_skills.cjs`——那个导出器不覆盖 212/232 线
   （`catalogSkillIds` 里只有 222 系列），属另一件事。
