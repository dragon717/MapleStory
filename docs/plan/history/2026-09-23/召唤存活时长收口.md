  ——「召唤**存活时长**的书写差异（冰魔 `time` 按秒、冰鋒刃 `time=4000` 按毫秒）未统一」。

## 缺口（收口前的三份账）

| 写入点 | 收口前的写法 | 问题 |
|---|---|---|
| `elemental.rs::cast_demon_summon`（冰魔 `2221005` / 火魔 `2121005`） | `level.time.unwrap_or(0) × 1000`，再 `.div_ceil(TICK_MS).max(1)` | 单位判据（秒）写死在这一处 |
| `skills.rs::cast_thunder_sphere`（閃電球 `2211011` / hidden `2211015`） | 同上，**但默认值另写** `20`／`60` | 同一套换算写了两遍，默认值还各写一份 |
| `elemental.rs::cast_frozen_orb`（冰鋒刃 `2221012`） | **写死 `4_000`**，连源都不读 | 源 `time` 改数不会跟着动 ⇒ **静默漂移** |

⇒ 三处**互相不一致**：前两处按「秒」换算、第三处按「毫秒」写死，而源里这两种写法**都存在**。

## 源字段核对（决定单位判据；逐条从源读出，非推断）

先按 `shared/mage-skills.json` 逐本核对五本已接线召唤书的等级 1 `time`：

| 技能 | 源 `time`（等级 1） | 源里按什么单位写 | 收口前的实际值 | 派生后 |
|---|---|---|---|---|
| `2221005 召喚冰魔` | `115`（满级 260） | **秒** | `115000ms`（当秒算） | `115000ms` |
| `2121005 召喚火魔` | `115`（满级 260） | **秒** | `115000ms`（当秒算） | `115000ms` |
| `2221012 冰鋒刃` | `4000`（全等级恒定） | **毫秒** | `4000ms`（写死） | `4000ms` |
| `2211011 閃電球` | `63`（满级 120） | **秒** | `63000ms`（当秒算） | `63000ms` |
| `2211015 閃電球`（hidden） | `22`（满级 60） | **秒** | `22000ms`（当秒算） | `22000ms` |

**逐件复现收口前的现行为 ⇒ 零行为漂移。**

### 单位判据：为什么只能用「量级」而不是结构字段

先试过三条**结构**判据，逐条被源数据否掉（都做了全目录核对）：

1. **「本书有没有 `summon` 节点」**——否。`1121055` 有 `summon` 节点（`summoned/die/stand/attack1..6`）
   却写 `time=10000`（只能是毫秒）；`2100010` 没有 `summon` 节点却写 `time=4+d(x/4)`（只能是秒）。
2. **「`attackDelay` 毫秒槽在不在场」**——否。`1301014` 带 `attackDelay=360` 却写 `time=5`（秒）。
3. **「`time` 是公式还是字面量」**——否。按秒的 `1301014` 写的是字面量 `5`，
   按毫秒的 `2221012` 写的也是字面量 `4000`。

⇒ 源里**没有任何结构字段**能定下 `time` 的单位。最终判据取**量级**，形状与同模块既有的
`summon_pulse_ms` 的 `subTime >= 一拍` **同源**（都是「按量级认单位」）：

```
time 缺                → SUMMON_LIFETIME_FALLBACK_MS（60 000ms）
time >= 1000（分界）   → 源里写的就是毫秒，原样返回
否则                   → 按秒 ×1000
```

分界取 `1000` 的依据是全目录 148 条带 `time` 的技能逐条核对的结果：按**秒**书写的召唤存活时长
最大只到 `260`（冰魔／火魔 `110+5*x`、閃電球 `60+3*x`／`20+2*x`、主教召唤 `40+2*x`／`60+16*x`），
按**毫秒**书写的三条是 `3000`（`3111013 箭座`）／`4000`（`2221012`）／`10000`（`1121055`）
——中间**没有重叠区**。这条「没有重叠」本身就是门禁里的一条断言（见下）。

## 做了什么

### ① 唯一派生点（`server/src/mechanics.rs`）

```rust
pub(super) const SUMMON_LIFETIME_FALLBACK_MS: u64 = 60_000;
pub(super) const SUMMON_LIFETIME_MS_THRESHOLD: i64 = 1_000;

pub(super) fn summon_lifetime_ms(skills: &MageSkills, skill_id: u32, level: u32) -> u64 {
    let Some(time) = skills.level(skill_id, level).and_then(|row| row.time) else {
        return SUMMON_LIFETIME_FALLBACK_MS;
    };
    if time >= SUMMON_LIFETIME_MS_THRESHOLD { time as u64 }
    else { u64::try_from(time.max(0)).unwrap_or(0).saturating_mul(1_000) }
}
```

与 `summon_pulse_ms` **同形同责**：`&MageSkills` + 技能 id + 等级进、毫秒值出，中间没有技能名单。
取 `&MageSkills` 而不是 `&self` 的理由也一样（调用点可能正持有 `player` 的可变借用）。

**「写明的 0」不许并进「缺失」那一支**：`time = Some(0)` 走第三支得到 `0`，
调用方照旧 `.max(1)` 收敛成「1 拍即到期」——与收口前 `cast_demon_summon` 的 `unwrap_or(0)` 语义逐字相同。

### ② 三个施放入口改走它

- `elemental.rs::cast_demon_summon`：`level: &MageLevel` → `_level`（不再自己碰 `time`），
  时长读 `summon_lifetime_ms(&self.mage_skills, skill_id, skill_level)`。
  顺带修掉一处**陈旧注释**：原文写「冰魔 1→30 级 90→200」，实测冰魔／火魔都是 `115→260`。
- `elemental.rs::cast_frozen_orb`：删掉写死的 `4_000`，改走派生点（并补上原本缺失的函数文档）。
- `skills.rs::cast_thunder_sphere`：删掉自己那套 `duration_source` 与 `20`／`60` 两个默认值，
  锚定形态读 `SKILL_THUNDER_SPHERE_HIDDEN`、非锚定读 `SKILL_THUNDER_SPHERE`（与改前同源），
  `level: &MageLevel` → `_level`。

⇒ 收口前的**两处静默默认**（冰魔侧 1 拍即到期、閃電球侧 20 秒／60 秒）被**一个契约值**取代；
五本已接线召唤书**逐级都带 `time`**，所以这条兜底分支**不可达**（下面有断言）。

### ③ 门禁 `scripts/check_tms273_damage_pipeline.cjs` 新增 §3h

这一段接在 §3g（「删一行 = 宣布已实现」必须有消费点撑腰）之后，同属「判据改动必须有行为撑腰」那一族。
断言是**双向**的：

1. **唯一派生点在不在**：`mechanics.rs` 里必须有 `summon_lifetime_ms`、必须从 `skills.level(…).time`
   派生、必须出现 `time >= SUMMON_LIFETIME_MS_THRESHOLD` 这个比较；
   且 Rust 侧的分界常量值必须与本门禁自己算的 `1000` **同值**（两处漂移即红）。
2. **三个施放入口是否都经过它**：`cast_demon_summon` / `cast_frozen_orb` / `cast_thunder_sphere`
   **逐条点名**，函数体里必须出现 `summon_lifetime_ms(`；
   **反向断言：这三个函数体里不许再出现 `.time`**——单位换算只许发生在派生点内部，
   施放入口自己读一次 `time` 就说明它又长出一份账。
3. **源侧独立重算 + 双录**：从 `shared/mage-skills.json` 逐本取 `time`，按分界算出期望毫秒，
   与门禁里的双录期望值逐项比对；同时**逐级**断言五本都有 `time`（⇒ 兜底分支不可达）。
4. **分界本身成立**：按秒书写的必须**恰好四本**、按毫秒的**恰好一本**，且两侧**没有重叠**
   ——一旦重叠，量级判据对这本目录不再成立，必须改成显式登记而不是按量级猜。

门禁自报新增一行：

```
召唤存活时长：1 个派生点（mechanics.rs::summon_lifetime_ms，分界 1000）+ 3 个施放入口；
源侧重算 2221005=115s→115000ms/2121005=115s→115000ms/2221012=4000ms→4000ms/2211011=63s→63000ms/2211015=22s→22000ms
```

### ④ 验收 `server/src/mechanics_acceptance.rs` 新增一条

`mech_summon_lifetime_comes_from_one_source_derivation`（四段）：

1. 五本逐件等于源值（硬编码期望 + 源值出处写在注释里）；
   **反向**：冰鋒刃不许被当成秒（`assert_ne!(…, 4_000_000)`）——改前写死 4000 恰好是对的，
   所以这里钉的不是「数值变了」而是「数值的**来源**变了」，谁把分界去掉、一律 ×1000，本条当场红。
2. **兜底不可达**：五本逐级都带 `time`（`1..=maxLevel` 全查）。
3. **派生值真被消费**：三件召唤各放一次，`expires_at - 施放拍` 恰好等于 `派生值 ÷ 一拍向上取整`。
4. **扰动验证**（合成目录，四本同形技能只差 `time` 一个字段）：
   `999 → 999_000`、`1000 → 1_000`、`0 → 0`（写明的 0）、缺失 → `SUMMON_LIFETIME_FALLBACK_MS`。

### ⑤ 注释同步

`mechanics.rs` 模块头、`world.rs` 的 `Summon` 结构文档与 `DEMON_SUMMON_SKILLS`／火魔那段的注释，
都从「脉冲周期唯一派生点」扩成「脉冲周期 + 存活时长各一个唯一派生点」。

## 偏离登记

1. **兜底值是一个新引入的契约值**（`SUMMON_LIFETIME_FALLBACK_MS = 60_000`）。它取代的是
   **两处互相矛盾的静默默认**（冰魔侧 1 拍即到期、閃電球侧 20 秒／60 秒）。五本已接线召唤书
   逐级都带 `time` ⇒ 该分支**不可达**（验收第 2 段 + 门禁 §3h 第 3 条各证一次）。
2. **量级判据是一条经验判据，不是结构判据**。已把三条被否掉的结构判据、以及全目录
   148 条 `time` 的核对结果写进 `mechanics.rs` 的常量文档里，并把「两侧无重叠」做成门禁断言。
   若将来新接的召唤书 `time` 落进 `[261, 999]` 或 `>= 1000` 而实际是秒，**门禁不会红**
   （它只校验已登记的这五本）——这是本轮明确留下的边界。
3. **`player.hyper_vortex`（冰雪结界）的存活时长未纳入**：它读的是源 `u2` 而不是 `time`，
   且住在 `HyperVortex` 而非 `Summon` 队列里，属另一类对象。本轮不动、也未登记为待办（不属本口径）。
4. **`time` 的另外两种语义（自增益窗 / 负面状态窗）未动**：自增益窗走 `AttackPlan::self_buff_window_ms`
   （S1 已交付），负面状态窗仍被门禁的 `NEGATIVE_STATUS_TIME_ATTACKS` 挡在表外。本轮只碰召唤那一支。
5. **未提交**、**未重启在线服务**（用户未要求）。内容未变，所以本轮**没有**上一轮那种
   「资源版本不一致」的短暂窗口。
