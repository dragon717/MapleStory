## 为什么它「只接线、不新增机制」

`PLAN.md` §1② 收口前给这条登记了**两条否决理由**，本轮**逐条复核，两条都不成立**：

| 收口前登记的判断 | 实测 |
|---|---|
| 「源美术组是 `summon/fly` 而非 `summon/move`，本包的 `Anchored` 简化不一致」 | **不成立**。用 `scripts/tms273_wz.cjs::createReader` + `unpack_tms273_ms` 直接读 `.img`（**不是** JSON dump）：`2321003/summon` 下的子节点顺序是 `summoned / fly / stand / attack1 / die`，与冰魔／火魔的 `summoned / move / stand / attack1 / die` **逐位相同**，只是位移组换了名字（`fly` 12 帧 ↔ `move` 12 帧）。「跟随施法者」正是**既有**的 `SummonMotion::Follow`（三转球形闪电已在用），不是新机制。 |
| 「召唤物的周期打击不走直接命中那条链 ⇒ 召喚火魔的跳伤不接」 | **不成立（这是一句事实错误）**。`step_summons` 的脉冲走 `cast_elemental_area_at` → `settle_area_segments`，而 DoT 的挂载点**就在** `settle_area_segments` 里（`skills.rs:2993` `if segment == 1 && resolution.damage > 0 { if let Some(dot) = plan.dot { … apply_dot_hit(…) } }`）——与直接命中**同一个**挂载点。⇒ 火魔源里的 `dot=53 / dotInterval=1 / dotTime=2` **一直在被消费**。本轮用新增验收 `mech_summon_pulse_mounts_the_source_dot` 钉住。 |

源字段核对（`shared/mage-skills.json`，等级 1）：

| 技能 | 源 `common` | 存活时长 `time` | 位移组 | 脉冲周期 |
|---|---|---|---|---|
| `2221005 召喚冰魔` | `mpCon,time,damage,mastery,s,v,subTime,attackCount,mobCount` | `115`（秒） | `move` | 契约兜底 `1080` |
| `2121005 召喚火魔` | 同上 + `dot,dotInterval,dotTime` | `115`（秒） | `move` | 契约兜底 `1080` |
| `2321003 召喚聖龍` | `mpCon,time,damage,mobCount,attackCount`（**没有** `mastery`） | `70`（秒，`60+10*x`） | `fly` | 契约兜底 `1080` |

⇒ 聖龍**不是**那两本的「同一格副本」（缺 `mastery`），所以它**不进** `MASTERY_SKILLS`、
**不进** `attribute.rs::INTRINSIC_DURATION_SKILLS`，也不进 `FIRE_DEMON_SUMMON_PARITY`。
它只属于「由召唤实体承担」这层**机制**关系。

## 做了什么

### ① 服务端：接纳名单从「两本副本」收口成「一张机制表」（`server/src/world.rs`）

改前：

```rust
const DEMON_SUMMON_SKILLS: [u32; 2] = [SKILL_ICE_DEMON, SKILL_FIRE_DEMON];
```

改后（**两层分工，判据各只有一处**）：

```rust
/// 召唤系四转：冰魔与火魔（**同一格副本**，源 `common` 与召唤美术组逐组同形）。
const DEMON_SUMMON_SKILLS: [u32; 2] = [SKILL_ICE_DEMON, SKILL_FIRE_DEMON];
const SKILL_HOLY_DRAGON: u32 = 2321003;
/// **通用召唤队列**接纳的全部召唤技能。**判据只有这一处**：施法白名单、施法臂、
/// 位移形态派生、动作时长都读它，不再各自写 `if skill_id == …`。
const SUMMON_SKILLS: [u32; 3] = [SKILL_ICE_DEMON, SKILL_FIRE_DEMON, SKILL_HOLY_DRAGON];
/// 「施放点定住」（`SummonMotion::Anchored`）的那几本。**位移形态的判据只有这一处。**
const ANCHORED_SUMMON_SKILLS: [u32; 2] = [SKILL_ICE_DEMON, SKILL_FIRE_DEMON];

fn summon_motion(skill_id: u32) -> SummonMotion {
    if ANCHORED_SUMMON_SKILLS.contains(&skill_id) { SummonMotion::Anchored }
    else { SummonMotion::Follow }
}
```

`DEMON_SUMMON_SKILLS` **保留**：它表达的是「三条分支共用同一格」这层**内容**关系
（`mage_branch_copy_acceptance.rs` 仍在钉它），`SUMMON_SKILLS` 表达的是**机制**关系。

### ② 服务端：施法臂不再按技能名写死前缀（`server/src/elemental.rs`）

`cast_demon_summon` → **`cast_summon`**，并删掉两处写死：

```rust
// 改前
let prefix = if skill_id == SKILL_ICE_DEMON { "ice-demon" } else { "fire-demon" };
summon_id: format!("{prefix}-{id}-{request_id}"),
motion: SummonMotion::Anchored,
// 改后
summon_id: format!("summon-{skill_id}-{id}-{request_id}"),
motion: summon_motion(skill_id),
```

⇒ 加第三本不会退化成 `if` 链。doc 注释同步重写，并把「召唤物的周期打击**确实**挂 DoT」
这条更正写进去。

### ③ 服务端：`skills.rs` 六处引用改读表

`castable` 白名单、动作锁判据、动作时长入口、`skill_cast_event`、`skill_duration_ms`
共 **6 处** `DEMON_SUMMON_SKILLS` → `SUMMON_SKILLS`；施法分发的 `cast_demon_summon` → `cast_summon`。
`SummonMotion` 补 `PartialEq, Eq, Debug`（验收要按**形态**比，而不是按坐标反推）。

### ④ 客户端：三张镜像名单 + 一处施法姿势白名单

| 文件 | 改动 | 为什么 |
|---|---|---|
| `features/player/input.ts` | `DEMON_SUMMON_SKILLS` → **`SUMMON_SKILLS`**（`[2221005, 2121005, 2321003]`） | 与 `world.rs::SUMMON_SKILLS` 同名同义（既有 `INFINITY_SKILLS` / `MAPLE_CURE_SKILLS` 等一律这样镜像） |
| `features/combat/view.ts` | `receiveDamageEvent` 的名单改读 `SUMMON_SKILLS` | 否则聖龍的周期打击**不切攻击帧、不出声** |
| `features/skills/view.ts` | `ACTIVE_SKILLS` 加 `'2321003'` | 有施放按钮才能拖进快捷栏 |
| `features/player/view.ts` | `startSkill` 白名单加 `2321003` | 否则施放没有施法姿势 |
| `features/player/input.ts` | `HOLY_FOURTH_SHORTCUT_SKILLS` 补 `Digit5: 2321003` | 对齐冰雷那套的 `Digit5 = 2221005`（"键位与冰雷那套对齐 1..0"的既有纪律） |

`combat/view.ts` 的召唤渲染**一行未改**：源 `fly` 被映射到运行期同一个 `summonMove` 键

## 偏离登记

1. **`SUMMON_SKILLS` 与 `DEMON_SUMMON_SKILLS` 并存**，不是「一张表打天下」。
   前者是机制关系（由召唤实体承担），后者是内容关系（三条分支共用同一格）。
   合成一张会让 `mage_branch_copy_acceptance.rs` 里「同格副本」那条断言失去判据。
2. **聖龍的 `summonSpawn` / `summonDie` 只导出源证据、不导出 PNG**（`role: cast-aura-only`），
   与冰魔／火魔同口径：`summoned` 是施放光环、`die` 是到期收尾，本包的召唤表现不走这两组。
   ⇒ 新增 PNG 恰好 68 张（= 五组帧数之和），与装配器自报的 `assets +68` 一致。
3. **`2321003` 不进 `MASTERY_SKILLS` / `INTRINSIC_DURATION_SKILLS`**：源里没有 `mastery`。
   这与冰魔／火魔（都带 `mastery`）**不同格**，所以不是漏登记。
4. **`BRANCH_AREA_ATTACKS` 仍是 14 条**：聖龍不是攻击技能，本轮一条未加。
5. **未提交**、**未重启在线服务**（用户未要求；且本沙箱 `ps`／`lsof` 不可用，
   `关闭3010.command` 与 `activate` 阶段无法代跑）。
   ⚠️ 因此存在一个**已知的短暂窗口**：`client/public-tms273/assets/manifest.json` 已是
   `tms273-43`，而在线服务仍发布 `tms273-42` 的 JS ⇒ 此时刷新页面会报「资源版本不一致」
   （`manifest.ts:722` 硬抛错且自愈路径不导航）。
   已按 §0 的口径跑完 `build-release.cjs prepare` 生成候选，**只差一次
   `zsh 启动3010.command`**（＝ `PLAN.md` §1① 本身）即恢复一致。
