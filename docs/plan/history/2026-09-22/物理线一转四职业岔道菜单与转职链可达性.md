# 物理线一转四职业岔道菜单 + 转职链可达性断言（2026-09-22 第十一轮）

> 上一轮（第十轮，只读核查）的结论：**战士 / 弓箭手 / 飞侠三条物理线的「一转」全部未完成**，
> 且这不是「数据缺一条」这种局部缺口——它让二/三/四转共 21 条转职任务**在运行期永远够不着**。
> 两条互相独立的不可达理由：
> 1. **前置任务本身做不完**：`1401 劍士之路` / `1403 弓箭手之路` 的 `executable` 是 `false`
>    （`blockedBy` 含 `other-job-route` + `script-counter`），而 `job-110/120/130` 与 `job-310/320`
>    把它们挂成前置 ⇒ 战士、弓箭手线**从二转起永久锁死**。
> 2. **起点根本不存在**：转职判据是 `durable.job == fromJob`，而职业 `100/300/400` 此前
>    **没有任何发放路径** ⇒ 飞侠线（`job-410/420`，已改成无前置）同样进不去，
>    整条分支链是「配置完全自洽、但够不着」的死代码。
>
> 用户在两条补法里选了 **「扩選擇岔道菜单」**：不新增 NPC、不复用三条不可执行的源剧情，
> 而是把法师那条已经跑通的 P 级适配器**从单选扩为四选**。本轮据此把 1+2 一起收口。

## 1. 选定路线：把 0001020000 / 漢斯 的岔道菜单从 1 个选项扩到 4 个

上一轮记录里已确认的**唯一已接通范式**是法师那条：

- `選擇岔道`（`templateId = 10201`）摆在 `001020000`，脚本节点 `gate → choose → advance → advanced`；
- `choose` 是一个 `Menu` 节点，**当时只有一个选项（法師 / `job: 200`）**；
- 服务端 `npc::QuestEffect::JobAdvance { from_job: 0, job: 200 }` 驱动职业切换，
  等级门槛 8、发放 100 点 MP 与两项隐藏技能（`grant_first_mage_fields`）。

扩成四职业＝把同一台适配器的**选项表**从 1 条变 4 条，其余通道（对话 / 事务 / 落库）零改动。
好处是**不引入任何新的源依赖**——三条物理线不需要各自的源剧情任务就可执行。

| 职业 | `job` | 沿用通道 | 等级门槛 | 一转发放 |
| --- | --- | --- | --- | --- |
| 剑士 | `100` | 岔道菜单 `10201` | **10** | 本书 SP +5 |
| 法师（对照，原样） | `200` | 岔道菜单 `10201` + 源任务 `1402` 完成 | **8** | 100 MP + 两项隐藏技能 + SP +5 |
| 弓箭手 | `300` | 岔道菜单 `10201` | **10** | 本书 SP +5 |
| 飞侠 | `400` | 岔道菜单 `10201` | **10** | 本书 SP +5 |

**等级门槛刻意不统一**：法师一转到二转的前置是源任务 `1402`（其 `requiredLevel` 是 8），
物理线走的是菜单直转，按系列惯例取 10。所以门槛**按线派生**（`auth::first_job_level(job)`），
不是共享一个常数。

## 2. 改动清单

### 2.1 客户端装配（权威层，`scripts/assemble_tms273.cjs`）

原来的法师单选菜单被重写成一张**派生自 `FIRST_JOBS` 表**的四职业菜单——`choose` 的选项
与 `advance-*` / `advanced-*` 节点全部由该表 `flatMap` 生成，**不再是四条手写分支**：

```js
const FIRST_JOBS = [
  { job: 100, zh: '剑士',   en: 'Warrior'  },
  { job: 200, zh: '法师',   en: 'Magician' },
  { job: 300, zh: '弓箭手', en: 'Bowman'   },
  { job: 400, zh: '飞侠',   en: 'Rogue'    },
];
```

生成 8 个节点（每职业一对）。原变量名 `mage` 改为 `crossroad`，
`compatibility.mageTransfer` 换成 `compatibility.firstJobTransfer`（旧键删除）。

⚠️ **这是装配器里的权威内容**，不是 `shared/gameplay.json`。直接改 `shared/` 会被下次
装配静默清零（见长期约定「派生副本永远不是写入目标」）。修改落在 `assemble_tms273.cjs`，
再重跑装配器派生。

### 2.2 服务端：三条判据从「法师硬编码」收口成「按线派生」

| 文件 | 改动 |
| --- | --- |
| `server/src/mage.rs` | 新增 `FIRST_JOBS: [u32; 4]` 与 `is_first_job(job)`；一转职业集**单一权威** |
| `server/src/auth.rs` | `first_job_level(job)`（法师 8 / 物理线 10）与 `grant_first_job_fields(job, …)`；`advance_job` 的两处 `if` 从 `job == MAGE_BOOK` 改为 `is_first_job(job)` |
| `server/src/dialogue.rs` | `mage_entry` → `crossroad_entry`、`is_mage_advance_npc` → `is_crossroad_advance_npc`；`apply_job_advance` 用 `first_transfer = from_job == BEGINNER_JOB && is_first_job(job)` 统一门槛与发放；**无 Store 路径改为调用同一份 `grant_first_job_fields`** |
| `server/src/world.rs` | 常量改名 `CROSSROAD_ADVANCE_{MAP_ID,NPC_ID,TEMPLATE_ID}`，判据函数 `is_crossroad_advance_npc` |
| `server/src/{third_acceptance,npc_click_acceptance,world_tests}.rs` | 常量名同步 |

**收口的价值**：门槛与发放原先是「法师一份硬编码 + 物理线没有」，现在**只有一条实现**，
四条线共用；给某条线改门槛时不会漏掉另一条。

### 2.3 转职目录（`shared/job-advance.json`）

去掉两条**永远做不完**的前置：

- `job-110/120/130` 的 `require.quests`：`1401` → `[]`
- `job-310/320` 的 `require.quests`：`1403` → `[]`

飞侠线（`job-410/420`）上一轮已是无前置，本轮不动。
`provenance.P` 追加说明第二种静默失败形态（起点不存在）与新增的两条可达性断言。

### 2.4 守门人（`scripts/check_tms273_job_advance.cjs`）

新增 **§2d 可达性断言块**，把上一轮发现的**两类盲区**变成会响的断言。此前已有的
§2b（表外前置的接取 NPC 必须真的摆位）只覆盖「**表内**任务的下发链」，
对「前置任务自身能不能做」和「起点职业能不能拿到」都无感。

`PREREQ_LESS_ALLOWED` 从 2 条扩到 7 条（补 `job-110/120/130/310/320`）。

## 3. §2d 的四条断言（全部从源独立重算，不读被检查的那张表）

| # | 断言 | 独立重算口径 |
| --- | --- | --- |
| 1 | 每条**表外前置**必须在 `shared/gameplay.json` 里 `executable` | 目录里的 `require.quests` 减去目录自身 id，去 `gameplay.quests` 反查 |
| 2 | 无入边职业必须**正好**是 `[100, 200, 300, 400]` | 从目录的 `fromJob → toJob` 图自己长出来，**不手写名单** |
| 3 | 每条 `fromJob` 必须在**可达集**里（入边 ∪ 一转发放入口） | 可达集 = 目录里的 `toJob` ∪ 脚本 `jobAdvance{fromJob:0}.job` ∪ 代码通道 |
| 4 | 一转发放入口必须**真的存在**：脚本节点解析出的 `job` 集合非空，且没有源任务通道的职业必须出现在脚本发放集里 | 解析装配产物的 `npcs[].script.nodes[].act.kind === 'jobAdvance'`；代码通道由 `server/src/quest.rs` 是否含 `first_mage_transfer` 派生 |

断言 3 同时覆盖了「**next 指向不存在的节点**」（转职生效了但成功对话没了）。

### 3.1 两条扰动验证（都真的响了）

| 扰动 | 手段 | 命中断言 |
| --- | --- | --- |
| **A：前置做不完** | 把 `shared/gameplay.json` 里 `1402` 的 `executable` 改成 `false`、塞入假 `blockedBy` | `job-210: 外部前置 1402 在 shared/gameplay.json 里不是可执行任务（blockedBy=["__perturbation__"]）——它永远变不成 completed，挂上去只会让整条转职链静默锁死` |
| **B：起点不存在** | 删掉漢斯脚本里 `advance-100` / `advanced-100` 两个节点，并把 `choose` 的第 0 个选项摘掉 | `job-110: fromJob 100 没有任何可达路径——既不是本目录里某条的 toJob，也没有一转发放入口，这条转职永远触发不了` |

两次扰动后均**逐字节恢复**原文件并重跑门禁回绿（`choose` 选项回到 `0:剑士, 1:法师, 2:弓箭手, 3:飞侠`，
`1402.executable === true`）。

> 另：断言 4 在**修复前**的状态下也响过（当时报 `job-110: fromJob 100 没有任何可达路径`），
> 那是本轮改动的负向验证第一步。
