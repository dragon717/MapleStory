理由是这个判据是后面每一条机制（窗口 / DoT / 投射物 / 第二命中盒 / 触发骰）落地的**唯一出口**，

## 1. 发现：判据看的是「字段在不在」，而源里存在**恒为 0** 的机制字段

`scripts/check_tms273_damage_pipeline.cjs::§3e` 的准入规则原文是：

> 源里 `damage ∧ mobCount ∧ attackCount ∧ lt ∧ rb` 齐备 ∧ 不是 `hidden` ∧ **不含任何
> 「本包还没有这条机制」的字段**。

判据实现成 `Object.keys(PHYSICAL_MECHANISM_FIELDS).find(field => fields.has(field))` ——
**只看字段名在不在**。于是 `1221009 騎士衝擊波` 被 `time` 挡下，而它的源数据是：

```text
common = { mpCon: "14+u(x/3)", damage: "250+3*x", attackCount: "10", mobCount: "3",
           time: "0", prop: "0", x: "1", lt: {x:-320,y:-160}, rb: {x:90,y:40} }
```

`time` 与 `prop` 在**所有 30 级**上都是字面量 `"0"`（已回到权威导出树
`resources/tms273-export/skills.json` → `catalog.skills["1221009"].common` 逐字核对，
不是派生副本的投影丢失）。这两个字段只是源模板留下的空槽 —— 技能**根本不使用**施放窗与触发骰。

后果不是「少一条」而是**同一本书里两条同形技能表现不一致**：兄弟技能 `1221011 鬼神之擊`
（同为 `122` 书、同样 `damage+mobCount+attackCount+lt+rb`）已在 `PHYSICAL_AREA_ATTACKS` 里，
玩家能放；`1221009` 因为两个空槽被永久锁在表外，点下去回「该技能尚未开放施放。」——
而这句文案是给「本包还没实现这条机制」用的，用在这里**说错了原因**。

## 2. 判据改造：从「字段在不在」到「机制组真的有取值」

新增**机制组**这一层，分组只有一个用途：判断这条机制到底有没有参与。

| 机制组 | 字段 | 含义 |
| --- | --- | --- |
| `buff-window` | `time` / `updatableTime` | 增益 / 召唤窗口 |
| `sub-window` | `subTime` | 子窗口计时 |
| `dot-field` | `dot` / `dotInterval` / `dotTime` | 持续伤害场 |
| `trigger-roll` | `prop` | 按几率触发 |
| `ball-timing` | `ballDelay` / `ballDelay1..3` | 投射物逐段时序 |
| `second-hitbox` | `lt2` / `rb2` | 第二命中盒 |
| `jump-counter` | `maxUseCountInOneJump` | 跳跃使用次数 |
| `attribute-slot` | `basicStatUp` / `mastery` | 走属性槽位，不是攻击 |
| `hp-cost` | `hcHp` / `hp` | HP 消耗类 |
| `fixed-damage` | `fixdamage` | 固定伤害 |

新判据：**同组字段里只要有一个在某一级上非零，这条机制才真的参与**；整组在所有等级上都恒为 0
⇒ 源里的空参数，不挡这条技能。

两条配套断言（这正是本轮新加的防退化层）：

1. **覆盖断言**：分组表必须与理由表 `PHYSICAL_MECHANISM_FIELDS` **逐字段互覆盖**。
   加了字段却忘了说明它和谁同组 ⇒ 立刻失败（否则新字段会绕过整条判据）。
2. **例证断言**：正反例都由**源自己**给出，不手写名单 ——
   `1221009` 必须进期望集（源 `time`/`prop` 恒为 0）；
   `1201013 騎士密令` 的 `time="1+u(x/4)"`、`prop="35+5*x"` 必须仍被 `buff-window` 挡住。
   只成立一边就说明判据退化回「看字段在不在」。

## 3. 全目录扫描：这是**唯一**一条受影响，不是一类问题

对 `shared/mage-skills.json` 全 504 条做同类扫描：

- `time` 在所有等级上恒为 0 的：**只有 `1221009`**；
- `prop` 在所有等级上恒为 0 的：**`1221009` 与 `1220010 進階神聖凝聚`**——
  后者是纯被动（无 `damage`/`mobCount`/`lt`/`rb`，没有攻击消费点），`prop:0` 与它的形态一致，
  任何一张决策表里都没有引用它 ⇒ 无缺陷。

所以本次纠偏的**影响面是一条**，不是「把一批技能误判了」；这一点也解释了为什么它能潜伏：
它只在「同书同形技能里恰好有一条带空槽」时才会显形。

## 8. 复用提示（踩坑记录）

- **「字段在不在」与「取值有没有参与」是两件事**。凡是用「源里带某字段」当准入/排除判据的地方，
  都要再问一句「这个字段在这条技能上真的有取值吗」——源模板会留下大量空槽，
  按存在性判会把「它不用这条机制」误判成「这条机制没实现」，而报文还会理直气壮地说错原因。
  更糟的是它只在**同书同形技能里恰好有一条带空槽**时显形，极易潜伏。
- **计数注释也是判据**（本仓库的既有教训）：`world.rs` 里「没进 31 条（17 + 14）」这类数字
  要么从源重算，要么别写。本轮同步改成 30（16 + 14）。
- **`cargo check` 告警对照要用 stash 基线**：`git stash push -- server/src/world.rs` 前后各存一份
  完整输出再 diff，才敢说「本轮贡献 0 告警」；只看总数会漏掉「删一条加一条」的对冲。
