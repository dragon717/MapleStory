## 2. 书准入：派生链从「三条分支各一条臂」收成「四张职业表按布局切片」

24 本新书意味着 24 条臂——那正是「写死名单」的老毛病。本轮改成**按职业表布局派生**：

### 5.1 收尾时抓到的两个真缺陷（本轮由「收尾验证」逼出来）

**① 物理分支的区域系数吃错了护盾（本轮新引入，已修）**

物理分支初版写的是 `self.boss_damage_multiplier(&map_id, true) - 100`——`true` 是**魔法**侧。
`boss_damage_multiplier(map_id, magic)` 里 `magic=true` 查 `magic_guard_until`（源 `MagicGuard`
113），`false` 查 `physical_guard_until`（源 `PhysicalGuard` 112）。于是战士／飞侠的技能会
**去吃魔法护盾、同时无视物理护盾**——两个方向都错，而它自称「与普攻同一口径」
（`attacks.rs:148` 用的正是 `false`）。

抓到它的是一条**形状判据**：`check_tms273_damage_pipeline.cjs` 原本断言
「`skills.rs` 里 `boss_damage_multiplier(..) - 100` **恰好出现 1 次**」。这条 `=== 1` 是当时
只有一个调用点的**副产物**，它拦下的是「多了一处」而不是「错在哪」。所以修法**不是改成 2**：
判据升级为「恰好 2 处 + **逐处钉 `true`/`false`**（魔法一处 `true`、物理一处 `false`）+
物理分支那一处必须落在 `if physical { … } else {` 块里」。
**负向验证**：把 `false` 改回 `true` ⇒ 判据报
「两处区域系数的伤害种类判据是 true/true，应当恰好一处 true（魔法）一处 false（物理）」。

**② `cargo test` 并非确定通过：跨用例的写失败注入串扰（既有，已根修）**

现象：全量 `cargo test` 一次 635 过 / 0 失败，下一次 **634 过 / 1 失败**
（`the_rental_sweep_reclaims_expired_rows_and_notifies` 拿到 5 而不是 3）；
`--test-threads=1` 则两条全绿。**用 `git stash` 把 `server/src` 退回 HEAD 后同样失败**
⇒ 与本轮改动无关，是既有的测试隔离缺陷。

根因：`Store::deny_persistence()` 的注入标志是**进程级** `AtomicBool`。它旁边那把
`PERSISTENCE_INJECTION_LOCK` 只能串行化**注入方之间**，挡不住**非注入方**在注入窗口内跑——
而每一个做**合法提交**的用例（现金／商店／背包整族）都读同一个标志。两条用例同选时，
回收那一条的提交被另一条的注入拒掉，于是过期品没被回收。

修法：把标志从**进程级**改成**线程级**（`thread_local! Cell<bool>`），去掉那把锁。
注入只可能发生在设它的那个线程上——`refuse_if_persistence_denied` 的调用方
（`auth/shop.rs`、`auth/cash.rs` 的提交 helper）都是**同步方法**、与设注入的测试同线程——
所以串扰在**结构上**不可能再发生，而不是把竞态窗口缩小。
修后：全量 **635 过 / 0 失败**，两条同选**连跑 3 次全绿**；且
`the_rental_sweep_keeps_memory_authoritative_when_persistence_fails`（注入仍然生效、
断言内存未动）照旧通过 ⇒ **注入没有被悄悄关掉**。
