## 1. 真正的主因：不是「缺施法分支」，是三条运行期闸只认冰雷

上一轮把「打不出去」归因成「主分发走 `_ => {}`」。那只说对了一半。把链路从入口往下走一遍，
**在到达分发之前就已经被三道闸拦掉了**，而且三道都只认冰雷那三本（`220/221/222`）：

| 闸 | 位置 | 改前写法 | 后果 |
| --- | --- | --- | --- |
| 施法与学习的职业闸 | `world.rs::skill_job_allowed` | `match` 冰雷书 → `_ => false` | 火毒/主教技能**学不了、也放不出** |
| 落库前的同一道闸 | `auth/skills.rs::job_allowed` | `expected_job == 0 / 200 / 220 / THIRD_JOB / FOURTH_JOB` 臂链 | 同上，且**客服端与服务端各判一次** |
| 升级发点 | `auth/db.rs::grant_level_sp` | `job if mage_job_allowed(job) => (MAGE_BOOK, 3)` | **把三条分支的升级点全发进 200 那本**：火毒/主教玩家升 100 级也拿不到本分支的 1 点 SP |

第三条尤其隐蔽：目录里技能、任务、地图全都在，玩家升级也确实「涨了 SP」，只是那些点**涨在了另一本上**。
这类「三处各写一份、且都按同一个错误假设收窄」的缺陷，单看任何一处都像是有意的白名单。

**修法：收口，不逐处补。** 全部三处改为读 `server/src/mage.rs` 的同一张派生表：

```
BOOKS: [u32; 11] = [0, 200, 210, 211, 212, 220, 221, 222, 230, 231, 232]
FOURTH_JOB_BOOKS: [u32; 3] = [212, 222, 232]
book_branch(book)  // 21x 火毒 / 22x 冰雷 / 23x 僧侶（十位）
book_tier(book)    // 0 二转 / 1 三转 / 2 四转（个位）
book_jobs(book)    // 书 → 可持有它的职业集合：x0 整条分支 / x1 三+四转 / x2 只有四转
book_for_job(job)  // 升级发点：0 → 初学者书 / 法师 → 自己那一本
```

书号**就是职业号**（`2201005 → 220`），所以「谁能学这本书」不需要任何人工名单。
`world.rs` / `auth/skills.rs` / `auth/db.rs` 三处只剩一行委托（`skill_job_allowed` /
`is_mage_job` / `book_for_job`），`auth.rs` 里那份重复的 `mage_job_allowed` 直接删掉。

## 2. 攻击技能接执行链：复用冰雷那一条，不另写一遍

上一轮估的成本是「等于把冰雷四转那一套再写两遍」。实际上**不需要**——`cast_elemental_area`
本来就是**与元素系无关**的范围管线（命中盒取源 `common/lt|rb` 绕玩家、倍率与段数取 `level`、
`lightning` 只决定要不要叠冻结层）。所以做法是把 14 条分支攻击技能**接到同一条管线**：

| 分支 | 已接执行链的技能（14 条） |
| --- | --- |
| 火毒 210/211/212 | `2101004` 火焰箭、`2101005` 毒霧、`2111002` 爆炸、`2111003` 致命毒霧、`2121003` 地獄爆發、`2121006` 火焰之襲、`2121007` 火流星、`2121011` 藍焰斬 |
| 主教 230/231/232 | `2301005` 聖光、`2301010` 神聖之箭、`2311004` 聖光普照、`2321001` 天怒、`2321007` 復仇天使、`2321008` 天堂之門 |

- `world.rs::BRANCH_AREA_ATTACKS` 是这 14 条的**具名数组**（同时供 `is_magic_attack_skill`、
  `counts_as_direct_hit`、施法白名单与分发四处读），客户端 `ACTIVE_SKILLS` 是同一份名单
  ——两侧靠 `check_tms273_skill_ui.cjs` 与 `view.check.mjs` 钉住。
- `lightning = false`：火（`f`）/毒（`s`）/聖（`h`）在源里没有冻结字段，不需要那条分支。
- **`counts_as_direct_hit` 刻意独立于 `is_nonsummon_direct_skill`**：后者还喂着暴风雪的
  后续段判定，直接往它里面塞 14 个 id 会顺手改掉冰雷的手感。两条判据同形但不同名，是有意的。
- 三条 Hyper 强化被动（`damR`）**从「登记不消费」转成真消费**：`2120043` → `2111003`、
  `2120046` → `2121006`、`2120049` → `2121003`（`magic_damage_breakdown` 的
  「被强化技能 → 强化被动」配对表）。`check_tms273_damage_pipeline.cjs::NOT_CONSUMED.damR`
  因此由 3 条登清空为 `{}`，门禁转绿——正好是上一轮那条反向断言（「哪天有人给它起了常量、
  接了施法分支，门禁立刻红，要求同时把消费补上」）按设计生效的样子。
- 四转冷却改由 `FOURTH_JOB_BOOKS.contains(&skill.book_id)` 派生（改前写死 `== 222`，
  于是 `212`/`232` 的 `cooltime` 不起作用）。

### 2.1 消息也要分对：主动但没接 vs 真被动

改前不在白名单的技能一律回「被动技能不能主动施放。」。火毒/主教的准入一开，这条文案就变成
**假话**（`2301002 群體治癒` 在源里明明有 `mpCon`）。现在按**源数据**分两句
（`MageSkill::is_active_source_skill()` 读 `levels` 里有没有 `mpCon`/`damage`，不另写人工清单）：

| 源里是什么 | code | 文案 |
| --- | --- | --- |
| 主动、但本包还没接执行链（召唤物/治疗/增益窗等） | `skill_unimplemented` | 该技能尚未开放施放。 |
| 真被动（源里只有被动字段） | `skill_passive` | 被动技能不能主动施放。 |

## 3. 客户端：四份副本 → 一份权威

客户端那张「书 → 职业」表原本有**四份**，三份是陈旧的：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| `skills/view.ts::BOOK_JOBS` | 唯一的权威（已含六条分支） | **搬到 `player/input.ts`** |
| `hud/view.ts::jobAllows` | `switch` 只列 `0/200/220/221/222`，**`default: return false`** ⇒ 火毒/主教的书一律显示「职业不可用」 | 读同一张 `bookAllowsJob` |
| `player/input.ts::canCastShortcut` | `skillId >= 2200000` 数值分段 | 书号从 id 派生（`bookIdForSkill` = `skillId / 10000`）后查权威表 |
| `hud/view.ts::shortcutId` | Shift 行**永远**解析成 222 的技能 | `branchFourthJob(job)`：210/211→212、220/221→222、230/231→232 |

`canCastShortcut` 那行是**客户端侧的同型缺陷**：`23xxxxx`（主教）在数值上 `>= 2200000`，
于是整条主教分支被划进冰雷区间 ⇒ 快捷栏与鼠标点击在**本地**就被判「职业不可用」。
服务端修好了、客户端还拦着，症状与改前一样——这也是为什么两条必须一起改。

**权威为什么落在 `player/input.ts`**：它是不引运行期依赖的叶子模块，`skills/view.ts` 与
`hud/view.ts` **都已经 import 它**，搬进来不会形成 `skills/view.ts ←→ player/input.ts` 的
循环，也不用建新文件。三张 Shift 快捷表（`FOURTH_/FIRE_FOURTH_/HOLY_FOURTH_SHORTCUT_SKILLS`）
与 `BOOK_JOBS` 同住一处，键盘层与 HUD 天然同源。

顺带两处一致性：技能详情的「Shift 快捷键」提示改扫**三张**表（改前只扫 222 那张，
火毒/主教四转技能看不到键位提示）；详情页的「战斗状态行」由 `bookId === '222'` 改为
`FOURTH_JOB_BOOKS.has(bookId)`（与 `mage.rs::FOURTH_JOB_BOOKS` 同名同义）。

## 4. 新增门禁：`scripts/check_tms273_skill_books.cjs`

`mage.rs` 的注释里早就写着「客户端的 `view.ts::BOOK_JOBS` 是同一张表的另一份实现，
`scripts/check_tms273_skill_books.cjs` 对两份表逐格**双向断言**」——而**那个文件并不存在**。
本轮把它补上（并登记进 `client/scripts/run-checks.mjs`）：

- **客户端一侧不比对源码文本，而是真跑**：`typescript.transpileModule` 转成 CommonJS 后
  注入 `new Function` 执行 `input.ts`，拿到运行期真正在用的 `BOOK_JOBS` / `bookAllowsJob` / `bookIdForSkill`。
- **Rust 一侧从 `mage.rs` 反解**：常量数组 + `book_jobs` 的分支臂（`Some((21, 0)) => &BRANCH_FIRE`
  / `[1..]` / `[2..]`），并断言**臂的切片下标 == 书的分支层级**（写错一个下标就会把四转书开给二转）。
- **断言**：书号清单两份逐项相等 → 四转书清单相等（客户端从三张 Shift 表反推，不再抄字面量）
  → 技能 id 派生书号往返 → **11 本书 × 14 个职业全格对**（含 100/112/999 这类非法师职业号）。
- **把唯一一处刻意的差异钉住**：未登记的书（战士书 `100`）在 Rust 侧是 `&[]`（拒绝），
  客户端却是「不限制职业」放行——因为技能窗还要渲染战士的永久被动（它的门控是
  `derivedStats.regenerationPassives.bookId`，`check_hud_skill_ui.mjs --regeneration` 依赖这条）。
  这处差异**不许被顺手抹平**，所以显式断言两侧各自的口径。
- **抗扰动实测**（4 组，全部被抓）：① 改 `Some((23, 1))` 的切片 `[1..] → [2..]` ⇒ 报「层级与切片
  下标必须同号」；② 客户端 `'231'` 少一格 `{231,232} → {231}` ⇒ 报「准入两份实现不一致（共 1 格）」；
  ③ 删掉主教 Shift 表 ⇒ 报「读不到 `HOLY_FOURTH_SHORTCUT_SKILLS`」；④ 客户端多一本没登记的
  `'240'` ⇒ 报「书号清单两份不一致」。
