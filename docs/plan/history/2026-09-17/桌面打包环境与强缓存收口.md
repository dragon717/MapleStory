## 1. Web 强缓存：内容寻址对象库

### 1.1 为什么是「复制对象」而不是「加版本参数」

v3 §4.1 已定：只在可变路径上挂 `?v=123`、服务器却始终返回最新磁盘文件，**不能**保证
旧客户端与回滚版本一致。所以建立内容寻址存储：

```
内容 JSON 引用闭包 → sha256 → objects/sha256/<摘要><扩展名>（只写缺失摘要）
                  → objects/index/<revision>.json（不可变索引）
                  → objects/current.json（固定名指针，最后写＝唯一的发布动作）
```

- **复制而不是硬链接**：源文件是 `writeFileSync` 原地截断（同一 inode），硬链接会把
  「快照」与可变源绑死，v3 §4.1 明文禁止。
- **先落临时名再 rename**：不产生半截对象；同目录 rename 原子。
- **`revision` 不参与自身哈希**：避免自引用。
- **地址由字节决定** ⇒ 服务端才敢给 `immutable`；服务端 `classify()` 与客户端
  `asset-index.ts` 都对「索引地址必须由 revision 自身命名」做同一断言（两侧都收窄）。

实测（`client/public-tms273/assets/objects`）：

| 项 | 值 |
| --- | --- |
| 引用闭包 | 28,065（其中 27,928 个图片/音频进对象库） |
| 去重后对象 | 27,772 个（156 个逻辑地址与别的文件字节相同，共用对象） |
| 体积 | 逻辑 376.7MB → 对象 376.2MB |
| 索引 | 4.78MB（`objects/index/<rev>.json`） |
| `assetRevision` | `95588f79e762ab773a589c57eba243109dde4a1706fd139dba41fb9c8000e00b` |
| 构建耗时 | 12.8s |

### 1.2 三个坑（都会静默失败，所以值得记）

1. **iCloud 未实体化文件会让索引永久卡死**。本仓库在 iCloud Drive 下，部分文件是
   「占位稿」（`st_blocks === 0`）。`readFileSync` 会阻塞在云下载上——实测**卡死于 28k 中的
   第 233 个且不再推进**（两次后台跑各挂 4~8 分钟，看起来像「很慢」，其实是死了）。
   现在**在读之前**用 `st_blocks` 预判并跳过（当前 130 个，合计 0.36MB），继续走逻辑地址。
   > 这不是索引脚本特有的问题：**任何**批量读内容资源的脚本都会踩到。
2. **`| tail -N` 会吞掉进度**。第一次排查时把 stdout 接给 `tail`，进程被杀后一行都没有，
   误判为「无输出」。改为写日志文件后才看见 `2000/27928 …` 的正常推进。
3. **iCloud 会静默回滚未提交编辑**。本轮 `resource-url.ts` 的 `resolveAssetUrl`、`main.rs`
   的 `ReleaseDescriptor::load` 调用、`index_client_assets.cjs` 的 dataless 判据**都被回滚过**，
   而同一文件的另一些编辑却保留了。后果是「脚本看起来改了、跑起来还是旧行为」。
   ⇒ 每个 Edit 后立刻用 Grep/读回复核（本轮靠这条抓出 3 处），是**必需步骤**而非保险。

### 1.3 客户端接线

- 新增 `client/src/assets/asset-index.ts`：取固定名指针（`no-cache`）→ 取不可变索引
  （`immutable`）→ 建「逻辑地址 → 对象地址」映射。幂等、并发共享、**任何失败都不抛**，
  退回恒等（v3 §5.3：强缓存是少下载的手段，不是资源能否取得的前提）。
- `resource-url.ts::resolveAssetUrl` 变为三步：① 换对象地址 ② 附加修复代数 `ce=`
  ③ 最后加桌面 `assetBase`（只加在 `/assets/**`）。**逻辑 key 一律不变**，
  所以 Phaser 纹理查找、`cache.audio.exists` 短路、DOM 引用语义全部保持。
- `manifest.ts::loadManifest` 把 `loadAssetIndex()` 与清单**并行**取，不额外增加登录延迟。
- `world.ts` 的预加载**本来就**对每个 url 调 `resolveAssetUrl`，因此 28k 资源无需改动即接入。

### 1.4 实测证据（对**正在运行的 3010**，未重启服务）

| 请求 | 响应头 |
| --- | --- |
| `/assets/objects/current.json` | `cache-control: no-cache`（313B，可变指针） |
| `/assets/objects/index/<rev>.json` | `cache-control: public, max-age=31536000, immutable`（4.78MB） |
| `/assets/objects/sha256/ef21675b….png` | `cache-control: public, max-age=31536000, immutable`，`content-type: image/png` |

对象正文与逻辑源地址的 sha256 **逐字节相同**（都是 `ef21675bd498e444…`）。
⇒ 刷新时这些地址**不再发生任何网络请求**。

> 注意：`/api/client-release` 的 `assetRevision` 要**新二进制**才会非空（旧实例仍报 null），
> 需经 `启动3010.command` 统一加载后确认。

### 1.5 收口复查：为什么「对象库建好了但刷新还是慢」

**根因不是服务端**（服务端对对象地址已给 `immutable`，线上实测通过），而是
**客户端产物没重建**：`build/current/client/assets/index-*.js` 时间戳 18:15，
而 `asset-index.ts` / `resource-url.ts` 是 19:44 / 19:53，产物里搜不到
`objects/current.json`。也就是说浏览器仍然在请求 27928 个固定名逻辑地址，
每一个都要 304 协商——强缓存根本没被用上。

⇒ **让强缓存生效的唯一步骤＝重建并切换客户端**。`启动3010.command` 的
`current-fresh` 判据包含客户端源码指纹，源码变了就会走 `prepare`（Cargo+vite）
→ 轮替激活，所以用户跑一次统一启动即可，**不需要单独记得跑构建**。

同时核对了两项此前未量的数：

| 项 | 实测 |
| --- | --- |
| manifest 引用的 `/assets/` 地址 | 28058 条 |
| 命中对象库（⇒ 强缓存） | 27928 条（**99.54%**） |
| 未命中 = 退回逻辑地址（仅协商缓存） | 130 条，**与索引里 `dataless` 数量精确相等** |
| 其中图片 | 27965 条，命中 27835（99.54%） |
| 去重收益 | 376.7MB → 376.2MB，仅 0.1%（内容资源本就几乎一一对应） |

130 条未命中全部是 iCloud 未落地的占位文件；等它们物化后重跑
`node scripts/index_client_assets.cjs` 即可补齐到 100%——**不会**因为少这
0.46% 而让刷新变慢，它们本来就走协商缓存。

**一处门禁断言被这轮改动证伪**（值得记，因为它正是「旧不变式与新目标冲突」的样本）：
`scripts/check_tms273_client_actions.cjs` 原先断言「代数为 0 时解析必须是恒等函数
（普通请求逐字节不变）」（`/return url;/`）。V3-P2c 的**全部目的**就是让传输地址与
逻辑地址不同，这条断言与强缓存直接冲突、必然失败。已改写为三条更准确的不变式：

1. 映射缺失必须逐字节退回逻辑地址（`assetObjectUrl(url) ?? url` 必须在位）；
2. 代数为 0 时不得附加任何查询参数（`ce=` 必须被 `epoch > 0` 守住）；
3. 非 `/assets/` 地址在加任何前缀前原样返回，`assetBase` 只加在 `/assets/**` 上。

改后 8 组断言全通过；22 个未接入的 DOM `<img>` 站点仍如实登记（名字过期会失败）。

### 1.7 本轮的环境阻塞：iCloud 占位文件（**不是「慢」，是永久死锁**）

排查过程中全仓扫描出 **39,177 个 iCloud 占位文件 / 9.8GB**（`参考/` 31,137 · `server/` 518 ·
`resources/` 6,616 · `evidence/` 239 · `client/` 516 · `references/` 145）。这些文件
`stat` 仍有 `size`，但 `blocks === 0`——数据块不在本地。**读它们不报错，而是永久阻塞。**
本轮抓到三种形态：

| 形态 | 现场 |
| --- | --- |
| `fs.readFileSync` | 内容索引卡在第 233 个文件，10 小时进度不动、CPU 0% |
| `rustc` 对内联 `.rlib` 做 `mmap` | 栈 `CrateLocator::find_library_crate → get_rlib_metadata → memmap2::map_copy_read_only → __mmap`，卡在**加载外部 crate 元数据**阶段、**根本进不了 codegen**（只 4 线程、零 `libLLVM` 帧、零磁盘写入）。它还**持有 `target/debug/.cargo-lock`**，会连带阻塞 `启动3010.command` 的构建 |
| `require()` | `scripts/node_modules/<pkg>/package.json` 占位 ⇒ `run-checks.mjs` 整链静默挂死 |

**判死锁的手法**：`sample <pid> 2 -file /tmp/x.txt`（沙箱内可用）看叶子帧 + `lsof -p <pid>` 看打开文件。
**教训**：别只凭「没有磁盘写入」下结论——我先误判为死锁、又反过来怀疑是编译慢，两个方向都得用
`sample` 落锤。**而且占位死锁不等于永久失败**：那次 `cargo test` 挂近 1 小时后 iCloud 自行物化，
`mmap` 随即返回，测试跑完 570 项——**先等再判死**。

**修法**（沙箱内 `brctl` 被拒：`Trying to invoke brctl from a sandboxed process`，
`dangerouslyDisableSandbox` 也绕不过；`ps` 同样仍被禁）：

- `node_modules/**` ⇒ `fs.rmSync` 删掉目录 + `npm install --prefer-offline`，走**本地** `~/.npm` 缓存。
  已实测：`scripts/node_modules` 167 → **0**（93 包 11s）、`client/node_modules` 613 → **0**（28 包 2s），
  修后 `tsc --noEmit` 仍 0 错误。**单跑 `npm install` 无效**（判「up to date」不重取），必须先删目录。
- `server/target`、`参考/`、`resources/` 等非 npm 文件 ⇒ 只能由**用户在 Terminal（非沙箱）**
  跑 `brctl download <目录>`。驱逐是**持续发生**的（一个下午内 `client/public-tms273/assets`
  的占位数从 130 涨到 516）。
- 盘点工具：`node scripts/scan_icloud_dataless.cjs`（只 `stat`、不读内容，所以自己不会被卡住；
  `--json` / `--fail-under N` 可当门禁）。

> 因此**「让强缓存生效」的正确顺序是**：先物化 `server/target` 与 `参考/` → 跑一次
> `./启动3010.command` → 再核 `/api/client-release` 与 DevTools 传输字节。

### 1.8 「卡在 37%」的两个真因（同日夜）

用户实测：客户端已重建（20:44，产物含对象库代码），但**预加载卡在 37%**。查下来是两个独立问题叠加。

**真因 A（我的 bug，且影响更大）：闭包名单写死，漏了 57% 的资源。**

`index_client_assets.cjs` 里 `CONTENT_FILES` 是一张**手写的 6 项清单**，漏掉了
`entry/appearance.json`（23MB 外观目录）、`entry/manifest.json`、`windbell/tms273.json`
以及 `tms273/appearance-cashshop/*.json`（1,718 个）。而 `preload-plan.ts` 会把
`manifest.appearanceCatalog`（正是从 `entry/appearance.json` 合并进来的）**逐帧收进预加载** ——
于是这些角色装备图从来没有对象地址。

| | 修复前 | 修复后 |
| --- | --- | --- |
| 引用闭包 | 28,065 | **69,692** |
| 进对象库 | 27,928 | **67,582** |
| 漏掉（只能走逻辑地址 + 304 协商） | — | **39,654（占 57%）** |

⇒ 修复前每次加载有 **3.9 万个资源在走逻辑地址**，这正是「刷新要很久」的主要成分（比强缓存缺失更直接）。
修法：**删掉手写名单，改成扫描 `assets/**` 下除 `objects/` 外的全部 JSON**（闭包取超集最多多写几个对象，
少一项却会挂死加载）。同时给这份扫描也加了 `blocks === 0` 预检——否则读到占位 JSON 会**永久阻塞**。
已重新发布：新 revision `a656c645b99d7ab2c3ccd2a1ec44325821cef1f8a7cbc172cf8eb2651e471049`，
对象 67,582 个 / 423MB，新增 39,238 个，耗时 28.3s；线上实测新索引 `immutable`、指针 `no-cache`。

**真因 B（环境）：服务端读被驱逐的文件会阻塞约 30 秒才返回。**

`client/public-tms273/assets` 有 **452 个占位文件**（`Character_Cap/Coat/Cape…` 正是「角色」资源）。
服务端由用户 Terminal 启动（**非沙箱**），读占位文件会等 iCloud 下载完再返回 —— 实测 **654 字节的文件
等了 32.8 秒**。任何一个落在预加载路径上的这类文件都会把进度条钉死。实测：

```
curl /assets/tms273/Character_Cap__Canvas_01001032...png   →  HTTP=200 但 8s 内 0 字节（挂死）
curl /assets/manifest.json                                  →  200 37MB 0.04s（正常）
```

**想用 HTTP 批量物化是行不通的**：`warm_dataless_assets.cjs` 用 16 并发请求触发下载，
结果把 iCloud 下载通道堵死——连单发请求都 90s 无响应（且**杀客户端不会取消服务端侧已阻塞的读**）。
故这条路只留作单文件应急，**批量必须由用户在 Terminal 跑 `brctl download` 或在 Finder 里
右键 →「立即下载」/「保留下载」**。

**发布的索引与运行中的服务有一个已知不一致**：`/api/client-release` 的 `assetRevision` 是
**服务启动时算一次**的（当前仍报旧值 `95588f79…`，指针已是 `a656c645…`）。客户端只用它做界面显示
（`client-actions/view.ts` 一行），**不参与任何比对**，故不会误报更新或触发循环；重启服务后自然一致。

### 1.9 强缓存生效的最后一块：大内容 JSON 预压缩（2026-09-18 凌晨）

用户复测：「卡进度」好了，但**刷新仍然等于首次加载**。服务端缓存头、客户端接线、索引覆盖率
（`manifest.json` 28,058 条引用 99.76%、`entry/appearance.json` 100%）全部复核为**正确**，
于是改成**用浏览器实测**：`qa/cache-effect-probe.mjs` 走 CDP 的 `Network.requestWillBeSent /
responseReceived / loadingFinished`，读 `fromDiskCache` 与 `encodedDataLength`（命中缓存时为 0），
并记录请求里有没有 `If-Modified-Since`。

**服务端的头是对的，但浏览器没留副本**。首次 66.3MB / 刷新 **61.3MB（92.4%）**，逐条看：

| 请求 | 刷新时 |
| --- | --- |
| `/assets/index-*.js`、`*.css`（immutable） | **0 B**（本地副本，连请求头都不发） |
| `/assets/entry/manifest.json`、`creation.json` | 91 B＝仅响应头（304） |
| `/assets/manifest.json`（35MB） | **37,073,582 B**（无条件、全量） |
| `/assets/entry/appearance.json`（23MB） | **24,200,082 B**（无条件、全量） |

**根因：浏览器对「单个响应」有缓存体积上限，超了就不写 HTTP 缓存。** 同一次实测里
1.5MB / 1.0MB 的 immutable 图片能留本地副本（刷新 0 B），而 **11.9MB 的索引留不下**
（刷新仍全量重下）—— 门槛落在 1.5MB 与 11.9MB 之间。既然根本没有本地副本，
`Cache-Control: no-cache` 的 304 重验证**没机会发生**：那两个请求里连
`If-Modified-Since` 都没有。这也解释了为什么「按分类规则看是对的」却依然慢。

减小**编码后**体积是唯一同时解决「字节量」与「门槛」的手段（br q9 / gz 9 实测）：

| 文件 | 源 | br q9 | gz 9 |
| --- | --- | --- | --- |
| `manifest.json` | 35.36MB | **1.49MB**（615ms） | 2.50MB（391ms） |
| `entry/appearance.json` | 23.08MB | **0.16MB**（94ms） | 0.72MB |
| 36 个 ≥256KB 的内容 JSON 合计 | 89.0MB | 6.20MB | |

做法是**离线预压缩 + 服务端只查文件**，两侧都刻意避开请求期压缩：

- 发布侧 `index_client_assets.cjs` 的 `publishPrecompressed`：只处理 ≥256KB 的内容 JSON，
  写 `<文件>.br` / `<文件>.gz` **兄弟文件**（`ServeDir::precompressed_*` 只认同目录同名的后缀变体）。
  幂等按 **mtime** 判定；源掉到门槛以下时**删除**遗留变体——否则服务端会继续发旧的压缩字节，
  那比不发压缩更坏。`--verify` 会**解压后逐字节比对源**（只比 mtime 挡不住这个）。
- 服务端 `ServeDir::new(&assets).precompressed_br().precompressed_gzip()`：**零 CPU**，
  档位由 tower-http 按 `Accept-Encoding` 协商（顺序 zstd > br > gz ⇒ 浏览器拿 br，
  只支持 gzip 的自动降级）。刻意**不**引入 `tower-http` 的 `compression-*` feature。
- 补 `Vary: Accept-Encoding`（tower-http 自己不加）：同一地址在有无压缩之间可变，缺了它
  任何共享缓存都可能把 br 的字节发给不支持 br 的读方。**只在响应确实带 `Content-Encoding` 时补**，
  纯函数 `apply_vary_for_encoding` + 双向断言（没带编码就不许贴 Vary）。

实测（隔离实例 **3011**，`CLIENT_DIST=build/tmp/client`，不打扰运行中的 3010）：

```
Accept-Encoding: br, gzip → content-encoding: br   content-length: 1565491  vary: accept-encoding
Accept-Encoding: gzip     → content-encoding: gzip content-length: 2618853
Accept-Encoding: identity → content-length: 37073375（不补 Vary）
```

浏览器复测（同一探针）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 首次 | 66,327,233 B | **6,791,252 B** |
| 刷新 | 61,274,297 B | **781 B** |
| 刷新/首次 | 92.4% | **0.0%** |

刷新时那 781 B 全部是 `/api/client-release`(326) 与几个 304 响应头；`manifest.json`、
`appearance.json` 各 91 B（304），JS/CSS 0 B。

**顺带修正 §1.8 的一处判断**：那里的「39,654 个资源只能走逻辑地址」是按**引用串**统计的
（含 1,713 个被引用的 `appearance-cashshop/*.json` 这类清单路径），而真正被预加载成
图片/音频的闭包是 28,058 条 —— 所以「97% 的资源没有对象地址」这个说法当时被高估了。
闭包自动发现本身是对的（必须修），但它不是「刷新等于首次加载」的主因，§1.9 才是。

**仍未解决的是另一半成本**：每张图的解码与建纹理在内存里，与 HTTP 缓存无关。
本轮没有动全量预加载（v3 §15-6：缩小集合属 P3 按图加载）——也就是说
**「刷新不再传字节」不等于「刷新不再解码」**，后者要等 P3。

## 7. 顺手修复：首页角标的长串排版（2026-09-18）

用户实拍：登录界面右下角「当前发布 / 资源修订」那一行，**64 位修订号溢出到圆角框之外**，
同时中文标签被挤成「当前发 布：」。

两个独立的排版原因，都会在**布局检查全绿**的情况下出现：

1. **没有断点的长串不会收缩**。修订号是 64 位十六进制，整串是一个词 ⇒ 它的
   `min-content` 宽度就是整串宽度，`max-width: min(340px, …)` 顶不住它，直接溢出。
2. **中文标签的最小内容宽度只有一个字**。`.client-actions-version` 是 `flex-wrap: wrap`，
   flex 项会先收缩到 `min-content` 再换行；中文可在任意两字之间断行 ⇒ 标签被拆成两截。

修法分两层，**两层都做**：

- 显示层（`view.ts`）：新增 `displayRevision()`，>16 位的修订只显示 `前8…后6`，
  **完整值留在 `title`**——角标只放得下首尾，但报障要用的仍是整串。
- 样式层（`style.css`）：标签 `white-space: nowrap`（换行只发生在条目之间）；
  长串元素补 `overflow-wrap: anywhere` 与 `min-width: 0`。
  **样式层不是「顺手加固」**：它保证即便将来有人把关掉的缩短显示改回来，面板也不会溢出。

验证用 `qa/client-actions-fit-probe.mjs`——判据是几何量本身（面板内容盒 vs 每个后代元素的
左右边界、标签高度 vs 行高），并带一档**注入超长值**的用例：本机验证实例的 `releaseId`
恰好是 `unversioned`，一行就放下了，**复现不出用户那张截图**，所以必须把两个字段改成真实长度
再量。实测 4 个用例（desktop/narrow × 真实/超长）全部通过；超长档下面板撑到 340px 上限、
修订号在框内折成两行。

`check_tms273_client_actions.cjs` 增第 9 组（排版）与第 10 组（预压缩）静态断言，防止回归。

## 8. 根因收口：那 26 秒从来不是缓存问题，是「整份 manifest 全量预加载」（2026-09-18 凌晨）

### 8.1 第三次复测之后换判据

前一轮把「登录页刷新等于首次加载」当成强缓存问题解决了（登录页 61MB → 781B），但用户进入游戏后**刷新依旧等于首次加载**。两轮的判据都不够：

| 判据 | 看到什么 | 为什么不够 |
| --- | --- | --- |
| `curl -I` 响应头 | 头全对（`immutable` / `no-cache` / `Vary`） | 头对 ≠ 浏览器缓存住了 |
| 同页两次加载比字节（只看 `/assets/**`） | 登录页已降到 781B | **完全没覆盖「登录之后」这条路径** |

于是写了一个**端到端探针**：注册/登录 → 频道 → 创角 → 开始游戏 → 等装载完成 → 刷新 → 再来一遍，按 URL 类别归集 `encodedDataLength`。第一版读数就很反常：

```
联网字节  冷 422,000,000 B / 刷新 417,000,000 B（比值 99.2%）
```

**刷新几乎一点都不省**，而且「刷新很慢」与「首屏很慢」是同一件事。

### 8.2 归因：瓶颈在客户端逐张建纹理，不在网络

两个数字放在一起就能定性：

- 进入游戏实测 **23,518 个对象请求 / 387MB / 26.1s**；
- 同一台服务端压测能跑 **6,000 req/s**（3,000 个对象 0.5s）。

⇒ **传输侧根本不是瓶颈**，时间等价于「每张图 ≈1.1ms 的客户端开销」。再去看 `preload-plan.ts`：它把**整份 manifest** 一次入队——**22,594 张**，而**当前地图只占 92 张（0.4%）**。宠物 7,850、其余 198 张地图 4,461、表情贴纸 3,727、物品图标 2,454，在进入游戏那一刻**一张都不会出现在屏幕上**。

也就是说：**HTTP 缓存做得再对，也救不了「根本不该在这个时候初始化」的东西。** 这也解释了为什么前两轮的成果都是真的、却都没解决用户的问题。

### 8.3 两处修改

**① 换掉 Phaser 的图片装载方式。** Phaser 3.90 默认 `imageLoadType: 'XHR'`，每张图走「XHR → Blob → `URL.createObjectURL` → `Image`」四跳。改成直连 `<img>`：

```ts
new Phaser.Game({ /* … */, loader: { imageLoadType: 'HTMLImageElement' } });
```

**单这一项 26.1s → 15.6s**（省的是中转，不是传输）。

**② 新增按需装载器 `client/src/assets/lazy-texture.ts`，首屏只装「当场要画的」。**

```ts
if (!ensureTextures(this, frames.map(frame => frame.url))) continue;  // 本帧先别画
```

合同五条（都写进了模块头注释）：纹理 key **就是逻辑 URL**（与 `preload-plan.ts`/`world.ts` 同一套，不需要第二份键名映射）；返回 `true`＝现在就能画、`false`＝**这一帧先别画**，调用方下一帧自然重试（不用写异步回调）；**装载器忙时不插队**（Phaser 的 `image()` 加进正在跑的批次看不到）；**拉取失败只记账不重试**（否则每帧重发同一个 404），并当作「已就绪」交调用方按现状绘制；**空闲时清空等待集合**（`scene.restart()` 会重置装载器，这是自愈的唯一入口）。

`preload-plan.ts` 的首屏集＝**当前地图 + 本角色 + 战斗 + 界面**；被移出的 5 类登记在 `DEFERRED_CATEGORIES`，与首屏集**双向断言**（进去了的要断言在，出去了的要断言**不在且已登记**）。7 个绘制点接上调用：`world.ts` 的宠物/怪物/掉落/NPC/表情贴纸、`combat/view.ts` 的技能特效（特效只装**本次施放的那个技能**）。新增 `lazy-texture.check.mjs`（8 用例：就绪判据/去重/不插队/失败不重试/空闲自愈）并进 `run-checks`。

### 8.4 最后一根钉子：对象索引自己也是「大文件」

改完 ①②，刷新降到了 **11.9MB** —— 正好是**对象索引自己**。它不是可有可无的元数据：`resource-url.ts` 把逻辑地址换成内容寻址地址全靠它，**它挡在所有资源前面、必须先取**；而它 11.9MB，**正好落在浏览器单响应上限之外**（上一轮的发现：1.5MB 能留本地副本、11.9MB 留不下）。

⇒ 走同一条 `publishPrecompressed` 出路：`index_client_assets.cjs` 现在对索引文件也跑一遍，**11.9MB → br 3.35MB / gz 3.24MB**。

### 8.5 实测（真浏览器，隔离实例 3011）

| | 接入前 | 只做 ① | ①+② | ①+②+索引预压缩 |
| --- | --- | --- | --- | --- |
| 冷加载「开始游戏→装载完成」 | 26.1s | 15.6s | 2.3s | **2.3s** |
| 刷新同一路径 | 25.9s | — | 1.4s | **1.4s** |
| 冷联网字节 | 422MB | — | 46MB | **38.6MB** |
