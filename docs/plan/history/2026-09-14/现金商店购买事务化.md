## 3. 实现范围

限定到玩家可做的具体事情：

1. **购买是可恢复的**。余额、交付的背包、限购计数与请求回执在同一 SQLite 事务里提交；任一步失败整体回滚，不再出现"扣了钱没发货／发了货没记账／回执成功但重启后丢失"。
2. **重试不二次扣款**。同一 `requestId` + 相同 `sn`/`quantity` 指纹重放**持久**回执，原样返回原结果。这一条现在跨进程重启成立（此前只有内存窗口）。
3. **requestId 一次性**。同一 `requestId` 换 `sn` 或数量 → `cash_request_conflict` 拒绝，不会以新参数重放旧结果。
4. **余额与限购以持久档案为准**。事务内读 `player_stats.cash` 与 `cash_purchases.units`；读不到角色档案 → `profile_unavailable` 拒绝；限购读取失败直接报错（`cash_store_unavailable`），**不再当作 0 继续**。
5. **拒绝也留回执**。`cash_limit` / `cash_not_enough` 与成功一样入 `cash_actions`，同一 `requestId` 重放拿到同一判决。
6. **内存回正**。事务返回的 `cash`／`purchased_units` 是持久读数，World 据此覆盖内存镜像，窗口显示的余额不会再与服务端实际可用余额分叉。

### 3.1 有意收窄的写入面

旧实现购买时调用 `save_profile`（整行 `player_stats`：hp/mp/level/exp/mesos/cash/map_id/x/y/skills…），会顺带把 World 内存里**当时**的其它字段写回库。新事务只 `UPDATE player_stats SET cash`——购买不改变那些字段，而它们各有自己的写路径（击杀奖励的 `profiles`、换图、断线）。收窄后，商城事务不再可能用陈旧的镜像值覆盖更新的持久值。

## 6. 数据变更

- **新增表**：`cash_actions(account_id, request_id, sn, item_id, quantity, cash_spent, cash_after, purchased_units, success, code)`，`CREATE TABLE IF NOT EXISTS`，服务端打开库时自动建。**无需人工迁移**。
- **既有表不变**：`player_stats`、`inventory`、`cash_purchases` 结构未改。
- **旧实例保真**：无既有行被改写、删除或重新解释；`cash_actions` 为空时行为与审计前一致（只多了一层持久回执）。
- **兼容窗口**：新表对旧二进制无害（旧代码既不读也不写它），因此**回退代码后新库仍可被旧版本正常读写**。反之，新版本读旧库会得到空回执表，等价于"尚未买过"——与旧版内存窗口的冷启动语义相同。

## 10. 用户实玩入口

需先在自己终端跑**统一入口**加载（服务端二进制已变）：

```
zsh 启动3010.command
```

协议号与内容版本**都没变**（仍 21 / `tms273-23`），所以不必担心前后端配套问题；但服务端必须换新二进制才会带上本次事务。重启作废会话 token，页面刷新重登即可。

观察点：

1. 登录 → 聊天框 `/cash 1000` → 打开左下角「商店」→ 买任意商品：余额与背包应同步变化，与改动前手感一致（正常路径无行为变化）。
2. **重登保留**：买完关闭窗口 → 刷新页面重登 → 余额与已购道具仍在（这是本次修的主症状）。
3. **重启保留**：记下余额 → 跑 `zsh 启动3010.command` 重启 → 重登确认余额与道具都在、限购计数仍在。
4. **失败不损失**：把余额买到不足一件的价位，再买一次应得"余额不足"，且余额/背包不变。
5. 限购商品（如某件 `Limit>0` 的）连续买到超限，应得"超出限购"且不扣款。
