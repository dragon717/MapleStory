# 高频操作反馈：被拒时说清是什么挡住了你（审计 T04 反馈面）

- 日期：2026-09-14
- 范围：审计 §11 **T04｜高频操作与战斗表现**中"反馈目标"那一半
  （"玩家能分清施放被拒绝、攻击未命中、命中但伤害很低、目标死亡与拾取成功；不能用相同的静默反馈覆盖所有情况"）
- 协议：**23 不变**；内容版本：**`tms273-23` 不变**（无装配数据改动）

## 1. 这次修的是什么

静态扫描 `server/src` 全部 `reject` / `send_reject` 调用点，与客户端 `PROTOCOL_ERRORS` 表对比，发现一批码在客户端没有文案。这些码走 `main.ts` 的兜底分支：

```ts
status(`${protocolText(message.code, message.message)} (${message.code})`, true);
```

于是中文界面上玩家看到的是**服务端英文诊断 + 裸错误码**，例如按攻击键时被拒：

```
Cannot attack while climbing or dead (invalid_state)
```

这不是反馈，是服务端在跟开发者说话。而且更糟的是——`handle_attack` 用 `invalid_state` **一个码**覆盖了「爬绳中 / 死亡 / 技能引导中」三种完全不同的情况。玩家按下去没反应，得到的答案既看不懂，也分不清自己是哪种情况。

同一类静默还有一处：采集物竞争失败（`reactor_spent` 被人先采走、`reactor_busy` 正在被摇动）在客户端**完全没有任何提示**，只有 `reactor_out_of_range` 给了一行。玩家点了一下，什么都没发生。

## 2. 实现范围（玩家能感知的变化）

| 之前 | 现在 |
| --- | --- |
| 爬绳/死亡/引导中按攻击 → `Cannot attack while climbing or dead (invalid_state)` | 分别是「爬在绳子或梯子上时无法攻击」「死亡状态无法攻击」「技能引导中无法攻击」 |
| 连点攻击被吞 → `Attack still active (cooldown)` | 「上一次攻击动作还没结束」 |
| 采集物被别人先采走 → 无声 | 「这个物件已经被采完了」 |
| 采集物正在被摇动 → 无声 | 「这个物件正在被摇动，请稍等」 |
| 所有未翻译的拒绝 → 英文 + `(code)` | 中文文案；裸码只进控制台，不再出现在玩家面前 |

## 3. 关键设计：为什么 `invalid_state` 故意没有通用文案

`invalid_state` 在各调用点自带原因（「死亡角色不能加点。」「当前状态不能施放技能。」）。若给它一条通用文案，**这些具体原因会被抹平成一句"现在无法执行这个动作"**——那是从"看不懂"变成"看不出区别"，同样是审计反对的"用相同的反馈覆盖所有情况"。

所以规则定为：**每个调用点必须有中文表达，来源可以是客户端文案表（可按语言切换），也可以是该调用点自带的中文 message**。原先两处英文（`revive.rs` 的 `Cannot revive while alive`、采集物的 `Reactor hit rejected`）已改为中文。

### 4.1 去掉 `(code)` 时踩到的一个真回归（已修，并加断言钉住）

`session.ts::scheduleReconnect` 原本是从**给玩家看的句子**里正则反解终端码：

```ts
const code = handshakeFailure.match(/\(([a-z_]+)\)\s*$/)?.[1];   // 依赖 "replaced (session_replaced)" 这个形状
```

把拼接改成 `protocolText(...)` 之后，展示串里不再有 `(code)`，**终端判定静默失效** —— `session_replaced` / `banned` / `unauthenticated` 全部退化成"普通断线，继续重试"，两个页面会对同一个角色无限争抢（正是该文件头注释要防的事）。

这是 T04 改动**自己引入**的，被既有检查 `session.check.mjs` 抓出（场景 2 变红：`session_replaced 必须停止自动重试`）。修法是让码与展示文本分离：`onmessage` 里 `handshakeCode = message.code` 单独存，`scheduleReconnect(handshakeCode)` 直接用，不再解析句子。同时把该检查的 `protocolText` 桩做成**不回填 code**，这样一旦有人再退回去从展示串反解，场景 2/4 立刻变红。

教训：把机器可读的字段嵌进人读的字符串里，任何一次文案本地化都会顺手废掉它。

### 4.2 `handle_attack` 的死亡判定多了 `hp <= 0`

原判定只有 `action == "dead"`，现为 `action == "dead" || hp <= 0`。严格说这超出"只改怎么说"的范围，记录在此：

- **理由**：`state.hp <= 0 || action == "dead"` 是本仓库既有的"死亡"谓词（`growth.rs`、`trade.rs`、`skills.rs`、`boss.rs`、`dialogue.rs`、`inventory_ops.rs` 都这么写）。这里用同一谓词是与引擎对齐，而不是新造语义；否则 hp 已归零、`action` 还没翻到 `dead` 的那一帧里，攻击会被**放行**而不是被拒（那是比"提示文案不统一"更糟的漏洞）。
- **风险**：理论上存在"hp<=0 但 `action != "dead"` 且原本允许攻击"的窗口，此改动会把该窗口关闭。判定为可接受：0 血能攻击本身就是缺陷。
- **未动**：攻击冷却、伤害、范围、命中逻辑一律未改。

### 4.3 服务端文案统一为简体

本轮新写的服务端 message 初稿误用繁体（「角色還活著，不需要復活。」「這個物件已經被採完了。」），已改为简体。依据：仓库既有的玩家可见中文文案是简体（`world.rs` 的「道具冷却中，还需 {seconds} 秒。」「角色死亡时无法使用传送卷軸。」、`dialogue.rs` 的「死亡角色不能使用仓库。」），只有专有名词（`STORAGE_KEEPER_FUNC = "倉庫"`）与物品名保留繁体。

已知遗留（未改，不属本轮）：`ship.rs:318` 的登船拒绝走 `if en { English } else { "現在無法登船，請稍後再試。" }` 双语模式，用繁体。它是飞行船模块既有写法，且是服务端自带双语而非查客户端表，单独处理。
