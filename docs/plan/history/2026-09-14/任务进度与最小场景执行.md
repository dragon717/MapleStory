## 3. 实现范围

### 3.1 C01：击杀进度是服务端已确认的事实

1. **类型化进度**。`QuestObjective` 支持 `kind: "kill"`，进度读 `Player.quest_kills`（持久计数的只读镜像）；物品类仍读背包事实，不另建副本。
2. **只由"认领了这只怪奖励"的那次击杀推进**。增量写在 `resolve_attack_with_party` 的击杀事务里，且只在 `monster_rewards` 认领成功（`reward_claimed`）时执行。重放的死亡消息、重发的请求、同一具尸体的第二条死亡消息都不会再加一次。
3. **只在任务进行中才收目标**。世界层用 `active_kill_objectives(id, 模板)` 在事务**之前**解析；未接任务、已交付、模板不匹配 → 空列表。客户端无法通过报文声明"我完成了"。
4. **练习图永远不算任务进度**（`!practice` 与技能／元素路径一致）。
5. **进度属于击杀落地的人**，队友伤害不替他记账。

### 3.2 C02：被阻塞的续章入口

1. **入口授权由服务端分发点决定**。`QuestOrigin`：NPC 菜单只能结算自己那个阶段；任务视窗只能结算源标为自服务的阶段；脚本对话保留历史路径。报文里没有"我是谁"的字段可以伪造 → 错方向回 `quest_self_service_unavailable`。
2. **36315 的目标怪真的进了世界**。3 条已核定依据：源 `QuestInfo` 的 `demandSummary`（「擊殺藍色蘑菇王 #R36315ExkillRef36315#」）、`Check.1.infoex` 的 kill 计数器、以及 `references/tms273-data/maple-island-calamity-source.json` 的 `classification.kill.mobId = 8645261`。原版专用修練图 993166xxx 几何本地不可解（U），故适配器把它放到已装配、且从出生图可达的 `001010000 冒險者修練場入口`，地形锚点复用该图已有的刷怪记录（`001010000-life-0` / foothold 68），**不新造坐标、不改原作地图的 life**。
3. **只放能让任务可达的怪**。36319／36322 的 8645264／8645262 **不放**：这两条任务的完成阶段在源 `QuestInfo` 里没有 `selfComplete`，属 script-scene 边界，放了不会让它们可达。台账里逐条写明。
4. **前端只提出请求**。任务视窗按源自助标记渲染按钮，服务端重新校验每一条作者闸门。

### 3.3 启动加载契约（本轮实证修复）

统一加载时 3010 起不来：

```
Error: "Cannot load gameplay .../shared/gameplay.json: quest references unknown npc or prerequisite"
```

根因：源里没有 NPC 的相位（`QuestInfo` 标 self-service、`Check/*/npc` 缺失）在装配数据里是**空字符串** `npcId`，而加载校验把 `Some("")` 当成"引用了不存在的 NPC"。服务端其余部位早就按"空串＝没有 NPC"读（`quest.rs` 的 `targetNpcId` 先 `.filter(|id| !id.is_empty())`），只有这条校验漏了同一处理。36315 一转为可执行，校验首次检查到它，整个 `gameplay.json` 被拒，服务端起不来。

修法：校验只把**非空**却查不到的 id 当错误（`server/src/gameplay.rs`）。这也解释了为什么当时的全部单测与 JS 检查都是绿的——它们都用 `serde_json::from_str` + `include_str!` 建夹具，绕过了 `Gameplay::load` 这一步。因此新增 `content_boot_acceptance.rs`，把 `main()` 的加载顺序（`Map::load` → `Gameplay::load` → `MapCatalog::load` → quest text → windbell → 构世界）钉成断言，并要求災禍篇的目标怪在世界上真的实例化。
