# 转职任务：原版转職官漢斯的二转／三转完整流程（TMS273）

日期：2026-09-21。需求单：原版转职官（漢斯，模板 `1032001` / 地图 `101000003`）此前只接得动**一转**
剧情任务（源 `QuestData/1402.img`，已可执行），二转／三转在点他时没有任何任务流程——玩家只能靠
「選擇岔道」漢斯（`10201`）那个按等级判定的**快捷入口**换职业。这一轮把完整任务链补上。

协议 **34**、内容 `tms273-33` **均未变**，客户端**零改动**（复用 `npc.conversation` 既有槽位与
既有任务日志条目形状）。纯服务端 + 一张手工维护的配置。

## 1. 缺口与病根

- 通用任务目录 `shared/gameplay.json`（70 条）里，`npcId = 1032001` 的任务**只有 1402 一条**
  （一转，等级 8）。二转（`200 → 220`）与三转（`220 → 221`）没有条目 ⇒ 30 级法师点漢斯，
  要么重复弹一转，要么什么都不弹。
- 既有的 `dialogue::apply_job_advance`（快捷入口，判据是**等级**）是用户指定的便利通道，
  **刻意不动**：它是「不想跑任务就直接转」的授权，与本任务是两条独立授权，互不改写。
- 源 273 包**未随附二转／三转的执行脚本**（`script/npc` 里没有对应实体），所以目标怪物、
  目标道具与数量是**本项目可执行化的补齐**，配置里逐条标 `provenance: "P"`；转职官、一转等级
  与前置、二转技能 `2200011`（源 `fixLevel=1`）是同版 WZ 已核字段，标 `"T"`。**不冒充原作数值**。

## 2. 为什么单独成模块（`server/src/job_advance.rs`）

转职与通用任务共享「接取 → 做目标 → 交付」的形状，但有三处本质差异，硬塞进 `world::quest`
只会把两套语义绞在一起：

- **奖励维度不同**：通用任务奖励是 mesos / exp / 道具；转职奖励是**职业本身**外加技能书 SP、
  固定技能与 MP 下限，落库时还要以职业做 CAS。
- **幂等键不同**：通用任务靠 `(quest_id, status)` 转场；转职一旦完成 `fromJob` 就再也不成立，
  因此「已转职」额外由职业字段兜底。
- **生命周期不同**：不可重复，且可接取性由**当前职业**唯一决定 ⇒ 同一时刻对同一角色最多一条
  命中（`fromJob` 在目录内唯一，由加载校验与门禁双向钉死）。

分层：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 配置与启动校验 | `JobAdvanceCatalog::load` | 缺项＝装配没跑完，**硬失败**（与 `npc-dialogue.json` 同一口径；静默降级的表现恰好是「点了没反应」） |
| 纯判定 | `rules` | **不接收 `World` / `Store` / `&mut`**，输入只取 `rules::Facts` 这份收窄过的只读事实集 |
| 唯一写路径 | `impl World`（`accept_job_advance` / `complete_job_advance`） | 顺序恒为「先算候选 → 再落库 → 成功后才写回内存并回执」 |
| 事务 | `auth/job_advance.rs` | `JobAdvancePlan`（职业 + 奖励契约的纯函数 `apply_job_advance_grant`）+ `Store::commit_job_advance`（职业 CAS、状态置 completed、奖励，同一事务） |

**进度存储不新建表**：复用通用任务的 `player_quests(account_id, quest_id, status)` 与
`quest_kills(account_id, quest_id, mob_id)`；收集类目标**直接读背包**，没有第二份副本
⇒ 转职进度与任务日志天然同源，客户端无需改动。

## 4. 分发位置与「剧情任务优先」

`dialogue.rs` 里 `handle_job_advance_talk` 排在通用任务菜单 `handle_quest_npc_menu`
**之前**（门禁断言这个顺序），命中判据是「当前职业 == `fromJob` 且站对了 NPC + 地图」，
所以新手（job 0）在这里不命中，照旧走一转剧情；已转职角色也不会被快捷菜单挡住。

**开场让路规则**（本轮自行纠出的一条真实回归风险）：漢斯同时是源一转任务 1402 的接取／交付
NPC，而 1402 的条件里写着职业 `0/200/220/221/222` ⇒ 走「選擇岔道」快捷转职过来的角色职业
已经是 200，**若本模块先接手，他们就再也没有入口把一转剧情补完**。因此开场时只要该 NPC 此刻
还有剧情任务要给（`quest_menu_choices` 非空），本模块返回 `false` 且不占用会话节点；
1402 补完之后同一位 NPC 才转回转职任务。由 `job_advance_defers_to_the_source_story_quest_at_the_same_npc` 钉死。

会话节点 `job-advance:<questId>`：**只有会话中途**（玩家真的选了选项）才认节点，开场一律重新
出菜单，免得上一次会话的残留节点把玩家锁在旧状态里。

## 6. 门禁 `check_tms273_job_advance.cjs`

Rust 侧验收断言的是**自带的**目录，证明不了「配置里写的怪／道具／转职官在装配出来的内容里真的
存在」。转职任务的失败形态又全是静默的：目标怪没有刷新点 ⇒ 击杀计数恒为 0、玩家只会一直听到
「試煉還沒有完成」；转职官没摆在那张图上 ⇒ 点了没反应；收集道具不在 `items.json` ⇒ 交付入口
永不出现；Windows 包漏表 ⇒ `main.rs` 硬失败、3010 起不来。

五组断言：① 形状（id 唯一、`fromJob` 目录内唯一、目标种类与数量、奖励与六段台词齐备）；
② 职业链（前置要么是本表内上一段且 `toJob == fromJob`，要么真的在通用任务目录里；等级门槛沿链
严格递增）；③ 内容可达（**从 `shared/*.json` 独立重算**：NPC 摆放、怪物刷新点、道具、地图）；
④ 反向断言（kill 与 collect 两类通道都要有实例、至少一条前置指向通用目录、目录不得为空）；
⑤ 接线（main.rs 加载与注入、world.rs 挂目录、dialogue.rs 的顺序、quest.rs 两处并入、
Windows 清单带它、本门禁已进 `run-checks.mjs`）。

**扰动 7 组全部被拒**（每组都打印到具体断言）：目标怪改成不存在的 id／改成有模板但**没有刷新点**
的怪（`3220000`）／转职官地图改成没摆放的图／`fromJob` 撞车／等级门槛不沿链递增／前置悬空／
抹掉 collect 通道；另有一组「Windows 资源清单删掉本表」也被拒，复原后两组均重新 PASS。

## 8. 如实登记的边界

- **目标怪物、道具与数量是本项目补齐（`provenance: "P"`）**，不是原作数值；只有转职官、
  一转等级与前置、二转技能 `2200011` 是同版已核（`T`）。
- **只做冰雷一条线**（`220` / `221`）。火毒（`210`/`211`）、主教（`230`/`231`）与三转的
  其余分支**没有**配置 ⇒ 相关职业点漢斯仍只会走既有路径，**不会**被本模块误接。
- 「選擇岔道」漢斯（`10201`）的等级制快捷转职**保留且未改**，与本链是两条独立授权。
- **未实跑 3010 服务**：本轮未做统一加载；协议与内容版本未变，客户端零改动。
- `shared/job-advance.json` 与三个新增 Rust 文件**尚未 `git add`**（工作树内为未跟踪状态）。
  配置是运行期硬依赖，提交时不能漏。
- 转职奖励**只加不减**：技能等级取「已有 vs 配置」的较高者，技能书 SP 按计划只发一次
  （`grant_is_idempotent_for_skills_but_adds_points_once`）；MP 只抬到下限、不削。
