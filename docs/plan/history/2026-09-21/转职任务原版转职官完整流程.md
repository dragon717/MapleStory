## 1. 缺口与病根

- 通用任务目录 `shared/gameplay.json`（70 条）里，`npcId = 1032001` 的任务**只有 1402 一条**
  （一转，等级 8）。二转（`200 → 220`）与三转（`220 → 221`）没有条目 ⇒ 30 级法师点漢斯，
  要么重复弹一转，要么什么都不弹。
- 既有的 `dialogue::apply_job_advance`（快捷入口，判据是**等级**）是用户指定的便利通道，
  **刻意不动**：它是「不想跑任务就直接转」的授权，与本任务是两条独立授权，互不改写。
- 源 273 包**未随附二转／三转的执行脚本**（`script/npc` 里没有对应实体），所以目标怪物、
  目标道具与数量是**本项目可执行化的补齐**，配置里逐条标 `provenance: "P"`；转职官、一转等级
  与前置、二转技能 `2200011`（源 `fixLevel=1`）是同版 WZ 已核字段，标 `"T"`。**不冒充原作数值**。

## 2. 为什么单独成模块（`server/src/job_advance.rs`）

转职与通用任务共享「接取 → 做目标 → 交付」的形状，但有三处本质差异，硬塞进 `world::quest`
只会把两套语义绞在一起：

- **奖励维度不同**：通用任务奖励是 mesos / exp / 道具；转职奖励是**职业本身**外加技能书 SP、
  固定技能与 MP 下限，落库时还要以职业做 CAS。
- **幂等键不同**：通用任务靠 `(quest_id, status)` 转场；转职一旦完成 `fromJob` 就再也不成立，
  因此「已转职」额外由职业字段兜底。
- **生命周期不同**：不可重复，且可接取性由**当前职业**唯一决定 ⇒ 同一时刻对同一角色最多一条
  命中（`fromJob` 在目录内唯一，由加载校验与门禁双向钉死）。

分层：

| 层 | 位置 | 职责 |
| --- | --- | --- |
| 配置与启动校验 | `JobAdvanceCatalog::load` | 缺项＝装配没跑完，**硬失败**（与 `npc-dialogue.json` 同一口径；静默降级的表现恰好是「点了没反应」） |
| 纯判定 | `rules` | **不接收 `World` / `Store` / `&mut`**，输入只取 `rules::Facts` 这份收窄过的只读事实集 |
| 唯一写路径 | `impl World`（`accept_job_advance` / `complete_job_advance`） | 顺序恒为「先算候选 → 再落库 → 成功后才写回内存并回执」 |
| 事务 | `auth/job_advance.rs` | `JobAdvancePlan`（职业 + 奖励契约的纯函数 `apply_job_advance_grant`）+ `Store::commit_job_advance`（职业 CAS、状态置 completed、奖励，同一事务） |

**进度存储不新建表**：复用通用任务的 `player_quests(account_id, quest_id, status)` 与
`quest_kills(account_id, quest_id, mob_id)`；收集类目标**直接读背包**，没有第二份副本
⇒ 转职进度与任务日志天然同源，客户端无需改动。

## 4. 分发位置与「剧情任务优先」

`dialogue.rs` 里 `handle_job_advance_talk` 排在通用任务菜单 `handle_quest_npc_menu`
**之前**（门禁断言这个顺序），命中判据是「当前职业 == `fromJob` 且站对了 NPC + 地图」，
所以新手（job 0）在这里不命中，照旧走一转剧情；已转职角色也不会被快捷菜单挡住。

**开场让路规则**（本轮自行纠出的一条真实回归风险）：漢斯同时是源一转任务 1402 的接取／交付
NPC，而 1402 的条件里写着职业 `0/200/220/221/222` ⇒ 走「選擇岔道」快捷转职过来的角色职业
已经是 200，**若本模块先接手，他们就再也没有入口把一转剧情补完**。因此开场时只要该 NPC 此刻
还有剧情任务要给（`quest_menu_choices` 非空），本模块返回 `false` 且不占用会话节点；
1402 补完之后同一位 NPC 才转回转职任务。由 `job_advance_defers_to_the_source_story_quest_at_the_same_npc` 钉死。

会话节点 `job-advance:<questId>`：**只有会话中途**（玩家真的选了选项）才认节点，开场一律重新
出菜单，免得上一次会话的残留节点把玩家锁在旧状态里。

## 6. 门禁 `check_tms273_job_advance.cjs`

Rust 侧验收断言的是**自带的**目录，证明不了「配置里写的怪／道具／转职官在装配出来的内容里真的
存在」。转职任务的失败形态又全是静默的：目标怪没有刷新点 ⇒ 击杀计数恒为 0、玩家只会一直听到
「試煉還沒有完成」；转职官没摆在那张图上 ⇒ 点了没反应；收集道具不在 `items.json` ⇒ 交付入口
永不出现；Windows 包漏表 ⇒ `main.rs` 硬失败、3010 起不来。

五组断言：① 形状（id 唯一、**`toJob` 全局唯一**——一个职业只能由一条任务转出、目标种类与数量、
奖励与六段台词齐备）；② 职业链与**分支**（同一 `fromJob` 的多条必须挂在**同一位 NPC 的同一组地图**上、
标题互不相同，否则玩家一次会话选不全或分不清；前置要么是本表内上一段且 `toJob == fromJob`，
要么真的在通用任务目录里；等级门槛沿链严格递增）；③ 内容可达（**从 `shared/*.json` 独立重算**：
NPC 摆放、怪物刷新点、道具、地图）；④ 反向断言（kill 与 collect 两类通道都要有实例、至少一条前置
指向通用目录、**至少一个职业是多分支的**否则服务端那段分支菜单是死代码、目录不得为空）；
⑤ 接线（main.rs 加载与注入、world.rs 挂目录、dialogue.rs 的顺序、quest.rs 两处并入、
Windows 清单带它、本门禁已进 `run-checks.mjs`）。

**扰动 8 组全部被拒**（每组都打印到具体断言）：目标怪改成不存在的 id／改成有模板但**没有刷新点**
的怪（`3220000`）／转职官地图改成没摆放的图／**分支挂到别的地图**／**分支挂到别的 NPC**／
**两条转向同一个职业**／**两条分支标题相同**／**抹掉多分支（分支菜单变死代码）**／
收集道具不在 `items.json`（`4009999`）／等级门槛不沿链递增／前置悬空；另有
「Windows 资源清单删掉本表」也被拒。复原后重新 PASS。

**判据随源码同步改过一处**：第一轮写的是「同一 `fromJob` 只能一条」，第二轮允许分支后这条
就必须换成「`toJob` 全局唯一 + 分支同处」，否则新配置会被自己的门禁挡下——改语义时判据要一起改。

## 10. 二转分支选择：同一个职业、同一位 NPC、三条路

法师二转在原版是**站在同一位转职官面前挑路线**（火毒／冰雷／主教），这与第一轮的
「一个职业最多一条命中」直接冲突——三条任务的 `fromJob` 都是 `200`。改法是让候选成为集合：

- 目录侧：`quest_for`（返回 `Option`）→ `candidates`（返回 `Vec`，**按 `questId` 排序**，
  不依赖配置书写顺序，否则菜单项顺序会随配置漂移）+ `by_id`（会话中途精确定位）+
  `active_quest`（已经接过的那条优先）。
- 会话侧：开场若候选 > 1 ⇒ 出**分支菜单**，选项就是各分支标题，末位「結束對話」；
  选中后会话节点切成 `job-advance:<questId>`，之后走与单条完全相同的路径。
  **让玩家选，不替玩家选**。
- **已接取的分支不再给第二次选择**：否则玩家能把三条二转任务同时挂在身上。
- 会话中途**只认节点里带着的那一条**：换了职业或换了 NPC 之后旧节点失效，此时如实回
  「该对话选项已失效，请重新交谈」，而不是静默什么都不回。
- 加载校验的新不变式：① `toJob` 全局唯一（一个职业只能由一条任务转出）；
  ② 同一 `fromJob` 的多条必须挂在**同一位 NPC 的同一组地图**上（否则「选分支」会变成
  「跑两张图各说一次话」）、标题互不相同。

三条新验收：`job_advance_second_job_offers_every_branch_and_sticks_to_the_choice`
（三条分支全给、选中即绑定、已接不再给分支菜单、别的分支一个都不出现在选项里）、
`job_advance_third_transfer_has_no_branch_menu`（三转只剩一条路，不问玩家）、
`job_advance_active_trial_hides_the_other_branches`。

## 12. 技能侧：当时的阻塞（第二轮**未**实装；**已由第三轮解除**）

> 本节保留第二轮实测的阻塞事实与「必经六步」计划，作为第三轮动手前的判断依据。
> **同日的第三轮已把三条阻塞逐条解除**，落地内容与验收见 §13。文中「本轮在配置里
> **刻意不写** `reward.skills`」的结论**已被第三轮取代**：二转三分支现按源 `fixLevel`
> 事实授予技能（`2100009` / `2200011` / `2300009`），三转因源无 `fixLevel` 节点仍只发技能书点数。

用户要的是「转职的**技能**和任务」。任务链两条分支都做完了；**技能没有做**，原因如下（都是实测）：

1. **装配产物里只有冰雷线**：`shared/mage-skills.json` 的 `bookId` 分布是
   `{0:3, 200:8, 220:9, 221:12, 222:24}`，**没有** `210/211/230/231`。
   火毒与主教的技能在客户端技能窗里根本不存在（技能窗按 `entry.bookId` 取点数）。
2. **白名单是硬编码的**：`scripts/tms273_skill_manifest.cjs` 的 `mageRules` 只收
   `['0','200','220','221','222']`；`scripts/export_tms273_skills.cjs` 的 `SKILLS` 数组逐条登记技能
   （`image` / `skillJson` / `canvasArchive` / `bodyAction` / `assetKinds`），
   `expectedCatalogCounts` 也是写死的 `{'0':3,'200':8,'220':9,'221':12,'222':24}`。
3. **源侧文本文件缺失**：导出器读 `参考/273/TMS273少爷一键端/TMS273/WZ_JSON_TW/String/Skill.json`
   取技能名与书名，而该文件**当前不存在**（同目录只有 `FamiliarSkill.json` / `MobSkill.json`）。
   另一份 `手工服务端/tms273/WZ_JSON_TW/String/Skill.json` 里 `210/230` 段只有
   `_dirType` + `bookName`（书名齐全：`火/毒魔法指南`、`魔導士之路(火毒)`、`僧侶指南`、`祭司之路`），
   **没有技能名**。⇒ 现在直接重跑技能导出会失败或产不出名字。
4. **源侧数值数据是有的**：`WZ_JSON_TW/Skill/210.json`（10 个技能）、`211.json`（11）、
   `230.json`（10）、`231.json`（15）都在，`String/Mob.json` 与客户端 `Data/Skill`（含 `_Canvas`）
   也在，`unpack_tms273_ms` 已构建 ⇒ **技术上可行**，但要先补齐第 3 条那条读名字的路径。

因此本轮在配置里**刻意不写 `reward.skills`**：不发放一个技能表里不存在的技能；
技能书点数（`skillPoints`）照发，等技能表补齐后同一批点数就能用。已把这条写进
`shared/job-advance.json` 的 `provenance.P`，不让「只发了点数」被误读成技能已经实装。

**技能部分的必经步骤**（下一轮）：① 从客户端 `Data/String.wz`（或恢复源文本）解出
`210/211/230/231` 的技能名与描述；② 在 `SKILLS` 里登记各分支的核心技能并确定图标所在
`_Canvas_XXX.wz` 与 `bodyAction`（角色动作帧，火毒／主教各需一批新动作）；③ 同步
`mageRules` 白名单与 `expectedCatalogCounts`；④ 重跑导出 → 装配，升 `CONTENT_VERSION`；
⑤ 服务端战斗侧接入（`skills.rs` 施放、`damage.rs` 管线登记新数值字段）；⑥ 全量回归。
其中 ② 的角色动作帧与 ⑤ 的战斗接入是这条链上最重的两段。

## 13. 技能侧落地（同日**第三轮**）

§12 的三条阻塞逐条解除。这一轮的重点不是「多导出四本书」，而是**让四条分支共用一套结构**：
同层的三本书共用页签下标、同一被动槽位在多条分支上对称消费、投影边界只许出整型——
任何一处仍按「技能 id」写死，下一条分支进来都会重新漏一遍。

### 13.2 源侧缺口：两份 `WZ_JSON_TW` 是互补的，改成双根查找

§12 第 3 条说直接重跑导出会失败（读不到 `String/Skill.json`）。实测原因是
**两份导出树各缺一半**：

| 根 | `Skill/` 八本 | `String/Skill.json` |
| --- | --- | --- |
| `TMS273/WZ_JSON_TW` | 缺 `220.json` | **缺** |
| `手工服务端/tms273/WZ_JSON_TW` | 齐全 | **有** |

导出器现在把两个根按序全部试过（`sourceJsonPath()`），两边都没有才抛错、并把两条候选路径
一起放进报错文本——不再写死单一路径，也不再静默产不出名字。

### 13.3 产物：9 本 / 102 条

`shared/mage-skills.json`（源版本 `TMS273.7`）的 `bookId` 分布：

| 书 | 0 | 200 | 210 | 211 | 220 | 221 | 222 | 230 | 231 | 合计 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 条数 | 3 | 8 | 10 | 11 | 9 | 12 | 24 | 10 | 15 | **102** |

四本新书（`210/211/230/231`）此前在客户端技能窗里**根本不存在**（技能窗按 `entry.bookId` 取点数），
现在与冰雷线同构。内容版本随之 `tms273-33 → tms273-34`；协议 **34 未变**（`ds_skillInfo` 形状没动）。

### 13.4 页签：下标是「转职层级」不是「技能书」

`scripts/tms273_skill_manifest.cjs` 里硬编码的 `['0','200','220','221','222']` 换成表 `SKILL_BOOK_TABS`：

| 书 | `0` | `200` | `210` / `220` / `230` | `211` / `221` / `231` | `222` |
| --- | --- | --- | --- | --- | --- |
| 页签下标 | 0 | 1 | **2**（同层三选一） | **3**（同层三选一） | 4 |

同层三分支**必须复用同一下标、不能顺延**——源 `UI/UIWindow2.img/Skill/main/Tab` 只有 **7 组**
页签图，顺延会超出范围退化成没有美术的占位按钮。`skillManifest()` 对「导出的书集合」
与「表里登记的书集合」做**双向闭包断言**（少导一本、或表里多登记一本，都断）。

客户端同步新增 `client/src/features/skills/view.ts` 的 `BOOK_JOBS`——**客户端唯一的书准入权威**：
原先 `canLearn` / `castBlockReason` / `books()` 三处各自内联 `bookId` 判断（四处），
现在全部读同一张表；服务端下标表与客户端职业表**必须一起改**，注释已互相指认。

### 13.5 投影边界：只许出整型（`RUNTIME_INTEGER_FIELDS`）

源公式允许小数（`2311003` 神聖祈禱 `x = "20+u(x*3)/2"` 在奇数级算得 **21.5**，与
`Wcr2 Calculator.cs` 的 `decimal` 口径一致），而 `MageLevel.x` 是 `i64` —— 一度让
**36 条验收**以 `invalid type: floating point 21.5, expected i64` 全数失败。

收口放在**投影边界**（`scripts/tms273_skill_manifest.cjs`），而不是改 Rust 类型：

- `RUNTIME_INTEGER_FIELDS` 列出全部运行期整型字段；`projectScalar()` 对这些字段 `Math.round`，
  **不在表里的字段原样透传**（`2111013` 劇毒領域 的 `t = 0.4` 保持 0.4，因为它不进契约）。
- 门禁 `check_tms273_skill_manifest.cjs` 从 `server/src/mage.rs` **反向解出** `Option<i64>` /
  `Option<u32>` 字段集合，与 `RUNTIME_INTEGER_FIELDS` **双向断言**（Rust 加字段忘登记、或登记了
  却删了字段，都红），再断言产物里这些字段无小数、并把 `2311003` 的逐级序列钉死为
  `[22,23,25,26,28,29,31,32,34,35,37,38,40,41,43,44,46,47,49,50]`。

### 13.6 服务端：按「槽位」消费，一处真实缺陷被收口时暴露

`server/src/world.rs` 把技能 id 收成具名常量 + **具名数组**：`MASTERY_SKILLS`、
`SPELL_MASTERY_X_SKILLS`、`INTELLIGENCE_SKILLS`、`ELEMENTAL_ADAPTING_SKILLS`、`ELEMENT_AMP_SKILLS`、
`ELEMENTAL_RESET_SKILLS`、`MAGIC_CRITICAL_SKILLS`、`CRITICAL_CHANCE_SKILLS`。
`attribute.rs` 的 `intX` / `mastery`+`x` / `asrR`+`terR`，与 `skills.rs` 的 `damR` / `mdR` /
`criticaldamage` / 暴击率 / 攻速 / MP 消耗，都改成**逐条 `Some(skill_id)` 留痕**——
同一个槽位上 2~3 本书各报各的来源，而不是合成一条说不清是谁贡献的带宽。

收口过程中暴露一处真实缺陷：`action_speed_bonus` 原先对**未学**的急速詠唱也会取
`boosterActionSpeed` 兜底，四条分支一进来就把每个 -2 累加（-3 → -6/-8）。改为**只有学过才计入**
（`ice-mage` 的 `-3` 断言随之恢复）。这正是「按数组消费」的副作用被验收抓住的例子。

### 13.7 `mage.rs::validate()` 从「名单」改成「从 id 派生」

原先写死 `BEGINNER_IDS` / `FIRST..FOURTH_JOB_IDS` / `HYPER_IDS` 五张名单与
`matches!(len, 8|17|29|32|43|56)` —— 加一条分支必然漏一处。现在：

- 书号 = `skill_id / 10000`，落在 `BOOKS = [0,200,210,211,220,221,222,230,231]`；
- 元素属性集合含 `f/s/h`（火/毒/聖）；二转上限 `(10, 6)`、四转 `(15, 15)`；目录长度含 `102`；
- `required(field)` 表按源 `rawCommon` 逐技能补齐 `210/211/230/231` 共 **46 条**，
  未进 `MageLevel` 模型的源字段留注释说明（不静默丢）。

### 13.8 任务侧随之补齐（§11 的表已更新）

二转三条分支按源 `fixLevel` 事实授予技能，与冰雷同构：`job-210` → `2100009` 元素吸收、
