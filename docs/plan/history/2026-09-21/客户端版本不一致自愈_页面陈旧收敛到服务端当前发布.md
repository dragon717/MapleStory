## 2. 根因

**版本身份在两侧都是「烘死在构建产物里的常量」**：

- 客户端：`shared/protocol.ts` 的 `PROTOCOL_VERSION` / `CONTENT_VERSION` 被 vite
  内联进 bundle；
- 服务端：`server/src/protocol.rs` 的 `const CONTENT_VERSION` 编进二进制。

而一次发布（`启动3010.command` 的 prepare → rotate → serve）是在**已经打开的页面脚下**
把服务端换掉的。于是那个标签页里的常量**再也追不上**服务端——这是结构性的，
不是偶发。

**真正该修的是处置方式**：项目其实已经有让页面收敛的全部素材
（`/api/client-release` 的发布描述、`entryUrl()` 的「带发布标识的入口地址」），
但那条路被 `update-service.ts` 的契约占着——`evaluateCompatibility()` 的语义是
「发布与本页不兼容就停在 `blocked`」，方向是**用户主动去校验服务端发布**。
陈旧页面需要的是**反方向**的动作：本页旧、服务端新，让**本页自己**走到服务端那一版。
这条路根本不存在 ⇒ 只剩一句「请刷新页面」把工作推给用户。

## 3. 修法：不新增机制，把已有的两件素材接起来

| 文件 | 改动 |
| --- | --- |
| **新增** `client/src/features/client-actions/version-heal.ts` | `healStalePage()`：取发布描述 → 若描述与本页同一版则不导航 → 否则用 `entryUrl()` 导航到服务端当前发布。不新增机制、不清缓存/Cookie、不动服务端数据（v3 §6.5），也不放宽兼容性校验（U04）——换的是**本页自己**，不是让服务端给旧客户端降级 |
| `client/src/network/auth-api.ts` | 版本拒绝改成**可辨识类型** `VersionMismatchError`（**错误文本一字不改**），让上层能把「这一页过期了」与「登录真的失败」分开处置 |
| `client/src/features/entry/view.ts` | `run()` 的 catch 里先调 `recoverStalePage(error)`：已在导航就不再显示那句文案（不闪错），否则照旧显示 |

**与 `update-service.ts` 的分工**写在模块头：那个是用户点的强制更新（校验发布是否与本页
兼容，不兼容停在 `blocked`）；本模块是页面被落下时的自愈（方向相反）。

### 3.1 四重护栏（防重载环与误判）

1. 只在**描述确实与本页不同**时才导航；描述与本页一致 ⇒ 不是「页面陈旧」，交回调用方报错；
2. 取描述失败 ⇒ **不导航**（U02 同款：不假成功、不猜测）；
3. 记忆载体是**地址里的 `r` 参数**（`entryUrl` 导航后本页 URL 就带上了它）——
   地址里的 `r` 已等于这次要去的 `releaseId` ⇒ 说明上一步就是为它导航的，仍然不一致便
   老实报错 ⇒ **结构上不可能无限重载**。刻意**不用 `sessionStorage` 布尔标记**：
   无痕模式下不可用会退化成「每次都导航」，正好是最该避免的成环形态；
4. 下一次发布是**新的 `releaseId`** ⇒ 自动重新获得一次自愈机会，不需要任何人来「清标记」。

自愈**不带 `ce`（资源修复代数）**——它不是「用户明确选择重新下载所需资源」，
带上会让每次发布都重下全部资源。

## 4. 顺带修掉的三处（都是把修复接进真实链路时才暴露的）

### 4.1 `platform/runtime-config.ts` 顶层裸读构建期全局 ⇒ 离线包整包崩

`export const codeMode = __CODE_MODE__` 是**模块顶层裸读**。生产构建由 vite `define`
替换成字面量，但本模块也会被**离线打包器**打进 bundle（`features/entry/view.check.mjs`
的 esbuild 就没有注入）⇒ 直接读会在模块求值时抛 `ReferenceError`，
**整个包连登录界面都出不来**。

实证：把 `version-heal` 接进 entry 依赖链后，`entry/view.check.mjs` **由绿转红**，
而且只报最外层的症状「`登录素材加载失败` / 背景图不出现」——症状离病因很远。
修法：`typeof __CODE_MODE__ === 'undefined' ? 'BUILT_PACKAGE' : __CODE_MODE__`
（`typeof` 对未声明标识符是安全的；vite 的两处都会被替换，替换后仍得 `BUILT_PACKAGE`）。
**生产产物实测已无裸全局残留。**

### 4.2 `fetchClientRelease` 写死根相对路径 ⇒ 桌面包取不到发布描述

`fetch('/api/client-release')` 是**根相对**。浏览器同源没问题，但桌面包外壳
（`client/src-tauri`）只注入 `apiBase` 指向真实服务端、**并不代理 `/api`**
⇒ 描述永远取不到，于是**自愈在桌面包上也不会发生**（连带原来首页的版本标签与强制更新检查）。
修法：改走 `apiBase`（`${apiBase}/api/client-release`）。
浏览器下 `apiBase === ''` ⇒ 输出与写死根相对路径**逐字节相同**。

### 4.3 `resource-url.ts` 两条无扩展名导入 ⇒ 两条判据一直是红的、等于没人跑

`resource-url.ts` 里 `from './asset-index'` / `from '../platform/desktop-config'` 没有后缀。
Node 的 ESM 解析器**不给相对导入补后缀**，于是**直接由 Node 装载**的那些 `.ts` 检查
（`--experimental-strip-types`）整条链装载失败：

- `features/client-actions/update-service.check.ts` —— **强制更新契约的判据**
- `scenes/layer-animation.check.ts`

这正是本仓库已经吃过两次的亏（`run-checks.mjs` 里两处注释都写着「一直是红的而没人看见」）。
补显式 `.ts` 后 `update-service.check.ts` **6 组断言全绿**（由红转绿）。
`assets/asset-index.check.mjs` 的说明符改写正则写死「无后缀」，同步放宽为 `(?:\.ts)?`
——它的本意是「依赖还在、还能被改写」，不是「不许带后缀」。

> 内容版本**不变**（`tms273-35`）：本轮只改客户端代码，不进内容版本；
> 下一次发布 `releaseId` 自然变化，届时陈旧页面即可自愈。

## 11. 现场取证：先证明「修复到底有没有生效」

取出来对，避免把「部署没生效」当成「修复没作用」：

| `?r=` 参数 | 服务端**完全不解析**：`/`、`/?r=<旧id>`、`/?r=BOGUS` 都下发同一个 `index-BUu4F73a.js` | 排除「旧 `r` 拉到旧包」的陷阱，自愈导航是安全的 |
| 真实浏览器端到端 | 全新页面 + 全新账号登录 ⇒ 进入 `entry-stage-channel`，`notice` 空、无页面错误 | **新页不可能不一致** |

⇒ 修复已生效；**全新加载的页面绝不会不一致**。那么残留的错误只可能来自
**「先于修复就打开的标签页」**——它内部的常量更旧，且**不含自愈代码**，所以
它跑不了自愈。这就是"鸡生蛋"：**在修复之前构建出来的页面，不可能运行修复**。

佐证：`runtime/3010-control/server.log` 是累积的启动横幅，内容版本一路
`tms273-31 ×6 → 32 ×7 → 33 ×12 → 34 ×3 → 35 ×2`——服务端被反复重启、每次递增。
任何跨过一次重启还开着的标签页，必然陈旧。

## 12. 本轮加固：把自愈提前到「进入首页」

上一轮的自愈只在**点登录拿到不一致时**触发。「页面开着不动、期间服务端换了代」
能被这一拍覆盖（那次登录就是最早能发现它的时刻），但**「这次载入拿到的本身就是
旧的 HTML/旧包」**（浏览器把旧页面/旧包缓存给了这次载入）在那一拍之前就已经陈旧，
玩家得先点一次登录才被告知。

修法（**同一份判据、同一组护栏，只多挂一个点**，不新增机制）：

```ts
// client/src/features/entry/view.ts 构造时
if (typeof location === 'object') void healStalePage(browserHealDeps(location.href));
```

- 与本页**同一版**时是**空操作**（`describesThisBuild` 一致即返回），正常加载不多跳；
- 取描述失败 ⇒ `unavailable` ⇒ 不导航（U02 同款，不假成功）；
- 落回同一 `releaseId` ⇒ `already-tried` ⇒ **结构上不可能成环**；
- `typeof` 兜底：没有 `location` 的 node 离线检查照旧能装载本模块。

两处挂点合并成一句可复述的话：**「页面陈旧」有两个能被发现的最早时刻——一进首页、
以及第一次点登录；两处都用同一套判据，且都是「一致即空操作」。**

# 续二：用户点出「访问了缓存，但右下角重置失效」——真缺陷定位与修正（2026-09-22 上午）

## 16. 用户线索

用户补上关键一句：**「根因问题是访问了缓存，但我点右下角重置失效。」**
右下角就是首页的「客户端操作区」（`features/client-actions/view.ts`）——那颗按钮的
文案是**「强制更新」**，悬停提示写着「联网检查最新发布，**并重新装载页面**与资源清单」。

## 17. 缺陷定位：那颗按钮恰好在唯一需要它的场景里是死路

读代码即可复现，无需猜：

```ts
// update-service.ts（修前）
async apply(repair = false) {
  const state = await this.check();
  if (state.phase !== 'verified' || !state.release) return state;   // ← blocked 直接返回，不导航
  …
  this.options.navigate(entryUrl(href, state.release.releaseId, epoch));
}
// view.ts（修前）
const state = await this.service.check();
if (state.phase === 'verified') this.confirm.hidden = false;        // ← blocked 时不给确认面板
else this.updateButton.disabled = false;
```

而 `evaluateCompatibility()` 只看「发布与本页是否同一版」：

| 情形 | `check()` 结果 | 修前行为 |
| --- | --- | --- |
| 发布与本页同版 | `verified` | 给出确认面板 → 可「重新装载页面」 |
| **发布比本页新（页面陈旧 / 缓存了旧页）** | **`blocked` / `incompatible-content`** | **不给面板、不导航**，只在状态区写「新发布的内容版本与本页面不一致，请更新客户端后再登录。」 |

⇒ **「强制更新」唯一的用途就是换掉陈旧页面，而它偏偏只在「不需要它」的时候可用。**
这正是用户说的「点了失效」。旧判据还把这条行为当成契约钉住了
（`update-service.check.ts` 修前 ⑤：`equal(navigated.length, 0, '不兼容不得导航')`），
所以缺口既不会被离线判据发现，也没有任何界面出口。

## 18. 修法：报告照旧如实，但不许扣着补救手段

**校验没有放宽**——这是一次**契约修正**，不是放松：

- `check()` **照旧**把不一致如实报成 `blocked`（`incompatible-protocol` /
  `incompatible-content`），界面**照旧**说明原因；
- `apply()` 改为**只要拿到发布描述就导航**：`if (!state.release) return state;`。
  理由：描述**就是服务端当前发布**，`entryUrl()` 指向的正是它的入口 ⇒
  「把这一页换到那份发布上」在**任何版本组合**下都是收敛方向（页面旧⇒升上去；
  服务端回滚⇒跟着回滚；描述是垃圾⇒服务端不解析 `r`，只是重载一次）。
  真正没法收敛的只有「取不到描述」（`failed` / `bad-response`）⇒ 不导航、不假成功（U02 不变）。
- `view.ts` 的 `startUpdate()` 改为**拿到描述就显示确认面板**：`if (state.release) …`。
- **缓存这一层顺带被治到**：`entryUrl()` 产出的 `?r=<releaseId>` 是**浏览器没见过的新 URL**
  ⇒ 绕过任何按 URL 的缓存副本，拿到新 HTML（`no-cache`）⇒ 指向新的带指纹 JS。
  这就是「卡在缓存里的旧页」缺的那一步。

分工因此变得自洽：**两条路都收敛到服务端当前发布，区别只在「谁触发」与「要不要重下资源」**
——`update-service`＝用户点的（可选带资源修复代数 `ce`）；`version-heal`＝自动的（永不带 `ce`）。

## 19. 负向验证：新判据确实有牙

新增的 UI 级判据（见 §20）在**修前写法**下必须转红。实测把接线临时改回
`if (state.phase === 'verified')` 后：


即**确认面板永远出不来** —— 正是用户遇到的「点了没用」。改回修后写法即全绿。
