## 判据的权威来源：源帮助文本那一句（本轮最值钱的发现）

`2321054` 的**帮助文本**（`String/Skill.img` 的 `h` 字段；导出树里是
`resources/tms273-export/skills.json` 的 `catalog.skills['2321054'].string.h`）**逐字写死**了四对对应关系与**顺序**：

> 消耗MP #mpCon，**群體治癒、淨化、神聖之泉、神聖之水**各別轉換成**天使之觸、勝利之羽、天使之泉、神聖之血**
> ＋「冷卻時間 #cooltimeMS秒」＋「#c[被動效果]#魔法攻擊力增加#madX、最終傷害增加#mdR%、無視怪物防禦率增加#ignoreMobpdpR%、攻擊屬性耐性減少#u%」

同一句顺带给出了三件事，全部成了判据锚点：

| 要用的东西 | 从这句读出来的 | 落到哪 |
|---|---|---|
| 四对配对的**成员与顺序** | 「A、B、C、D 各別轉換成 a、b、c、d」 | `world.rs::TRANSFORM_PAIRS` |
| `cooltimeMS` 的**单位** | 文案写「冷卻時間 #cooltimeMS**秒**」，而源值是 `500` | 调用点字面量 `500_000` |
| `[被動效果]` 的**三项原文** | `madX` / `mdR` / `ignoreMobpdpR`（＋攻擊屬性耐性） | 属性层 / 伤害管线 / 无视防御 |

### ⚠️ 目录键顺序陷阱（第一版实现踩了这个坑）

第一版按「两批 id 各自按导出树键顺序按位配对」实现。**导出树的键对整数样 id 是数字升序**，
所以復仇侧被排成 `天使之觸(2301010) / 天使之泉(2311014) / 勝利之羽(2311015) / 神聖之血(2321016)`
——与源写的顺序不同 ⇒ **配错两对**。门禁当场报出：

```
world.rs::TRANSFORM_PAIRS 与源描述标记重算的配对不一致：
  源侧重算 = 2301002→2301010、2311001→2311015、2311011→2311014、2321015→2321016
  world.rs = …2311001→2311014、2311011→2311015…
```

**修法**：配对与顺序改从**帮助文本按名配对**读（唯一依据），形态标记只负责**成员资格**，两路互证。

### 形态标记：区分两侧，且必须带方括号

`description` 里含 `#c[慈愛]#` 的属慈愛侧、含 `#c[復仇]#` 的属復仇侧，**各恰好 4 条**（实测）。
必须带方括号——`2321054` 自己的文案写的是 `#c慈愛#`／`#c復仇#`（**无**括号），不带方括号会把施放者自己也算进去。
反例同样要钉：`1310018`／`1311019`／`1320011`／`1320043`（闇靈復仇／追隨者族）正文里有「復仇」二字
但**不含该标记**，门禁断言它们**不在**復仇侧。

## 用户裁决（本轮三次拍板，全部落地）

源里**没有任何**关于「转换持续多久 / 怎么解除」的表达（无 `time`、无開關文案、无再次使用说明），因此需要裁决：

1. **转换时长／解除方式 ＝ 常驻（学会即转换）**——转换永久、不可逆。
   落点：转换态**从技能表派生**（`transform_done` ＝「復仇那几本在技能表里」），**不新增任何状态位**，
   于是它随技能存档自动持久。
2. **本轮范围 ＝ 骨架 + 属性层 + 逐本接**——技能轉換接纳表 ＋ 源派生配对判据 ＋ 状态 ＋ 施放门槛
   ＋ 准入按形态反转 ＋ `[被動效果]` 三项消费 ＋ 客户端镜像 ＋ 门禁 ＋ 验收 ＋ 扰动 ＋ 文档。
3. **施放那一刻 ＝ 执行转换**——`mpCon(100)` ＋ `cooltimeMS(500 秒)` 是价格，效果＝把四本復仇技能
   按慈愛对应等级授予进技能存档。**施放有真实效果、零新状态位、随存档持久。**

## ⚠️ 本轮最值钱的操作教训：`cp -p` 还原 ＋ mtime 增量 ⇒ **陈旧二进制假红**

收尾跑全量时出现一条**自有红灯** `xform_admission_flips_with_the_form`，
报文正是 E2 的症状（「转换之后 天使之觸 仍被拒」），可是：

- 单独跑**也红**（不是并行干扰）；
- 在施放前插一行临时打印，实测 `form=Some(Avenge) has=true granted=true`——
  **闸门的三个析取项全是绿的，却仍然报 `skill_hidden`**；
- 把打印删掉再跑，**12/12 绿**；带着打印跑也是 **12/12 绿**。

⇒ 结论：**不是代码问题，是验证用的产物没重编。**

**机制**：扰动用 Edit 工具改（mtime 更新）⇒ cargo 重编 ⇒ 报红（符合预期）；
还原用 `cp -p`（**保留原 mtime**）⇒ `build/.cargo-cache` 是 **mtime 增量** ⇒
cargo 认为「源码比产物旧、不用重编」⇒ 之后跑的 `cargo test` 用的是**还带着扰动**的二进制。

这与仓库既有的「装配器不重编会 <1s 假成功」是同一类陷阱，但**发作方向相反**：
那次是「假绿」，这次是**假红**——而且报文看起来完全像真缺陷。

**纪律（已写进 `SKILL.md` §7）**：扰动还原之后，**必须**把改过的源文件 `touch` 一遍
（或直接 `touch` 整个 crate 的源文件）再跑验收，否则「还原成功」这句话没有证据。
真正的判据是**二进制 mtime > 源文件 mtime**，不是「`cmp` 说文件内容一致」。
本轮 `cmp` 逐字节一致、文件内容确实对，**但产物是旧的**。
