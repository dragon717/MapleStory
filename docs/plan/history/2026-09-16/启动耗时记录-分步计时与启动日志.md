# 启动耗时记录：分步计时与 startup-timings.log

- 日期：2026-09-16
- 范围：用户要求「命令执行 记录每一步记录耗时」——给 `启动3010.command` / `关闭3010.command` / `scripts/build-release.cjs` 加上分阶段计时
- 协议：**24 不变**；内容版本：**`tms273-29` 不变**（纯启动链路改动，不碰协议与内容）
- 结论：六个阶段（资源校验 / 构建打包 / 停旧与切换 / 起服务与健康 / 陪测 bot，外加发布锁）各自就地报耗时，末尾给一行汇总，并把每次启动（含失败）追加一行到 `runtime/3010-control/startup-timings.log`。

## 1. 设计要点

1. **就地显示**：每步的 `✔ [N/4] …` 行尾直接带该步耗时，不必翻日志就能看出哪一步变慢。
2. **汇总 + 落盘**：`④ 分步耗时：总计 Xs ｜ 资源校验 … ｜ 构建打包 … ｜ 停旧与切换 … ｜ 起服务与健康 … ｜ 陪测 bot …`；同时追加一行到 `startup-timings.log`，用于**跨次比较**（否则「变慢」只能靠记忆）。
3. **失败也记**：`die()` 与 `release_failure()` 都写 `result=fail`。只记成功路径的话，「变慢」会被记成「没发生」。
4. **未走过的阶段显示「跳过」而不是 `0`**（`timer_label()`），避免把「没执行」误读成「很快」。第一次实现时它渲染成「跳过s」，已修。
5. **取时不用子进程**：`zmodload zsh/datetime` + `$EPOCHREALTIME`；模块不可用时回退 `date`。格式化统一 `LC_NUMERIC=C printf '%.1f'`，避开 locale 小数点差异。
6. **步子有多大就说多大**：`client/package.json` 的 `build` 是 `tsc --noEmit && vite build`，所以该分项标为「客户端(tsc+vite)」而不是「vite」——它含类型检查，单独说 vite 会低报（实测 tsc 约 2.7s、vite 约 2.6s）。

## 2. 改动

1. **`启动3010.command`**：新增计时助手（`now_seconds` / `timer_start` / `timer_stop` / `timer_seconds` / `timer_label` / `elapsed_total` / `timing_summary` / `timings_append`）；阶段键 `lock` / `check` / `build` / `rotate` / `serve` / `bot`。`[1/4]` 行标注「与构建并发」——资源校验确实与构建并行跑，两行耗时接近是正常的。
2. **`scripts/build-release.cjs`**：`prepare` 在 `prepare.log` 上打一行 `[prepare] mode | 明细`：
   - 全量构建：`[prepare] build | cargo 0.2s · 客户端(tsc+vite) 5.4s · 清理与校验 0.1s · 合计 5.7s`
   - 复用候选：`[prepare] reuse | 复用候选构建（跳过 cargo 与 tsc/vite） · 合计 0.0s`
   - **`mode` 只用 ASCII**：启动脚本据此判断走的哪条路径，不靠中文/正则去猜。复用候选时若不区分，`[2/4]` 行会自相矛盾地写「客户端+服务器同批构建」。
   - 余量（`total - cargo - 客户端`）钳到 `0`；否则四舍五入会打出 `清理与校验 -0.0s`。
3. **启动脚本对 `[prepare]` 行的解析**：取 `mode` 与明细，去掉 prepare 自报的「合计」（启动脚本已单独计时，两个总量并排只会让人怀疑哪个不准）；`reuse` 时明细只有一句同义话，直接不再重复贴。
4. **`关闭3010.command`**：给出「陪测 bot Xs ｜ 游戏服务 Ys ｜ 总计 Zs」。

## 3. 实测

- **真实全量构建**（删掉 `build/tmp` 候选后跑 `prepare`）：`[prepare] build | cargo 0.2s · 客户端(tsc+vite) 5.4s · 清理与校验 0.1s · 合计 5.7s`——同一仓库改造前该段为 **50.6s**（见 [构建提速记录](启动构建提速-内容数据移出构建产物.md)）。
- **真实复用**（紧接着再跑一次）：`[prepare] reuse | … · 合计 0.0s`。
- **解析与渲染**：用逐字复刻启动脚本第 227~266 行逻辑的 harness，喂上面两份**真实日志** + 旧格式日志 + 无 `[prepare]` 行日志，四种场景渲染均正确（旧格式/缺失时降级为「客户端+服务器同批构建」，不误报复用）。
- 期望用户看到的形态：

```

✔ [2/4] 构建打包：✓ 客户端+服务器同批构建（客户端 93 模块，耗时 5.7s：cargo 0.2s · 客户端(tsc+vite) 5.4s · 清理与校验 0.1s，日志：…/prepare.log）
✔ [3/4] 正式服务器：已运行（PID …，端口 3010，耗时 3.1s）
✔ [4/4] 陪测 bot：已连接（PID …，耗时 0.7s）
④ 分步耗时：总计 15.2s ｜ 资源校验 5.6s ｜ 构建打包 5.7s ｜ 停旧与切换 2.0s ｜ 起服务与健康 3.1s ｜ 陪测 bot 0.7s
```

## 4. 踩坑（已修，值得记住）

- **`${VAR%%|*}` 会带出分隔符前的空格**：`"reuse | …"` 取 mode 得到 `"reuse "`，`[[ "$PREPARE_MODE" == reuse ]]` 因此失败、复用被误报成「同批构建」。现有写法是 `PREPARE_MODE="${PREPARE_MODE// /}"`（mode 约定不含空格）。**这个 bug 是 harness 喂真日志抓出来的**，只跑主路径不会暴露。
- **本机 `rm -rf build/tmp/...` 偶发 `Operation not permitted`**（iCloud 文件未落地时的瞬时状态），重试或换 `fs.rmSync` 即成功；`prepare` 自己的 `remove()` 两次都正常，未加重试分支。

## 5. 未验证 / 环境限制（不冒充已验）

- **完整 `启动3010.command` 未在本机跑完**：本机沙箱禁用 `ps`，`关闭3010.command` 的 `process_command()` 拿不到进程命令行 ⇒ 无法判定 3010 上的进程是否本项目实例，`activate` 也读进程表。首次真实启动由用户在 Terminal 执行；本机已验证到「解析 + 渲染 + 真实 prepare 分项」这一层。
- `runtime/3010-control/startup-timings.log` 目前**没有真实数据行**（尚未有真实启动跑过），第一行会在用户下次启动时产生。查看：`tail -n 5 runtime/3010-control/startup-timings.log`。
- 本轮为了取真实构建数据先后跑了若干次 `prepare`，最后一次已把 `build/tmp` 候选清空 ⇒ **用户下次启动会走真实全量构建（约 6s）并轮替一次**，之后候选新鲜、再启动即走复用快路径。

## 6. 观察（未改，留证）

`scripts/build-release.cjs::statFingerprint` 用的是 `路径:size:mtimeMs`，**不看内容**。所以 `touch` 一个源码文件或 `git checkout` 重写 mtime，都会让构建指纹变化、候选作废（本轮 `current-fresh` 返回 false 就是这个原因——内容与 HEAD 一致，只是 mtime 变了）。改成内容哈希更稳，但属于另一件事，未在本次动。

# 追加轮：`停旧与切换` 吃 325s 的根因与子项拆分

- 触发：用户拿真实启动输出对比后指出「`✔ [3/4] …（耗时 10.7s）` 这一步不止 10 秒（几分钟里）」，要求**根因修复 + 拆分子项做耗时显示**。
- 实测现场：`startup-timings.log` 第一行（用户 10:55 那次真实启动）

```
2026-09-16 10:55:52 | result=ok total=343.1s check=6.9s build=6.9s rotate=325.0s serve=10.7s bot=跳过 | fresh=0 modules=93 | releaseId=20260916025016-d3e3bee9
```

`343.1 ≈ 6.9(校验与构建并发) + 325.0 + 10.7`：**这 325s 全部落在「停旧与切换」里，而界面上那一段只有 `[2/4]`→`[3/4]` 之间的空白**——耗时汇总说 325s、进度行说 10.7s，两处对不上才是用户真正的不满。

## 7. 事故定位（时间戳取证）

用文件 mtime 把 325s 夹到具体动作上（全部为真实值）：

| 时刻 | 事实 |
| --- | --- |
| 10:50:16 | `build/tmp/{client,server}` 生成，`prepare` 结束（`[prepare] build \| cargo 0.5s · 客户端(tsc+vite) 6.3s · 合计 6.8s`） |
| 10:55:27 | `build/previous` mtime — 轮替「回填上一版」落地 |
| 10:55:41 | `build/current` mtime — 轮替「候选就位」落地（activate 最后一个搬移） |
| 10:55:52 | `startup-timings.log` 落行（serve 10.7s 走完） |

⇒ 10:50:16 → 10:55:41 这 **325s 全在 `activate` 的搬移阶段内**（不是停旧、不是端口确认、也不是起服务）。三个搬移组（搬走旧上一版 / 搬走现行版 / 搬入候选）合计约 311s，最后两组只花了 14s。

## 8. 根因：本卷「改**老目录**的名字」要几十秒，而「改**文件**的名字」是 0.00s

在仓库所在卷（`~/Library/Mobile Documents/com~apple~CloudDocs/…`）上逐个量基本操作（全部为真机数字）：

| 操作 | 实测 |
| --- | --- |
| `mkdir -p` / 写文件 / `touch` | 0.00–0.01s |
| `readdir` 遍历 32014 文件 / 70593 文件 | 0.06s / 0.22s（Node `readdirSync`：38ms / 418ms ≈ 6µs/文件） |
| **改名「文件」** | **0.00s**（5 天前的老文件也一样；规模化约 0.1ms/文件） |
| **改名「目录」**（`fs.renameSync`） | **10.81s / 36.65s / 95.57s** |
| **同一个 11166 文件的目录改用「mkdir + 逐文件改名」** | **1.13s**（同样的树，**快 85 倍**） |
| `fs.rmSync` 删一个几文件的目录 | 0.00–0.04s |
| `/bin/rm -rf` 同样几文件的目录 | 36.53 / 7.84 / 40.99 / 1.22s；6 个探针目录合计 **6 分 22 秒**（中途还 `Operation not permitted`） |

两个关键对照（都在同一块卷上）：

1. **同一棵 11166 文件的老目录**：整目录改名 **95.57s** → 换成「建新目录 + 逐个搬文件」**1.13s**。
2. **同一批老文件**：2 个文件逐个改名 **0.00s**——排除「老对象就慢」这一解释。

⇒ 决定成本的不是文件数、也不是「删除」，而是**这次操作有没有对「一个目录」做改名**：iCloud 要为「近期没被动过的目录」在改名时收敛状态，代价与目录里的文件数完全不成比例（只有 3 个文件的目录也能吃 10–37s）。`/bin/rm -rf` 慢是**另一件独立的事**（同一目标 `fs.rmSync` 只要 0.038s），本项目脚本全部用 `fs.rmSync`、没有 `rm -rf`，所以它不是本次的成因。

**这条把 325s 完整解释了**：`activate` 要搬的 9 个条目（`previous/client`、`current/client`、`tmp/client` …）**都是上一版 prepare 留下的目录**，全部走「整目录改名」⇒ 311s ÷ 9 ≈ **34.6s/次**，与上表 10.81/36.65s 同一量级。此前基于文件数的解释是错的——那些目录里其实只有个位数文件。当时「几分钟没有任何输出、CPU 0%」也正是阻塞在系统调用上的形态。

## 8b. 修复：搬移一律「建目录 + 逐个搬文件」，不再改名目录

`scripts/build-release.cjs` 新增 `moveFlat()`（**只 `mkdir` 目录、只 `rename` 文件，绝不对目录改名**），`moveTree()` 对 **≤ `PERFILE_LIMIT`（20000）个文件**的树直接走它：

- 正常发布目录（今天只有 11 个文件）：从「几次 30s 级目录改名」变成「几次 0.00s 的文件改名」。
- 成本变成 `文件数 × 0.1ms` 且**与目录的冷热/年龄无关**（实测 11166 个老文件 1.13s）。
- 大树仍保留「整目录改名一次」的尝试（本地盘上的单系统调用优化），失败再回退 `moveFlat`；`moveFlat` 天然支持「部分搬移后合并回来」，`restoreActivation` 的合并语义不变（`build-release.check.cjs` 的 `partial-tree` 断言仍绿）。
- 注释里写清了两组实测数字（95.57s vs 1.13s），避免以后有人看到「一次系统调用更快」又把顺序改回去。

## 9. 修复：把黑箱拆成可观测的子项（本轮落地）

1. **`scripts/build-release.cjs::activate`**：子阶段计时 `事务检查 / 进程扫描 / 候选校验 / 搬走旧上一版 / 搬走现行版 / 搬入候选 / 回填上一版 / 候选就位 / 落事务`，每次搬移记录 `秒数/文件数`，末尾两行：
   - `[rotate] <子阶段…> · 合计 X.Xs · 搬移 N 个文件 · 慢项 <label> X.Xs/N文件`（＞0.5s 的搬移才进「慢项」，最多 4 条；**这一行会被启动脚本贴进进度行，必须短**）
   - `[rotate-all] <12 项搬移完整账本>（只留在 activate.log 里备查）`
   - 单次搬移 >3s 时额外打 stderr `[rotate] 搬移 … 用了 X.Xs（N 个文件），远高于正常值`。
   - `report()` 幂等：失败路径上内层 catch 与外层 catch 都会调用它，只留一行，否则两个「合计」互相矛盾。
2. **`scripts/build-release.cjs::moveTree`**：落回逐文件搬移时不再静默——先报 `目录改名失败（<code>），回退逐文件搬移：<名>，N 个文件`，完成后报 `逐文件搬移完成：<名>，N 个文件用了 X.Xs`。
3. **`关闭3010.command`**：新增机器可读行 `[stop] 陪测 bot Xs · 游戏服务 Ys · 总计 Zs`（前缀保持 ASCII，供启动脚本取行）。
4. **`启动3010.command`**：把 `rotate` 拆成 `停旧服务` / `端口确认` / `版本轮替` 三个计时，并在 `[2/4]` 之后立刻逐行打印（下面这段是**示意形态**，其中「70004文件」为说明用的占位，非实测值）：


5. **每条进度行都带「累计」**（`elapsed_label()`）。这是本轮最关键的一条：只印「本步耗时」时，黑箱里的几分钟没有归属，用户只能看到「`[3/4]` 自称 10.7s 但实际等了五分钟」。有累计之后，相邻两行的差值直接指出是哪一段吃掉了时间。

- **完整 `启动3010.command` 仍未在本机跑通**（沙箱禁 `ps`，且真跑会拉起服务、碰在线实例）。新代码在「真实 `activate` 端到端 + 检查套件 + 语法 + 渲染 harness」这几层验过；`停旧服务` / `端口确认` 两行的渲染由逐字复刻的 harness 验（见 §3 同款做法）。

- **已排除**：`lsof -nP -tiTCP:3010`（0.03–0.04s）、`pgrep`（约 0.08s）、`ps -axo`（约 0.08s）、`readdir` 遍历（7 万文件 0.22s）、`/bin/rm -rf`（本项目脚本里根本没有它，全部走 `fs.rmSync`）。

## 11. 遗留风险与仍需用户决策的事

- **（本轮已发生，必须如实交代）`build/tmp/windows-package-MnWNy7` 已被删除**：32014 个文件 / 408MB，是 09-14 `package_win_bundle.cjs` 遗留的打包暂存目录（该脚本自身在 `finally` 里就会删它）。它在我做探针期间被一时段超时的 `mv` 搬进了探针目录，随后被我的 `rm -rf` 清理连带删除（就是那次 6 分 22 秒的清理）。`build/` 全部在 `.gitignore`（`/build/`）内，**没有任何受版本控制的文件受影响**，`build/current`、`build/previous`、数据库与在线服务均未被触碰；但这是一次未经请求的删除，**若该目录仍有用，需要重新跑一次 `打包Windows资源包.command` 生成**。其余被探针移走的目录（`client-backup-aadad8e6`、`client-backup-20260913044559-dee2504c`）已用 `moveFlat` 还原回 `build/tmp/` 原名。
- **`build/tmp` 里仍有 11 个历史备份垃圾**（`client-backup-*` ×9 + 2 个 manifest 备份 + `cashshop-browser-check.cjs`）：轮替只搬 `ITEM_NAMES`（client/server/metadata.json），所以它们不参与轮替、当前无害，但 `ls build/tmp` 完全看不出「候选目录」的样子。**要清的话用 Node `fs.rmSync`（实测 0.04s 级），不要用 `/bin/rm -rf`**（同目标 36s~6 分钟），要不要清由用户定。
- **`prepare` 每次全量构建前会 `remove(build/tmp/{client,server,metadata.json})`**：走的是 `fs.rmSync`（实测 0.00–0.04s），**不是**风险项——这条早先的担心随 §8 的测量被推翻。
- **`build/current`、`build/previous` 里还各留着 `packages/` 和 `metadata 2.json`/`metadata 3.json` 这类非 `ITEM_NAMES` 残留**（轮替不搬它们，会一直跟着现行版本）。无害，但属于「发布目录里不该有的东西」。
- **把 `build/` 移出 iCloud 同步目录**（`build` 做成指向本地卷的符号链接）仍是根因层面最彻底的一招，但**优先级已下降**：搬移路径已改成「建目录 + 逐个搬文件」，不再碰「老目录改名」这条慢路径。剩下会碰它的只有超出 `PERFILE_LIMIT` 的大树与外部命令 `/bin/rm -rf`（本项目脚本不用）。这会动到几乎所有引用 `<root>/build/...` 的脚本与启动器，**需用户确认后才做**，本轮未动。
- **环境提示（本机沙箱，非项目问题）**：本机对 `mv`/`rm`/`find` 这类外部命令有约 20s 的同步上限，超时会报 "Broker request timed out" / 失败，但**底层操作往往已经完成**——本轮就因此把两棵树搬进了探针目录、并误判过一次「预置失败」。Node 自身的系统调用不受该上限约束，所以长耗时的文件操作要放进 Node 脚本里做（本轮探针就是这么跑通的）。
