# 3010 启动「构建打包」提速：内容数据移出构建产物

- 日期：2026-09-16
- 范围：启动流程 `✔ [2/4] 构建打包` 过慢的根因修复（用户指名「这一步太慢了，根因修复」）
- 协议：**24 不变**；内容版本：**`tms273-29` 不变**（本次不动协议与内容，只改「资源怎么交给浏览器」）
- 结论：该步骤 ~50s 中有 **95% 以上是把 843MB / 7 万个美术音频文件原样复制一份**；复制取消后，vite 段 50.61s → **3.1~3.4s**。

## 1. 根因（实测，非推测）

`client/vite.config.ts` 把 `publicDir: 'public-tms273'`（843MB / 70593 个文件，其中 `assets/tms273` 70463 个）交给 vite，于是**每次**生产构建都要把它全量拷进 `build/tmp/client`，再由 `activate` 把这些文件轮替进 `build/current`、`commit` 时删掉上一版。分项计时：

| 阶段 | 耗时 |
| --- | --- |
| cargo 增量编译（`build/.cargo-cache` 未变） | **0.34s** |
| `tsc --noEmit` | 2.69s |
| vite 转换/打包 93 模块（关掉 publicDir） | **3.40s** |
| vite 含 publicDir 拷贝 | **50.61s**（同一仓库另一次 22.06s，随 iCloud 元数据状态波动） |
| 单看「把 assets 复制一遍」（`ditto --clone`，APFS CoW 也一样） | **24.83s** |

也就是说：这一步几乎不是在构建，而是在**复制内容数据**。而这两份数据实测**逐字节相同**（`manifest.json` 同一 sha256；源目录 vs `build/current/client` 抽样 200/200 一致），且两个启停入口本来就已把 `ASSETS_DIR` 指向源目录：

- `启动3010.command:32,230` → `ASSETS_DIR="$ROOT/client/public-tms273/assets"`
- `scripts/windows-control.ps1:124` → `ASSETS_DIR = Join-Path $Root 'client/public-tms273/assets'`

**内容数据被误当成构建产物**，这是根因。

## 2. 改动

1. **`client/vite.config.ts`**：`publicDir` 只在 dev 生效（`command === 'serve' ? 'public-tms273' : false`）。生产构建不再把内容数据写进产物；dev 仍由 vite 直接从源目录服务 `/assets`（`_cashshop-check.html` 这类页面 import `/src/...`，本来就只在 dev 可用，不受影响）。
2. **`scripts/build-release.cjs`**：
   - `computeFingerprint` 移除 `client/public-tms273/assets`。它不再进产物 ⇒ 改内容不该作废候选；顺带让「复用候选」的判定**不再白扫 7 万个文件**（实测判定 0.04s）。
   - 复用候选（快路径）时**同步刷新 stamp 的 `releaseId`**。此前不刷新 ⇒ `commit` 之后 `currentFresh` 恒假 ⇒ 每次启动都空跑一遍 `prepare + activate` 只为换一个 id，「跳过构建」的快路径永远走不到。
3. **`server/src/main.rs`**：`/assets` 的两类来源顺序写下注释并保持 **dist 优先、ASSETS_DIR 兜底**。**顺序不能反**——vite 的 bundle 默认也输出到 `assets/`（`dist/assets/index-<hash>.js|css`），与内容资源共用 `/assets` 命名空间；本次一度把 dist 去掉，实测 bundle 立即 404。改造后 `dist/assets` 只剩构建产物，两者不再重叠，也就不存在「旧副本遮蔽新内容」。
4. **`scripts/check_tms273_runtime.cjs`**：资源自愈来源由 `build/current/client`（构建副本，已取消）改为上游导出源 `resources/tms273-export`，按原路径一一对应。实测导出源 72156 个文件覆盖装配产物 70463 个中的 **70462** 个，差集只有 1 个**不被任何清单引用的孤儿副本**（`assets/tms273/chapter/Npc__Canvas_0010300...`，manifest 引用的是同名的 `assets/tms273/` 根路径那份），故无需文件名兜底分支。
5. **`scripts/build-release.check.cjs`**：把新语义钉住——内容数据变化**不得**改变构建指纹、**不得**让候选失效；源码变化仍必须作废。
6. 未改：两个启停入口、`windows-control.ps1`、`package_win_bundle.cjs`（Windows 包仍随源码树带上 `client/public-tms273/assets`，改造后 Windows 端首次构建同样不再复制）。

## 3. 验证（全部实测）

- 计时：`prepare` 首次 26.03s（含一次性清理上一轮遗留的 7 万文件 + 重编 `main.rs`）、另一次 16.46s（仅重编 Rust），其中 **vite `built in 3.11~3.19s`**；输入未变时 `prepare` **0.05s**、`current-fresh` **0.04s**。候选产物 **3 个文件 / 3.3MB**（此前 70596 个 / 882MB）。
- 端到端：用**新形态候选**（dist 只有 `index.html` + 2 个 bundle 文件）在 `127.0.0.1:3011` 起独立实例（独立端口 + 独立数据库副本，**在线 3010 全程未受影响**）7/7 通过：`/api/health` 200、`/` 200、`/assets/index-*.js` 200 `text/javascript`（dist 优先）、`/assets/index-*.css` 200、`/assets/manifest.json` 200（ASSETS_DIR 兜底）、`/assets/tms273/*.png` 200 `image/png`、缺失资源 404。
- 自愈两分支：删掉一个被 manifest 引用的资源 ⇒ 从导出源补回且 **sha256 与删除前一致**；连导出源也移走 ⇒ 退出码 1 并报「装配资源缺失且导出源里也没有 + 重跑装配脚本」。测试删掉的孤儿副本已按原字节还原。
- 门禁：`check_tms273_runtime.cjs` 退出 0（188 图 / 108483 源引用）、`tsc --noEmit` 0、`check_repository_layout.cjs` PASS、`启动3010.command` / `关闭3010.command` `zsh -n` 通过、`prepare.log` 仍含 `93 modules transformed`（启动脚本提取 `CLIENT_MODULES` 依赖该短语）。

## 4. 未验证 / 环境限制（不冒充已验）

- `scripts/build-release.check.cjs` 在本机沙箱内跑不到断言：`ps -axo` 被拒（`operation not permitted`），`assertNoRunningReferences` 直接抛「无法检查 macOS 进程表」。**HEAD 既有基线**，与本次改动无关；本次改动的是它内部的指纹断言，已用独立探针核对同一语义。
- `scripts/check_launcher.mjs` 同样在本机失败，且**失败原因与本次改动无关**：`启动3010.command:10` 在 `set -u` 下引用未设置的 `$TERM_PROGRAM`，非 Terminal 环境直接退出 1。该检查会**真的拉起服务**（`check_launcher.mjs:30` 用默认环境跑启动脚本），按 AGENTS.md「保留在线服务」本轮不为了让它变绿而重启 3010。
- 完整 `启动3010.command` 未在本机跑完：其 `activate` 同样要读进程表。首次真实启动由用户在 Terminal 执行，预期 `[2/4]` 为秒级。

## 5. 语义变化（用户需要知道的）

- **改内容不再需要重新构建**：直接改 `client/public-tms273/assets/**` 立即对浏览器生效（刷新页面即可）。旧做法的「`rsync` 覆盖 `build/current/client/assets/manifest.json` 热修」**不再有效**（dist 里已没有内容副本）。
- 代价：内容管线（如 `build_tms273.cjs`，约 6 分钟）运行期间若服务在跑，浏览器会**立即**读到半成品资源；此前那份 dist 副本会把半成品遮住直到下次重启。恢复该保护的可行做法是把 `ASSETS_DIR` 指向一份内容版本快照（本次未做）。
- `build/previous` 里旧版本残留的那份 843MB 内容副本，会在下一次 `prepare → activate → commit` 时随上一版一起被清掉。
