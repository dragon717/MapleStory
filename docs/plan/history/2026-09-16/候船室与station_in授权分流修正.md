## 2. 候船室 `200000112` 与阿霖 `2012002`：为什么不做

**核定过程**（全部为源侧实测，非推断）：

1. `200000112 候船室<開往維多利亞>` 已在装配目录内（188 图之一），阿霖 `2012002`
   也已在 `shared/gameplay.json` 的 `npcSpawns` 里：`200000112-life-0`，
   源坐标 `(61, -454)`（`Map.wz/Map/Map2/200000112.img/life/0`，foothold 16）。
2. **但全目录没有任何一扇门指向 `200000112`**。逐图扫描 188 图的全部 portal：
   指向它的只有它自己的 `h002`（pt:1，`targetMapId: 200000112`）——即自指门，
   作用是图内上下层移动，不是入场门。
3. 源 `Map/Map/Graph.json` **全文不出现 `200000112`**（跨全图搜索 0 命中）。
   Graph 是原版「门户授权表」，某张图不在其中，说明它没有任何被授权的入场跳转。
4. 该图 `entryScripts` 的 `first`/`each` 都是空串 ⇒ 也没有 onUserEnter 类脚本来拉人进场。

**结论**：原版进候船室靠的是脚本体（`inERShip` 一类，本地源不含），而本仓库既没有该
脚本体、源授权表里也没有对应跳转 ⇒ **照实登记为不可达，不凭空造一扇入场门**。
方案 §4 当初写「一期不路由进候船室（`east00` 保持关闭门旧行为）」是同一判断，
本轮把依据补全了。阿霖因此也不承载机制——`ship.rs` 里 `ROUTE_ORBIS_VICTORIA.announcers`
保持空切片是有意的，不是漏配。

> 如果将来要开放候船室，需要的是**脚本体语义**（谁在什么相位把人送进去），
> 不是补一扇门——补门会造出一条源里不存在的通路。

## 3. `station_in` 接线修正（本轮唯一的代码改动）

### 3.1 旧接线错在哪

`server/src/ship.rs::ship_portal_gate` 原本把 `200000100 天空之城售票處` 的
`east00`（pt:7 脚本 `station_in`，脚本体缺失）**旁路到港口通道 `200000120.west00`**，
依据是「`200000120.west00` 的 tm/tn 正是 `200000100/east00`」这条**源邻接**证据。

这条推理有问题，**权威依据应该是 `Graph.json` 的授权表**。`Map/Map/Graph.json` 的
`20/200000100/portal` 给这扇门授权了**七个**目标：

| portal | portalNum | targetMap | scriptPortal | 本仓库装配 |
| --- | --- | --- | --- | --- |
| 1 | 4 | `200000111` | station_in | ✗ |
| 2 | 4 | **`200000121`** | station_in | ✓ 碼頭<開往玩具城> |
| 3 | 4 | `200000131` | station_in | ✗ |
| 4 | 4 | `200000141` | station_in | ✗ |
| 5 | 4 | `200000151` | station_in | ✗ |
| 6 | 4 | `200000161` | station_in | ✗ |
| 7 | 4 | **`200000170`** | station_in | ✓ 碼頭<前往埃德爾斯坦> |

**`200000120 港口通道` 根本不在授权表里。** 它只是码头的另一条回程旁路：
`200000120.east00 → 200000121.west00`，而 `200000121.west00` **本就有静态门
直接回售票处** ⇒ 接上它是冗余的，而且会把登船相位门包过去（玩家会穿进一张
没有票务/相位语义的中间图）。

### 3.2 修正后的行为

新增纯函数 `ship.rs::station_in_exit(target_map) -> Option<&'static str>`，
按授权表把已装配的目标映射到落点门（两图的 `west00`，`portalNum: 4` 的落点语义）：

- `200000121` → `Some("west00")`（登船码头，剪票員 `2012013`）
- `200000170` → `Some("west00")`（二期埃德爾斯坦线回程码头）
- 其余（含 `200000120`）→ `None` ⇒ **如实拒绝**，走近收门提示，
  不再一律旁路。这修掉了「走近未装配目标会踩进空图/掉出地图边界」的问题。

门体取 `200000121` 优先（有船可上、玩家最常去），`200000170` 作为已装配次选。

### 3.3 关键连带修复：客户端目录暴露

**这是比服务端分流更严重的一层。** `client/src/scenes/world.ts::tryPortal`
（第 145 行）的候选过滤要求 `candidate.targetMapId` 非空；
而源 `tm` 是 `999999999` ⇒ 目录里 `east00.targetMapId` 是 `null`
⇒ **玩家按 ↑ 根本发不出请求，服务端写好的路由永远收不到消息 = 死代码**。

这不是新问题：`scripts/tms273_remaster.cjs::exposeScriptedGateRoutes` 就是专为
前几片模块（`ellinel.rs` / `helios.rs` / `ufo.rs`）修同一类缺陷而设的表，
本轮把 `station_in` 按**同一张授权表**加进去：

```js
['200000100', 'east00', '200000121', 'west00'],   // 本轮新增
```

装配后实测：`east00` 变成 `{type:7, targetMapId:"200000121", targetPortalName:"west00",
script:"station_in"}`，并自动获得 8 帧 `pv/default` 可见光束（`portals["200000100/east00"]`）。
**刻意不暴露 `200000120`**——理由同 §3.1。

### 3.4 改动的实际尺寸

`shared/maps.json` 语义差异经逐字段核对，**只有一个 portal 的两个字段**：

```
200000100/east00:  targetMapId: null -> "200000121"
                   targetPortalName: null -> "west00"
```

`birthMapId`、`returnMaps`、其余 187 图全部逐字节未变（188 → 188 图）。

## 4. 票务道具：核定结果与已知偏离

方案 §6 第 5 条定的口径是「TMS273 同版船票道具 ID 未核（`4031043` 等旧版票据不能冒认）
→ 一期 P 级免费登船」。本轮复核该口径**仍然成立**：源里没有可用于本版乘船的票务道具，
且 `Graph.json` 对 `east00` 的授权是**纯位移**，不带任何条件字段。

因此本轮**不做**票务校验，`200000100` 这门按源授权做成与 `104020110` / `200000121` /
`220000110` 三处站台同口径的免费登船。**这是一处已知偏离，如实登记**：原版这门由
`station_in` 脚本体把关，其具体条件（是否验票、是否限相位）本地源不含，不可推断。
