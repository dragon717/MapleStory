## 1. 审查结论（要点）

| 事实 | 证据 |
|---|---|
| 物品**没有身份**，位置即身份 | `PRIMARY KEY(account_id, inventory_type, slot)`；`InventoryItem` 无 id / owner / state |
| Owner 隐含在 `account_id` 列 | 唯一显式 owner 是 `drops.owner_account_id`（即可空列） |
| State 完全缺席 | 拾取保护 `protected_until_ms`、租赁 `_expiresAt`、宠物 `_petActive`、待认领 `reward_claimed` 四处裸字段 |
| `put`/`take` 级原语 `pub` 且被生产直调 | `inventory::add_items` 8 处 / `remove_items` 13 处 / `move_items` 3 处（生产代码） |
| 全或全无靠约定 | 12 处 `state.inventory.clone()`、17 处 `state.inventory =`、6 处 `state.equipped =` |
| 仓储泄漏修改权 | `write_inventory(account_id, &[InventoryItem])` 整表重写，4 处生产调用 |
| 无邮件 / 拍卖 / 玩家交易 | `server/src` 无相关代码 ⇒ Escrow / Lock / TransferOwnership 零消费者 |

与世界模型逐条对照：完全违反 8 条、部分符合 11 条、已符合或不适用 13 条；8 条完全违反里 6 条同根
（"位置即身份"）。

## 2. 落地 ①：物品世界事实词汇 + 仓库搬运收敛

### 2.1 新增 `server/src/auth/item_world.rs`

- `Owner` / `ItemLocation` / `ContainerSide` / `ItemState` + `LockReason`（§2 / §3.1 / §3.2 / §3.3 / §39）
- `drop_fact()` / `pickup_allowed()`：掉落保护窗的**唯一**翻译点（§3.3 / §41）
- 私有 `trait Source`（`peek` / `take`）与 `trait Destination`（`can_accept` / `put`），
  只有背包与仓库实现（§7 / §9 / §10 / §41）
- `move_stack(tx, from, to, quantity) -> MoveOutcome`：完整业务动作，一个事务内全或全无（§6 / §13 / §32）

**落地时发现并如实建模的事实**：本项目放入动作一律由容器自选落点（合并同叠或找空格），
故模型拆成"事实（带槽位）`ItemLocation`"与"意图（无槽位）`ContainerSide`"——
目标槽位在类型上写不出来（§39）。

### 2.2 接入点

| 文件 | 改动 | 保持不变的 |
|---|---|---|
| `auth.rs::Store::storage_transfer` | 两段手写 `peek → guard → take → insert` 合并为一次 `move_stack` | 函数签名、`StorageOutcome` 字段、6 个失败码、事务边界、调用方 `trade.rs` |
| `auth/loot.rs::Store::pickup` | 内联的"保护窗 + owner"比较改为 `drop_fact` + `pickup_allowed` | `drop_owned` 拒绝码、触发时机、其余分支 |

这两处是里氏替换原则的**字面**应用：接口与契约逐字不变，实现换成世界模型。

## 3. 落地 ②：拒绝原因类型化 —— 容器只回答*原因*，措辞由业务动作决定

① 遗留问题：`Source` / `Destination` 用 `String` 表达拒绝原因（`Err("storage_full".to_owned())`），
把**业务措辞**下沉进了容器实现，违反世界模型 §31（容器知道的是"我没装下"，不该是"该给玩家看哪个码"）。

| 内容 | 变化 |
|---|---|
| `MoveRefusal` | 新增 `pub(super) enum MoveRefusal { InvalidSlot, InvalidQuantity, SourceEmpty, DestinationFull }` |
| `Source::peek` / `Destination::can_accept` | 返回 `Result<Result<_, MoveRefusal>, String>`：`Ok(Err(原因))`＝业务拒绝，`Err(_)`＝持久化失败（硬错误，回滚事务） |
| `MoveOutcome::Refused` | 携带 `reason: MoveRefusal`（不再是 `code: String`），新增 `refusal() -> Option<MoveRefusal>` |
| `StorageOperation::refusal_code` | **唯一**翻译点（`invalid_slot` / `invalid_quantity` / `source_empty` / `storage_slot_empty` / `storage_full` / `inventory_full`）；同一个 `SourceEmpty` 在存入/取出两个方向译成不同的码 |
| `move_stack` 执行顺序 | **不变**（`peek → can_accept → take → put`）；只有前两者记业务码，后两者仍是硬错误 |

**顺带修正一处潜在错标**：`reserve_storage_slot` 原先把 `query_row` 的**失败**也标成 `storage_full`
并写进幂等回执（SQLite 异常会被告成"仓库满"且当成功拒绝提交）。现 `Ok(Err(DestinationFull))`＝业务拒绝、
`Err(_)`＝持久化失败中止事务。**该路径当前不可达，属静态修正，无测试覆盖**（如实交待）。

## 4. 落地 ③：增量 4 的前置测试 —— 商店购买路径（并修掉重复扣款）

增量 4 要动 `write_inventory` 整表重写，前提是先有等价性证据。补测试前先清点站点，**发现路线图写错了**
（"四条路径 = 商店买卖/整理压缩/任务奖励/GM"不准确）：真正的分界是有没有事务。

- **A 组：非事务整表写回（内存权威，持久化结果被 `let _ =` 丢弃）——4 处**：
  `trade.rs` 商店购买 / 卖出 / 买回 + `cashshop.rs::step_rental_expiries`（租赁到期清扫）。
  这才是危险的一类：先改内存再丢弃写库结果 ⇒ 失败静默、内存与磁盘分叉。
- **B 组：事务内整表写回——11 处**（`auth/bag.rs` 7、`auth/quests.rs` 2、`auth/cash.rs` 1、
  `auth/db.rs:1406` 即 `add_inventory_tx` 内部 1）。不吞失败，问题是§34 的修改权泄漏。

**由此暴露的真缺陷**：`handle_shop_buy` 没有 `requestId` 幂等账本，而三个同样动金币的兄弟动作都有
（`ShopSell` / `ShopRebuy` / 现金购买）。**重发同一个 `ShopBuy` 包会再扣一次金币、再发一次道具。**

实测复现（临时短路保护后跑新测试）：`a replayed shopBuy must not deduct mesos twice` → `left: 900, right: 950`
（1000 被扣成 900）。恢复保护后全绿。

修法（在 `trade.rs` 末尾）：
- `world.rs` 新增 `ShopBuyOutcome` + `shop_buy_requests: BTreeMap<(玩家,请求), _>`（构造处与 `commands.rs`
  两条断开路径的 `retain` 清理同步）；**不加 `mesos` 字段** ⇒ wire 形状逐字不变。
- `trade.rs` 新增 `send_shop_buy_result`（唯一记录点，7 个出口全改走它）；`send_shop_result` 保持纯发送。
- `handle_shop_buy` 开头命中即原样重发。

**已核实不会误伤**：客户端每次购买都生成新的 `requestId`
（`client/src/features/npc/dialogue.ts::buy` → `shop-${++seq}-${Date.now().toString(36)}`），第二次购买本就是新请求。

新增 `server/src/shop_buy_acceptance.rs`（8 条，此前该路径**零覆盖**）：花钱用商人要价 / 部分同叠就地补满 /
**页签满则一分不扣** / 余额差 1 也拒绝 / 0 个不成交 / 伪造店铺·走远·买不售商品都不动钱 /
重放只成交一次且换新 id 仍能买 / 拒绝也被记住。所有 helper 带 `sb_` 前缀（该文件与卖/买回验收 `include!`
进同一模块，裸名已被占用）。

## 7. 后续增量（已论证结论 + 路线图，详见审查文档 §7）

1. **增量 2（装备栏）—— 已论证：不纳入**。三条代码级理由（槽位占用互换 / 目标槽位非容器自选 / 准入规则分层）
   任一独立即可否决；`unequip_items` 一并排除。这是 §41 的正确结论，**不是遗留缺陷**。
2. **增量 3（地面掉落）—— 已论证：只能纳入"去处命名"，不纳入容器契约**。决定性证据（对着 `HEAD` 核过）：
   同一个 `add_inventory_tx` 内层业务码，`storage_transfer` 用 `?` 当**硬错误**中止事务，`pickup` 用
   `match Ok(Err(code))` 当**业务拒绝**并 `UPDATE drops SET active=1` 恢复掉落 ⇒ 两边语义相反，
   共享 `Destination` 必然改写其中一边，违反"行为零变化"。收窄后的范围：`PickupSink`（背包 / 图鉴卡 / 金币）
   + 三个分支的 SQL 搬回 `auth/db.rs`；**依赖增量 4** 先收敛 `add_inventory_tx` 的返回类型。
   `drop_inventory` 的 `is_drop_restricted` 分支按词汇是**销毁**而非 Move，应另立领域动词。
3. **增量 4**：`add_items`/`remove_items`/`move_items` 降级为内部原语；堵住 `write_inventory` 整表重写。
   **前置 1（③ 已更正并推进）**：真正的分界是**有没有事务**——A 组 4 处非事务写回（商店买/卖/买回 + 租赁清扫）
   是"内存权威且丢弃写库结果"的危险子集，现已 3/4 有失败边界测试，**还差 `step_rental_expiries`**；
   B 组 11 处事务内写回问题是 §34 的修改权泄漏，非失败吞掉。
   **前置 2**：收敛 `add_inventory_tx` 的返回类型（它用 `.code()` 抹掉了 `inventory::InventoryError`）。
4. **增量 5**：邮件 / 拍卖 / 玩家交易 / 离线收益立项时再建 `Escrow` / `Lock` / `Reward` / `DomainEvent`
   —— 当前零消费者，提前建会违反项目"不提前建空抽象"规范。
