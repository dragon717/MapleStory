# GM 命令 `/exp <经验值>`（TMS273）

日期：2026-09-18。用户需求单：「写一个 gm。/exp 10000 加玩家经验」。
协议 **24** 与内容 **`tms273-31`** 均未变；**客户端零改动**；纯服务端，重启 3010 生效。

## 1. 命令契约

- 入口与既有 GM 命令完全一致：聊天框输入 `/exp 10000` → 客户端原样作为 `chatSend` 发出 →
  `World::handle_chat`（`messaging.rs`）在文本策略/幂等/限流**之前**截断到 `gm.rs`，
  文本**永不**进入地图聊天广播，回执 `gmResult` **只发给发起者**。
- 用法：`/exp <经验值>`，单个参数，窗口 **1..=1000000000**（与 `/cash` 同量级）。
  缺参、非数字、0、负数、超上界、多余参数一律 `gm_usage`，**不发经验、不发快照**。
- 成功回执 `gm_exp_ok`，消息里带等级与进度：升级时「已获得 N 经验，升级至 L 级（e/E）。」，
  未升级时「已获得 N 经验，当前 L 级（e/E）。」
- 未知命令提示补上第三条：`可用：/add <道具id> <数量>；/cash <楓點数>；/exp <经验值>`。

## 2. 关键决定：不另写一条加经验逻辑

`World::add_exp`（`quest.rs`，战斗/任务奖励同一条路径）已经是**唯一**的「加经验 + 升级结算」实现：
跨级时逐级扣阈值、每级 **+5 AP**、按职业 `auth::grant_level_sp` 发书页 SP、刷新 `exp_to_next`，
并在表跑完（273 表 200 项、末项 0）时把 `exp_to_next` 收 0。
`/exp` 直接调它 ⇒ 升级奖励与正常玩法**结构上不可能分叉**，也**不为 GM 特判等级上限**。

- 升级后调 `refresh_player_derived`（与战斗路径同一处），把新的属性聚合投影出去
  （`max HP/MP` 的最终值由每 tick 的属性聚合刷新，与既有战斗升级路径同节奏）。
- 持久化走 `store.save_profile` + `profile_from_state`（与 `/cash`、购买同一条存档路径）。
  **写失败不谎报**：回执追加「（存档失败，重连后可能回退）」，而不是只说「已获得」。
- 加完经验 `send_snapshot`：客户端 `level`/`exp`/`expToNext` 都来自权威快照，HUD 立即更新。

## 3. 已知边界（如实登记，未修）

- `/exp` 与 `/cash` 一样**没有 requestId 幂等回执**：GM 命令在聊天的幂等窗口**之前**被截获，
  所以同一 requestId 重发会**再发一次**（`/add` 有幂等，是因为它走 `store.grant_inventory_item`
  的持久回执表）。当前阶段全角色可用、单机复刻用途，按既有口径不扩权限/幂等体系；
  后续接 GM 账号表时，身份闸门与幂等应一起加在 `handle_gm_command` 入口。
- 等级上限行为沿用表语义：表尾 `0` ⇒ 满级后经验继续累加但不再升级、`exp_to_next` 为 0。
- 死亡状态下也可加经验（未加状态闸门）；升级所得的 AP 仍需按既有规则在存活时分配。

## 4. 验证

- 新增 `server/src/gm_acceptance.rs` 两条：
  - `gm_exp_grants_experience_through_the_shared_level_up_path`：另起一张三段表 `[10,20,30]`，
    `/exp 5` → `(1, 5, 10)`；`/exp 25` 跨两级 → `(3, 0, 30)` 且 **AP +10**（每级 +5）；
    同一批消息里断言**恰好一条 `snapshot`** 且其中该玩家 `level == 3`；无 `chatMessage`
    回给任何一方、`bob` 什么都没收到。
  - `gm_exp_rejects_out_of_band_amounts_without_touching_progress`：`/exp`、`/exp 0`、`/exp abc`、
    `/exp -5`、`/exp 1000000001`、`/exp 5 6` 六条全部 `gm_usage`、全部 `success=false`，
    等级/经验**一动不动**、也不发快照。
  - 顺带修掉验收夹具自己的一个坑：`gm_take_kind` 每次调用会**清空整个队列**，只留一种 kind。
    一条命令同时产生 `gmResult` + `snapshot` 时，先取一种就会把另一种丢掉。新增
    `gm_take_all`（按发送顺序取全部）与 `gm_of_kind`（本地过滤），两条命令的两类消息
    因此必须从**同一次 drain** 里分类。

- 非测试构建 `cargo check`：**0 告警**；测试构建 **49 条**，与既有基线同数（本轮新增 0）。
- 未跑客户端 `tsc` / `run-checks.mjs`：本轮**未改任何客户端与被测脚本**（`gmResult` 的渲染
