## 4. 环境与坑

- **cargo 不在非交互 shell PATH**：先 `export PATH="$HOME/.cargo/bin:$PATH"`；`cargo test --manifest-path server/Cargo.toml`（不碰 build/current，在线服务运行时可安全跑）。**非测试构建必须 0 告警**。测试构建基线＝**49 条告警 / 47 条可自动修复**（两个数别混用，`--message-format=short | grep -E "generated [0-9]+ warning"` 读总数、`grep -cE "^src/.*warning"` 读明细），分布：`away_acceptance.rs` 25、`world_tests.rs` 2、其余（含 `storage_acceptance.rs` / `party_acceptance.rs`）每文件 1 条 `unused import: super::*`、`auth/quests.rs` 1。判绿看「我改的文件贡献 0 条」。
- **想强制重编别 `touch server/src/lib.rs`**：该文件不存在、也**.gitignore 之外从未被跟踪**，crate 根是 `main.rs`（Cargo.toml 无 `[lib]`）；但 Cargo 会自动把 `src/lib.rs` 认成一个 **lib target** ⇒ `touch` 会凭空造出 0 字节 `lib.rs` 并污染告警统计。要强制重编请 `touch server/src/main.rs`。
- **本机沙箱禁用 `ps`** ⇒ `build-release.check.cjs` / `check_launcher.mjs` 跑不到断言（`check` 可用 `PATH` 前置 `exit 0` 的 `ps` 桩代跑），`activate` 与 `关闭3010.command` 的进程判定无法代跑 ⇒ **完整启动链验证必须由用户在 Terminal 跑**。`check_launcher.mjs` 会**真的拉起服务**，别为让它变绿而重启 3010。`启动3010.command:10` 在 `set -u` 下引用未设置的 `$TERM_PROGRAM`，非 Terminal 环境退出 1。
- **本机沙箱对外部命令（`mv`/`rm`/`find` 等）有约 20s 的同步上限**：超时报 `Broker request timed out` 并让命令返回失败，**但底层操作往往已经完成**（曾因此把两棵树误搬进探针目录、并误判过一次「预置失败」）。Node 自身的系统调用不受该上限约束 ⇒ 需要跑几十秒以上的文件操作时，写进 Node 脚本再执行（`dangerouslyDisableSandbox` 也绕不过这个 shim）。
- **本仓库所在 iCloud 卷的代价（2026-09-16 实测）**：`mkdir` / 写文件 / `readdir`(7 万文件 0.22s) / **改名「文件」**（5 天前的老文件也是 0.00s，规模化约 0.1ms/文件）/ `fs.rmSync` 都很快；**只有「改名一个近期没被动过的目录」要几十秒——`fs.renameSync` 实测 10.81 / 36.65 / 95.57s，且与目录里的文件数无关**（只含 3 个文件的目录也要 10–37s）。同一棵 11166 文件的目录，「mkdir + 逐个搬文件」只要 **1.13s**（快 85 倍）。⇒ **搬移一律走 `moveFlat`（只 mkdir 目录、只 rename 文件），不要对目录做改名**（`build-release.cjs::moveTree` 已按此实现，`PERFILE_LIMIT=20000` 以上才赌整目录改名）。这正是 2026-09-16「停旧与切换 325s」的成因：`activate` 搬的 9 个条目都是上一版留下的目录，311s ÷ 9 ≈ 34.6s/次。另：`/bin/rm -rf` 也慢（36s~6 分钟/次），**清理一律用 `fs.rmSync`**（同目标 0.04s）；本项目脚本里没有 `rm -rf`。
- **bash grep 静默漏匹配 ⇒ 一律用 Grep 工具**；改文件一律 Edit/Write。**zsh 函数里 `local path=...` 会覆盖与 PATH 绑定的特殊数组 `path`**（函数内命令全部找不到）；`${X%%|*}` 会带出分隔符前的空格（`"reuse | …"` → `"reuse "`），比较前必须去空格。
- **iCloud 静默回滚未提交编辑 ⇒ 每个 Edit 后必须 Grep 复核**，批次完成后整批复查。iCloud 文件未落地时 `rm -rf` 偶发 `Operation not permitted`（重试即成功）。不重启在线服务，重启由用户跑 `启动3010.command`。
- 加载校验空串坑：源无 NPC 的相位 `npcId` 是空串；`gameplay.rs` 只把非空却查不到的当错误。
- world 抽模块 `#[path] mod` + `use super::*`，公开字段类型不能搬进私有子模块（E0446）；**世界侧私有子模块不能被 `auth` 反向引用**（图鉴目录因此放 `auth/notebook.rs`）。
- `build/tmp` 里还剩 11 个历史备份垃圾（`client-backup-*` ×9 + 2 个 manifest 备份 + `cashshop-browser-check.cjs`）。原有一份 408MB / 32014 文件的 `windows-package-MnWNy7`（09-14 `package_win_bundle.cjs` 的打包暂存）已于 2026-09-16 被误删，需重新跑一次 `打包Windows资源包.command` 才能再生成。它们不参与轮替（只搬 `ITEM_NAMES`）故当前无害；清理用 `fs.rmSync`。

## 5. 伤害修正管线（`server/src/damage.rs`，2026-09-17）

**唯一求值点**：`DamagePipeline`。两条路径都只构造它——`attacks.rs::resolve_pending_attacks`（普通攻击，4 处修正）、
`skills.rs::magic_damage_breakdown`（魔法技能，9 处）；`elemental.rs` 的元素场经 `magic_damage_with_passives`
（＝`magic_damage_breakdown(..., &[]).total()` 的取值包装）进同一入口。两个技能施放点的**前置修正**
（元素弱化的 `x`、被消耗冻结层的 `x`/`y`）以 `pre: &[(DamageSource, i64)]` 传入，**不许在调用点手写乘算**。

三条**别再犯**：

1. **分组只按源字段名判定，且只有 `DamageSource::group()` 一处**。`damR`→`AdditivePercent`（求和后整组乘一次）、
   `criticaldamage`→`Critical`（**基准 200 不是 100**：源语义是「在双倍之上再加」，所以 `criticaldamage = 0` 的暴击**仍是 ×2**、
   `add()` 里那条「0% 即恒等」的短路只对基准 100 的组成立）、
   `indieDamR` / 无标记字段（`x`/`z`/`damage`/`mdR`）/ `FreezeLayerBonus` / `RegionGuard`→`IndependentPercent`。
   **调用点只给来源变体，不许自己挑分组**；源里没有分组标记的字段**就不猜**，归独立乘算并把字段名带进留痕。
   `RegionGuard` 的 `percent` 是 `boss_damage_multiplier(..) - 100`（**负数表示减伤**），系数 100（恒等）时
   `add()` 因 `percent == 0 && base == 100` 直接跳过 ⇒ 不留痕（`dmg_an_identity_region_coefficient_leaves_no_trace` 钉住）。
2. **取整只在末端一次**。全仓 `.floor()` **恰好 1 处**＝`apply_target_mitigation` 里那条既有公式（作用在**基准**上，是第 0 层）；
   玩家侧修正一律不进 `f64`，`resolve()` 用 **`i128` 有理数累乘**（分子/分母），末端一次 `num/den` + `max(1)`。
   ⇒ **结果与修正项的施加顺序无关**；**退回「每步 floor」会让魔力無限这类修正的位置重新变得有意义**（改前两条路径位置不同、数字不同）。
   诊断用的 `projected_after` 也是取整点，但它**不参与结算**（门禁数出「终点取整恰好 2 处」＝诊断 + 权威）。
3. **上限只在各字段自己的 `clamp` 声明处**（如 `ignoreMobpdpR` 的 `clamp(0,100)`，`apply_target_mitigation` 里对
   `ignored_percent` 再 clamp 一次）。管线只有一条**防负数因子守卫** `MODIFIER_FLOOR_PERCENT = -99`（因子 ≥ 1/100）——
   源里没有任何把伤害乘成负数或零的技能，触发即**数据出错**，不是游戏规则。

**同一来源两条路径必须同一个取值口径**：源 `indieDamR`（傳說冒險 `2221053`）经
`hyper_adventurer_damage_percent(mage_skills, player)` 取值。改前普通攻击取「已学等级」+ `clamp(0,100)`、
魔法路径**固定 1 级且不 clamp** ⇒ 该技能 `maxLevel = 1` 所以**今天数值相同但形状不同**，
`maxLevel` 一改就静默分叉。门禁断言这个访问器**只在 `damage.rs` 定义一处**且两条路径**都通过它取值**。

**两处有意数值偏离（已量化登记，别当 bug 改回去）**：

| 偏离 | 具体 | 量化 |
| --- | --- | --- |
| 同源 `damR` 由「各自乘」改「求和后乘一次」 | `base=1000`、20%+50%：改前 `floor(1000×1.2)=1200`→`floor(1200×1.5)` = **1800**；改后 `floor(1000×(100+20+50)/100)` = **1700** | 由验收 `dmg_damage_rate_sources_add_up_and_reach_the_pinned_total` 钉死 |

**刻意不碰的边界（改了就红）**：

- **玩家受伤侧**：`monsters.rs` 的护盾 / 魔心防禦抵偿（`reduced_damage as i128 * MAGIC_GUARD_COVERED_PERCENT`）
  是**另一条通道**，一行未改，门禁第 4 组把它**正向登记为边界**。统一它要先核定 TMS273 的受伤公式，源里没有。
- **目标侧减免的两套模型不统一**：魔法技能走 `mdRate` − 无视防御（管线的 `apply_target_mitigation`），
  普通攻击走**等級差 + PDD**（`combat_rules.rs::attack_range_against`，**作用在区间上**）
  ⇒ 普通攻击**不调用**管线的目标减免（基准里已含），`combat_rules.rs` 也**不许构造管线**（门禁断言）。
  `trunc` 与 `floor` 对正值等价，所以 §4.2 那处旧 `i128 / 100` 改入独立乘算组不引入新偏离。
- **基准伤害与命中/目标选择**（技能倍率 × 魔法攻击、普通攻击区间、`nearest_attack_target`）留在各自调用点。
