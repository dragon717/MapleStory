## 4. 环境与坑

- **cargo 不在非交互 shell PATH**：先 `export PATH="$HOME/.cargo/bin:$PATH"`；`cargo test --manifest-path server/Cargo.toml`（不碰 build/current，在线服务运行时可安全跑）。**非测试构建必须 0 告警**（测试构建既有 45 条告警是基线）。
- **本机沙箱禁用 `ps`** ⇒ `build-release.check.cjs` / `check_launcher.mjs` 跑不到断言（`check` 可用 `PATH` 前置 `exit 0` 的 `ps` 桩代跑），`activate` 与 `关闭3010.command` 的进程判定无法代跑 ⇒ **完整启动链验证必须由用户在 Terminal 跑**。`check_launcher.mjs` 会**真的拉起服务**，别为让它变绿而重启 3010。`启动3010.command:10` 在 `set -u` 下引用未设置的 `$TERM_PROGRAM`，非 Terminal 环境退出 1。
- **本机沙箱对外部命令（`mv`/`rm`/`find` 等）有约 20s 的同步上限**：超时报 `Broker request timed out` 并让命令返回失败，**但底层操作往往已经完成**（曾因此把两棵树误搬进探针目录、并误判过一次「预置失败」）。Node 自身的系统调用不受该上限约束 ⇒ 需要跑几十秒以上的文件操作时，写进 Node 脚本再执行（`dangerouslyDisableSandbox` 也绕不过这个 shim）。
- **本仓库所在 iCloud 卷的代价（2026-09-16 实测）**：`mkdir` / 写文件 / `readdir`(7 万文件 0.22s) / **改名「文件」**（5 天前的老文件也是 0.00s，规模化约 0.1ms/文件）/ `fs.rmSync` 都很快；**只有「改名一个近期没被动过的目录」要几十秒——`fs.renameSync` 实测 10.81 / 36.65 / 95.57s，且与目录里的文件数无关**（只含 3 个文件的目录也要 10–37s）。同一棵 11166 文件的目录，「mkdir + 逐个搬文件」只要 **1.13s**（快 85 倍）。⇒ **搬移一律走 `moveFlat`（只 mkdir 目录、只 rename 文件），不要对目录做改名**（`build-release.cjs::moveTree` 已按此实现，`PERFILE_LIMIT=20000` 以上才赌整目录改名）。这正是 2026-09-16「停旧与切换 325s」的成因：`activate` 搬的 9 个条目都是上一版留下的目录，311s ÷ 9 ≈ 34.6s/次。另：`/bin/rm -rf` 也慢（36s~6 分钟/次），**清理一律用 `fs.rmSync`**（同目标 0.04s）；本项目脚本里没有 `rm -rf`。
- **bash grep 静默漏匹配 ⇒ 一律用 Grep 工具**；改文件一律 Edit/Write。**zsh 函数里 `local path=...` 会覆盖与 PATH 绑定的特殊数组 `path`**（函数内命令全部找不到）；`${X%%|*}` 会带出分隔符前的空格（`"reuse | …"` → `"reuse "`），比较前必须去空格。
- **iCloud 静默回滚未提交编辑 ⇒ 每个 Edit 后必须 Grep 复核**，批次完成后整批复查。iCloud 文件未落地时 `rm -rf` 偶发 `Operation not permitted`（重试即成功）。不重启在线服务，重启由用户跑 `启动3010.command`。
- 加载校验空串坑：源无 NPC 的相位 `npcId` 是空串；`gameplay.rs` 只把非空却查不到的当错误。
- world 抽模块 `#[path] mod` + `use super::*`，公开字段类型不能搬进私有子模块（E0446）；**世界侧私有子模块不能被 `auth` 反向引用**（图鉴目录因此放 `auth/notebook.rs`）。
- `build/tmp` 里还剩 11 个历史备份垃圾（`client-backup-*` ×9 + 2 个 manifest 备份 + `cashshop-browser-check.cjs`）。原有一份 408MB / 32014 文件的 `windows-package-MnWNy7`（09-14 `package_win_bundle.cjs` 的打包暂存）已于 2026-09-16 被误删，需重新跑一次 `打包Windows资源包.command` 才能再生成。它们不参与轮替（只搬 `ITEM_NAMES`）故当前无害；清理用 `fs.rmSync`。
