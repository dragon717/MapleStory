# 2.5D 轨道巨像世界技术基建规范

状态：草案，作为进入核心实现前的技术入口。本文只整理约束、现状、边界和验证顺序，不代表 3D 运行时已经完成。

## 0. 适用范围与标记

本规范覆盖：2.5D 轨道空间、巨像作为承载土地与空间结构的特殊移动个体、独立移动地域、服务端权威、参考系转换、快照与插值、相关性同步、分区加载、性能测量，以及水体和云层的待定路线。

不覆盖：剧情分幕、具体美术资产、最终渲染引擎选型、可直接上线的水体算法、完整 QA 计划。两份巨像剧情草稿保持不变。

文中标记：

- `[现状]`：由当前代码或有效项目文档直接取证。
- `[约束]`：用户已明确的产品或工程约束。
- `[方案]`：基于现状的实现方向，落地前仍需测量或评审。
- `[待定]`：不能凭空替项目做决定的问题。

核心原则：

1. 服务端决定玩法状态；客户端只提交意图并负责渲染、镜头、动画、插值和表现计算。
2. 默认运动模型是沿轨道、曲面或局部参考系运动，不是无约束自由 3D 移动。
3. 先用一段可测的肩部场景验证参考系和网络，再扩展巨像分区、水体与云层。
4. 单进程、单逻辑 `World` 和有界队列优先；没有测量证据，不引入分布式模拟、每角色任务或重型流体模拟。

## 1. 已确认的产品要求

### 1.1 视觉与空间

- `[约束]` 视觉参照为《艾尔之光》式的 2.5D 轨道空间与漫画渲染；可参考 [官方站点](https://elsword.koggames.com/)、[官方媒体页](https://elsword.koggames.com/community/media/) 和 [Water Dragon Sanctum](https://www.youtube.com/watch?v=GRh2Cl1fTXk)。这些链接是风格参照，不宣称已经从视频/图片可靠核实具体配色、描边或泡沫参数。
- `[约束]` 角色可以是 2D 手绘/漫画切片，在 3D 场景的侧向轨道、曲面或分层路径上运动。
- `[约束]` 轨道可以绕山、盘旋上升；镜头可以沿路径跟随并调整朝向，关键段允许 3D 奇观镜头。
- `[约束]` 不把所有镜头伪装在一张 2D 平面上，也不把默认玩法改成自由 3D 移动。
- `[待定]` Phaser 叠加层、Three.js 场景宿主或混合方案尚未选定。当前安装 Three.js 不等于已经接入。

### 1.2 巨像与移动区域

- `[约束]` 世界允许多个彼此独立的移动地域；古老巨像只是其中具有唯一连续身份和历史的一个个体，其本体还可以承载多个移动区域和可进入分区。
- `[约束]` 肩部/背部可有稳定村落；手、脚、心脏、神殿等区域可进入。
- `[约束]` 巨像有 NPC 行为和目的地。沉睡时可作为岛屿，苏醒后缓慢移动；内部生活需要稳定，外部浪、脚步和转身会产生影响。
- `[约束]` 巨像既不是纯背景动画，也不只是一个可替换的移动平台。
- `[约束]` “恒定”是巨像作为承载土地与空间结构的单一权柄：保持其承载区域的结构连续性和归属，不冻结时间，也不授予全知全能。
- `[方案]` 服务端将巨像身份、路径、区域挂接关系和外部运动作为可观测的世界状态；其内部区域仍按各自玩法更新。

### 1.3 权威与边界

服务端权威范围包括：

- 碰撞、移动、跳跃/落地、攻击、伤害、NPC 行为；
- 世界事件、生产、路线、巨像运动和区域状态；
- 进入、离开、挂接、脱离参考系，以及跨区域交互的判定。

客户端可以做：

- 输入采集和意图提交；
- 镜头、动画、插值、粒子、雾、浪花、云层等表现计算；
- 不改变权威状态的预览、提示和视觉 LOD。

`[待定]` 客户端预测是否存在、预测哪些动作、回滚成本如何控制，未决策前不默认开启。严格等待服务端会增加响应延迟，规范不承诺“无延迟”或“网络无影响”。

## 2. 当前实现基线

下表是开工前的事实，不是未来设计的完成声明。

| 区域 | `[现状]` | 证据 |
| --- | --- | --- |
| 服务端循环 | Rust 单 `World` 顺序处理命令、模拟和广播；`TICK_MS = 50`，即 20Hz | [`server/src/world.rs`](../../server/src/world.rs) |
| 网络边界 | WebSocket 输入进入 `World` 队列；当前帧上限 2048 bytes、输入频率上限 60/s；每连接输出队列有界 | [`server/src/network.rs`](../../server/src/network.rs) |
| 协议 | `PROTOCOL_VERSION = 30`、内容版本 `tms273-33`；客户端消息是输入/请求意图，不带客户端坐标或伤害结果 | [`shared/protocol.ts`](../../shared/protocol.ts) |
| 快照时钟 | 快照携带 `serverTick` 和 `tickMs`，没有单独的墙钟 `serverTime` | [`shared/protocol.ts`](../../shared/protocol.ts)、[`server/src/world.rs`](../../server/src/world.rs) |
| 当前客户端 | 主世界是 Phaser `3.90.0` Scene；`World.update()` 接收快照、做显示插值、更新视图和镜头 | [`client/src/scenes/world.ts`](../../client/src/scenes/world.ts) |
| 插值 | 已有 20Hz 快照到浏览器渲染的显示插值；目前只处理 x/y，不做客户端预测或外推 | [`client/src/features/net-motion/motion-interpolator.ts`](../../client/src/features/net-motion/motion-interpolator.ts) |
| 水体 | 服务端是平面矩形水域；客户端已有 1D 波面、浮动、浪花和倾斜表现，但不是巨像海域的 3D 流体 | [`server/src/geometry.rs`](../../server/src/geometry.rs)、[`client/src/features/world/water.ts`](../../client/src/features/world/water.ts) |
| 资源加载 | 主要按当前地图和实体懒加载；尚无巨像 body-zone 的 LOD、分块和场景流送 | [`client/src/assets/preload-plan.ts`](../../client/src/assets/preload-plan.ts) |
| 3D 依赖 | `three` 已在 `client/package.json` 中，但客户端源码没有 Three.js 主世界导入 | [`client/package.json`](../../client/package.json) |

当前数据规模取证：`shared/maps.json` 有 198 张地图；默认 `shared/map.json` 有 111 个 foothold；`shared/gameplay.json` 有 1712 个出生点、70 个怪物模板和 265 个 NPC 模板。它们用于估算和回归，不是本规范的容量承诺。

因此当前明确的缺口是：

1. 现有世界坐标仍是二维地图坐标，没有巨像/身体分区的参考系树。
2. 现有快照没有参考系 ID、参考系版本和相对速度语义。
3. 现有插值只覆盖 x/y；无法表达平台转动、离面跳跃、跨边界飞行。
4. 现有水体和加载系统不能直接支撑巨像分水、体积云或可进入身体空间。

## 3. 目标模块与数据所有权

### 3.1 模块职责

| 模块 | 唯一职责 | 不应承担 |
| --- | --- | --- |
| `server/src/world.rs` | 逻辑时钟、世界实体、命令顺序、快照生成 | 渲染、镜头、材质和粒子 |
| `server/src/movement.rs` | 权威移动、跳跃、参考系转移后的速度处理 | 客户端平滑或镜头补偿 |
| `server/src/geometry.rs` | 轨道、地面、水域、局部/全局碰撞查询 | 视觉波面和浪花 |
| `server/src/network.rs` | 鉴权、限流、消息解析、队列边界 | 直接修改世界状态 |
| `shared/protocol.ts` 与 Rust 协议 | 输入、快照、事件和版本契约 | 把客户端显示状态当权威状态 |
| `client/src/scenes/world.ts` 及 feature | 快照消费、镜头、视图、表现和加载 | 写回玩家坐标、伤害或事件结果 |
| 资源/内容层 | 地图、轨道、区域、模型、材质、LOD 等静态定义 | 持有运行时玩家/巨像状态 |

继续沿用当前“网络 IO 可并发、逻辑 `World` 单顺序所有权”的边界。不要为了 3D 场景复制一套客户端物理世界，也不要把一个角色拆成一个模拟任务。

### 3.2 定义、运行时状态、表现状态分离

```text
内容定义：World / Region / Track / BodyZone / Model / Material / LOD
        ↓
权威状态：entityId / frameId / frameRevision / transform / velocity / action
        ↓
表现状态：camera / interpolation / animation / particles / fog / visibility
```

同一实体的模型、材质、碰撞形状和 LOD 规则可以预加载或卸载；运行时状态仍由服务端发送，不能因资源卸载而丢失世界因果。

## 4. 坐标与参考系契约

### 4.1 参考系树

目标语义层级为：

```text
World
├── MovingRegion
│   └── Track / LocalSpace
│       └── Entity
└── Colossus
    └── BodyZone / Track / LocalSpace
        └── Entity
```

- 每个节点有稳定 `frameId`；变换更新递增 `frameRevision`。
- 子节点坐标只对其父节点有意义；参考系图必须无环。
- 服务端持有父子关系、变换、速度和生效时间；客户端只消费并显示。
- 旧二维地图可继续使用 world XY；迁移应是增量式，不为了一次 3D 改造重写现有地图。

推荐的速度语义为：

```text
v_world = v_parent + ω_parent × r + R_parent · v_local
```

其中 `r` 是实体相对父原点的位置，`ω × r` 是旋转参考系带来的切向速度。最终轴向、单位、左/右手系和角度单位必须在协议字段落地前定稿；公式是语义约束，不是可直接复制的 API。

### 4.2 挂接、脱离和跨边界

服务端必须决定：

1. 何时进入轨道、肩部或身体局部参考系；
2. 何时跳起、脱离或重新落地；
3. 脱离瞬间如何继承平移速度与旋转切向速度；
4. 飞行中受自身推力、风、巨像加速度和转向影响的规则；
5. 落地时采用哪个候选参考系和碰撞面。

脱离不能把速度强行归零，也不能用客户端“自动跟随”弥补参考系错误。鸟类或其他飞行体初速度可以继承载体速度；持续飞行应由自身推力和环境规则更新，而不是永久绑定载体。

碰撞查询分两层：局部参考系宽相位 + 巨像/区域的全局外部代理。跨边界的攻击、飞行体和临界落点必须进入候选集合，不能因为实体当前不在同一局部场景而漏判。

### 4.3 兼容当前协议的增量字段方向

未来快照需要能表达以下最小语义；字段名暂不锁死：

| 语义 | 最小信息 | 所有者 |
| --- | --- | --- |
| 所在参考系 | `frameId`、`frameRevision` | 服务端 |
| 显示位置 | 局部位置；必要时给世界校验值 | 服务端 |
| 运动 | 局部速度、参考系变换所需的父速度/角速度 | 服务端 |
| 动作 | 动作类型、开始 tick、落地/脱离事件 | 服务端 |
| 资源 | body-zone、模型、材质、LOD 规则 ID | 内容定义 |

不在本阶段改协议；先用验证场景确认字段确实足够表达转动平台、跳离和跨边界，再一次性更新 TypeScript、Rust、浏览器和陪测机器人契约。

## 5. 时间、快照与网络行为

### 5.1 三种频率分离

```text
固定模拟步长：服务端决定碰撞、移动和事件顺序
网络发送频率：按相关性发送快照/事件，不能等同渲染帧率
浏览器渲染频率：客户端独立绘制、插值和表现计算
```

当前固定步长是 50ms。未来若调整模拟或发送频率，必须分别测量，不把提高渲染 FPS 当作提高权威模拟精度。

快照以 `serverTick`/`tickMs` 作为跨实体显示时钟。巨像、区域和其上的角色在同一显示时刻取样；需要跨进程调度或墙钟排程时，另行增加时间语义，不能把本地 `receivedAt` 当世界时间。

### 5.2 插值与迟到包

- 客户端继续保持显示插值与权威状态分离；当前 self 半 tick、其他实体一 tick 的策略属于现状，不是巨像场景的最终值。
- 迟到包不能阻塞浏览器渲染；旧序列丢弃，短暂缺包时保持最近有效显示状态。是否允许受限外推须单独决策，未决策前不擅自外推。
- 参考系改变或 `frameRevision` 不连续时，优先以事件和新参考系重建显示状态，不能把两个不同父坐标直接线性插值。
- 网络过载可以增加响应延迟、丢快照或触发重连；服务端必须保证权威模拟继续按规则推进，不能承诺“无影响”。

当前服务端每连接输出队列为 32；队列满时当前实现会丢弃快照，连接仍可继续模拟。该行为应纳入验证场景的过载测试，而不是用无限队列掩盖问题。

### 5.3 输入契约

- 连续输入使用递增序号；离散攻击、交互、切换等请求使用 `requestId` 做幂等处理。
- 客户端只发方向、跳跃、攻击、交互等意图，不发送“我已经在这里”或“我造成了这个伤害”。
- 服务端在网络边界验证枚举、长度、有限数值、速率和版本；协议变化同步更新 Rust、TypeScript、浏览器与机器人。

## 6. 相关性同步与场景流送

相关性不能只等于摄像机当前可见矩形。推荐分层：

| 层级 | 应同步的内容 | 目的 |
| --- | --- | --- |
| 全局 | 巨像身份、路线/目的地、区域结构版本、全局事件、队伍状态 | 保持世界因果和队伍一致 |
| 交互邻域 | 当前轨道、碰撞体、NPC、怪物、掉落、可交互静态物变化 | 保证玩法判定 |
| 即将进入 | 路径前方、转弯后、跳跃/飞行可能到达的区域及实体摘要 | 避免进场才开始加载/同步 |
| 远端摘要 | 生产、旅行、事件进度、时间戳和结果版本 | 不观察时仍推进，不冻结世界 |
| 静态变更 | 地形、门、桥、机关、可破坏物的 revision | 修复只同步动态实体的遗漏 |

生产、旅行和远端 NPC 可以按事件或经过时间批量推进；“不在屏幕上”不等于停止模拟，必须保留可追溯的世界因果。

客户端 body-zone 采用带滞回的预加载/卸载：

1. 远景：轮廓、低细节模型或切片；
2. 近景：肩部村落、轨道和交互实体；
3. 进入内部：心脏/神殿等局部空间及其专用资源。

镜头旋转改变可见面时，资源选择要考虑视锥和即将进入的方向。资源卸载只释放模型、材质和特效，不删除服务器状态。

## 7. 性能预算与首轮测量

本规范不编造浏览器、显卡或网络阈值；先在首个验证场景采集 p50/p95/p99，再把测量结果转成预算。

| 指标 | 采集点 | 最低验收问题 |
| --- | --- | --- |
| 浏览器帧耗时 | update、渲染、GPU/主线程 | 旋转镜头、2D 切片和近景特效是否产生长帧 |
| 服务端 tick 耗时 | 单 tick 模拟、队列处理、快照生成 | 是否超过固定步长并形成积压 |
| 输入响应 | 客户端发送到权威确认可见 | 延迟与抖动下是否可解释、可恢复 |
| 网络负载 | 每类包大小、发送频率、丢包、输出队列深度 | 相关性分层是否真的减少无效同步 |
| 场景切换 | 预加载、解码、首帧、卸载 | body-zone 切换是否卡顿或黑屏 |
| 内存 | 纹理、模型、缓存和运行时状态 | 卸载后是否仍有持续增长 |

首轮护栏：

- 保持单进程逻辑世界；路径寻找批量化，远端生产/旅行按事件时间推进。
- 不做 SPH/FLIP 等全局流体模拟，不为每个实体启动独立模拟任务。
- 平面反射、体积云和高频粒子属于成本项，必须经过场景测量后再启用。
- 每次优化保留场景录制、输入序列和服务端 tick 日志，避免用主观“看起来顺滑”替代数据。

## 8. 水体与云层：已知要求，方案待定

### 8.1 权威状态与视觉状态分离

| 水体语义 | 归属 | 说明 |
| --- | --- | --- |
| 水位、可涉水深度、浮力、阻力、碰撞/进入退出 | 服务端 | 决定玩法；可以是局部体积或规则体，不要求全局流体求解 |
| 大尺度波形、法线、漫画深浅色带、受控泡沫 | 客户端表现 | 由共享种子/参数驱动，不能改写水位和实体位置 |
| 巨像分水的水幕、浪脊、喷雾、雾 | 客户端表现，必要时由事件驱动 | 使用局部实体几何表现，不把一次局部位移解释为全球海洋守恒 |

### 8.2 推荐先验证的视觉候选

- 大尺度用解析波或低成本可重复函数，配合漫画式浅/深色带和受控泡沫；不要从最昂贵的全局流体开始。
- 解析候选可以从正弦/Gerstner 类波叠加开始。Gerstner 波带有顶点横向位移，不再是严格的高度场；如果服务端需要查询任意世界水平点的水高，必须采用逆向求解或明确的近似一致协议，并限制陡峭度，不能把 GPU 代入公式当作 CPU 查询天然逐位一致。
- 巨像手部/身体分水需要有厚度和高度差时，用局部实体水幕、浪脊或体积几何；只改法线贴图不足以表达“巨物分开海水”。
- 近景喷雾、泡沫和雾采用有限数量、可按距离裁剪的特效；平面反射是可选成本项。
- 远景云用分层/卡片/低成本体积表现，镜头真正进入云层时才启用局部体积；统一山体、角色和云的色板、明暗带、边缘、细节密度与雾。
- 如果未来需要持续、广阔且动态的海洋，再把 FFT 作为对照路线；[Sea of Thieves 的 SIGGRAPH 案例](https://history.siggraph.org/wp-content/uploads/2022/09/2018-Talks-Ang_The-Technical-Art-of-Sea-of-Thieves.pdf)说明 FFT 海面可以叠加视角/太阳着色、波峰与交叉物泡沫、艺术纹理，云则可用不透明几何、低分辨率离屏处理、深度和模糊实现风格化体积感。FFT/WaveWorks 的 DX/Vulkan 数据不能直接充当 Web 预算。
- WebGL2/WebGPU 兼容范围、移动设备降级、相机旋转下的深度/泡沫算法均为 `[待定]`。

已有资料只能支撑方向，不直接指定实现：[GPU Gems 的解析/Gerstner 水面](https://developer.nvidia.com/gpugems/gpugems/part-i-natural-effects/chapter-1-effective-water-simulation-physical-models)和[局部扰动案例](https://download.nvidia.com/developer/GPU_Gems_2/GPU_Gems2_ch18.pdf)不能替代服务端水状态；Unity 风格的水深、泡沫和折射技巧不能当作 Web 库；主机级体积云成本不能直接套用浏览器预算；Three.js WebGPU 水体示例只能证明能力存在，不能证明它适合本项目。

## 9. 首个验证场景与分阶段落地

### 9.1 首个验证场景

只设计一个最小但能击穿关键风险的场景：

- 缓慢平移并转动的肩部平台；
- 两名联网玩家；
- 一条弯曲、上升的轨道；
- 玩家跳离、短暂飞行、重新落回肩部；
- 至少一次跨局部/全局边界的攻击或交互。

验收观察：脚底相对平台是否稳定；平移、转动和落地的速度是否连续；跨边界是否漏碰撞；延迟/抖动/丢包后是否能恢复；重连后世界因果是否仍一致；巨像和乘员是否按同一显示时刻呈现；输出队列压力是否能解释为响应延迟而不是逻辑分叉。

### 9.2 阶段门

| 阶段 | 只验证什么 | 通过后才能做什么 |
| --- | --- | --- |
| 0. 契约与测量 | 参考系字段草案、日志字段、场景录制和指标采集点 | 进入最小服务端/客户端改动 |
| 1. 参考系原型 | 肩部平台、2 玩家、轨道、跳离/飞行/落地、跨边界、重连和抖动 | 扩展 body-zone 与相关性同步 |
| 2. 巨像分区 | 肩部村落、内部区域、父子 frame、LOD、预加载/卸载、静态 revision | 进入局部水体和云层方案比较 |
| 3. 水云候选 | 视觉 A/B、低端设备降级、视角旋转、玩法水位/浮力与表现解耦 | 选定可量化的实现路线 |
| 4. 奇观段 | 相机路径、远近切换、镜头进入云/水幕、完整性能回归 | 小规模陪测与内容扩展 |

当前任务只完成文档和取证，不执行上述代码实现、服务重启或数据库迁移。

## 10. 未决问题清单

1. 最终渲染宿主是 Phaser 叠加、Three.js 主场景，还是混合桥接？2D 角色切片的深度/遮挡策略是什么？
2. `frameId/frameRevision`、变换单位、角度单位、坐标手性和协议兼容方式如何定稿？
3. 挂接、跳离、继承速度、飞行推力、重力方向、转弯和落地候选的玩法规则是什么？
4. 是否启用客户端预测？若启用，哪些输入可预测、如何纠错、如何处理参考系切换？
5. 相关性半径/路径前视距离如何由碰撞、飞行速度和网络 RTT 推导，而不是凭感觉设置？
6. 巨像外部区域与内部区域的时间尺度、世界事件和生产推进如何关联？
7. 水体是规则体积、分层水域还是其他模型？哪些部分影响浮力/碰撞，哪些只做视觉？
8. 云层允许进入到什么程度？低端 WebGL2 和支持 WebGPU 的设备分别保留哪些效果？
9. 目标浏览器、设备档位和场景基准机是什么？没有这组设备就不能锁定绝对预算。

## 12. 实现入口

进入代码前必须先补齐三件事：

1. 用首个验证场景确定参考系字段和继承速度的可观测日志；
2. 用目标浏览器/设备测出服务端 tick、浏览器长帧、输入响应、包大小和队列积压；
3. 在验证结果能表达“转动平台 → 跳离 → 飞行 → 落地 → 跨边界”后，再决定渲染宿主、body-zone 流送和水云候选。

在此之前，增加 3D 依赖、替换现有引擎、重写协议或启动分布式服务都属于越过证据的实现，不纳入当前基线。
