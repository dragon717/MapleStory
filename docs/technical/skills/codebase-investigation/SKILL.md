# Codebase Investigation

用于在编辑前建立真实的调用链和实现边界，避免只修复报告中提到的一个表象路径。先读当前工作区的项目入口和相关文件，再决定改动是否需要共享函数、模型或状态源。

## 适用范围

- 一个 bug 可能影响多个调用方或多个平台路径
- 同一功能存在多个实现，需要解释差异后再统一
- 继承旧代码、重构或修复不清楚根因的行为
- 用户明确要求调查、标准化或影响面分析

单个文件的局部拼写、明显编译错误或一次性常量不需要加载本技能。

## 调查流程

### 1. 定义问题和边界

记录用户报告的触发条件、实际症状、预期行为、涉及的项目根目录和不可变约束。确认当前工作区，不要依据历史路径猜测仓库。

### 2. 建立完整候选集

优先用 `rg` 和 `rg --files`，先找文件再找文本：

```bash
rg --files -g '*.swift' -g '*.ts' -g '*.tsx' -g '*.py' .
rg -n "关键类型|函数名|状态字段|用户可见文案" .
rg -n "目标函数名\(" .
rg -l "目标协议|目标通知|目标字段" .
```

同时查找定义、所有调用方、写入方、读取方、异步回调、缓存和持久化边界。搜索结果只是候选，不把字符串命中当成调用关系。

### 3. 沿数据和状态链路阅读

从用户动作或入口开始，依次追踪：

1. 入口与输入校验
2. 状态/模型写入
3. 共享服务、网络或持久化
4. 异步回调、通知和合并
5. 查询、渲染或外部副作用

记录每一段的线程/actor、错误处理、可选值、生命周期和缓存行为。对准备修改的共享函数，先读完全部调用方和相邻实现。

### 4. 对比工作正常的实现

如果有“这里正常、那里失败”的对照，找出同一链路上最小差异：输入、默认配置、颜色/资源来源、状态时序、错误路径和依赖版本。不要先假定问题就在报错文件。

### 生成数据与持久化故障（仅相关时）

- 阶段标签只说明失败位置，不能直接证明数据库损坏；定位被破坏的不变量及全部读写方。
- 沿权威来源→生成物→构建制品/缓存→运行时→持久化记录核对。修上游来源与必需消费者，不只手改单个生成结果；编译进制品的数据不能靠刷新文件更新。
- 不通过删数据、清库、忽略未知引用或放宽校验使加载“成功”。只有证据证明需要迁移才使用保留实例字段的事务/幂等路径。
- 验证有效记录可保存→关闭→重载，非法记录仍拒绝；项目路径、槽位格式和具体值从当前契约读取，不沿用其他项目结论。

### 5. 形成根因和最小修复边界

调查结果至少回答：

- 可复现触发条件是什么？
- 哪一个不变量被破坏？
- 哪个共享层同时覆盖所有受影响调用方？
- 修复为何不会改变未涉及的变体？
- 哪些不确定性仍需要运行时、平台或用户确认？

优先在共同根因处修一处。只有实现确实有合法差异时，才保留分支；不要为了一个调用方创建新抽象或全局标准。

### 6. 验证影响面

运行与改动风险匹配的最小检查：静态搜索、类型检查、单个有意义的测试或现有项目检查。至少重新搜索共享函数的调用方，并验证错误路径、空值和恢复/重启路径。平台构建、联网或外部写入不在用户授权范围内时，明确标记未运行。

## 调查记录模板

```markdown
## 问题
- 触发条件：
- 实际行为：
- 预期行为：

## 影响面
- 入口与调用方：
- 共享状态/持久化：
- 异步或外部边界：

## 根因
- 被破坏的不变量：
- 证据：

## 最小修复
- 修改位置：
- 保留的合法差异：
- 验证：
- 未验证的环境边界：
```

## 常见错误

- 只查报告中的文件，遗漏兄弟调用方；使用 `rg -n "函数名\\(" .` 重新查全。
- 只改 UI 症状，未追踪状态源、缓存或同步回调。
- 把默认值、空值或异步时序当成用户一定会改变的配置。
- 在没有实现差异证据时合并技能、抽象接口或批量重写文件。
- 把静态检查结果写成已完成的真机、模拟器、联网或跨设备验证。

## 输出

交付调查报告或修复时，按“症状 → 证据 → 根因 → 最小改动 → 验证与限制”的顺序写，引用实际文件和符号；不要附带与当前问题无关的项目模板。
