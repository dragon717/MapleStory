# MapleStory 3D 场景交付

目标是让玩家在正常行走镜头下读懂空间、选择路线并安全到达目标。先读 `AGENTS.md`、`docs/technical/BUSINESS_DEVELOPMENT.md`、`docs/plan/PLAN.md`，再按本指南对应方法推进；详细的项目实例、坐标和历史记录留在 [`3D 场景开发通用指南`](../../../Code/MapleStory/docs/technical/3D场景开发通用指南.md)。

## 范围与事实边界

- 先确认当前地图的同版名称、地图 ID、有向连接、入口、标高和现有运行时入口。名称、缩略图或旧目录残留不能单独证明地图可进入；原版事实、项目已有实现和本次视觉改编分开记录。
- 当前授权决定改动范围。局部灯光、材质或 NPC 工作不自动扩大到路网、任务、存档或战斗；“先讨论/先设计”保持相应只读边界。
- `World`/服务端继续拥有玩家、NPC、任务、怪物、技能、物品、动画时钟、碰撞和命令。3D 层负责环境、镜头、遮挡、显示桥接和输入重投影，不另造玩法权威或移动状态机。
- 具体地图的比例、像素/米、路线数量、坐标、建筑布局和光照参数属于该地图清单，不能从一个地图推广成所有地图标准。

## 从来源到可走场景

按需要跳过未受影响的阶段，但每一阶段都要有可审阅成立条件：

1. **来源取证**：记录同版地图名称/ID、故事职能、门户方向和连接类别，区分固定门、NPC/脚本交通、组队实例和旧目录。
2. **空间方案与尺度卡**：表达主路、分支、汇合、环路、上下层、目标视线、角色/门/桥净空和常用镜头。原创连接、地标和高度标 `P`，不反写原版事实。
3. **鸟瞰原型与正常行走视角**：鸟瞰图须能读全局拓扑；代表性行走镜头须能读角色尺度、前进线索、遮挡和回出路径。概念图不能冒称实景模型。
4. **可走白模**：道路中心线、路面、共享节点和权威导航使用同一几何基准；上下层、桥、楼梯、坡道、室内/洞口均须连续、有净空并能往返或回出。静态检查后再做实际运行验收。
5. **可编辑模型与实装**：先检查几何完整性、部件语义、动画归属、材质/UV 和授权，再导出 `.blend`/GLB/预览并同步运行资源。GLB 不承担权威碰撞。

每条路线都要有来源或明确的设计标记；不要用穿过区域中心的直线替代街道，也不要用“隐藏”解释断路。浮岛道路必须有明确承载体，动态桥、浮阶和缆索按两端当前变换更新，不能逐帧累加漂移。

## 角色纸娃娃与装备数据

- TMS273 纸娃娃导出保留源帧的 `origin`、命名 `map`/anchor、基础 `zmap`/遮挡 `smap`、动作 `delay`、UOL/源 URL 和装备槽信息。`x/y` 是相对脚点图像左上角的组合结果，运行时不要再次减 `origin`；整套角色作为一个容器翻转，不能逐图片翻转。
- 装备外观来自服务端当前 `equipped` 与角色外观；船上预览和真实 `PlayerView` 共用 `composeAppearance`。普通装备、现金装、武器动作分支、遮挡槽和空装备必须沿同一层规则解析，不在船上复制一套组合器。
- 懒加载必须同时核对层 JSON 和 PNG/纹理是否就绪；异步回调使用当前角色/组合 key 或 generation 守卫，过期结果、失败结果和地图切换要清理。导出报告可保留完整源映射，运行时精简数据仍须保留 `x/y/origin/z/width/height/part` 等绘制所需字段。
- 设备、地图和模型值均以实际资源为准；发现缺装、脚点漂移、站立抖动或前后层错位时，先对比真实 `PlayerView` 的权威快照、动作延迟和整容器朝向，再做最小修复，不能用船上本地状态掩盖源数据问题。

## 航船入口、地图标配与运行时交互

- 航船入口保持船上正常行走；加载采用非阻塞底部小进度窗，用户仍能看见并操作船上内容。只有世界资源和权威快照 ready 后，才播放书页/灯光过渡；失败或过期结果恢复可操作状态并销毁旧资源。
- 默认游戏镜头应服务正常行走，不能只按鸟瞰或展示镜头调模型。路线和碰撞由共享布局/服务端权威规则决定，视觉网格不能反推碰撞。
- 路口提示只提供上、下、左、右四个方向，不组合斜向选项；持续按键沿当前连续路线转弯，去程与回程使用同一连接规则。NPC/传送交互键与方向输入分开配置。
- 室外保留栏杆、楼梯边缘等有意的部分遮挡；全身确实被遮住时才启用角色附近的局部透视，不能凭大包围盒把空门洞当墙。已有室内按明确房间体积和外壳语义剖视：隐藏对应外壳与挡住下层的上层部件，保留脚下地板、当前道路和陈设，退出恢复原可见状态，门口留小滞回范围。没有室内的合并外观建筑不能以透视冒称室内已实现。
- 地表脚步反馈读取真实接地、速度、地表、湿度和当前天气。雪地需求至少覆盖踏雪脚点、雪粉/扬雪强度及停步清理；是否有持久脚印、积雪形变或多人共享天气必须单列需求，未实现就写成验收条件，不写成完成事实。
- 船和地图模型必须保持可编辑语义部件：补齐缺失栏杆；主帆应能独立收放并挂接布料动画；保留一个可独立编辑的枫叶。对象检查通过不等于运行时已接入，需分别记录 source、preview、production 状态。

## 检查与交付

只执行本轮改动相关的静态检查、类型/构建或资源检查；不以浏览器预览、隔离截图或模型能打开替代真实运行证据。需要实装时保留现有服务、账号和数据库，按项目规定入口验证健康与资源新鲜度。

交付报告分开写：

- 已从源文件、导出报告、共享布局或服务端快照核实的事实；
- 本轮实际修改和对应检查；
- `source`、`preview`、`production` 各自成立到哪一步；
- 用户还需在正常行走镜头下验收的路线、装备、遮挡、天气、栏杆、主帆、枫叶和航船过渡。

未实现功能写需求、依赖和验收条件，不写成“已完成”。不要为满足流程制造代码、坐标或额外测试；通过与改动匹配的检查后停止重复验证。
