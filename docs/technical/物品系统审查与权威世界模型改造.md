## 1. 结论摘要

1. **当前物品模型是"容器中心"的，不是"世界事实"中心的。** 物品没有身份——身份就是它所在的位置
   （`PRIMARY KEY(account_id, inventory_type, slot)`）。Owner 隐含在 `account_id` 列里，State 完全缺席。
   世界模型 §2 要求的三维拆分（Owner / Location / State）在代码里一层都没有。

2. **`put` / `take` 级原语是 `pub` 的，并且被生产代码直接调用**（`add_items` 8 处、`remove_items` 13 处、
   `move_items` 3 处）。这正是 §6 / RULE-2 明确禁止的形态。"全或全无"目前靠
   `clone 一份 → 改副本 → 整体写回` 的**约定**维持（12 处 `state.inventory.clone()`、17 处
   `state.inventory =`、6 处 `state.equipped =`），类型系统不给任何保证。

3. **仓储泄漏了修改权（§34）**：`write_inventory(account_id, &[InventoryItem])` 用内存里的 Vec
   **整表重写** `inventory` 表，调用点 4 处（生产）。这是当前最实际的正确性风险点。

4. **本项目没有邮件、拍卖、玩家交易**（已核：`server/src` 无 `auction` / `escrow` / 玩家间 trade 代码）。
   因此世界模型里 `TransferOwnership` / `Escrow` / `Lock(LockReason::{Auction,Trade,Contract})`
   **没有任何消费者**。按项目规范"不为未实现的功能提前建目录或通用工厂"，本轮**刻意不建**这些类型。

5. **里氏替换原则在这里的正确用法是"拒绝合并"，不是"尽量统一"**（§11 / §41）。现有物品的五个存放处
   里，只有**背包**与**账号仓库**真正共享同一份行为契约（`put` 成功后物品确实在容器里；
   `take` 成功后确实被移除）。地面掉落、卖回列表、待认领奖励都属于 §11 说的
   "为什么物品发生变化 / 谁在什么时候获得操作权"那一类——**把它们做成 `Container` 才是真正的 LSP 违反**。

6. 好消息：代码里**尚未出现**这种伪抽象（没有任何 `Container` trait）。所以 ① 的价值是
   **先把真正的契约边界画对**，而不是事后拆一个错的东西。

## 2. 现状：物品事实分散在五个"位置"

物品本身的数据结构只有一份：

```rust
// server/src/protocol.rs:875
pub struct InventoryItem {
    pub slot: u16,  pub item_id: String,  pub quantity: u32,
    pub stats: Option<BTreeMap<String, i64>>,   // 实例私有字段（卷轴强化、宠物身份、租赁到期…）
    pub remaining_slots: Option<u32>,           // 装备剩余可强化次数
    pub upgrade_count: Option<u32>,
}
```

注意它**没有 id、没有 owner、没有 state**。它在世界中的"位置"由它所在的表与主键决定：

| # | 位置 | 持久化 | 主键 | Owner 表达 | State 表达 |
|---|---|---|---|---|---|
| 1 | 背包（5 页签） | `inventory` | `(account_id, inventory_type, slot)` | 隐式 `account_id` | 无 |
| 2 | 装备栏（穿着） | `equipped` | `(account_id, slot)`（槽位为负） | 隐式 `account_id` | 无 |
| 3 | 账号仓库 | `storage` | `(account_id, slot)` | 隐式 `account_id`（**跨角色共享**） | 无 |
| 4 | 地面掉落 | `drops` | `id` | `owner_account_id`（**唯一一处显式 owner**） | `protected_until_ms`（拾取保护窗）、`active` |
| 5 | 商店卖回列表 | `shop_rebuy` | 自增 | — | — |

另有三个"准位置"，它们都持有物品但都不叫容器：

- `monster_rewards`：击杀后**待认领**的奖励，`reward_claimed` 是"还没真正进入玩家世界"的状态位
  （对应世界模型 §27 的 inbox 概念，但没有任何 `Reward` 类型）。
- `cash_purchases` / `quest_kills`：**不是**物品，是计数器；它们混在同一个库里，容易被误当成位置。
- `world.deferred_quest_drops`、`pets.rs` 的召唤状态：**进程内**镜像，重启即清。

### 2.1 位置即身份带来的实际问题

因为身份就是位置，所以：

- 同一件装备从背包第 3 格移动到第 7 格，代码上是"删一行 + 插一行"，**没有任何地方能说"还是那一件"**。
  装备的实例属性（`stats` / `upgrade_count`）目前靠**人工搬运字段**（`StorageStack` 就是为此存在的手工载体）。
- "系统拥有"无法表达。地面掉落用的是 `owner_account_id: Option<String>` —— 这恰好是 §3.1 点名的
  `{ owner_type, player_id: Option<_> }` 反例形态：它可以写出"有 owner 但没有保护窗"这种语义上可疑的组合。
- 同一个 `equipped` 槽位用负数、`inventory` 槽位用正数（见 `BUSINESS_DEVELOPMENT.md` 存档槽位约定），
  但两者共用同一个 `InventoryItem.slot: u16`/`i16` 字段 —— 槽位语义靠**约定与注释**而非类型区分。

## 5. LSP 分析：在这里，里氏替换原则要求我们**拒绝**合并

§41 把 LSP 在这个语境下的含义写得很清楚：

> 只有当所有实现都能遵守同一个行为契约时，才应该共享一个抽象。

把这句话套到本项目的五个存放处：

| 位置 | `put` 的真实语义 | 能遵守容器契约吗 |
|---|---|---|
| 背包 `inventory` | 合并同叠 / 找第一个空页签格 | ✅ **能** |
| 账号仓库 `storage` | 合并同叠 / 找第一个空格（上限 `STORAGE_SLOT_LIMIT`） | ✅ **能** |
| 装备栏 `equipped` | "穿上" —— 要按职业/等级/槽位合法性判定，且同槽互斥；实际是**槽位占用互换** | ❌ **不能**：已论证（§7 增量 2），目标槽位由物品决定、还会反向 put 回来源侧 |
| 地面 `drops` | "掉落"= 建立 owner + 保护窗 + 位置广播 | ❌ **不能**：`put` 的语义是"建立拾取权"，不是"放进去" |
| 卖回列表 `shop_rebuy` | "卖掉了"= 记录价格与数量，物品已离开玩家世界 | ❌ **不能**：它不是容器，是交易凭据 |
| 待认领奖励 `monster_rewards` | "还没真正属于玩家" | ❌ **不能**：这正是 §19 说 `MailAttachment` 不一定是 Item 的情形 |

于是本轮的设计决定是：

1. **只让背包与仓库实现共享契约。** 契约内容就是"`put` 成功后物品确实存在于该容器 / `take` 成功后确实被移除"，
   并且用**同一段断言序列跑两个实现**来强制它（`item_world.rs::tests::both_containers_honour_the_same_contract`）。
2. **地面、卖回列表、待认领奖励一律不做容器。** 它们的规则类属于 §11 的第二类："为什么物品发生变化、
   变化依据什么业务规则、谁在什么时候获得操作权"。给它们建 `Container` 才是 LSP 违反。
3. **契约里不放槽位。** 落地时发现一个必须诚实面对的事实：本项目**放入动作一律由容器自选落点**
   （合并同叠或找空格），业务层说不出也不该说出目标槽位。所以模型分成两个类型：

   - `ItemLocation` —— **事实**，自带槽位（`Inventory { kind, slot }` / `Storage { slot }`）
   - `ContainerSide` —— **意图**，只有"哪一侧"（`Inventory { account }` / `Storage { account }`）

   这样"目标槽位"在类型上根本写不出来，而不是靠文档约定不要写。这就是 §39。
4. **`peek` / `take` / `put` 不公开**（§7 / §9），`Container` 概念本身也不是 `pub trait`（§10）。
   业务模块只看得见 `move_stack` —— 一个**完整业务动作**（§6）。

## 6. 已落地的增量（行为零变化）

### 6.1 ①：物品世界事实词汇 + 仓库搬运收敛（`server/src/auth/item_world.rs`）

| 内容 | 世界模型依据 |
|---|---|
| `enum Owner { Account(&str), System }` | §3.1 |
| `enum ItemLocation { Inventory{..}, Storage{..} }` | §3.2（自带身份，非法组合写不出来） |
| `enum ContainerSide { Inventory{..}, Storage{..} }` | §39（意图没有槽位） |
| `enum ItemState { Normal, Locked(LockReason) }` + `LockReason::PickupProtection` | §3.3 |
| `drop_fact()` / `pickup_allowed()` | §3.3 / §41 —— 掉落保护窗的唯一翻译点 |
| 私有 `trait Source`（`peek` / `take`）+ `trait Destination`（`can_accept` / `put`） | §7 / §9 / §10 |
| `InventorySource` / `StorageSource` / `InventoryDestination` / `StorageDestination` | §41（两个真同契约的实现） |
| `move_stack(tx, from, to, quantity) -> MoveOutcome` | §6 / §13 / §32 |
| `MoveOutcome::{Moved, Refused}` | 区分"业务拒绝"与"持久化失败"，与既有幂等回执语义对齐（② 起 `Refused` 携带 `reason: MoveRefusal`，见 §6.4） |

`move_stack` 的执行顺序与重构前逐字一致：**先 `peek` 探测 → 再目标 `can_accept` 预判 → 然后 `take` → 最后 `put`**。
只有 `peek` / `can_accept` 的拒绝被记成业务码，`take` / `put` 的失败是硬错误——与原实现的 `?` 用法完全对应。
任何一步失败都返回 `Err`，由持有事务的调用方回滚，所以 §32 的"全或全无"由**事务**保证，而不再靠调用者自觉。

### 6.2 接入点一：`Store::storage_transfer`（`auth.rs`）

重构前是两段手写的 `peek → guard → take → insert`（Deposit / Withdraw 各一段，含 6 个失败码分支）；
重构后是**一次** `move_stack`：

```rust
let (from, to) = match operation {
    StorageOperation::Deposit => (
        ItemLocation::Inventory { account_id, kind: inventory_type, slot },
        ContainerSide::Storage { account_id },
    ),
    StorageOperation::Withdraw => (
        ItemLocation::Storage { account_id, slot },
        ContainerSide::Inventory { account_id },
    ),
};
let moved = item_world::move_stack(&tx, from, to, quantity)?;
```

**这是里氏替换原则的字面应用**：`Store::storage_transfer` 的签名、返回的 `StorageOutcome` 字段、
6 个失败码（`invalid_slot` / `invalid_quantity` / `source_empty` / `storage_slot_empty` /
`storage_full` / `inventory_full`）与事务边界全部**逐字保持**，调用方 `trade.rs::handle_storage_transfer`
一个字都没改，而实现已经换成世界模型的 Move。

### 6.3 接入点二：`auth/loot.rs::pickup` 的拾取权判定

重构前：

```rust
if protected_until_ms > now_ms()
    && owner_id.as_deref().is_some_and(|owner| owner != account_id)
```

重构后：

```rust
let (owner, state) = item_world::drop_fact(owner_id.as_deref(), protected_until_ms);
if !item_world::pickup_allowed(&owner, &state, account_id, now_ms())
```

四条真值（本人 / 他人 / 系统 × 窗口内 / 已过期 / 无窗口）现在有独立单元测试，不再只是被
`world_tests` 间接覆盖。

### 6.4 ②：拒绝原因类型化 —— 容器只回答*原因*，措辞由业务动作决定

① 落地时留了一个不干净的地方：`Source` / `Destination` 用 `String` 表达拒绝原因
（`Err("storage_full".to_owned())`），等于把**业务措辞**下沉进了容器实现。这违反世界模型 §31
（Command 与 Event 分开）的精神——容器知道的是"我没装下"，不应该是"该给玩家看 `storage_full`"。

② 把它收紧成类型：

```rust
pub(super) enum MoveRefusal { InvalidSlot, InvalidQuantity, SourceEmpty, DestinationFull }
```

| 内容 | 变化 |
|---|---|
| `Source::peek` / `Destination::can_accept` | 返回 `Result<Result<_, MoveRefusal>, String>`：`Ok(Err(原因))` = 业务拒绝，`Err(_)` = 持久化失败（硬错误，回滚事务） |
| `MoveOutcome::Refused` | 携带 `reason: MoveRefusal`（不再是 `code: String`），新增 `refusal() -> Option<MoveRefusal>` |
| `StorageOperation::refusal_code` | **唯一**翻译点（6 个既有码：`invalid_slot` / `invalid_quantity` / `source_empty` / `storage_slot_empty` / `storage_full` / `inventory_full`）；同一个 `SourceEmpty` 在存入/取出两个方向译成不同的码 |
| `move_stack` 执行顺序 | **不变**（`peek → can_accept → take → put`）；只有前两者记业务码，后两者仍是硬错误 |

**为什么这一步是增量 3 的前置**：地面掉落接入时，新位置不必再伪造别人的拒绝码（`drop_inventory` 的
`invalid_inventory_type` 现在由业务动作自己给），容器只需如实回答"空 / 满了 / 槽位非法"。

**顺带修正一处潜在错标**：`reserve_storage_slot` 原先把 `query_row` 的**失败**也标成 `storage_full`
并写进幂等回执——SQLite 异常会被误报成"仓库满"且被当成成功拒绝提交。现在
`Ok(Err(DestinationFull))` = 业务拒绝、`Err(_)` = 持久化失败中止事务。
（该路径当前不可达，属静态修正，未新增测试暴露它。）

### 6.6 ③：增量 4 的前置 —— 商店购买路径的失败边界测试（并修掉缺失的幂等回放）

增量 4 要"收窄 `pub` 面 + 堵住整表重写"，前提是**先有等价性证据**。动手补测试时先把"内存 clone →
写回"的站点数清点了一遍，发现上一版路线图**写错了**（见 §7 增量 4 的更正）。

**新发现（真缺陷，非重构问题）**：商店购买 `handle_shop_buy` 没有 `requestId` 幂等回放账本。
三个同样会动金币的兄弟动作都有——`ShopSell`（`trade.rs::send_shop_sell_result`）、
`ShopRebuy`、现金购买（`cashshop.rs::replayed_cash_request`）——只有购买没有。于是：
**同一个 `ShopBuy` 包被重发（网络重传 / 客户端重试）会按原价再扣一次金币、再发一次道具。**

复现证据（本次实测，把保护临时短路后跑新测试）：
`a replayed shopBuy must not deduct mesos twice` → `left: 900, right: 950`——1000 被扣成 900。

修法与既有模式逐字对齐：

| 内容 | 位置 |
|---|---|
| `ShopBuyOutcome`（重放用，字段与线上消息一致，**不加 `mesos` 字段**以免动 wire 形状） | `world.rs`（`ShopSellOutcome` 旁边） |
| `shop_buy_requests: BTreeMap<(玩家, 请求), ShopBuyOutcome>` | `world.rs` 字段 + 构造 + `commands.rs` 两条断开路径的 `retain` 清理 |
| `send_shop_buy_result`：**唯一**记录点，7 个出口全部改走它 | `trade.rs`（`send_shop_result` 保持不变，仍是纯发送） |
| 回放检查（命中即原样重发，不再重算） | `handle_shop_buy` 开头 |

顺带证明了一件容易被想当然的事：客户端每次购买都生成**新的** `requestId`
（`client/src/features/npc/dialogue.ts::buy` → `shop-${++seq}-${Date.now().toString(36)}`），
所以补回放保护**不会**妨碍正常连买——第二次购买本来就是一个新请求。

新增测试文件 `server/src/shop_buy_acceptance.rs`（8 条，覆盖此前**零覆盖**的购买路径）：

| 测试 | 钉住的边界 |
|---|---|
| `shop_buy_spends_mesos_and_grants_the_stack` | 花钱用**商人要价**（非目录卖价）；余额与道具同时到位 |
| `shop_buy_merges_into_an_existing_stack_instead_of_taking_a_second_row` | 部分同叠被**就地补满**，不多开一行 |
| `shop_buy_refuses_a_full_tab_without_spending_a_meso` | **关键不变量**：页签满 ⇒ 一分钱不扣、道具不发（"对副本校验"的意义） |
| `shop_buy_refuses_without_enough_mesos` | 差 1 金币也拒绝，余额不动 |
| `shop_buy_refuses_a_zero_quantity` | 0 个不成交（落 `shop_rejected`，如实钉住现状） |
| `shop_buy_rejects_an_unknown_shop_a_distant_merchant_and_an_unstocked_item` | 伪造店铺 / 走远 / 买不售商品三种伪造请求都不动钱 |
| `shop_buy_ignores_a_replayed_request_id` | 重放只成交一次；**换新 id 仍能买**（证明账本按请求而非按道具） |
| `shop_buy_replays_a_refusal_instead_of_re_deciding_it` | 拒绝也被记住：重放不会"因为后来有钱了就偷偷成交" |

验证：cargo **430 通过 / 0 失败**（基线 422 + 新增 8）；`check_protocol_errors` 142 调用点不变
（未新增拒绝码，未改 wire 形状）；客户端零改动。

**这一步买到了什么**：购买路径从"零覆盖"变成"失败边界齐备"，这就是增量 4 敢动它的等价性证据；
另外顺手关掉了一个重复扣款的洞口。**没有**改动的：`write_inventory` 的整表重写、内存先于持久化的次序。

## 7. 后续增量路线图（每步都必须行为零变化）

### 增量 2 —— `inventory ⇄ equipped` 的 Move（难度：中高）

- 新增 `ItemLocation::Equipped { account_id, slot }`，实现 `EquippedSource`。
- **前提是先论证 `equipped` 的 `put` 是否真的同契约**：装备要按职业/等级/槽位合法性判定，同槽互斥，
  且"穿上"会改变角色的派生属性（`derived.rs` / `combat_rules.rs` 读 `state.equipped`）。
  如果论证不过，就**不纳入契约**（§41），保持现状——这正是本轮学到的判断方法。
- 收益：`inventory_ops.rs` 里 6 处 `player.state.equipped = ...` 与配套 `state.inventory = ...`
  由一次 `move_stack` 取代；"换个位置"与"穿上"共用同一份全或全无保证。

> **✅ 已论证（2026-09-15）：结论是不纳入这一份契约。** 三条代码级理由，任何一条单独就足以否决：
>
> 1. **它不是"放入"，是"槽位占用互换"。** `equip_items`（`inventory.rs:1418-1428`）在放上新装备的
>    同时把被占槽位上的旧装备**挤回背包**（找第一个空格），连身衣还会额外挤掉 `-5` 槽并可能挤回来源格。
>    一次动作改**两处**位置、还可能**反向** put 到来源侧——§13 的单次 Move 模型表达不了。
> 2. **目标槽位不是容器自选。** 目标由 `equipment_slot(item_id)` 唯一决定，且必须与请求的 `to_slot`
>    相等，否则 `InvalidEquipmentSlot`（`inventory.rs:1398-1401`）。这与 `ContainerSide`"意图没有槽位"
>    的设计正好相反。
> 3. **放入前有物品自身的准入规则，且拒绝码分层。** `is_equipment` + `quantity == 1` +
>    `meets_requirements`（职业/等级）；`RequirementsNotMet` 与 `InventoryFull` 产生在**不同阶段**
>    （`inventory.rs:1383-1424`），语义层级比 `can_accept` 复杂。
>
> 顺带否掉一个诱人的简化：`unequip_items`（`inventory.rs:1441-1473`）**看起来**是干净的单一 Move，
> 但它的目标槽位由**玩家指定**且**禁止合并**（槽上有东西直接 `InventoryFull`），
> 与"落点由容器自选"的 `ContainerSide` 也不一致。要表达它需要第三种意图
> （"指定落点的背包侧"），而它当前没有独立消费者 ⇒ 按项目规范**不提前建**。
>
> **结论的用法**：装备栏不是"还没做完"，而是"按 §41 判定不该合并"。后人若想推翻，
> 必须给出反例推翻上面三条，而不是重读一遍代码。

### 增量 3 —— 地面掉落的 `ItemLocation::Ground`（难度：中）

> 下面三条是**立项时的假设**，已在下方结论块里被逐条核对（其中第 3 条推翻了"纳入容器契约"的设想）。
> 保留原假设原文，是为了让读者看见判定发生在哪一步。

- ~~把 `drops` 的读写表达成 `GroundSource` + `GroundDestination`，`pickup` 从 `drops` 到 `inventory`
  也走 `move_stack`。~~（**已否决**，见结论 3）
- 难点：`pickup` 的"先 `UPDATE active=0` 抢占 → 失败时在同事务内恢复 `active=1`"是一个**竞争保护**，
  不是普通容器语义。要么把它表达成 `Destination::can_accept` 的前置锁定，
  要么承认它是"获得操作权"而**刻意留在容器契约之外**（§11）。→ **结论：取后者。**
- 同时把 `world.drop_owners`（进程内事实镜像：**7 个生产文件共 20 处引用**，见 `world.rs` 5 处、
  `inventory_ops.rs` 7 处、`skills.rs` 3 处、`boss.rs` 2 处、`pets.rs` / `elemental.rs` / `attacks.rs` 各 1 处）
  换成 `drop_fact` 的投影，消除"同一事实存两份"。→ **结论：不在本增量做**（进程内镜像服务高频
  伤害归属，改读库是性能决策而非模型决策，需单独论证）。

> **✅ 已论证（2026-09-15）：可以纳入的只有"去处命名"，不是容器契约。**
> 下面三条都对着 `HEAD` 的代码核过，"可以纳入"这半句已被第 3 条推翻——保留原话是为了
> 让人看见判定是怎么变的。
>
> 1. **掉落物的目标不是一种容器。** `pickup`（`auth/loot.rs:476-575`）一行可能落到三个不同的去处：
>    `inventory`（普通物品）、`monster_book_cards`（`consume_on_pickup` 且**有 5 张上限**）、
>    或直接变成 mesos（`item_id == "0"`）。这正是 §19 说的"附件不一定是 Item"。
>    补充一个落地时才看清的事实：**三个去处里只有一个会拒绝**——`monster_book_cards` 是
>    *饱和* 语义（`capped_existing = existing.clamp(0, 5)`，`accepted` 可以是 0 但仍算拾取成功），
>    mesos 根本不失败，chance 拒绝的只有 `inventory`。所以"按类别分派"确实需要，但它的产物是
>    **去处（sink）**这个名词，不是第二个 `Destination` 实现。
> 2. **丢弃方向存在"take 之后不 put"的分支。** `drop_inventory`（`auth/bag.rs:855-895`）里，
>    若 `is_drop_restricted(item_id)` 为真，物品被**取出后直接消失**（跳过 `INSERT INTO drops`）。
>    按世界模型的词汇，这不是 Move，而是**销毁**——它应该是一个独立的领域动词。
>    顺带记一笔：`drop_inventory` 建掉落行**从不预判**（没有 `can_accept`），
>    所以"地面"作为**目标**一侧在当前代码里没有任何拒绝语义。
> 3. **同一个 helper 的同一个业务码，两个业务动作处理方式相反 ⇒ 契约不能共享（§31 / §41）。**
>    这是本轮新核出来的硬证据，`HEAD` 上逐字可查：
>
>    | 动作 | 对 `add_inventory_tx` 内层业务码的处理 | 结果 |
>    |---|---|---|
>    | `storage_transfer`（Withdraw） | `.map_err(\|error\| error)?.map_err(\|reason\| reason.to_owned())?` | **硬错误**：中止事务，不写幂等回执 |
>    | `pickup` | `match add_result { Ok(Err(code)) => … }` | **业务拒绝**：`UPDATE drops SET active=1` 恢复掉落，把码写进 `pickup_actions` |
>
>    同一个 `inventory_full` / `unknown_item` / `quantity_mismatch`，在仓库动作里是"服务器出错了"，
>    在拾取动作里是"背包满，东西还在地上"。**拒绝码是业务动作的词汇**（② 已经按这个前提把
>    仓库侧类型化了），而 `Destination::put` 的失败按 ① 的契约是硬错误。
>    两者不可能同时成立 ⇒ 把 `drops` 接进 `move_stack` 必然要**改写其中一边的语义**，
>    那就不是"行为零变化"。
>
> **于是增量 3 的可落地范围被收窄为**：给"拾取去处"这个名词建模（`PickupSink`：背包 /
> 怪物图鉴卡 / 金币），并把三个分支的 SQL 从业务动作搬回 `auth/db.rs`（模块自述的边界：
> "所有 SQL 仍在 `auth/db.rs`"）。**不做** `ItemLocation::Ground` / `GroundSource`。
>
> **标注一个前置**：`PickupSink` 想回*类型化*拒绝就得先给拒绝一个类型，而 `pickup` 现在的拒绝通道是
> `add_inventory_tx` 压平过的 `&'static str`——它真正的类型是 `inventory::InventoryError`，
> 却被 `.code()` 提前抹掉了，且 `add_inventory_tx` 有多个调用方。所以这一步的干净做法依赖
> **增量 4**（收窄原语面）先把 `add_inventory_tx` 的返回类型收敛。**当前不做**，避免在
> 半途引入第二个拒绝枚举。

### 增量 4 —— 收窄 `pub` 面并堵住整表重写（难度：中，收益最大）

- `inventory::add_items` / `remove_items` / `move_items` 从 `pub` 降为 `pub(crate)`，
  最终只保留完整动作；顺带跑门禁脚本把调用点钉住。
- 把 `write_inventory(account_id, &[InventoryItem])` 改为"领域原语 + 仓储按差异持久化"，
  对应 §33 / §34。

> **⚠️ 上一版把"四条路径"的站点数写错了（2026-09-15 更正）。** 真实清点如下——
> 关键分界不是"哪个业务"，而是**有没有事务**，因为失败语义完全不同。
>
> **A. 非事务整表写回（内存权威，且持久化结果被 `let _ =` 丢弃）——4 处**：
>
> | 站点 | 覆盖 |
> |---|---|
> | `trade.rs:157` 商店购买 | ✅ ③ 新增 `shop_buy_acceptance.rs` |
> | `trade.rs:406` 商店卖出 | ✅ 既有 `shop_sell_acceptance.rs` |

> | `cashshop.rs:388` 租赁到期清扫（`step_rental_expiries`，每 10s tick） | ❌ **仍未覆盖** |
>
> 这四处是真正危险的一类：先改内存、再 `let _ = store.write_inventory(...)`——**持久化失败被静默丢弃**，
> 内存与磁盘就此分叉（重登/重启才暴露）。增量 4 必须先决定这四处的模型：
> 是改成"事务成功后才改内存"（仓库/现金已经这么做），还是保留内存权威但让失败可见。
>
> **B. 事务内整表写回——11 处生产调用**：`auth/bag.rs` 7 处（背包动作簇）、
> `auth/quests.rs` 2 处（任务结算）、`auth/cash.rs` 1 处（现金购买）、
> `auth/db.rs:1406` 1 处（`add_inventory_tx` 内部，即 put 自己）。
> 这一类不涉及"失败被吞"，它们的 §34 问题是**修改权泄漏**（业务可从内存任意构造整表）。
>
> **前置条件的当前进度**：A 组 3/4 有失败边界测试，**还差租赁清扫**；
> B 组靠既有验收（storage / consume / scroll / slot_expand / cashshop / quest_store）间接保护，
> 未逐一清点等价性。**结论：增量 4 尚未解锁，先补租赁清扫这一处。**
